## 为什么需要它

engineering.md 的 Mandatory Flow 是任务级流程（design → review → approve → eng-coder → code review → verify），但没有定义**每轮行为**。结果：模型在工程模式下行为漂移——该设计时去改代码、该等批准时去实现、决策不落盘、评审时机失控。真实的设计人员有稳定的工作循环：**理解 → 澄清 → 设计 → 确认 → 移交 → 验证 → 汇报**，每轮都有明确产出和下一步。

## 工作循环（每轮用户消息）

### 第 0 步：状态判断（先定位，再行动）

收到消息先确定当前**状态**（按优先级）：

| 状态 | 判定依据 | 默认动作 |
|---|---|---|
| **需求探索** | 无设计文档 / 需求不明确 | 澄清需求 → 探索现状 → 写设计文档 |
| **设计阶段** | 设计文档存在，无 token | 细化设计 → 更新文档 → 请求用户确认 |
| **设计就绪待评审** | 设计文档已成形，用户尚未发起评审 | 呈递设计摘要 + 提醒"可以评审了"→ **等待用户发起**，不自行调 advisor |
| **评审修复中** | 设计评审打回 | 呈递发现 + 逐项修复建议 → 用户逐条拍板 → 修改 → 再提醒复审 |
| **待批准** | design review 已通过（`_engDesignToken` 存在） | 呈现设计摘要 → 等用户明确批准 |
| **实现中** | 已批准，eng-coder 已 spawn | 等待 eng-coder 交付（期间不并行改设计） |
| **交付评审** | eng-coder 已返回 | code review（**自动流程节点，不问用户**）→ 汇总汇报 |
| **收尾** | 评审通过 + verify 通过 | 汇报结果 → 等用户下一步 |

状态不需要显式变量——由**事实**推断：设计文档存在性、`_engDesignToken`、eng-coder 是否已 spawn、评审是否已通过。

### 第 1 步：处理消息（按消息类型）

| 用户消息类型 | 动作 |
|---|---|
| 新需求 / 变更请求 | 澄清（who/what/why，不问 how）→ 若影响现有设计：更新设计文档并标注变更 → 请求重新确认 |
| 设计反馈 / 决策 | **当轮更新设计文档**（落盘纪律）→ 简述变更摘要 |
| **发起设计评审**（"评审吧"等） | 调 `advisor(type="design", documents=[...])` → 打回则呈递发现+修复建议等拍板；通过则进入待批准 |
| 明确批准 | spawn `eng-coder`（task 按 METHODOLOGY.md 的任务结构：设计路径 → 文件清单 → 验收标准；token 走 designToken 参数） |
| 问题 / 讨论（不涉实现） | 直接回答 → 若有决策产生则落盘 |
| eng-coder 交付 | 检查交付（对照验收标准）→ code review（**自动，不问用户**）→ 汇报 |
| 命令（关/开模式、切会话等） | 执行命令 → 状态重置说明 |

### 第 2 步：收尾检查（每轮必做，固定顺序）

1. **决策落盘**：本轮对话是否产生了新决策/约束/偏好？是 → 更新对应文档（设计文档、METHODOLOGY.md、ENGINEERING-MODE.md），不等人点名。
2. **状态同步**：明确告诉用户当前处于什么状态、下一步是什么、需要用户做什么（批准？澄清？继续？）。
3. **不越界**：本轮没有产生代码修改（除非处于"交付评审后的 minor fix"且设计已批准）；没有自行发起设计评审（评审发起权在用户，agent 只提醒）。

## 默认不做什么（硬约束）

- **不自行发起设计评审**——呈递就绪 + 提醒为限，用户发话才调 advisor；评审打回不自行修完重送，每轮呈递、用户逐条拍板。
- 交付 code review 是自动流程节点（eng-coder 返回后自动评审一次），除此之外不主动、不频繁调用 advisor。
- 设计未批准前不 spawn eng-coder；需求未澄清前不写设计（先问）。
- 不直接修改代码文件（design 门禁机械兜底；design 批准后的 minor fix 除外）。
- 用户反馈的范围外需求：停下，提出设计更新，不静默扩展。
- 不跨状态并行：实现中不推翻设计，评审中不新增范围。

## 与普通模式的区别

| 维度 | 普通模式 | 工程模式 |
|---|---|---|
| 收到需求后 | 按复杂度分级直接实现 | 澄清 → 设计 → 评审 → 等批准 → 委托 |
| 代码修改 | 自己写（lint/verify 自检） | eng-coder 写，父代理评审 |
| 评审 | discipline 的收敛协议（每轮强制） | 评审时机纪律（不主动、流程节点一次） |
| 决策落盘 | memory_put | 文档优先（设计文档/方法论），memory 为辅 |
| 产出物 | 代码 + 验证 | 设计文档 + 批准 + 交付评审 + 验证 |

## 验收（如何判断循环生效）

1. 用户提需求 → 模型先澄清/写设计，不直接改代码。
2. 用户给决策 → 当轮文档更新，无需追问。
3. 设计就绪 → 模型只呈递+提醒，**不自行调 advisor**；评审打回 → 呈递发现等用户拍板，不自行修完重送。
4. 设计评审通过 → 模型等批准，不擅自 spawn eng-coder。
5. eng-coder 交付 → 模型自动做 code review（流程节点）并汇报验收情况。
6. 每轮回复末尾明确"当前状态 + 需要用户做什么（发起评审/批准/澄清/继续）"。
