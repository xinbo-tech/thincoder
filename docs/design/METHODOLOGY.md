## 2. 基本流程

任何开发任务都走四步，不跳：

1. **需求** — 讨论清楚要什么，落成需求文档，确认后再往下走。需求文档按**三层**组织：
   - **总目标（overall goal）** — 一句话说清这个任务为谁解决什么问题；
   - **功能用户故事（functional user stories）** — 逐条可验收，格式：**作为一个 [角色]，我想要 [功能]，以便 [目的]**。只描述 who / what / why，不写 how；
   - **非功能标准（non-functional standards）** — 性能、安全、兼容性、可用性等约束，写清度量方式。
   
   需求完成的判据：三层都具体到可以据此设计（用户确认，或答案不再改变需求）。需求确认后逐条建立 checklist 条目——checklist 是需求验收的标志：没有 checklist 条目意味着需求还没落地。
2. **设计** — 方案、架构、怎么实现，落成设计文档：问题陈述、方案与理由、受影响文件全清单、可验证的验收标准（每条验收标准回指用户故事）。设计定了再动手。
3. **开发** — 写代码。
4. **测试** — 验证。测试要有测试文档：每条用户故事至少对应一个测试用例，覆盖正常情况、边界条件、异常情况。每条用例写清楚测什么、给什么输入、期望什么输出。不写实现细节。

这四步不是"最佳实践"——是硬流程。三步要写文档：需求文档、设计文档、测试文档。跳到第 3 步就开始写代码，十次有九次是错的。

## 3. 代码结构：理解成本分层

### 来源

三支柱：Dijkstra 局部推理 → Parnas 模块分解（"模块是工作分配单元，不是子程序"）→ 认知复杂度 + 本项目教训（500 行 = 很难理解；函数档 = 早期预警线，文件档 = 不可协商底线）。

### 动机

1. **理解成本是状态，不是行数**——关键不在文件多大，而在读者能否局部推理。
2. **局部推理**——人能理解放得进工作记忆的代码；超了只能靠翻页，翻页即丢上下文。
3. **改动隔离（Parnas）**——模块分解使一处改动不波及其他模块，是并行与独立演进的前提。
4. **可独立测试 = 质量底线**——拆出的小单元能单独验证。
5. **本项目特有：模型是高频第二读者+写者**——分层省上下文（读哪层只加载哪层）、降幻觉（局部代码比全貌易推理）。

> 行数不是目标，但档位表是不可协商判据（D-S3b）。

### 档位表

**函数体**：

| 行数 | 判定 |
|---|---|
| ≤50 | 正常 |
| 50–100 | 正常，审视是否该拆 |
| ≥100 | 主动审视拆子函数 |
| ≥300 | 必须拆骨干 |

**文件**：

| 行数 | 判定 |
|---|---|
| ≤300 | 正常 |
| >300 | 主动审视抽模块 |
| >500 | 必须拆——**硬限，无例外，无相对比较通道** |

关系：先函数后文件；**相对大小永远不是豁免**（"这文件虽 600 行但都是声明"不成立——声明也是理解成本）。

### 原则

1. **一函数一概念**——一个函数只做一件事，名字说清它做什么。
2. **骨干—细节两层**——每个模块/文件 = 薄骨干（入口 + 流程 + 调用细节函数）+ 细节函数。读者先看骨干懂流程，需要时再下钻细节。
3. **时机：边写边分层**——不是写完整块再回头拆（2026-09-05 裁定）。分层是写作过程，不是整理步骤。
4. **子函数提取判据**——细节自成一段完整逻辑（可独立命名）即提，不以行数论。
5. **模块边界围住决策**——把"可能变的决策"围进一个模块，变化只改一处。
6. **控制流局部化**——guard clause 提前返回，嵌套 ≤3 层。
7. **状态机显式化**——状态枚举 + 转移表，不散落 if。
8. **注释与决策同行**——注释写"为什么"（决策/坑），不写"是什么"（代码自明）。
9. **双端 parity**——CLI/VS Code 镜像结构同步演进，不各自漂移。
10. **撞到错误结构就改，不挂账**——发现结构/状态归属错了就改结构（重写正确结构），禁止在错结构上叠补丁掩盖症状（2026-09-07）。

### 动手自检

- **拆前四问**：这段能被读者独立理解吗？改动会波及其他模块吗？能独立测试吗？读者需要多少上下文？
- **拆后两验**：骨干可复述（不看细节能说出模块做什么）；行为零变 + **断言数不减**（拆分轮专用——存量清理轮 = 删除清单制）。

### 反例档案

| 反例 | 教训 |
|---|---|
| 31 行 payload 凑数 | 行数不是目标——为拆而拆制造碎片 |
| 压注释 | 注释是理解成本的一部分，压缩注释 ≠ 降低理解成本 |
| 凭记忆重述迁移 | 迁移必须读原文——记忆会漂移 |
| 该拆的问"要不要拆" | 档位表是不协商判据——不问，拆 |
| 相对大小打折硬限（2026-09-06） | "虽然超 500 但别的不大"不成立——硬限无豁免 |

## 4. 常用纪律

- **检查表（checklist）**：项目级跟踪（`.thincoder/checklist.md`，每次注入）；task 是会话级。需求确认后建 checklist 条目，完成后勾销。
- **遇到问题三招**：①读日志（根因在末尾）；②查资料（官方文档/协议验证）；③二分法（切半定位，再切）。
- **不要陷在长时间反复阅读代码里**：读不懂就跑——写测试、加日志、二分法。动手比动眼有用。

## 5. 需求池攒批工作流

> 状态：已批准（2026-09-03 三轮收敛 0🔴）。动机：单点流水线固定成本 ~40 分钟被一个需求点独扛；攒批摊薄，质量不降（只改触发时机，不改每点做法）。

**机制**：

1. **登记（提需求时）**：你提普通需求 → agent 当场澄清 → 更新所属板块需求文档（需求句落档）→ `docs/TODO.md`「需求池」组登记一行（日期 / 需求句 / 归属板块 / 状态=待设计）——**不做设计**。
2. **攒批**：需求点累积——设计启动权在你（说"开始吧/这批做"）。
3. **建议阈值**：同板块积 **≥2 点** 或 池全局 **≥3 点** → agent 提醒一次（"池够大了——可以开始设计"）——提醒不代替发起。
4. **批设计**：一次落多个需求点（同板块同文档多段 / 跨板块多文档同批）→ 同批评审 → 用户批准 → 批实现。
5. **快车道**：你说"这个急/马上做" → 不登记——单点走现有完整流程（设计 → 评审 → 实现——一步不少）。
6. **边界**：池只收**用户需求点**——技术待办（设计遗留/评审发现/债）走 `docs/TODO.md` 技术组——不混池；紧急 bug 由快车道覆盖。

**用例语义**：dedup 键 = 板块 + 规范化需求句（同点重复提 = 更新不新增）；批进行中阈值再达 = 提醒延后不打断；撤回 = 池行撤销注保留。池是**工程模式机制**——main.md 普通模式不承诺。
