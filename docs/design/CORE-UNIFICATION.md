### 2.2 目标形态与消费契约

目标形态 = 「一个核 + 两个薄壳」：核是**单一权威源**（一个真包，独立版本，**发布到 npm**），
核的内容 = **两产品共有的机制实现 + 共享提示词内容**（A7）；两壳各自只留**结构性不对称**的端特有部分（A9）；
核的引入**不冻结行为**（A10）——面内（已归一的对称面）行为按**裁决结果**走，未涉面不得无故回归。

```

│   ├── package.json                   ← name / version / type / exports / files（含 prompts/ · tool-docs/）
│   ├── <模块>.mjs                     ← S1 逐模块提取（来源可追溯——§2.5 裁决表）
│   ├── prompts/                       ← 15 档槽位提示词（唯一副本——A7；来源 = 两产品 src/prompts/）
│   ├── tool-docs/                     ← 25 档工具描述（唯一副本——A7；来源 = 两产品 src/tools/*.md）

│   └── test/                          ← 核自带测试（S1：两边测试合流）
├── docs/design/prompts/               ← 中文权威镜像（**唯一副本**——D-C14；S3 后由两产品文档树迁入）

│   ├── src/prompts/ · src/tools/*.md  ← S2 逐端接线后**删空**（S3 零残留）
```

**R3 删面（R2 轮拟建条目已撤——明确不再产生）**：`core-link.mjs`（落 `scripts/`）· `package.mjs`（落 `thincoder-vscode/scripts/`）· 仓根 workspace `package.json` · 成员 lock 删除 · `.gitignore` 分阶段目录行——**整条垫片面不存在了**（用户否垫片判定 + 本轮实测证明不需要）。

**消费契约（7 条）**：

1. **核的边界 = 包边界（含提示词内容）**：核内容 = 两产品共有的机制实现 + 共享提示词内容（`core/prompts/` 15 档 + `core/tool-docs/` 25 档——A7）；
   壳 = 各自**结构性不对称**部分（CLI 的 TUI / 命令面，VSC 的宿主 API / webview——A9 第 2 条）。
2. **核 → 壳禁止，壳 → 核允许**：核内 import 面**只含核内相对路径 + `node:` 内建**；核的依赖闭包必须落在核内（否则该模块不进核——§2.4 判定闸 G2）。
3. **壳按包名 import 核**：产品代码以裸名 `@thincoder/core`（含子路径导出）引用——**开发期**由本地链接解析、**生产期**由已发布核包解析。同一个 `dependencies` 声明两态通用（manifest 恒为真 semver 范围，无 `workspace:` / `file:` / `*`）。
4. **双态引用（R3 选定）**：
   - **开发期 = 本地链接**：`npm link`（在 `core/` 一次、在产品目录一次）⇒ `node_modules/@thincoder/core` 为指向 `core/` 的链接；**不发布也能开发**，且**零 manifest / lock 污染**（§2.2.1 R8）。
   - **生产期 = 已发布核包**：`npm publish`（核先发）→ 产品以真 semver 范围从 registry 解析；VSC 的 vsix 因 marketplace **无依赖解析**而**内嵌**核（反排除行，§2.2.1 R4/R5）。
5. **端差以注入表达**：两侧差异用显式参数 / 回调 / 配置项承载，核内**禁止 `if (vsc)` 式壳判断**与产品标识字符串。
6. **核测试独立**：核测试住核包内、只依赖 `node:` 与核内模块；产品侧测试中与核重叠的部分随 S2 改指或收敛（不重复两份断言）。
7. **CI 增设 `core` job**：核测试（B8 三 job 之外新增一个；两产品 job 内部命令不变——依赖由 `npm install` 自动解析）。
8. **提示词面 = 核内唯一副本 + 单一加载面**：核内 `prompts/`（15 档槽位）与 `tool-docs/`（25 档工具描述）为**唯一副本**；
   两端**不得**自持提示词档（S2 接线 + 删档，S3 零残留）；解析面 = 核内 `prompt-files.mjs`（以 `import.meta.url` 为根——D-C13），
   产品侧只调用、不做路径运算。
9. **缺档语义按调用方保留（不统一）**：四个加载面各自的缺档行为是**现状可观测行为的一部分**（B4），
   核内加载面照搬：槽位 ⇒ 静默空串 + 装配期警告；advisor / 工具描述 / consult 消费点 ⇒ 抛错（§2.7 D-C13）。
10. **端特有段以注入进入共享档**：核内提示词档不得出现端名判断或产品标识分支；
    确属结构不对称的端特有指令段 ⇒ 端侧以**注入段**拼入（拼装点在产品装配层），核档内**保留锚点与注入位**（§2.4 提示词面适用性）。

### 2.4 S0 的方法与产出形态

**边界原则（本段的总则——A8 / A9，不得反向使用）**：

1. **对称 ⇒ 进核**——凡两产品**功能基本对称**的面（含低相似度真分叉面）都是核的候选；**相似度低不是排除理由**。
2. **差异不得作为排除理由**（A9）——差异是**本项目的工作内容**；S0 对对称面的职责是产出「**以谁为准 / 融合 / 以何参数注入**」，**排除不是选项**。
3. **端特有桶只收结构性不对称**：① 该机制**只在一侧存在**（无对位）；② 或**依赖壳能力**（CLI TUI / 命令面；VSC 宿主 API / webview）。
   **给出「端特有」判定必须附结构性不对称的证据**（file:line 或「仅单侧存在」的枚举读数）——**不得**以「行为有差异 / 实现不同 / 合并费脑」为由（A9）。
4. **行为不冻结**（A10）——对称面归一后行为按裁决结果走；不要求等于任一端的旧行为；只有**未涉面**不得无故回归。
5. **逐条裁定关口**（A11）——凡归一将改变**可观察行为 / 对外契约**的条目 ⇒ 逐条提交用户裁定（三选一口径与四要素提交形式见 §2.5.1）；**裁定未完毕的条目不得进 S1**。

**范围**：107 对全量（67 `.mjs` + 40 `.md`）**逐条**分类 + **中文镜像 15 对**（`docs/design/prompts/` 两端对位——B14）
外加一遍**语义对位发现**（依据 B9——同路径对不是全部差异面；B16 实测：会话面同路径对 = **0**，必须靠对位遍配对）。
**A8 后的范围收正**：对位遍不再是「补充」，而是与 107 对**同等地位**的席位来源（B15 量级）。
**零代码**：S0 不改产品、也不改核（核尚不存在）。

**四分类（分类是本段唯一产出）**：

| 类 | 名称 | 判据 |
|---|---|---|
| ① | **近乎同（可直取）** | 相似度 ≥0.9 且逐行差异经判读属非语义（注释 / 空行 / 措辞）⇒ 取一侧入核 |
| ② | **语义同实现异（融合）** | 目的同一、实现不同（结构 / 命名 / 边界处理差异）⇒ 融合为一份，逐点记录取舍 |
| ③ | **语义真分叉（须判决）** | 两侧存在**行为可观察差异**（同名函数在边界 / 错误路径行为不同，或两侧测试期望相抵）⇒ 逐条裁决 |
| ④ | **端特有（不进核）** | **仅限结构性不对称**：只在一侧存在，或依赖壳能力（CLI TUI / 命令面；VSC 宿主 API / webview）⇒ 留在壳内 |

**提示词面的分类口径（R4 新增——与实现面不同形，但同规模）**：提示词档的「实现」就是它的**文本**；因此平行定义：

| 类 | 提示词面判据 |
|---|---|
| ① | 逐字节相同 ⇒ 直取（B14：槽位 8 档 / 工具描述 20 档） |
| ② | **指令等价**但文本 / 版式 / 注解 / 跨端文档指针不同 ⇒ 融合（取语义并集、形态归一、指针参数化） |
| ③ | 同一场景给出**相抵指示**（禁止 vs 允许同一行为）⇒ 逐条裁决 + 用户裁定 |
| ④ | 单端独有的**指令段**（对应结构不对称的端机制）⇒ 端特有段，以**注入**拼入共享档（契约 10；**不整档复制**） |

**前提校验遍（R4 新增——A12 派生方法；与分类同席、在其之前）**：每个**分叉面**（②/③/④ 候选）先回答两问——

1. **为何分叉？**——把分叉理由写成**可核的句子**（附两侧证据：`file:line` / 行为读数）；
2. **当年前提还成立吗？**——以**实测 / 权威源**核对（不凭记忆、不凭「以前以为」）。

处置：

- 前提**仍成立** ⇒ 按常规分类处置（② 融合 / ③ 裁决 / ④ 结构性不对称）；
- 前提**已失效 / 本就错误** ⇒ **直接归一**（理由消失 = 分叉消失）——**不得**当作 ③ 类行为裁决拉锯（禁止把「两侧实现不同」当成「需要选边的语义分歧」）；
- **范例（B20）**：记忆面分叉源于「VS Code 内置 Node 不支持 sqlite」——该前提不成立 ⇒ A12 判**记忆面向 CLI 语义归一**（以 CLI 为准）；
- ⚠ **归一的后果仍走 A11 裁定**：前提校验只消去「以谁为准」的争议，**不豁免**「改变可观察行为 / 对外契约」的逐条裁定（B20 的引擎下限即此类——§2.11 A8）。

**核内容的判定口径（5 条闸——R4 按 A8 / A9 收正）**：

1. **G1 两侧同职责（两义——R4 收正）**：
   - **G1-a（机制面）**：核只收两产品**都持有**该功能面的机制——**「持有 ≠ 实现一致」**：只要两侧都有这个面（功能对称）就过 G1；
     实现分叉（含相似度 <0.2）**不构成排除理由**，只决定该行进 ②（融合）还是 ③（须判决）。
   - **G1-b（提示词面）**：核收**两端同名提示词集合的并集**（R4 实测：槽位 15 + 工具描述 25，集合**相等** ⇒ 无独有档）；
     单端特有的**段** ⇒ 端特有段（注入），**不构成整档排除**。
   - 单侧独有且**无对位** ⇒ ④（须附 B17 式枚举证据）。
2. **G2 依赖闭包在核内**：核内 import 只允许核内相对路径 + `node:` 内建；被依赖的模块若属壳 ⇒ 该模块不进核（依赖须一并下沉，或改注入）。
   **提示词面同理**（R4 补）：核内提示词读取**只从核包内目录**解析（不得指向产品侧 `src/prompts/` / `src/tools/`——N3）。
3. **G3 可独立验证**：无宿主 API（`vscode`）、无 TUI 依赖；测试可纯 Node 跑。
   提示词面：档存在 + 装配可跑（纯 Node）即满足。
4. **G4 作废，替代为 G4'「裁决落实 + 不得无故回归」（R4 按 A9 / A10 收正）**：
   - **两条作废的读法** ✗：①「统一必然改行为 ⇒ 判 ④ 端特有」（把差异当排除通道——违 A9）；
     ②「行为不变 = 准入门槛」（违 A10——分叉的实现与逻辑必然导致分叉的行为，那正是要解决的问题）。
   - **现行读法** ✓：**先判对称性**（G1）——对称 ⇒ **进核**；该面的行为**由裁决决定**（以谁为准 / 融合 / 以何参数注入 ⇒ 归一后行为 = 裁决结果，**不要求**等于任一端的旧行为）。
   - **唯一的「不变」要求 = 未涉面不得无故回归**（N1 改写）：本批不动的既有功能，其既有测试仍须绿。
5. **G5 差异以注入表达**：禁 `if (vsc)` 式壳判断与产品标识字符串（可读性约束，人工核 + 抽查）；提示词档内不得出现端名判断（契约 10）。

**残余张力（已裁——§2.11 A6 · 2026-09-13「碰到再议」）**：若某差异**无法**以注入表达（如两侧对同一 API 的名称 / 形状根本不同，或注入点会改变调用方），

**术语（全文统一——评审口径）**：

- **面内** = 本批裁决并归一的对称面：归一后行为按**裁决结果**走——**行为变化是预期**，不是缺陷（A10）。
- **未涉面** = 本批不动的既有功能：**不得无故回归**（其既有测试仍须 exit 0）。

「与迁移前基线逐数一致」**只在未涉面上是判据**；面内的基线对照仅作**变更可见性**证据（改了什么、改在哪，逐条登记），**不是**验收判据。

**分类不得只靠相似度**：相似度是**排序面**（先看哪儿可能合），语义裁决以两侧代码 + 测试 + 调用点**实读**为准——

### 2.9 与既有纪律的冲突点核对

1. **F7（phase 1：产品运行行为零改动）**：**R4 起本板块不适用** ✗（A10）——它是**搬迁批**的约束（纯位置变更不应改行为），
   本批是**统一批**；替代 = G4' / D-C15（**不得无故回归**）。
2. **D14（提示词不做单副本合流）**：**R4 起作废** ✗——用户 2026-09-13 裁定 **A7** 直接推翻；本板块以 D-C5（改写）/ D-C13 / D-C14 承载新口径（核内唯一副本 + 单一加载面 + CN 镜像合流）。原 R3 句「核与提示词面互不指涉」**同轮作废** ✗。
3. **「单一权威源」纪律**：核的唯一撰写处 = `core/` 包本体（**含 `core/prompts/` 与 `core/tool-docs/`**）；仓内零副本（提示词面亦零副本）；
   CN 权威镜像（仓根 `docs/design/prompts/`）是**内容权威面、非第二撰写面**（双源纪律：改 CN → 内容把关 → 回填核内落地档——D2 单源）；
   dev 链接是解析指针、非撰写面——不构成第二权威源。（R4 后本条覆盖面由实现面扩至提示词面。）
4. **「多实现面 · 语义同源、不做 byte-identical 硬一致」纪律**：本板块**跨端无多实现面**（核与壳是包边界；R4 后提示词也跨端单一副本）；
   **保留的多实现面 = 「CN 权威 ↔ 核内落地」双面**（同一内容的中/英两面——与两产品现状同形）——适用：语义同源、文本自持、不做 byte-identical（语言不同，字节比较无意义）、各面独立语义锚断言。
5. **CLI「零运行时依赖 / 无构建步骤」承诺**：**改述**——零依赖只约束**第三方**（B7 自述语境；自家核不在范畴）；「无构建步骤」= 两产品仍直接运行、无源码编译（装载靠 npm / vsce 的**标准**依赖机制，不引入打包步骤——D-C9）。N7（核内零裸包名）继续守住第三方零依赖。
6. **机器检查面**：核目录 `core/` 不在 V5 的代码树枚举（`src` / `scripts` / `bin` / `test`）内 ⇒ 核**符号**不进宽形态索引（报告面，不入闸）；
   核路径锚的可解析性由「仓根相对路径」解析序保证。**S1 前须实跑一次确认零红**（N6）。
7. **发布链边界**：「不改发布链（npm publish / vsce + ovsx）」的边界解读 = **对外命令接口与双源流程不变**；
   R3 形态下发布链**连内部步骤都不新增**（无垫片、无分阶段），只在既有钩子上加**预检 / 断言**（§2.8）——F7 边界改述见需求档。
8. **零依赖 / 零构建与**核的发布**（R3 新增）**：核发布到 npm 引入「核先发、产品后发」的顺序依赖——**不是**新增构建步骤，而是**发布编排**前置（D-C12 / §2.11 A3）；用户 A6 已明示接受该顺序。
9. **提示词面的「端特有段」（R4 新增；R5 口径收正）**：端特有指令段（如 VSC 的池规则段——B14 实测 `discipline-engineering.md` VSC 侧含该节）以**注入**保留在端侧；
   核档内留**注入位**、不留端名分支（契约 10）；注入后该端模型看到的指令集按**裁决结果**成立（A10——面内改判须逐条登记于 §2.5「归一后行为说明」列）；
   **「注入」不得成为行为的遮羞布**：未涉面不得无故回归（T-C6 按「未涉面逐数不变 · 面内按裁决改判并登记」口径读）。
10. **「以差异排除」的写法禁区（R4 新增——A9）**：本档 / 需求档 / 批次档 §2 中，凡「因为两侧不同 ⇒ 判端特有 / 不进核」的句式均为**违规形态**；

11. **对外契约兼容（R5 新增——A7 / F13 / D-C18）**：与既有纪律**无冲突**——「不改发布链对外命令接口」（本节第 7 条 / F7）是本条的**实例**（命令面冻结）；
