### 2.2 目标形态与消费契约

目标形态 = 「一个核 + 两个薄壳」：核是**单一权威源**，两壳各自只留端特有部分；核的引入不改变任一产品的可观察行为。

```
<合并仓根>/
├── core/                        ← 核（权威源——唯一撰写处）
│   ├── <模块>.mjs               ← S1 逐模块提取（来源可追溯——§2.5 裁决表）
│   └── test/                    ← 核自带测试（S1：两边测试合流）
├── thincoder/
│   └── src/core/                ← CLI 运行期副本（S2 生成——与 core/ 逐字节一致）
├── thincoder-vscode/
│   └── src/core/                ← VSC 运行期副本（同左）
└── scripts/core-sync.mjs        ← 同源校验 / 生成（S2 新增）
```

**消费契约（7 条）**：

1. **核的边界是包边界**：核内容 = 两产品共有的机制实现；壳 = 各自端特有部分（CLI 的 TUI / 命令面，VSC 的宿主 API / webview）。
2. **核 → 壳禁止，壳 → 核允许**：核内 import 面**只含核内相对路径 + `node:` 内建**；核的依赖闭包必须落在核内（否则该模块不进核——§2.4 判定闸 G2）。
3. **壳按包内相对路径 import 核**：产品代码引用**本包内副本**（`./core/<模块>.mjs`）——导入面不得指向仓根（B2 / B3 的打包边界）。
4. **权威源 → 副本单向生成**：`core/` 是唯一撰写处；产品内副本由 `core-sync.mjs --write` 生成、默认态为**校验**（不一致即 exit 1）⇒ 漂移是硬红，不是纪律。
5. **端差以注入表达**：两侧差异用显式参数 / 回调 / 配置项承载，核内**禁止 `if (vsc)` 式壳判断**与产品标识字符串。
6. **核测试独立**：核测试住核目录、只依赖 `node:` 与核内模块；产品侧测试中与核重叠的部分随 S2 改指或收敛（不重复两份断言）。
7. **CI 增设 `core` job**：核测试 + 同源校验（B8 三 job 之外新增一个；两产品 job 不变）。

### 2.4 S0 的方法与产出形态

**范围**：107 对全量（67 `.mjs` + 40 `.md`）**逐条**分类，外加一遍**语义对位发现**（依据 B9——同路径对不是全部差异面：
不同路径的同职责模块，如 CLI 的 `cli/` 面与 VSC 的 `extension/` 面、`agent-tools/` 面）。
**零代码**：S0 不改产品、也不改核（核尚不存在）。

**四分类（分类是本段唯一产出）**：

| 类 | 名称 | 判据 |
|---|---|---|
| ① | **近乎同（可直取）** | 相似度 ≥0.9 且逐行差异经判读属非语义（注释 / 空行 / 措辞）⇒ 取一侧入核 |
| ② | **语义同实现异（融合）** | 目的同一、实现不同（结构 / 命名 / 边界处理差异）⇒ 融合为一份，逐点记录取舍 |
| ③ | **语义真分叉（须判决）** | 两侧存在**行为可观察差异**（同名函数在边界 / 错误路径行为不同，或两侧测试期望相抵）⇒ 逐条裁决 |
| ④ | **端特有（不进核）** | 只在单侧存在，或语义绑定壳（CLI TUI / 命令面；VSC 宿主 API / webview）⇒ 留在壳内 |

**核模块清单的判定口径（5 条闸——四条须全过，第五条为表达约束）**：

1. **G1 两侧同职责**：核只收两产品**都持有**的机制；单侧独有 ⇒ ④。
2. **G2 依赖闭包在核内**：核内 import 只允许核内相对路径 + `node:` 内建；被依赖的模块若属壳 ⇒ 该模块不进核（依赖须一并下沉，或改注入）。
3. **G3 可独立验证**：无宿主 API（`vscode`）、无 TUI 依赖；测试可纯 Node 跑。
4. **G4 行为不变**：合并不改变任一产品的可观察行为——**若「统一」必然改行为，该条判 ④ 端特有，或以注入表达**（行为统一另立需求，见 §2.7 D-C6）。
5. **G5 差异以注入表达**：禁 `if (vsc)` 式壳判断与产品标识字符串（可读性约束，人工核 + 抽查）。

**分类不得只靠相似度**：相似度是**排序面**（先看哪儿可能合），语义裁决以两侧代码 + 测试 + 调用点**实读**为准——
低相似度而语义同、高相似度而语义异，两种情形都存在。

**产出落点**：裁决表落**本档 §2.5**（S0 完成后由 eng-designer 收正填表——设计档修订，写权不变）；
原始读数（逐对相似度 / 逐字节结果）落批次档 §5。**执行者 = eng-designer**（零代码分析 + 直接落档，避免「分析者 ≠ 记录者」的二次加工）；
重型实读可委派**只读** explore 子代理（勘察预算 ≤6/批）。

### 2.6 分段执行（S0–S3）

| 段 | 动作 | 进入条件 | 退出条件（验证） | 回退点 |
|---|---|---|---|---|
| **S0** | 差异分析 + 逐模块裁决（零代码） | 需求收口（§1）+ 本档批准 + 度量脚本补齐（F10） | 本档 §2.5 覆盖 107 对全量 + 语义对位遍；分类列无空值；③ 类逐条带行为实证与建议；**用户对 ③ 类存疑条目裁定完毕** | 无代码改动 ⇒ 撤回本档修订 |
| **S1** | 建核（两产品**一行不改**） | S0 退出达标 | 核测试独立跑绿（`node --test` 于核目录 exit 0）· 核内零产品 import、零裸包名 import · 两产品 `git diff --stat` 为空 | 删核目录即退（产品零改） |
| **S2** | 逐模块迁移（一次一个模块族：接线 + 副本落位 + 删旧实现 + 复跑） | S1 退出达标 + 该模块接线方案（含副本落位）明确 | 该产品全链复跑与迁移前基线**逐数一致**（Lint / test:full / 集成 + 机检）· 同源校验 exit 0 · 该模块旧实现零引用 | 单模块一步一提交 ⇒ `git revert` 该提交 |

**段序纪律**：每段独立提交、独立可验；S2 内先做完一个产品（或一个模块族）再接下一个——**不做跨模块大包**；
S1 的「两产品一行不改」是硬判据（可用 `git diff --stat` 直接判）。

### 2.9 与既有纪律的冲突点核对

1. **F7（phase 1：产品运行行为零改动）**：本板块把它作为核的准入条件（G4 / D-C6），不放松。
2. **D14（提示词不做单副本合流）**：本板块**不改**其边界——核内零提示词档（D-C5）。
   与 D-C3 的「同源副本」形态**不矛盾**：提示词是**按产品各自持有、允许各自演进**的内容源（B4 硬加载路径各自独立），
   核是**同一份实现的分发副本**（不允许独立演进）——两者机制不同源、不得互相外推。
3. **「单一权威源」（文档规范 §3.3 规则 4）**：核的权威源 = `core/`；产品内副本是**生成物**，不构成第二权威源；
   核模块的语义只在本档 §2.5 + 核内档正文一处详述。
4. **「多实现面 · 语义同源、不做 byte-identical 硬一致」纪律**：本板块的副本**不是独立实现面**，而是同一权威源的发行副本
   （无独立语义、不得独立演化）⇒ 硬一致在此是**目标**而非约束；若某端日后确需偏离，走**注入**（G5），不得改副本。
5. **CLI「零运行时依赖 / 无构建步骤」承诺**（B2 / B7）：由 N7（核内零裸包名 import）+ §2.3.2 候选 b 的否决共同守住。
6. **机器检查面**：核目录 `core/` 不在 V5 的代码树枚举（`src` / `scripts` / `bin` / `test`）内 ⇒ 核**符号**不进宽形态索引（报告面，不入闸）；
   核路径锚的可解析性由「仓根相对路径」解析序保证。**S1 前须实跑一次确认零红**（N6）。
