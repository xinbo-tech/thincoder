## 0. 铁律（发起权与批准权归用户——2026-08-24 决策）

背景：agent 曾两次越权抢跑（自行提交设计评审 → 拿 token → 直接开发，其中一次全程零确认）。此后固化四条铁律：

1. **设计评审只能由用户发起**——agent 准备并提醒“设计就绪，可以评审”，不自行调 advisor。
2. **打回后逐条呈递**——评审打回后每轮呈递发现 + 修复建议，**用户逐条拍板**再改（agent 不自行修完重送）。
3. **交付 code review 保持流程节点自动**——eng-coder 返回后自动评审，不问用户（现行由 eng-coder 内部协议默认承担）。
4. **系统推回（guard）在工程模式一律关闭**——未来若启用也只作提示，评审仍由用户发起。

## 1. 需求（Requirements）

### 1.1 总体需求

普通模式靠纪律提示词约束模型；工程模式把“设计先行、评审把关、验证收尾”提升为**半机械流程**——可硬性拦截的环节一律拦截（写文件门禁、token 校验），无法硬拦的靠纪律层槽位提示词约束。
核心承诺：**代码必须先有被评审过的设计；评审对象由任务定义而非遍历猜测；评审循环在实现者内部闭环（不依赖父代理持有凭证）。**

### 1.2 用户故事（从用的人角度看——为什么需要这些机制）

**发起权（对应 §0 铁律）**

- 作为开发者，我想**自己决定什么时候发起设计评审**——在我的需求讨论完了、我认为可以了的时候——而不是 agent 自己觉得想清楚了就开评。
- 作为开发者，我想让评审打回后**逐条听 agent 说发现和修复建议、由我决定改哪些**，而不是它自己改完直接送回——否则我看不到它替我做了什么决定。

**设计先行（FR1 / FR2 / FR3）**

- 作为开发者，我想让有规模的任务**先写出“打算怎么做”并经过独立评审、我点头，才允许改代码**，这样我不会一觉醒来看到一堆没经过我同意的改动。
- 作为开发者，我想**只有我批准的方案才能进入实施**（凭证落到实现者手里），这样没人能跳过评审直接改代码。

**独立评审（FR2 / FR5）**

- 作为开发者，我想让**另一个独立的评审角色**（不是写方案的那个、不共享它的上下文）挑毛病，这样我不会被写方案的 agent 的自信误导。

**实现者的纪律（FR4 / FR6）**

- 作为开发者，我想让实现者在交给我之前**先自查、再被独立评审一遍**，这样我不用当第一个 QA。
- 作为开发者，我想让实现者**撞到设计漏洞时停下来告诉我**，而不是自己编一个方案继续干。
- 作为开发者，我想让改动**超出原定范围时逐条告诉我**，而不是悄悄改。
- 作为开发者，我想在它**卡住、没收敛时被告知**，而不是等一个看起来正常的失败。

**并行与留痕（FR7 / FR8）**

- 作为开发者，我想能**同时推进多个互不相干的任务**，而不必排队等。
- 作为研发负责人，我想让技术待办**集中在一处**，而不是散在设计文档里到处找。
- 作为团队的一员，我想让**每一步的决定都有据可查**（谁提的、什么时候批的、怎么验证的），这样半年后或换了人也能接手。

### 1.3 功能性需求（机制约束，架构级表述）

| # | 机制需求 | 约束 |
|---|---|---|
| FR1 | 设计先行 | 设计文档（三层）存在且通过设计评审前，任何代码文件（含提示词档 `thincoder-core/prompts/*.md`）不可被修改 |
| FR2 | 设计评审独立 | design review 由独立上下文执行；评审对象 = 调用时显式传入的文档清单（documents + object 参数），不遍历 git diff |
| FR3 | 授权链 | 评审通过签发 token + 随机 designId，存于会话内多设计槽；spawn eng-coder 须携带匹配凭证；链终消费（细则见 FR3 注） |
| FR4 | 代码评审归属 | eng-coder 交付前自查（对照验收标准/文件范围，非 LLM）→ **内部协议闭环**：实现 → explore 偏差审计 → 自修 → advisor(type=code) 复评 → 收敛后一次交付（完整协议权威 = 设计档主流程 step 6）；修正轮默认不重跑审计/复评；父侧复核保留可选（stalled/存疑才复核） |
| FR5 | 评审时机 | **设计评审仅由用户发起**（agent 呈递就绪并提醒，不自行调 advisor）；打回后每轮呈递发现 + 修复建议、用户逐条拍板；**交付 code review 流程节点自动**（eng-coder 内部协议默认承担，不问用户）；advisor 失败停止重试 |
| FR6 | 范围约束 | **A 裁定**：去掉“文件清单外不可改”硬约束——清单外改动**允许**（交付必要），但**必须逐项报告中说明**（透明）；审计“out-of-list”判据 = “**改了且未报告 = 偏差**（静默越权）”；已报告 = 透明可接受；父代理不得修改设计文档外的范围；超范围停下提出设计更新 |
| FR7 | 待办管理 | 技术待办统一在 `docs/TODO.md`，不落入设计文档（避免触发重新 doc review） |
| FR8 | 多任务并行 | 相互独立的设计可**并行推进**，上限 ≤4 并发（提示词纪律——无机械门禁）。**调度器条款**：spawn 声明 `files`+`dependsOn`——冲突/顺序交调度器自动处理（重叠域 queued、依赖链自动顺序、同步冲突报错），不再手动串行；锚句 “overlapping domains are queued by the scheduler, never hand-serialized”（`design/AGENT-LOOP.md` §10）；未声明 files 不参与冲突检测。token 按 designId 隔离互不覆盖；发起权不变（FR5） |
| FR9 | **角色三段链**（用户裁定） | **主 agent = 产品经理（会话面）**：收集/登记/澄清/与已有需求文档对账 + **批次式记录**（`docs/batches/`）+ 编排/确认/核验 + 设计判断权；<br>**eng-designer = 设计与需求成文（写稿面）**：依批次登记需求、**维护需求文档体系的整体性**，需求成文后再写设计；自勘察；无 token；不发起评审；eng-coder = 实现。<br>定位：设计 = 对需求的检验；撞问题 → 停下报告交回主 agent。见 §1.6 与 §1.5。 |
| FR16 | **批次记录机制**（机制见 `requirements/ENGINEERING-MODE-MECHANISM.md` §1.12） | 工程模式任务以**批次**为流转单元：一批一份 `batches/<批>-<主题>.md`，**六段 append-only、一段一作者**；**§2 即 eng-coder 任务书本体**；随件传递、子代理自写己段；整档冻结 |
| FR17 | **交界面契约**（机制见 §1.11） | 环节间传递只有三类（对话 / 参数 / 文档路径）；**五条界面铁律**（产物落盘消息只报告 / 凭证走参数 / 澄清必经主 agent / 三方条目一致 / 批次档随件传递、各写己段）；B1–B14 交界面逐项定义传什么/怎么传/产出什么/怎么放 |
| FR18 | **需求池指针台账**（机制见 `requirements/ENGINEERING-MODE-MECHANISM.md` §1.13） | 条目 = **一行指针**（需求句 → 需求档节 + 任务书 §2 + status）；**不展开任务细节**（重述 = 漂移源）；状态机**六态**，**在途起任务书指针必填**；两池不混（需求池 / 技术待办）；**记录 + 状态推进 + 物理落笔 = 主 agent**，提交 designer 时必须带上本批 todo 项 |
| FR19 | **设计要求（eng-designer 产出要求）**（内容见 §1.8） | 产出物两件：**批次任务**（独立产物，落批次档 §2）+ **设计档**（8 项：选型对比 / 接口契约 / 受影响文件带行数+拆分计划 / 决策记录 / 验收标准逐条回指 / 用例表 / 边界 / UI 决策落档）；合格判据 = **advisor 设计评审八维**（权威源 `thincoder-core/prompts/advisor-design.md`）；设计边界五条（不发明需求 / 不过度设计 / 不写实现 / 不碎片化 / 不静默改语义） |
| FR20 | **失败与异常路径有定义**（**九条清单见 §1.14**） | ①L2 不过 → **fix round** ②轮次用尽 → **用户裁决** ③评审不收敛 → **用户裁决** ④否决设计 → **补需求**（同批继续）⑤撤回/废弃 → **批次档标状态 + 同步需求池** ⑥退出模式 → **纯操作开关** ⑦token 过期 → **再次评审拿新 token** ⑧依据缺失 → **必传 `batchDoc` + 执行者拒收** ⑨崩溃 → **报告，用户决策** |
| FR21 | **文档更新纪律**（机制见 `requirements/ENGINEERING-MODE-MECHANISM.md` §1.15） | 写权矩阵（文档类→唯一作者）· 单一权威源（一处详述、其余引用）· 计数/枚举与列表同改 · 指针形态 `文档:节`（行号只作 as-of）· **冻结窗口** · **回读核对** · 变更留痕 + **核销同步清单**；机械校验最小集 V1/V2（段引用可解析 / 计数与列表一致），快层可跑、零假阳才常驻 |
| FR22 | **批次档段写入工具**（目标与澄清见 `requirements/ENGINEERING-MODE-MECHANISM.md` §1.16） | 一个**无路径参数**的专用工具（目标档由 spawn 注入 + 门禁）：**角色×段白名单**（designer→§2 · 设计评审→§3 · coder→§5）· **append-only** · **凭证行由工具剥除** · **只对设计评审开**（代码评审保持纯只读）· 写入失败**明示 + 父侧代写打标**；机械校验 **V3**（§3 非空 + 含轮次行） |
| FR23 | **VSC 端镜像**（目标与澄清见 `requirements/ENGINEERING-MODE-MECHANISM.md` §1.17） | 工程模式机制（batchDoc 门 · eng-designer 角色+行为纪律 · 文档更新纪律 V1/V2/V3 · `batch_segment` 工具）**完整落到 VSC 端**；**语义同源、原文自持**（两端各自实现，不共用代码）——终局判据 = **VSC 会话可 spawn eng-designer 并令其自写 §2/设计档** |
| FR24 | **台账提醒与可见面**（机制见 `requirements/ENGINEERING-MODE-MECHANISM.md` §1.18） | 两池**分显不合计**：状态行极简标记 `台账 <需求池数>·<技术待办数>`（当前项目 · 老化>0 警示色）· 明细行三面（启动 / 批次收口 / 变化）落会话流（可回看）· 变化行**一次性去重**（老化首次越线 / 需求池达阈值）· **数字单源**（解析/计数/老化/阈值一处实现）· VSC = 状态栏 item + 原生 tooltip 增量。**否决在案（不得复活）**：`/todo` 命令 · 触发字段回填+机检强制 · 点击面板 · 状态行合计/多行 |
| FR25 | **文档体系各仓自持**（机制见 `requirements/ENGINEERING-MODE-MECHANISM.md` §1.19） | 台账只收本仓条目 · 明细见该档 §1.19 |
| FR26 | **文档↔实装对账**（机制见 `requirements/ENGINEERING-MODE-MECHANISM.md` §1.20） | 现行档内的事实锚（用例号 / 文件路径 / 符号）**能机械地对上实装**——悬空的锚当场报红（阈值 0）；机器判不了的语义句**有归属、有周期**；明细见该档 §1.20 |

> **FR3 注（授权链细则）**：designId 为**同 scope 实例恒定**（复审沿用同 id，旧 token 存活至 TTL 保留）；不锚定文档路径/内容（“文档锚失效”路线已否决）。spawn 单设计时 designId 可省略。
> token 随会话 slot 持久化跨进程（**TTL 7 天 fail-closed**）。**链终核销由父侧 consume-design 消费**（细则 = `design/ENGINEERING-MODE.md` §「Token 生命周期」）。

> **FR16 注（批次记录机制细则）**：六段 = §1 讨论 / §2 批次任务 / §3 设计评审 / §4 用户批准 / §5 实施记录 / §6 验证与收口（**一段一作者**）；
> **它是全链路唯一贯穿的档**；**§2 即 eng-coder 任务书本体**（spawn 传路径，**不另写副本**）；子代理自写、不经父侧转述；**§6 验收归父代理**；模板骨架固定（agent 只填不定位）；整批做完整档冻结。细则权威 = `requirements/ENGINEERING-MODE-MECHANISM.md` §1.12。

### 1.4 非功能性需求（技术标准）

| # | 维度 | 标准（**目标态**——本表只放标准，实现细节归设计档） |
|---|---|---|
| NFR1 | 性能 | token 校验在 spawn 时同步完成、无网络依赖（设计目标 **<10ms**）；design review 每轮一次 LLM 调用 |
| NFR2 | 收敛性 | code review 轮次有硬上限（**现行 5 轮**，第 6 次调用被机械拒绝）；design 评审不消耗该预算（cap 豁免） |
| NFR3 | 安全 | token 机械匹配（**格式 + TTL fail-closed**）+ designId 定位槽；token 为**无签名流程凭证**；复审失败不波及其他设计的槽；随 slot 持久化跨进程（**TTL 7 天**） |
| NFR4 | 兼容 | 两模式**互斥**：工程模式禁用 `coder` 角色，普通模式禁用 `eng-coder` 与 `eng-designer`；行为不互相污染（提示词两套独立） |
| NFR5 | 可维护 | 代码/文档判定逻辑**单一来源**，且**不得写死目录名**（与 FR12 一致——锚定字符串不得作为判定依据） |
| NFR6 | 可恢复 | eng-coder 失败/中断可重新 spawn（同 token——链中未消费）；advisor 工具失败不重试，向用户报告 |

> **NFR3 注（存量旧格式拒绝——活机制）**：旧 3 段格式 token（`uuid:expiresAt:HMAC` 形态——HMAC 指历史防伪层签名段，已删，此处仅作拒绝判定的格式描述）即使 TTL 内也**格式即判错** → fail-closed 拒绝 → 需重新设计评审。

### 1.5 角色重定义裁定清单（FR9 澄清产物——用户逐条确认；设计见 `design/ENGINEERING-MODE.md`）

| 12 | **勾销归属** | 验收勾销/逐条验收结论/需求池核销落**批次档 §6**；**设计档内不写勾销状态** |

**差异面收口（RF-1–RF-6；三方一致锚**：本清单 = 批次档 §2 条目表 = 设计档对应节，AC 回指 = 设计档验收标准）：

- **RF-1 勾销口径收口**（#12）· **RF-2 内容权与提示词流程**（#8/#10）· **RF-3 作者归属面**（#10/FR9）· **RF-4 子代理提示词角色句**（#1/#3）· **RF-5 登记面**（#11——D3/D7）· **RF-6 回归锁**（FR19）。
- **判定句**（供核对——每条可机器验证）：
  - **① 勾销口径（RF-1）**：文档规范与设计档模板**无「勾销进设计档」表述**；验收勾销/逐条结论单指**批次档 §6**。
  - **② 内容权与流程（RF-2）**：落笔链口径 = **主 agent 内容权 + eng-coder 落笔（走正常链）**——两档一致。
  - **③ 作者归属（RF-3）**：需求档与设计档作者 = **eng-designer**——`docs/README.md` / `AGENTS.md` / 设计档角色节同口径，无「过渡期主 agent 代行」「尚未落地」类残留。
  - **④ 子代理角色句（RF-4）**：子代理提示词不将设计档表述为父代理产物、不含「coder 更新设计档」类句（双端各自核）。
  - **⑤ 登记面（RF-5）**：三档计数/状态自洽（无过期计数、无过期「待实施/尚未落地」）。
  - **⑥ 回归锁（RF-6）**：新增/更新断言全绿 + 批级宽度/一致性门**零新增违规**。

### 1.6 工作流程

**一句话**：人按批次提需求；主 agent 收、对、问；需求清爽且人点头后，才交给设计者；设计者**先把需求文档整合干净，再写设计**。

**适用范围**：**纯文档维护同样是需求**——它**入口走需求侧**（登记进需求池 → 澄清/收口），**但不需要走代码侧的后续流程**：

| | 代码变更 | **纯文档维护** |
|---|---|---|
| 需求侧（登记/澄清/收口） | 走 | **走** |
| 设计评审 → 用户批准 → eng-coder 实施 → 验收链 | 走 | **不走**（没有开发，哪来后面那些） |
| 实施者 | eng-coder | **写稿面唯一作者（= eng-designer）**——它做了就完 |

**理由**：代码侧那些环节（评审/批准/凭证/验收）保护的是“**改代码**”这件事；文档改动由写稿面唯一作者实施，**做完即完**。
**“不拦”≠“免登记”**——免的是代码流程，不是需求登记。

**分步**

1. **人提需求——按批次**。想起什么说什么，交代给主 agent（不是一次把整个产品想清楚）。
2. **主 agent 负责会话**：收集、登记本批需求，把含糊处问清楚。它是人与后续角色之间唯一的对话口。
3. **与已有需求文档对账**：新需求要跟**现有需求文档**比对——跟已有条款冲突、重复、或语义打架的地方，**回头问人**，不自己挑一个解释。
4. **需求清晰 + 人同意 → 才进设计**：本批需求都问明白了，且用户同意开始，主 agent 才去调 **eng-designer**。
5. **设计者先整需求、再写设计**：eng-designer 接手后**第一件事不是写设计文档**，而是把本批需求**整合进整体需求文档**——保证全篇逻辑连贯、前后不矛盾。
6. **整不动就把问题打回**：整合中发现需求本身说不通（缺口、矛盾、不可实现）——**打回主 agent**，由它向用户澄清。
7. **需求文档干净了，才写设计文档**：需求整合完整是写设计的前置条件。

**要点**

- **张力是客观存在的，不是缺陷**：需求文档要的是**整体性**，而人提需求是**批次式**的——这个张力**正是 eng-designer 存在的理由**。
- **分工**：**主 agent 以批次式记录需求**（适应交互节奏）；**eng-designer 根据批次去登记需求，维护需求文档体系的整体性**。**批次记录在会话面，整体成文在写稿面**。

**记录规范**

- **记理解，不记原话**：需求文档记主 agent 的理解（结论），不搬用户口述原文；理解错了由用户纠正。
- **记录不加工**：主 agent 把口述整理成条目时**不得掺入自己的排序/推断**——那是解读不是记录。
- **需求层问题当回合改**：定性与流程属需求本身的问题，不等攒批。

**两道关（谁审谁）**

| | 负责什么 | 不管什么 |
|---|---|---|
| **第一关：主 agent ↔ eng-designer**（同层边写边核） | 设计者：**需求不漏、跟踪不乱、据需求做好设计**；主 agent：核需求是否漏、跟踪是否乱（台账/文档体系），问题回给设计者改 | 不审设计好坏 |
| **第二关：advisor 文档审核**（独立上下文） | **审核设计本身是否有问题** | 不管需求收集与跟踪 |

**顺序**：先过第一关 → 再交 advisor 审设计（发起权在用户）。

### 1.7 主会话需求讨论循环

> 循环**由用户驱动**（想起什么说什么）——agent 不主动起头。

| # | 主 agent 的动作 | 关键点 |
|---|---|---|
| 1 | **复述确认** | 用自己的话把用户的表述复述一遍——**只复述，不加工**（不排序、不补全、不揣测言外之意） |
| 2 | **落批次记录** | 写进 `docs/batches/<批>-<主题>.md` §1——**按模板骨架填槽**（骨架见 `requirements/ENGINEERING-MODE-MECHANISM.md` §1.12） |
| 3 | **与已有需求文档对账** | 去 `docs/core/requirements/` 逐条比：冲突 / 重复 / 语义打架 → 记下；相关不冲突 → 增量；全新 → 新板块 |
| 4 | **把对账结果回给用户** | 有冲突/含糊/缺边界的**一次问一个**（不连珠炮）；**不自己挑一个解释** |
| 5 | **问缺** | 追边界（不做什么）、验收怎么算过、与既有条款怎么共存 |
| 6 | **收口回读** | 本批说完 → 回读“本批需求清单” → 用户说“就这些” = 本批收口 |

**出口**：收口后**停住**（发起权在用户）——用户说开始设计，主 agent 才去调 eng-designer。交出去的东西 = 批次记录档（§1 讨论）+ 相关现有需求文档 + 本批清单。**需求层不过评审**（用户确认即定稿）。

**循环期间的纪律**：批次档不是规格（需求永远在需求档成文）· 冲突一律回问（无“自己决定”的口子）· 随时可改口（追加/修正 → 回到第 1 步，批次档跟着改）· 猜攒批（零散点先落批次档，攒够了用户决定何时正经谈）。

### 1.8 eng-designer 工作流

**授权范围 = 需求文档体系整体**（非单板块）。理由：只改自己能改的**保证不了全体系一致性**——跨板块矛盾会永远无人处理。

**边界（能改什么）**：

| 可自主修 | 必须打回澄清 |
|---|---|
| **一致性问题**：跨板块重复、措辞矛盾、结构错位、过时表述、指针失效 | **需求语义**：改含义、砍范围、改优先级——那是用户的决定 |
| 均需**逐条报告**（改了哪几处、为何）——不得静默改 | 打回主 agent → 用户澄清 |

**收到什么**：批次记录档 §1 讨论 + **本批 todo 项** + 需求文档体系 + 本批需求清单 + 归属板块。**缺料（归属不明/清单不全）→ 打回**，不自己猜。

| # | 动作 | 产出 |
|---|---|---|
| 1 | **自己勘察现状**——读代码/文档/既有设计，拿 `file:line` 证据（可派 explore 并行） | 现状事实 |
| 2 | **把本批需求并入需求档**（todo 侧 = 需求档条文修订——状态推进 / 物理落笔归主 agent）——新条目落位（不新开档）；**并做全体系对账** | 需求文档体系更新 |
| 3 | **每条需求配验收口径（判定句）**——执行面 + 判据面 | 需求完备 |
| 4 | **需求成文后写设计** `design/<板块>.md` | 设计文档 |
| 5 | **自检 + 交回**——逐条核需求覆盖、需求档与设计档一致；报告 + **停** | 交付报告 |

**失败路径（一律打回，不自己编）**：需求说不通（缺口/矛盾/不可实现）· 勘察发现需求与现实冲突 · 归属不明。

**纪律**：不发起评审 · 不写实现代码 · **写稿面唯一作者**；澄清必须经主 agent（它是唯一对话面）。

**产出物（两件——不要混为一谈）**：

| 产出 | 内容 | 落点 |
|---|---|---|
| **A. 批次任务**（独立产物） | 本批覆盖的需求条目 + 明确不在本批的条目 + 受影响文件 + 验收标准 | 批次档 §2（**不写进设计档**） |
| **B. 设计档** | 下表 8 项 | `design/<板块>.md` |

**为何批次任务必须独立成件**：需求并入体系后会**化掉批次边界**——不写它，“本次开发要做什么”就找不着了。**下游**：它就是 eng-coder 的任务书；advisor 设计评审也要读它（八维 #1 需求覆盖 / #6 范围 靠它判）。

**设计档必须包含（8 项——缺一项即不完备）**：

| # | 内容 | 判据来源 |
|---|---|---|
| 1 | **方案选型与理由**——候选 ≥2 时**必须有对比表**（候选 / 判据 / 取舍 / 否决理由）；单方案显式声明豁免 | 纪律层文档规范 |
| 2 | **架构 / 接口契约** | 同上 |
| 3 | **受影响文件清单**——源/测试文件**带当前行数 + 预计增量**；跨档位文件**带拆分计划**（文件档：>300 主动拆分评审，>500 必须拆；**函数档是第一判据**） | 评审八维 + 结构硬指标 |
| 4 | **关键决策记录**（含被否决的备选） | 纪律层文档规范 |
| 5 | **验收标准**——**逐条回指批次任务里的需求条目**，且**可验证** | 评审八维 #5 |
| 6 | **测试用例表**（正常 / 边界 / 错误 + 输入/预期输出） | 三层结构·测试层 |
| 7 | **边界**（不做什么） | 纪律层文档规范 |
| 8 | **UI/交互决策全落档**——未定部分标 `open`，**绝不静默发明** | 主流程 |

**合格判据** = **advisor 设计评审八维**（权威源 `thincoder-core/prompts/advisor-design.md`：需求覆盖 / 可行性 / 方法论合规 / 清晰度 / 验收标准 / 范围 / 文档归属 / 受影响文件规模标注）；此处不复制（单一权威源）。**其中“需求覆盖有漏点” = 🔴 必须处理**。

**设计的边界（不做）**：不发明需求（缺口→打回）· 不过度设计 · 不写实现代码 · 不碎片化 · 不静默改需求语义。

### 1.9 eng-coder 工作流（按现状落档）

**收到什么**：**任务书 = 批次档 §2（路径，不是消息副本）**——designToken + designId（授权凭证，**经参数传、绝不进任务文本**）+ 涉及文档 + 文件清单 + 验收标准。

**授权与边界**：

| 项 | 现状 |
|---|---|
| 机械门禁 | 无有效 token 时 write/edit/apply_patch/hashline_edit/insert_after/delete 全拒；spawn 时按 designId 定位槽比对 token，不符即 throw |
| 设计是权威规格 | 通读设计、遵循、不偏离；**撞设计缺口 → 停下报告**，不静默适应 |
| file 域声明 | = **预期触碰面**（调度排队 + 披露基准），**非授权边界**；超声明 ≠ 越权，**如实披露即可** |
| 永不编辑设计文档 | 真实文档漂移写报告，归父侧处理 |
| 子代理身份 | 任务已被父代理确认过——**不等用户、不请确认**，立即执行 |

**内部交付协议**（权威 = 设计档主流程 step 6）：实现 → 自查透明表 → **explore 偏差审计**（审计任务书 = 父 spawn 任务书 ∪ 实际 `_touchedFiles` 机械并集；查四类偏差：部分实现 / 静默简化 / 文档漂移 / 超清单改动未报告）→ dirty 自修（**修正轮 ≤5**）→ clean → **advisor(code) 复评** → findings 自修 → **收敛交付**。
审计节点 ≤6 次（第 7 次机械拒绝 = stalled 信号）；不收敛 → 报告 `stalled`，**绝不静默**。

**交付报告**：改了什么/为什么 · 碰过的文件路径 · 怎么验证的（命令 + 结果）· **交付透明表**（Done / Simplified / Not done，无 deferred 列）· 审计/评审轮次 + 终态（`clean` | `stalled`）。

**父侧接手**：交付 settle → 改动合并进父代理 → 父侧对照验收标准核、跑 **L2 全量恰一次** → verify → 链闭合后 `consume-design` 消费槽。**父侧不再自动 spawn 审计/评审**（防双重审计）。

### 1.11 交界面契约（每个环节传什么/怎么传/产出什么/怎么放）

**传递方式只有三类**：

| 类 | 用途 | 铁律 |
|---|---|---|
| **对话** | 人与主 agent——**唯一对话面** | 子代理无对话面；引擎室向用户澄清必经主 agent |
| **参数** | spawn 调用面（凭证/文件域/评审对象） | **token / designId 走参数，绝不进任务文本** |
| **文档路径** | 产物与输入都落盘，交界面只传路径 | 产物**不靠消息传**（消息只用于报告） |

| # | 交界面 | 传什么进去 | 怎么传 | 产出什么 | 怎么放 |
|---|---|---|---|---|---|
| B1 | 用户 → 主 agent | 需求表述 | 对话 | 批次记录 §1 | `docs/batches/<批>-<主题>.md`（新建） |
| B2 | 主 agent ↔ 需求体系 | 本批需求 + 现有需求档 | 读 | 冲突/含糊/缺边界清单 | 记入批次档 §1；冲突**回问用户** |
| B3 | 主 agent → eng-designer | 批次档 §1 + **本批 todo 项** + 需求档 + 本批清单 + 归属板块 | spawn：task 文本（**传路径，不搬内容**）+ `files` 声明（**不声明台账档**） | — | — |
| B4 | eng-designer → 需求体系 | 本批需求 | 直接编辑（**写稿面**） | 需求条目（**带判定句**）+ 全体系对账修正 | `docs/core/requirements/<板块>.md` |
| B5 | **主 agent** → 需求池 | todo 项状态推进 | 主 agent 直接编辑（台账管理权归主 agent） | 状态更新 | `docs/TODO.md` 需求池组 |
| B6 | eng-designer → 批次档 §2 | **批次任务** | **追加**（不重写 §1） | 本批覆盖条目 + 不在本批条目 + 受影响文件 + 验收标准 | 批次档 §2 |
| B7 | eng-designer → 设计 | 设计 | 直接编辑（写稿面） | 设计档（**产出要求 8 项**） | `design/<板块>.md` |
| B8 | eng-designer → 主 agent | —（交回） | **最后一条消息**（报告） | 改了哪几处 / 设计在哪 / 自检结果 / 打回点 | 报告不落档；主 agent 核（**第一关**） |
| B9 | 主 agent → advisor | documents 清单（设计档 + 需求档 + 批次档 §2——**§3 段不在评审对象清单内**）+ object 声明 | advisor **参数**（**发起权在用户**；设计评审带 `batchDoc`——有批次档在飞时必传；工具侧口径 = **若传则须可读**） | 发现表 + VERDICT + token/designId | **凭证入会话槽，不落文档** |
| B10 | 用户 → 主 agent | 显式 sign-off / 逐条拍板 | 对话 | 批准（或打回） | — |
| B11 | 主 agent → eng-coder | **批次档 §2 路径**（= 任务书本体）+ designId + designToken | spawn：task 文本 = **极简指针** + `files` 声明；凭证走**参数** | — | — |
| B12 | eng-coder → 交付 | 设计（权威规格）+ 任务书 + **批次档路径** | 读文件 | 代码改动 + **自写批次档 §5** | 改动留**工作区未提交**；§5 落档；消息只报指针 |
| B13 | 父侧验证 → 收口 | 验收标准 | 跑 L2 全量 + verify | 验收结论 | 批次档 §6 |
| B14 | 链闭合 → consume | designId | 参数 | 槽消费（同 designId 再 spawn 机械拒） | 会话态 |

**五条界面铁律**：

1. **产物落盘，消息只报告**——交界面传路径不搬内容（防上下文膨胀 + 防双源）。
2. **凭证走参数**——token/designId 绝不进任务文本、绝不落文档。
3. **澄清必经主 agent**——任何子代理撞到需要用户决定的事，一律打回主 agent；无旁路。
4. **三方条目一致**——批次档 §2 本批条目 = 设计档验收标准回指的条目 = 需求档条目。advisor 八维的 #1 需求覆盖 / #6 范围**靠这份清单判**，所以 B9 的 documents 清单必须含批次档 §2。
5. **批次档随件传递、各写己段**——每个环节的子代理都收到批次档路径，**只写自己那一段**（append-only，段不重叠 → 无写冲突）；**子代理自写，不经父侧转述**。**例外：§6 验收归父代理**。

### 1.14 失败与异常路径

| # | 情形 | 处置 |
|---|---|---|
| 1 | **L2 验收不过** | **发修改任务让 eng-coder 再改**（fix round，同 token——链中未消费） |
| 2 | **修正轮用尽仍不过** | **用户裁决** |
| 3 | **设计评审打回不收敛** | **用户裁决**（不静默循环） |
| 4 | **用户否决设计** | **补充需求**——由主 agent 继续与用户沟通补充需求（回 §1.7 讨论循环）；**同批继续**（补需求追加进本批批次档 §1，状态仍「未收口」） |
| 5 | **需求阶段撤回** | **批次档标注状态「已撤回 <日期>」+ 同步更新需求池**（条目 → 已废弃） |
| 6 | **批次废弃 / 实施中途叫停** | **批次档标注状态「已废弃 <日期>」+ 同步更新需求池** |
| 7 | **中途退出工程模式** | **纯操作模式开关**——不扩大语义（见下） |
| 8 | **token 链中过期**（TTL 7 天） | **再次评审拿新 token**（同 scope 沿用同 designId，作该实例复审 → 签发新 token → **继续原链**） |
| 9 | **批次档缺失/写歪** | **两道**：①**机械校验**——spawn **必须传 `batchDoc`**；没传即拒（判据 = 参数在 + 路径可读）②**执行者拒收**——查不到任务书就不执行、打回 |
| 10 | **子代理崩溃 / 工具失败** | **停下报告 → 用户决策**——**不自动重派**；报告须含：崩在哪一步、工作区已改了什么、批次档哪段空着、可选项（原样重派 / 带半成品继续 / 清理后重来 / 作废） |
| 11 | ~~代码善后 / 回滚策略~~ | **撤销——不构成独立问题**：工作区有改动 = 常态，产品已有 `/undo` / checkpoint / git 三套手段，工程模式不另立规则 |

**“用户裁决”的含义**：停下向用户报告（情形 + 已试手段 + 可选项），由用户定下一步；**不自行决定、不静默循环**。

**“退出工程模式”的边界**：**它只是一个操作模式开关**，**不得扩大语义**：

| 它不是 | 说明 |
|---|---|
| **不是撤销批准** | 已签发的 design token **跨模式存活**（仅 TTL 过期清）——重进后可直接续用 |
| **不是批次废弃/撤回** | 批次档**不动**；下次进入继续 |
| **不要求在途链先收尾** | **无退出门槛** |
| **不影响在途子代理** | 子代理配置是 spawn 时快照，照常跑完 |

## 2. 可移植性需求（工程模式是产品功能）

**定位前提**：ThinCoder 是**面向任意项目的产品**（npm 发布 / marketplace 上架 / 全球 i18n）——工程模式是其**产品功能**，必须在**任何项目**上可用，不得假定用户项目形如 ThinCoder 自研仓。

| # | 需求 | 约束 |
|---|---|---|
| FR10 | **不得假定项目约定** | 产品不得假定用户项目的文档布局/命名/语言/构建/测试方式；凡需知道项目约定处，必须由**项目自述**（AGENTS.md 等）或**配置**提供；**缺失时降级可见**（写进报告），不得静默失效 |
| FR11 | **开启前提不得依赖本产品自退役的物** | 开工程模式不得把某个硬编码文件名当门禁（现况：要求项目根某模板档而该模板已不存在——选项必炸）——前提应为**项目自述的可用性**或无前提 |
| FR12 | **代码/文档判据不得写死目录名** | “什么算产品代码”不得以 `^src/` 之类**字符串锚定**判定（嵌套布局会被当文档、**静默绕过设计门禁**；非 `src/` 布局项目则所有文件都当产品代码）——判据须**单一权威 + 项目自述/配置可诉**，且任何布局不漏判 |
| FR13 | **纪律层不得把本产品形状强加给用户项目** | 纪律层提示词不得教 agent 在用户项目里建 ThinCoder 形状的目录/维护本产品的流程文件；不得要求跑**本仓自带**的脚本 |
| FR14 | **推进档位入需求** | auto（每步自动推进）/ manual（每步等用户放行，叫停即切）是**用户可感知的交互契约**，须在需求层有据 |
| FR15 | **非 git 项目行为有定义** | 工程模式在非 git 项目下的行为需明确定义——现况：评审范围采集/代码索引/检查点均依赖 git，缺失时**部分静默为空** |

> 上述六条均为**需求**（待设计）——具体实现方式（配置项 / 项目自述 / 探测策略）属设计层。
> 验证方向：用一个**非 Node、非 `src/` 布局、无 `docs/` 树、非 git** 的项目试跑工程模式全流程——不得出现静默失效，不得被不存在的文件卡住。

## 3. 边界（信任模型）

- **eng-coder 拦截型机械约束**：token 校验、写文件门禁。质量靠 eng-coder 自查 + 交付前自评。
- **父代理拦截型机械约束**：design token 前写产品代码被拒。其余（等批准、不写实现、验收）靠纪律层提示词。
- **门禁豁免边界**：豁免仅覆盖设计产出物（`docs/**`、根级 README/AGENTS/LICENSE）；产品树 `src/**` 下一切文件（含提示词档）为产品代码。
