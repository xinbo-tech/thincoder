### 1.12 批次记录档（产品机制）

> 归属：本机制属**产品需求**（要能装到任意项目）。设计侧机制（门禁 / 段写入工具 / VSC 镜像）= `design/BATCH-RECORD.md`。

**定位：任务流转的核心依据**——**全链路唯一贯穿的档**：

| 环节 | 靠它做什么 |
|---|---|
| B1 讨论落档 | §1 讨论 |
| B3 → eng-designer | §1 是本批输入源 |
| B6 designer 追加 | §2 批次任务 |
| B9 → advisor | §2 是八维 #1 需求覆盖 / #6 范围的判据基准 |
| B11 → eng-coder | **§2 即任务书**（路径传递，无副本） |
| B13 父侧验收 | §2 验收标准为对照基准 → 结论入 §6 |
| 需求池核销 | §6 是证据 |

**为何只有它全链**：需求档管“现状是什么”（**无批次概念**——条目并入即化掉批次）· 设计档管“怎么做”（跨批次演进）· **任务书即 §2**。**只有批次档有“起 → 派 → 验”完整链条。**

**两条硬要求**：① **它不能缺、不能写歪**（外部记忆——agent 上下文会丢）；② **“不是规格”的边界不得模糊**（它是**流程依据**，不是**现状依据**）。

**依据缺失的处置**（FR20 #9）：**查不到任务书就不执行、打回去**——执行者 spawn 时若**任务书／依据不存在或不可用**（coder 找不到 §2、designer 找不到 §1），**拒收并打回**。**归属 = 执行者纪律**（提示词层）。

**机械校验**：**一律规定必须传 `batchDoc` 参数**（批次档路径），**designer spawn 与 coder spawn 都要求**；**没传即拒绝（打回）**。
判据只到“参数在 + 路径可读”——**不校验内容/措辞**；内容够不够由“执行者拒收”兜底。

**粒度**：**一批一份**——`docs/batches/<批>-<主题>.md`。
**主题**：批次的概括词——通常就是主板块名，但**允许跨板块**；跨板块批用能概括的主题词，**仍是一份档**（档内分区）。
**六段 append-only，一段一作者**（一个段只有一个写手——两写手共段 = append-only 破功 + 归属含糊）：

**为什么不是“一板块一份滚动档”**：滚动档要求 agent 反复做四件事——定位不漂、结构不错位、记录不加工、长档不腐——**它们恰好是 agent 最弱的地方，且已被实证**（滚动档全部腐化，批次档从未腐化）。**形态迁就 agent**：新建一份、写完冻结、永不回改旧档。

**生命周期**：§1 讨论起草于批次开始 → 需求谈清由 eng-designer 抽入需求档 → §2 批次任务 → §3 设计评审 → §4 用户批准 → §5 实施记录 → §6 验证与收口 → **整档冻结**。

**模板（固定骨架——agent 只填不定位）**：

```markdown
# <板块> · 批次记录（<批>）

> 六段 append-only，**一段一作者**：§1 讨论（主 agent）· §2 批次任务（eng-designer）·
> §3 设计评审（评审子代理）· §4 用户批准（主 agent）· §5 实施记录（eng-coder）· §6 验证与收口（父代理）。
> 不是规格：需求在 requirements/ 成文；整批做完整档冻结。

## §1 讨论（主 agent）
### 批次范围
### 谈成什么（逐条）
### 对账结果（与现有需求文档的冲突/含糊 + 用户澄清）
### 本批需求清单（回读给用户 → 用户确认）
### todo 项（提交 designer 时必须带上）
### 过程留痕（可选：讨论约定/踩过的坑）
### 状态：未收口 | 已收口 <日期> | 已撤回 <日期> | 已废弃 <日期>

## §2 批次任务（eng-designer 自写）
### 本批覆盖的需求条目
### 明确不在本批的条目
### 受影响文件（源 / 测试档带当前行数 + 预计增量；文档档两列填 —）
### 验收标准（逐条回指需求）
### 任务书就绪（本节即任务书——spawn 传路径，不另写副本）

## §3 设计评审（评审子代理自写）
### 轮次与发现（发现摘要 / 🔴 处置——**凭证值不落档**）

## §4 用户批准（主 agent 记）
### 批准（日期 + 批准范围）

## §5 实施记录（eng-coder 自写）
### 交付摘要（改了什么 / 碰过的文件 / 如何验证）
### 交付透明表（Done / Simplified / Not done）
### 审计与代码评审（轮次 / 终态 clean|stalled）
### fix round（如有：发现 → 修复）

## §6 验证与收口（父代理自写）
### 父侧验证（L2 全量结果 + verify）
### 逐条验收结论（通过 / 未过 / 未做 + 理由）——**验收勾销住本节，不进设计档**
### 需求池核销
### 核销同步清单（逐项打勾——角色表 / 状态行 / 计数 / 指针 / 变更记录 / 待办勾销 / 台账可见面（收口行））
### 遗留项
```

**段与环节的对应**：§1 = B1–B2 · §2 = B3–B7 · **§3 = B9** · **§4 = B10** · **§5 = B11–B12** · **§6 = B13–B14**。
**凭证铁律**：§3 只记“评审通过（轮次 N）”，**token/designId 值绝不落档**。

**各段作者 + 随件传递**：

| 段 | 作者（一段一作者） | 写入手段 | 为何是他 |
|---|---|---|---|
| §1 讨论 | 主 agent | 普通文档写（工具链无 `batch_segment`） | 它是唯一对话面 |
| §2 批次任务 | **eng-designer** | `batch_segment`（段 = §2——**无路径参数**，spawn 绑定批次档） | 任务出自它的设计——一手 |
| §3 设计评审 | **评审子代理（advisor）** | `batch_segment`（**仅设计评审、工具已挂载时**） | 它自己的发现——一手 |
| §4 用户批准 | 主 agent 记 | 普通文档写 | 批准发生在会话面 |
| §5 实施记录 | **eng-coder** | `batch_segment`（段 = §5） | 它自己的交付——**父侧转述 = 二次加工** |
| §6 验证与收口 | **父代理** | 普通文档写 | **它是验收者** |

**段的划分标准**：**段 = 链上的角色，不是“环节里的每个动作”**。入场者 = 有独立写手身份的链上角色（主 agent / eng-designer / 评审子代理 / eng-coder / 父代理）。**进程内工具不设段**——只读子代理与子代理内部 advisor 都是 eng-coder 的内部工具，其结论由 eng-coder 写进 §5。

`batchDoc` 参数既有的模型面文案与越界错误文案**按角色集（eng-coder / eng-designer）参数化**——门禁先行而样例不教 = 每次撞墙。

### 1.13 需求池（产品机制）

**职能**：跟踪**每一条需求的落地情况**——一行一条，条目级台账。没有它，要知道“哪条需求落地了没有”就只能遍历全部文档。

**条目形态（一行一条）**：

```
- [ ] <需求句> → 需求 `<板块档>` §X · 任务书 `<批次档>` §2 · status=<状态>
```

**铁律：不展开任务细节**——需求池是**指针台账**，不是第二份任务书。细节住在需求档与批次档 §2；**在需求池里重述 = 漂移源**，也把台账变成长条垃圾场。
**为何挂任务书**：一条需求“做到哪了”→ 点开指针直接看任务书/验收结论。

**状态机**：

| 状态 | 含义 | 任务书指针 |
|---|---|---|
| 待讨论 | 已登记，还没谈清 | `—` |
| 待设计 | 需求收口，等设计 | 可挂批次档（讨论段） |
| 在途 | 设计已批准，实现中 | **必填**（批次档 §2） |
| 待核销 | 已实现，等验收/签入 | **必填** |
| 已核销 | 完成——勾销（锚行改 `- [x]`）后**移入 `docs/TODO-archive.md`** | 保留指针（已冻结）——随条目入归档档 |
| **已废弃** | **终止**（需求撤回 / 批次废弃 / 中途叫停）——**同移入归档档** | 保留指针（含批次档状态标注） |

**两池不混**：需求池收**用户需求点**；**技术待办**（设计遗留/评审发现/债）另组分列——两者同一格式、同一铁律（指针化），但**不混放**。
**分组不是排版偏好而是归属判定**（错组 = 后续状态推进认错对象）。**组计数**（每组「N 条」）与组内实条目数**必须同改**（D3）——计数口径 = **未决数**（活文件只留未决；归档条目不计入）。

**状态取值面**：台账 `status=` **只能取上表六态**（机判面见 §1.15 机械校验边界）；**活文件内取值实为未决四态**（待讨论 / 待设计 / 在途 / 待核销）；**已核销 / 已废弃 = 归档态**。

**技术待办的指针形态**（FR7 与 FR18 的口径衔接）：

- **(b) = 指针（可指则指）+ 最小证据行**（`file:line` + 症状短语）。
  - **可指则指**：技术项凡有归属档/设计节，**必须挂指针**；无归属档时指针写 `—`。
  - **证据行是不可省的那一半**：技术项没有“需求档 §X + 任务书 §2”这两根天然锚，`file:line` + 症状是它唯一可核验的锚。
  - **正文细节仍归设计档 / 批次档**：台账里只留“哪条、在哪、什么症状”。
- 需求池与技术组**同一铁律**，但**锚的形态不同**（前者挂需求档节 + 任务书，后者挂归属档节 + 证据行）——这是“两池不混”在**格式层**的必然结果。

**触发字段与老化报告**（技术待办专属）：

- **触发字段**：每条技术待办**带一种触发**（随条目尾，与 `status=` 并列）：`触发=归批（<批名/批号>）` / `触发=条件（<条件句>）` / `触发=认账不排期`——三者**合法选项**（`认账不排期` 区别于遗忘）。
- **无任何触发的条目 → 审计批默认进「待处置」**；审计模式输出「**待处置清单**」（全部无触发技术条目；**行龄超 N 天**者标「老化」——N 默认 30 天）。
- **报告不自动删 / 不改文件**——处置要人判（主 agent 与用户）。

**职责分工**：**记录 + 状态推进 + 物理落笔（台账 / 归档档编辑）= 主 agent**；提交给 designer 时必须带上本批 todo 项；**eng-designer 的台账侧职责 = 需求档条文修订 + 收拢应用清单**（不落笔台账本体）。台账档**不入任何子代理 `files` 声明**。

**可见面**（提醒 / 状态行 / 明细行）= **§1.18**——本节的口径由彼处消费。

### 1.15 文档更新纪律（FR21）

**动机**：“你根本没想过更新文档的复杂度，随便写要不了几下就把文档体系搞乱了。”写稿权唯一只是**必要条件**；两轮设计评审反复栽的是**更新纪律缺位**：

| # | 纪律 | 一句话 |
|---|---|---|
| D1 | **写权矩阵** | 文档类 → 唯一作者（§1.5 #10）：批次档 = 主 agent · 需求/设计档 = eng-designer · 提示词 = 主 agent 内容权 + eng-coder 落笔；**例外**（§1.23 0-7 · 用户 2026-09-16 裁定）：三类父侧直笔 —— ① 自有写域（批次档 §1/§4/§6 · 台账）② 纯机械形态收正（折行 / 指针形态 / 计数）③ 小修改（单行 / 表格级 · 无新语义 · 可逐条核验）——**三类皆须打标**（「父侧直接执行」+ 可 revert） |
| D2 | **单一权威源** | 一条机制**只在一处详述**，其余处**只引用不重述**（模板同理） |
| D3 | **计数·枚举纪律** | 声明“N 项/N 处/N 条”必须与列表**同时改**；可机判（V2） |
| D4 | **指针纪律** | 指针形态 = `文档:节`；行号只作 **as-of** 参考；**禁**“见上/见该节”式相对指针 |
| D5 | **冻结窗口** | **评审在途不改被审文档**（改了 = 评审对象已变 → stale，token 不签发）；“在途”的下界定义见设计档 |
| D6 | **回读核对** | 任何写入后**回读核实**再报完成 |
| D7 | **变更留痕 + 核销同步** | 每批核销跑**核销同步清单**（批次档 §6 模板槽位）：角色表 / 状态行 / 计数 / 指针 / 变更记录 / 待办勾销 / 台账可见面（收口行） |

**机械校验最小集**（可机判的才上机械——语义一致性仍归评审）：

| 校验 | 内容 |
|---|---|
| V1 **段引用可解析** | 扫描域内 `§N` / `文档:节` 引用，目标节号在目标文档或本档内存在 |
| V2 **计数与列表一致** | “N 项/处/条”声明与同节列表条数一致，不符即报 |
| V3 **批次档 §3 轮次行** | 已批准批次的 §3 非空且含工具写入轮次行 |
| V4 **跨仓形态合规** | 正文引用他仓文档的形态须在封闭枚举内（枚举外即红） |
| V5 **文档锚一致性** | 现行档内的事实锚（用例号 / 文件路径 / 符号）存在性——判据规格 = `design/DOC-DISCIPLINE.md` |

**非功能性需求（本项）**：校验必须**快层可跑**、**零假阳才能常驻**（「存量 / 入基线」已废——阈值 = 0；违规一律阻断）、**不得靠自然语言理解**（只做字符串/结构判）。
**同批继续**：补充需求**追加进本批批次档 §1**，批次状态仍「未收口」；**不新开批次**。

**机械校验边界**：

- **V1 跨仓边界**：V1 的域 = 本仓扫描域——**跨仓引用 = 显式域外**；形态规范 = 「名称（仓别）§N」（去 `.md` 后缀、去路径前缀，如 `WEBVIEW（VSC 仓）§5`）。
  **判定句**：本仓文档内的跨仓引用按规范形态书写 → V1 零命中；带 `.md` 的跨仓形态 → 检查器 fail-closed 如实报。
- **宽度规则表格行豁免**：宽度检查豁免 markdown 表格行（结构性不可折行）。
  **判定句**：>300 字符表格行零报告；非表格 >300 行照常报告。
- **文件硬限合规（存量债收束）**：超 500 硬限的测试档拆档（用例数守恒）；安全线内者**不拆**（拆分计划登记——触发 = 再度增厚）。
  **判定句**：拆分后两档各 ≤500、用例总数守恒、全绿。

**收尾批与文案卫生批的逐条声明「无新需求」**（编号修正 / 行号指针修正 / 地图回写 / 设计档侧超宽折行 / 描述面同步 / 旧锚清理 / 机制正文同步 / 注释断链 / 需求档同步 / 死产物清理）——均为既有条目面维护，**不构成新需求**；设计与用例见 `design/DOC-DISCIPLINE.md`。

### 1.16 批次档段写入工具（FR22）

**总体目标**：六段机制要求「**一段一作者**」，但子代理**没有写批次档的手段**——现实是**父侧代写**，而代写 = 二次加工 = 失真源。本项给子代理一条**受控写入通道**：各写各段、写到准确位置、不留后门。

**功能性需求**

- **F1 单一工具 + 无路径参数**：工具不接收目标路径；**目标批次档路径由 spawn 时注入**（参数在 + 路径可读，否则拒）——**语法上就写不到别处**。
  **评审侧口径**：设计评审的 `batchDoc` = **若传则须可读**（非必传）——不传即工具不挂载、评审照常跑；主 agent 侧纪律 = 有批次档在飞时必传。
- **F2 角色 × 段白名单**：`eng-designer → §2` · `设计评审子代理 → §3` · `eng-coder → §5`；**跨段/越段写入被拒**。父代理**不走本工具**。
- **F3 append-only**：只追加，不覆写、不删除已有段；多轮评审 → 追加 `### 轮次 N（评审子代理）` 小节。
- **F4 §3 内容 = 评审结论全文**：该轮的 🔴/🟡/🔵 发现表（逐字）+ VERDICT 行 + 计数；多轮各自成节。**批次档是唯一持久档案**——无表的 §3 是空壳。
  **来源戳口径**：小节标题由**工具生成**——N 只数**工具写入过的**轮次行（固定骨架行不计）。
- **F5 逐字，不经转述**：表由评审者自己的人话原样写入（父侧不得代为润色/缩减）。
- **F6 凭证剥除（工具做，非纪律）**：写入前过滤 token / designId 形态行——**模型可能忘，机械不能忘**。工具用**自有正则**（不复用巡检正则——后者匹配不到冒号态）。
- **F7 失败语义**：写入失败 → **明示报告「§× 未写入」**；回退父侧代写**必须打标**。

**非功能性需求**

- **N1 安全面不扩**：**代码评审保持纯只读**——写权只对**设计评审**开；不给 advisor 通用 `write`。
- **N2 与 D5 不冲突**：§3 写在**批次档**——**§3 段不在评审对象清单内**（B9 只含批次档 **§2**）——追加 §3 **不改变被审内容**。
- **N3 可机械校验（V3）**：**「某批 §3 非空且含工具写入的轮次行」**——与 V1/V2 同族，快层可跑。触发条件**只取机器判据「§4 或 §6 非空」**——**不引用 §1 讨论状态词**。
- **N4 不可伪造来源**：工具写入的段落**由工具加盖来源戳**——代写与自写一眼可辨。
- **N5 零回归**：既有 spawn / 评审 / 门禁行为不变。

**判定句**：段白名单越段必拒；`batchDoc` 缺参/不可读必拒（目标角色两路同判）；§3 写后档内零凭证命中；V3 在飞批次零假阳。设计与用例 = `design/BATCH-RECORD.md`。

### 1.17 VSC 端镜像（FR23）

**总体目标**：工程模式是**产品功能**，但机制原先只落 CLI 仓——**VSC 宿主会话至今停留在机制前时代**。本项把机制**完整搬到 VSC**，使两端**同一套机制、各自实现**。

**功能性需求**

- **F1 batchDoc 门移植**：spawn 子代理时注入批次档路径，门禁 = 「**参数在 + 路径可读，否则拒**」。VSC 无 CLI 的双路装配单点——**两处各落 + 共享校验函数**（选型归设计）。
- **F2 eng-designer 角色落地**：角色判定 + 工程模式角色 enum + 工具装配分支 + **webview 角色枚举四处** + 人格文件新建。
- **F3 行为纪律移植**：六段自写 · 执行者拒收 · 澄清必经主 agent · 三方条目一致。
- **F4 §3 自写工具移植**：`batch_segment`（无路径参数 / 段白名单 / append-only / 来源戳 / 剥凭证 / fail-closed）；适配点 = 工具集落点与评审实例键通道。
- **F5 文档更新纪律 + V1/V2/V3 机械校验移植**：宽度脚本扩为一致性扫描（V1/V2/V3）+ 基线 + 测试，并**接线进 VSC 测试面**。
- **F6 提示词双源**：两端各自 `docs/core/design/prompts/` 中文权威镜像 + 新增 `persona-eng-designer.md`。
- **F7 镜像锚纪律**：需逐字一致的段**在设计档定稿**——实现面照抄，**不得自行解释设计**，差异如实上报。

**非功能性需求**

- **N1 语义同源·原文自持**：两端**各自实现、不共用代码**——机制语义必须同源。
- **N2 零回归**：VSC 现有用例 + 冒烟集不得因镜像变红；新通道不削弱「代码评审纯只读」安全属性。
- **N3 可机械验证**：VSC 侧新用例需覆盖机制的关锚点（门禁 / 角色 / 段白名单 / 来源戳 / 剥凭证 / V1-V2-V3）。
- **N4 验收两层**：①机械面全绿 ②**用户手动重载扩展后自验**（在 VSC 会话 spawn 一次 eng-designer 看其自写 §2/设计档）。
  **明确前置**：源码改动**需重载扩展才生效**——“文件在了”≠“机制活了”。
- **N5 档位纪律适用**：镜像文件同样受 `>300 主动拆 / >500 硬顶` 约束。

**判定句**：VSC 会话可 spawn eng-designer 并令其自写 §2/设计档；两端锚句逐字一致；镜像差异显式登记。

### 1.18 台账提醒与可见面（FR24）

**总体目标**：把台账（§1.13）的未决状态送到用户眼前——**有可动作项才出声，其余时间零噪音**；状态行给常驻的两个数，会话流给三处可回看的文本行；两端**语义同源、各自实现**。

**功能性需求**

- **F1 两池分显（不合计）**：每个项目的两个数（需求池未决数 / 技术待办未决数）分列显示——**不混一个数、不合计**。
- **F2 状态行极简标记**：`台账 <需求池数>·<技术待办数>`（如 `台账 4·32`）——**只显当前项目**；**老化 > 0 转警示色**；不铺开、不多行、不可点击。
- **F3 三处文本行（明细面）**：各自落入所在会话流（可回看）——① **启动行**（**有可动作项才出**）② **批次收口行**（核销同步清单内的机械步骤——单源命令的输出即收口行）③ **变化行**（**老化首次越线 / 需求池达阈值**——事件驱动、一次性去重）。
- **F4 多项目判据**：**当前项目 = 上下文目录向上（含自身）最近的含台账目录**；**项目集 = 当前项目 + 其同级兄弟仓中含台账者**；**明细行集 = 当前项目 ∪ 可动作项目**；**无台账的根不显**。
- **F5 变化行一次性去重**：同一事件**只报一次**；去重载体**跨会话、跨端**；**只在行真正落入会话流后才记账**（未送达不计）。
- **F6 收口行 = 机械步骤**：核销同步清单新增「台账可见面（收口行）」项——跑单源命令，输出即明细行；**保留在会话流**（不落档、不改台账、退出码 0）。
- **F7 数字单源**：台账解析 / 计数 / 老化 / 阈值**一处实现**——机检器与两端显示面**共用该口径**。
- **F8 VSC 增量**：状态栏 item（文本 = F2 标记；**原生 tooltip = 同款明细行**；老化>0 = 警示底色）+ chat 流文本行（同 F3）——**纯增量、非新机制**。

**口径**：

- **计数**：`##` 组标题含「需求池」→ 池组；含「技术」→ 技术组；计数 = 组内 `- [ ]` 未决条目数。
- **老化**：技术组中**无 `触发=`** 的条目，**行龄 > 30 天**（git blame 行级时间；取不到 = 不计——零假阳）。
- **阈值（可开批）**：`池 ≥ 3` 或 `任一板块 ≥ 2`。
- **可动作项**：`老化数 > 0` 或 `阈值达成`。

**非功能性需求**

- **N1 零噪音与降级**：无可动作项 → 零输出；台账不可读 / 非 git / 去重档损坏 → 降级不崩；headless 零新增输出；台账档**只读**（本机制唯一写面 = 去重档）。
- **N2 成本有界**：刷新 = 周期 + 事件触发；无候选条目时不跑 git 子进程；单次刷新有界。

**判定句**：见 `design/LEDGER.md` 验收标准（逐条回指 F1–F8 / N1–N2）；三方条目一致：本节 F/N 条目 = 设计 AC 回指条目 = 批次档 §2 本批条目。

### 1.19 文档体系各仓自持（FR25；设计见 `design/LEDGER-SELF-CONTAINED.md`）

**动机（事故溯源）**：跨仓登记——他方把外部产品线的债（含一条安全项）登记进本仓台账，随主线合入并推到公开远端。内容层已清，**机制上没有闸**：同形态条目今天可以照样再登记进来。
**同病的第二种形态**：本产品的两个仓之间互相承载对方的事项。病因同一：**「能记一处就不写两处」**。

**总体目标**：一个开发者在一个工作区里同时维护多个产品时，任一产品的文档只承载自己的事项——对端产品的事项不写进来；缺的文档层就地补齐，不因「对端已有」而省略。

**功能性需求**

- **F1 台账射程**：台账（需求池 / 技术待办）只收本仓条目——禁登记本项目之外的事项；指针面收窄为**仓内可解析**。
- **F2 批次档同规**：批次档只登记本批范围（含本批的受影响文件与验收）。
- **F3 文档体系自持**：需求档 / 设计档 / 批次档 / 台账各自成套；**非复制**（语义同源、各端原文自持）。
- **F4 缺失层必须补齐**：缺失的文档层就地补建——**不得以「对端已有」「避免重复」为由省略**；**逐层成套**。
- **F5 约束须落提示词层**：F1–F4 的行为面必须在提示词层落地——文档层是规格，提示词是代理运行期实际读到的纪律。
- **F6 机检闸**：台账条目的证据 / 指针路径须在**本仓内可解析**；违规一律 fail-closed（**「存量 / 入基线」已废**——阈值 = 0）。
- **F7 核验职责**：同一机制跨多个实现面产出**一式多份设计**时，主 agent 有义务核验各份逻辑是否一致（核验四维 = 裁定同源 / 判据同一 / 边界同形 / 差异显式登记）；该职责须落提示词层。
- **F8 提示词通用化**：提示词中的多实现面条文不得绑死本产品两端；勘察 checklist 同步通用化。
- **F9 存量无豁免**：凡**触及对端**的存量批档一律处置（迁移 / 各仓持其份）；**不得以「历史已收口 / 审计链 / 重复 / 量大 / 在飞」为由豁免**。
- **F10 文档体系逐层成套**：各产品文档体系**逐层对位**；需求层**逐档三值齐备**（① 建本仓需求档 · ② 已有对位（允许异名）· ③ 本端无此面（写理由））；**不得只建单层壳**。
- **F11 需求层必须在本仓有档**：**需求层必须在本仓有档**——「对端有」「design 层有」不构成理由；**② 已有对位不得以 design 层充当**。
- **F12 结构档位硬限无豁免（适用范围 = 程序代码）**：>300 软线 / >500 硬限**仅约束程序代码（源 / 测试档）**；超限档**本批拆**（拆分判据四条：组内同面 · 迁出组夹具 ⊆ 新档自持集 · 切点零交叉 · 两档 ≤500 且余量充足）；用例数守恒。**文档（设计 / 需求 / 批次 / 台账）不受行数限制**——**无任何行数义务**（不限行数、不登记读数、不写拆分规划）（**用户裁定 2026-09-16**：「300 行 500 行那是对程序代码的限制，现在你们怎么对文档也搞起这种限制了？」）。
- **F13 对端引用形态零残留**：设计 / 需求 / 批次档正文引用对端产品文档一律**规范形态**（`名称（仓别）§N`）；**存量不是合法态**。
- **F14 先例不构成例外依据**：任何「以前也这样 / 已落形态 / 他批先例 / 存量在案」**都不构成偏离规则的依据**——**例外的唯一依据是判据句（可机判）**；找不到判据句 → 按规则办，或停下上报。
  **同条（残留即示范）**：文档 / 台账 / 变更记录中的**残留即示范**——合规形态必须显式；历史语义可保留、**形态必须规范**；**「存量豁免 / 入基线」不得再设（阈值 = 0）**。
  **同条（例外须带消解期）**：任何登记在案的例外必须写明**消解路径与到期条件**。

**非功能性需求**：**N1 零假阳**（机检新规则对本仓合法内容零命中——零假阳才能常驻）· **N2 fail-closed**（越出仓根的登记形态必被拦住）· **N3 可分步**（存量迁移允许分期——每期须有明确触发条件与逐档清单，不得停在「待议」）· **N4 否决在案**（**不得**以「另有他档」为由放宽指针射程）。

**两轴并列（不留两套口径）**：本节管**条目与归属**（轴一）；文档正文引用对端产品文档按既有 V1 边界规范（**轴二**）。一句话：**正文可以指对端（规范形态），条目与归属按仓内可解析**。

**判定句**：逐条见 `design/LEDGER-SELF-CONTAINED.md` 验收标准与用例表。行为面（F5 / F7 / F8）落提示词层，验收 = 落笔逐字 + 评审核验（机检面不设：提示词句子断言属已退役的散文锚面——见 §1.15 / `design/TESTING.md`）。

### 1.20 文档↔实装对账（FR26；设计见 `design/DOC-DISCIPLINE.md`）

**动机**：「我希望**完整的全面清理**解决。」背景：串行排查中「撞见即清」250+ 处，但**没有全量清单**——清的是撞见的，不是存在的。

**病根四条**：① 批次「受影响文件表」不列描述被改面的设计档 → 无归属 ② 一段一作者下 coder 不碰设计/需求档 → 描述句无人认领 ③ 子代理自查只核「我的改动是否自洽」→ 抓不到「全档与现态不符」④ 机检 V1–V4 管**形态**→ **不管「句子说的还是不是真的」**。

**总体目标**：现行档（设计 + 需求）里的**事实锚**（用例号 / 文件路径 / 符号）能**机械地对上实装**——悬空的锚当场报红（阈值 0）；机器判不了的语义句**有归属、有周期**。

**层 0 · 先重锚（对账前置步——2026-09-16 批 5 增补）**

- **0-1 先定权威副本**：每条待对账证据**先判其权威副本落在现行档的哪一档哪一节**（现行档 = `docs/**` 内，扣除批次档与 `_archive/`）；**旧坐标**（`thincoder-cli/docs/**` · `thincoder-vscode/docs/**`）**不构成改笔对象**。
  **判定句**：证据未经重锚即判「哪边为准」⇒ 判**违规**（漏前置步）。
- **0-2 参照历史面不参与对账**：迁移期参照历史档（`thincoder-cli/docs/**` · `thincoder-vscode/docs/**`——**保留 ≠ 维护**）的正文**不参与对账**；命中即登记「重锚至新树落点」后结案。
  **判定句**：对参照历史面正文落笔 ⇒ 判**违规**；在账证据数按**重锚后**计数（参照历史面命中不计入在账）。
- **0-3 双向对账判定（哪边为准）**：① **对外契约面**（README / `USAGE` / 用户可见提示串）以**实装可达能力**为准——能力在位 ⇒ 改文档；能力缺失 ⇒ 走需求变更全链；② **内部机制描述**以**实装 + 需求档判据**为准；③ 反向「删实装以对齐文档」= **能力回归**。
  **判定句**：以改文档掩盖能力缺失、或以删实装对齐文档 ⇒ 判**违规**。
- **0-4 逐条判定与处置三叉（批 10 增补）**：起点清单**逐条**给「号 → 档:行 → 事实句 → 现码 / 现测读数 → 判定 → 处置 → 证据」；判定**三值** = **仍漂**（事实句与现态不符）·**已消**（声明 = 实测 / 断言在档 / 现测成立）·**判不出（合法终态——须留痕：写清为何不判 + 重锚落点）**；处置**三叉** = **改文档**（事实句收正）∥ **改码**（**不属对账批**——登记另批）∥ **留痕**。
  **追加证据通道**：他批 / 他轮撞见同族漂移 ⇒ **追加一行证据**入台账该条（不扩批、不静默）；本条触发 = **条件**（「对账轮点检 ∨ 三机检报新漂移 ∨ 他批撞见事实句失真」）。
  **收口判据**：① 清单逐条有结论（零漏项）② 「仍漂」项全部处置完（改文或以注记消解）③ 处置后复跑清单 ⇒ 零未处置项。
  **判定句**：漏项 / 留「未处置」在账 / 静默弃项（不判不留痕）/ 以对账批名义改码 ⇒ 判**违规**。

**层 1 · 机检器（V5「文档锚一致性」）**

- **F1 三锚机检**：现行档内抽取锚三类（用例号 / 文件路径 / 符号）判其存在性——判据规格落设计档（正则、存在性域、排除式）；落点 = 独立档 `scripts/doc-anchors.mjs`（**不入产品提示词**——本仓自用工具）。
- **F2 零假阳（硬）**：已识别的假阳类**逐条显式排除或转另类判定**——**判据不精确 = 红一片 = 无人看 = 等于没有**。
- **F3 注记即通过**：锚带**退场/已废注记**（封闭标记集 + 来源指针）⇒ **通过**。
- **F4 报告态 → 阻断态（阈值 0）**：首落**报告态**（不阻断）+ 交付**全量清单**；清账完成后**转 fail-closed**。
- **F5 全量清单**：检查器可输出**逐条清单**（档:行 + 锚 + 锚类）+ 汇总——作为层 2 清账的输入。

**层 2 · 按锚类型清账**

### §1.21 变更面分流（产品代码 ∥ 工程工具 ∥ 文档面）（FR27）

**动机（2026-09-15 实证）**：为把 `docs/core` 纳入两扫描器的扫描目录（两行常量）走了完整 eng-coder 链（token + 审计 + advisor）= 授权过度。根因 = 提示词只规定「产品代码走全流程」，未区分**工程工具面**（只影响本仓开发/CI 的变动）。

**总体需求**：任何改动在动手前先判**变更面**——产品面走全流程；工程工具面父侧可直改；文档面按写权矩阵（D1）。

**功能性需求**：

- **0-1 三分面判据（枚举）**：
  - **产品代码面** = `thincoder-core/**` · 两产品 `{src,bin,webview,test}/**` · **产品文本面**（产品仓内对外文本：两产品 `README.md` / `package.json` / `.vscodeignore` / 仓根与产品 `AGENTS.md`）；
  - **工程工具面** = 仓根 `scripts/**` · 两产品 `scripts/**` · `.thincoder/**` · CI 配置 `.github/**` · `package-lock.json`；
  - **文档面** = `docs/**`（需求 / 设计 / 批次 / 台账 / 提示词）。
- **0-2 默认归类（补枚举缺口）**：**未列入工程工具面与文档面的路径一律按产品代码面处理**（fail-closed——宁可走流程，不得默认直改）。产品文本面**单列**（出厂产物、用户可见的对外契约）而不并入工程工具面。
- **0-3 工程工具面直改三条硬约束**：① 机械改 ⇒ 直改 + **改完实跑报读数**；② **改判据语义的**（抽取谓词 / 阈值 / 什么算违规）⇒ **仍走设计**；③ 凡直改 ⇒ 报告记明「父侧直接执行」+ 单笔可 revert。
- **0-4 授权判据 ≠ 绕过门禁**：门禁（`thincoder-core/agent/dispatch.mjs` 的 token 门 / 产品代码写门）**判定为准**；与分流判据不一致 ⇒ **停下上报**。两条已知机械面冲突（产品文本档免门 / 工程工具面被拦）登记于 `design/ENGINEERING-MODE.md` §4.1（含消解路径 + 到期条件），**不进提示词正文**。

**非功能性需求**：**N1 零回归**（只加授权判据，不改机械面）· **N2 可判**（路径枚举 + 默认规则，无灰色地带）· **N3 不引凭证面**（工程工具直改不需 designToken、不 spawn）。

**范围边界（本节不做）**：不改分类器 / 门禁 / 机检实现（另批）；不重述既有写权矩阵（D1——指针见 `design/BATCH-RECORD.md` 档头）。

**判定句**：改动面未列入两枚举 ⇒ 按产品代码面走全流程（fail-closed）；工程工具面机械改 ⇒ 直改 + 实跑 + 报告「父侧直接执行」。设计与用例 = `design/ENGINEERING-MODE.md` §4.1 / A-EM9 / EM-8–EM-9。
