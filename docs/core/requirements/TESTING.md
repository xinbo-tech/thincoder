> 板块：测试基建——测试方法（技法 ∕ 寿命 ∕ 执行三轴 ∕ 防膨胀）· 集成测试集 · 散文锚禁令 · 终端程序自动验证。
> 设计层指针：`docs/core/design/TESTING.md`（分层表 ∕ 生命周期 ∕ 集成测试集承载 ∕ 散文锚退役 ∕ harness 面）。
> 归属与命名判据 = `docs/core/design/DOC-SYSTEM.md` §5.1（P1–P5）· §6；本档不重述（D2 单一权威源）。
> **依据线**：本档全部判据的来源 = **用户裁定 + 项目实测**（实证优先）——不引外部实践为据；与外部惯例相近之处，亦以本档为准。**术语定义除外**（见 §0——官方源逐字引用、标明出处）。

## 0. 概念（两个词 · 官方定义）

> 本档其余一切（§1 起）都建立在这两个定义之上；引用原文，不改写。

**单元测试（unit testing）**——ISTQB 术语表（glossary.istqb.org · 公开）原文：
> "component testing: A test level that focuses on individual hardware or software components."
（组件测试 ∕ 单元测试 = 针对**单个**软 ∕ 硬件组件的测试——CI 语境亦称 unit testing。）

**集成测试（integration testing）**——IEEE 610.12（后并入 ISO/IEC/IEEE 24765 词汇标准）原文：
> "testing in which software components, hardware components, or both are combined and tested to evaluate the interaction between them."
（把软 ∕ 硬件组件**组合起来**测，以评估它们之间的**交互**。）

两点由此直接推出（本档后续判据的根）：
- 两者的区别 = **测的对象不同**（单个组件 ⟷ 组件之间）——不是同一测试的两种跑法；
- 由此：**单元永不转集成**（§2 F8）——「把单元测试改写成集成测试」在定义上就不成立。

> 来源与成色：ISTQB 原文 = 公开术语表逐字；IEEE 610.12 原文 = 多份公开标准 ∕ 政府文档逐字复引（ECSS-Q-80B ∕ 美 DOE ∕ 美 DOT 等）。更细的外部源对照见文末「附」。

## 1. 总体需求

### 1.1 为什么（这套方法在解决什么）

- **测试的用途只有一个：让人在改代码时知道「改对了没有」。** 单元测试 = 开发者自己的反馈回路——改完立刻跑，几秒钟得到答案；集成测试 = 上线前的验收回路——从用户能看见的入口，把真实业务走一遍。**测试不是资产、不是交付物、不是指标**——它是手段，用完就该放下。（**界定**：**单元测试**如此；**集成测试（= UAT）不是**——它是交付物，须留存并出具 RTM 总表，见 §7。）
- **单元测试「用毕即删」的原因（用户口径 · 对抗模型本能——非文档洁癖）**：**模型有「改一点代码就跑全量」的本能**；ThinCoder 是工程级产品（项目大、周期长、代码多）——**一个 agent 一天就能产出需要几百个单元测试去验证的代码**，而单元测试是**每批一次性的**：**存量测试量 × 跑全量本能 = 跑测成本远超写码成本**。⇒ **判据：单元测试件用毕即删（零留存）**——**删掉可跑的东西，就没有可跑的全量**。**边界**：只针对单元测试件（内部面）；**集成测试（UAT）不适用**（交付物：保留 + 出 RTM 总表）。
  - **本 why 为何只到这一层**：完整叙述（含「本应…」类让步句等）**不进规范面**——那些是**给你我的诚实交代**，写进执行面会被读成许可证（「本应留存」→ 可以留、「还没把握」→ 可以不做）。**规矩：why 可进规范面，让步句不得进。**
- **测试的成本天天收，收益靠概率兑。** 多一个永久驻留的测试 = 以后每一次相关改动都要照顾它：跑它、修它、分拣它红不红、改行为时还要过它那一关。而真正的收益——它抓到真问题——只在极少数时刻兑现。**总量一旦超过业务真实需要，测试就从资产变成债务。**
- **所以：保险按事故史买，不按想象力买。** 集成用例只从两个入口长出来——**业务上真实需要的场景** + **生产上真实出过的问题**。「万一以后有人改坏」不是理由；不为没发生的事预付成本。
- **测试 ≈ 业务，不是 ≈ 代码。** 一仓 50–100 个场景 ≈ 前端能做的业务动作总数；核仓 ∕ 渲染核不设独立场景——它们被前端场景**带过**：从入口驱动，链路自然全覆盖（测前端自然带到后端）。
- **单元测试按批次结算；它是证据，不是库存。** 一个批次的单元测试 = 那个批次的「改对证明」：写完、跑过、**用毕即删（零留存）**——批档 §5 留一行读数（验了什么 ∥ 命令 ∥ 结果）；不并入任何常驻集合、不承担长期义务。
- **总目标一句话：把「从改到确认」的路径压到最短，把测试花销只花在真实发生过和真实需要的事情上。**

### 1.2 三轴（怎么落）

一次代码改动的验证按三轴收口——**技法**（测什么）· **寿命**（留多久）· **执行**（谁、什么时候跑）：

**技法轴**（定义见 §0——两种测试测的对象不同）：
- **单元测试** = 隔离测单个单元（依赖以桩 ∕ 假件替身）——回答「这一件对不对」；
- **集成测试** = 把组件组合起来测交互（真实装配、可贯穿整条链——如从三前端入口驱动、自然带到核）——回答「合起来对不对」；
- 两类是**测试技法之分**，非同一测试的两次执行；**永不互转**——问的问题不同，一个不会「长大」成另一个。
- **「这块得留个长期守卫」这条本能 = 集成测试在说话**：写代码时想把某几条断言留下来看着，这个冲动指向的不是「保留单测档」，而是「这里需要一个从用户可见入口走一遍的集成用例」；两类的落点与出身见 §2 F8，不是同一件事的两种长度。**当这条冲动出现而没有可对应的业务场景时，说明守卫尚未成立**——记成待办，不要临时造一个常驻件把冲动糊过去。

**寿命轴**：
- **单元测试 = 开发期工具**：为改对代码而写；住批次目录（`docs/batches/`），**永不进任何门**、零维护。它出生就是为了这一批的这一次——**使命完成即删（用毕即删 · 零留存）**：不留可执行文件、不留「复跑旧件」面。
- **集成测试 = 业务资产**：按业务设立 + 按生产实际问题补入；常驻，承担发布门验收。两类来源不重复覆盖（单元不属于验收）。

**执行轴**：
- 反馈要**闭合**：谁改代码谁写测试、谁写谁跑——自己立刻看到结果，比别人代跑再汇报快一个量级；别人的测试集与本任务无关，不跑、不分拣、不代跑。
- 成本大头是重 IO 而非用例数量——**数量不是成本，重 IO 才是**；
- 集成测试**恰一次、收口时、父侧**——发布门动作，不是工作节奏：没装到一起跑过，就不知道装起来行不行；没变的东西，没必要每轮重新证明。

### 1.3 防膨胀（成本判据）

> 判据一句话：**测试总量不得随项目规模增长**——膨胀 = 推高成本 = 拖垮项目。

- **膨胀机制（为什么会乘法式失控）**：永久测试 = 一次性写、永久缴税——每次相关改动都要：跑它、分拣它红不红、改行为时还要过它那一关。测试量 ∝ 覆盖野心（≈ 代码面）· 改动频次 ∝ 项目规模，两项都随项目长大 ⇒ 维护成本 ≈ **测试量 × 改动频次**——是乘法，不是加法。
- **二段衰减（比膨胀更狠的后续）**：膨胀到一定程度，人开始绕开它（跳过 ∕ 删除 ∕ 改弱）⇒ **成本还在、保护没了**——「绿」变成剧场；假绿比没测更贵（给的是虚假的安全感）。
- **两道闸（制度性——守闸即防膨胀从后门回来）**：① **不累积** = 单元测试永不转集成测试（F8）——单元测试档用毕即删（零留存）、不进任何常驻集合，下一个改动不为它缴税；② **有上限** = 集成测试超窗即裁（N19）——一仓 50–100 用例，规模有界。
- **根判据（本档一切成本取舍的总纲）**：**验证投入 ∝ 失败代价，与代码量脱钩**——花在「伤过的地方」（事故史）与「真实需要的地方」（业务场景），不花在「想过的地方」。
- **物种差（为什么可公开展示的测试实践不可照搬）**：能公开展示测试的项目很多是**库**——测试集对库本身是产品的一部分（面向下游用户的规格书）；教程 ∕ CI 文化一侧又偏好仪式。自有产品仓照搬 = 张冠李戴。
- **执行形**：本判据为**纪律判据**（暂不配机械闸——按「保险按事故史买」：真发生超窗事件再立闸）；两闸守闸动作挂收口测试行（F9 ②半 = 集成影响 ∕ 窗口读数）。

## 2. 功能性需求

| # | 需求 | 说明 |
|---|---|---|
| F1 | 改动内只跑单元测试 | eng-coder 只验**自己这项改动**——跑改动面相关单元测试（单档 ∕ 相关子集）；**不跑集成测试、不逐轮复跑** |
| F2 | 报告义务句 | 未跑集成测试时原样带：“not integration-test verified — the parent-side closeout run is the only integration-test run.” |
| F3 | 集成测试归属父侧 | 集成测试（= 集成测试集）= 收口恰一次/端，父侧跑——不在 eng-coder 链内跑 |
| F4 | verify 不代跑 | verify 只收模型的 `verification.status` 声明（passed / skipped+reason），不代跑任何测试 |
| F5 | 单文件调试可用 | `node --test <档>` 直达（单元测试档 ∕ 集成测试档同法——不经 runner，无拦截） |
| F6 | 三层来源与寿命 | ①单元=单元测试档（一档一至几个文件、名随批次档、住 `docs/batches/`；用毕即删（零留存）、不进任何门）· ②集成·业务（业务场景设立——常驻）· ③集成·生产（实际运行常出的问题补入——常驻） |
| F7 | 层次不重复 | ① = 开发期自证（可断言实现内部）· ②③ = 验收（只断言业务可观察结果）——②③ 不是 ① 的改写镜像；同一断言不在两层重复持有 |
| F8 | 两层永不互转 | 单元与集成永不互转：单元测试档用毕即删；集成用例一律按业务需要单独设立（业务设立 ∕ 生产收编） |
| F9 | 批次收口测试行 | 每批 §6 核销同步清单含「测试」行（双半）：①本批单元测试档清单（用毕即删——批档 §5 留一行读数）＋②本批是否触及集成场景（新增/修订/无）＋**窗口读数**（本仓集成测试集现量 vs 50–100 窗口——守闸读数、零新增簿记）；漏填 = 记录可见缺口 |
| F10 | ②集随需求演进 | 触发 = 需求发展/行为变化 → 主 agent 评估（不外包不自动）→ 需变则出条目 → eng-designer 定形 → eng-coder 落 |
| F11 | ③收编 | 生产真问题处理完后：用户 → 主 agent 登记 → 收编为业务场景（业务语气、只断言业务可观察结果） |
| F12 | 集成测试集 = 发布门 | 上线前必须跑集成测试集（②+③全绿）；集成测试集常驻、独立执行面；验收/发布门依据 = ②③ |
| F13 | 普通模式场景必选 | 集成测试集必须含「普通模式完整工具流」场景（正常/边界/错误三态齐全） |
| F14 | 三前端实例化 | 场景在 CLI ∕ VSC ∕ desktop 各自实例化（语义同源、各端原文自持、不做 byte 一致；桌面驱动/隔离单源 = `docs/desktop/design/E2E-TESTING.md`） |

### 2.1 维护模型（零新角色）

| 件 | 执行人 | 钩子 |
|---|---|---|
| ①本批单元测试档清单 + ②集成影响 + 窗口读数核 | 主 agent | 批次 §6 核销同步清单「测试」行（F9） |
| ①落手（批次本地档的**写、跑与删**——验证完成后即删） | eng-coder | 批内（实施者本人——F1 ∕ F2） |
| ②新增与演进 | 主 agent 评估 → eng-designer 定形 → eng-coder 落 | 需求收口 ∕ 行为变化 ∕ 发布前（F10） |
| ③收编 | 用户 → 主 agent 登记 → 场景化 | 每个真问题处理后（F11） |
| 规则本身 | eng-designer 写 · 用户裁定 | 规则变更时 |
| 争议裁决 | 用户（唯一例外裁判） | 随时 |

## 3. 非功能性需求

| # | 维度 | 标准 |
|---|---|---|
| N1 | slow 标注（纯别名） | 作用域 = 单元测试档（`docs/batches/*.test.mjs`）：需真实 fs / git 子进程 / 定时器 / 网络的用例（单跑 >500ms）以 `slow(name, fn)` 包装；`slow` = **纯别名（照跑，无 skip）**——无分层 ∕ 无门控；集成测试档不用 `slow()`（见 `docs/core/design/TESTING.md` 接口契约） |
| N2 | 零漂移 | 测试文件原地不动——单元 = 批次目录（用毕即删）· 集成 = `test/integration/`；不搬移 ∕ 不改名 |
| N3 | slow 标注纪律 | 单元测试档内单跑 >500ms 的用例用 `slow()` 标注（**纯标注——无机制**；便于人工识读） |
| N4 | 阈值口径 | 标注线 = **500ms**（单跑实测） |
| N5 | 并发上限 6 | `--test-concurrency=6`（勿再调高——并发过高会让中位带通胀，产生打地鼠式误红） |
| N6 | 阈值依据（实测） | >500ms 的用例约占重 IO 成本的 95%，而 <5ms 的过半用例合计仅数百毫秒——数量不是成本，重 IO 才是 |
| N7 | ②集与需求同步演进 | 需求发展/行为变化必须触发集成测试集评估（主 agent——不外包不自动）；集成测试集不得落后于需求（判据 = 每批收口测试行 ②半 有记录） |
| N8 | 最小可跑起步 | 集成测试集起步 = 场景最小集（三态齐全）；扩面只走两个入口（业务设立 ② / 生产收编 ③）——不预防性铺量 |
| N9 | 自动可跑 | 集成测试集必须可自动执行（发布门内跑——不依赖真实付费端点、不依赖人工操作） |
| N19 | 集成测试集规模窗口 | 一仓 **50–100 用例**为合理窗口——超过即过度测试；超窗须裁减回窗口内 |
| N20 | 集成测试域分布 | 集成测试集**只住三个前端**（cli ∕ vsc ∕ desktop）——核仓（`thincoder-core` ∕ `thincoder-render-core`）不设集成测试集；测前端自然覆盖核（核面问题由前端场景带出） |
| N21 | 总量不随规模增长（防膨胀） | **测试总量不得随项目规模增长**——膨胀 = 推高成本 = 拖垮项目；两道闸为**硬纪律**：① 单元测试永不转集成测试（F8）② 集成测试超窗即裁（N19）；根判据 = 验证投入 ∝ 失败代价，与代码量脱钩（§1.3） |

**判定句**：`npm test`（单入口）全绿——**且空集不算绿**（零用例 ⇒ 非零退出 + 说明，理由见上一条）。

## 4. 范围边界（不做）

- 收集根 = `test/integration/`（单根约定：集成测试档只住这里）；`test/` 的其它位置一律判错位、`docs/batches/` 的单元测试档不入收集——**这不是按目录划分执行层**，而是同一条门的两种失败面：档放错位 = 永不执行，故入口必须当场报错（`docs/core/design/TESTING.md` §10.3 SC 表）。同档门控让单文件调试与收口时跑的那一次永远走同一断言（见 F12）。
- 不设独立测试角色（维护模型零新角色——见 §2.1）
- 集成测试集不调真实付费端点、不依赖人工操作（真端点 smoke 仍独立于所有层）
- 不维持存量测试库存（「按需加」）——本机制为「按需加」的产物补寿命口径（**用毕即删 · 零留存**）与收口测试行

## 5. 散文锚测试退役（PROSE-ANCHOR-RETIRE）

> 一句话：**读档断言「某句在场 / 缺席」的测试一律不做**——收益无实证（举不出该类锚抓到真实漂移的记录），成本可量化（改一字即红、失败信息零信息量、锚红后的动作永远是「把字改回去」）。
> 设计 + 逐条删除清单 = `docs/core/design/TESTING.md`。
> 双端语义同源：本档 F15–F22 / N10–N12 与对端档同标识、语义同源、各端原文自持（不做 byte-identical）——对端条目自持于对端档，本档不代写对端规。

### 5.1 判据（三条同时成立 = 散文锚）

| # | 条件 |
|---|---|
| ① | 断言对象是**非测试文件**文本（`thincoder-core/**` · `thincoder-cli/src/**` · `docs/**` · `AGENTS.md` · `README*` · 仓根 `*.md` / `*.json` · `scripts/**` · `bin/**` · `webview/**` · `locales/**`〔资源文本保留——C1-d〕）或其派生切片 |
| ② | 断言其**文本内容**在场 / 缺席 / 出现次数 / 相对顺序（`.includes` · 常量子串 `assert.match` · `.startsWith` · `.endsWith` · `.indexOf` · 文本计数） |
| ③ | 断言对象**不是**结构机检保留面所判的属性（保留面 = F17 封闭枚举） |

**载体判据（判据 ① 的落地口径）**：断言对象是**执行产物**（函数 / 工具返回值、子进程输出、渲染帧、测试自建临时域文件）或**结构 / 数值常量** → 不命中 ①；经 `import` 取到的源码静态文案字面量 → 命中 ①。

**判据补充（判据 ① 的「实质」判法）**：

| # | 补充 | 内容 |
|---|---|---|
| C1-a | **提示词句子不豁免** | **不问文本从哪来**（读盘 / 装配器或渲染出口的返回值 / 写入 `systemPrompt` 的装配结果），只问**断言的是否是提示词句子**——断言提示词句子 → 命中 ①；**「不读文件」不是豁免理由** |
| C1-b | **工具契约面与工具返回文案保留** | **模型实际收到的工具契约对象**（`tool.description` / 参数说明）与**工具返回 / 拒绝文案** → 契约守卫 / 行为输出 → 不命中 ①；读源码档文本（含源码里的描述串）仍命中 ① |
| C1-c | **非句子对象保留** | 结构 / 数值 / 判定信号（槽文件表与集合成员、长度、警告清单与警告文案、旗位、退出码）→ 不命中 ① |
| C1-d | **locales 资源文本保留** | `locales/**` 文本值 = **产品资源文案**（界面 / 本地化面）→ **不命中 ①**（保留、不进清单）；读非测试文件**源码 / 文档文本**仍命中 ① |

## 6. 终端程序自动验证（harness 方法学）

> 主轴 = **agent 具备驱动 TTY 程序的能力**：能力需求主承载 =
> `TOOLS.md` §4.7（U1–U4 · 非功能候选 · 边界 · 待定项）；**本节射程 = 该能力的验证方法学**（对任何 harness
> 成立的部分）。thincoder 自身 CLI / TUI = 该能力的一个**被驱动对象**（用户原话：「只是碰巧这次我们是在开发 thincoder」）。
> **终端程序自动验证的设计面 = 待重做（另轮）**——**当前无有效设计档**；本节验收依据 = 本节内联判据（§6.1）+ 能力面判定句（`TOOLS.md` §4.7）。
> **`node-pty` 可用性**：走包内预编译，免编译安装即得真 TTY（安装即装成·被驱动子进程自报为真终端）——本机无可用的原生构建链。

### 6.1 方法学条目（任何 harness 适用）

> 口径：本节持有**验证方法学**；**能力面**（真 TTY / 发输入 / 判输出 / 取退出码）住 `TOOLS.md` §4.7（D2 单一权威源——不重述）。

**9 条**：

| # | 条目 | 判据 / 标准 |
|---|---|---|
| F23 | 真子进程驱动（非模块级直驱） | 验证路径不 import 业务模块——驱动对象 = 真进程（对象泛化：任意终端程序） |
| F26 | 覆盖边界写死 | 「能测 / 不测」逐条列明（承 §6.2）；自动绿**不得**被误读为未测面已被验证 |
| F27 | 确定性 | 被驱动对象的非确定性来源（模型 / 网络 / 时钟）走脚本化替身（零外网 / 零付费端点）；隔离 HOME 与 cwd；重复执行结果一致 |

### 6.2 范围边界（不做）

- **不做伪 TTY / 属性伪造形态**（U1 要求真终端；伪 TTY 下 raw mode / 终端尺寸不存在）。
- **不做渲染观感与主观体验的自动判定**——自动面 = 可脚本化面；「真机上好不好用」仍由人工判。
- **不进单入口执行集 / 不用 `slow()` / 不动分层机制与既有 runner / 不改发布门脚本**（承 §2–§4 与 §6.1 N18）。
- **不调真实付费端点**（真端点 smoke 保持独立形态）。
- **不代立各端验证的设立口径**——能力归属 = 工具系统统一面（见 `TOOLS.md` §4.7）；各端对位用例是否同期设立属另批裁定（本档不代立规）。

## 附：外部权威源对照（查证记录 · 非判据）

> 用途：说明本档与「外部可见的标准实践」的关系；**本条目不构成判据**（本档判据来源 = 用户裁定 + 项目实测，见 §1.1）。

| 源 | 可达性 | 与本档的关系 |
|---|---|---|
| NASA 软件工程与保证手册（NASA-HDBK-2203 · Rev C） | **全公开**（swehb.nasa.gov 可直读——含 NPR 7150.2 ∕ NASA-STD-8739.8B 全文链接） | 安全关键域方法：V&V 与硬件同级投入、「目标证据」文化——其成本模型 = 失败代价极高（任务级损失）；与本档「按事故史投保」**同源、量级相反** |
| ISTQB 术语表（glossary.istqb.org） | 公开（站点可查） | 组件测试（individual components）∕ 集成测试（components 之间的交互）——与本档技法轴同口径 |
| ISO/IEC/IEEE 24765（词汇） | 标准本体付费（预览页公开） | 术语类定义源；未作依据使用 |
| DO-178C（航空软件） | 标准本体付费；FAA AC 20-115D **公开**（已实取） | 结构覆盖（语句 ∕ 判定 ∕ MC/DC）驱动验证——极端高保障端；本项目场景不适用 |

**结论两条**：① 「标准组织的做法不可见」**半对**——安全关键域的公开手册（NASA）与术语标准（ISTQB ∕ ISO）可查且口径一致；真正不可见的 = 企业内部的日常工程规程。② 公开的标准实践共同点 = **验证投入 ∝ 失败代价**——本档的「按事故史投保」是其**低代价端的同类原则**，非背离。
