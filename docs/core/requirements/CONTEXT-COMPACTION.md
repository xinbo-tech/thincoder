## 2. 功能性需求

### 2.1 本子系统条目

- **【派生 · 非用户原话】** 上下文压缩 / 会话标题 / 文本额度归一为**核内单一纯函数面**（压缩触发 · 摘要 · 降级截断 · 尾部预算；计长口径 = UTF-16 码元）；会话标题的格式分派（CLI 仅 OpenAI 兼容 / VSC 三格式）按**端差注入**。
  源 = 设计档 `CONTEXT-COMPACTION.md` §2.1 #162–#164。

- **【派生 · 非用户原话】** **恢复面回声安全**：已落盘会话的机读线在**恢复路径读取时**归并回声病态形态（「无 `reasoning_content` 的 assistant 紧邻 assistant」——前条并入后条）；恢复后首个请求不携带该形态；**不推用户**（静默归并）、**不改会话档**（人读线 / 双线约定不变）。
  判定句：夹具 = 含病态对的落盘机读线 ⇒ 恢复后 `agent.history` 该形态计数 = **0**，文本拼接逐字守恒 + `tool_calls` 总数守恒，干净输入返回**同一数组引用**（零回归）；两端（CLI / VSC）各 ≥1 用例。源 = 设计档 `CONTEXT-COMPACTION.md` §6.10 #8 / D-CC19。

- **【派生 · 非用户原话】** **压缩调用复用会话前缀**：压缩请求 = 会话前缀（system + 中段真身消息——不截断、不序列化、**随带与回合请求同声明面的 `tools`**（**不随 `tool_choice`**——实施轮实测：该参数致服务端**丢弃 tools 区**（token 证据：prompt 与无 tools 形态同值）⇒ 按设计预注册判定规则 §6.14 采纳**备选②**；命中面按 `tools` 声明分区——同前缀带 tools **84–98%** vs 去 tools **0%**）；

  **并随带与回合请求同源的 `reasoningEffort`**（实测：同值 ⇒ 生产口径首现命中 **92.86% / 93.65%**（两次独立运行）vs 异值 **0%**；不硬编码 · 无配置 ⇒ 缺省）+ 尾部指令一条；不再以「全新 user 消息 + 序列化正文」形态发送。

  判定句：同会话回合调用命中率 ≥90% 时，compress 轨迹 `cached / prompt ≥ 0.9`；**选中面**一致（仍只喂中段），**表示面**改变（真身消息、不截断——保真度预期↑）；切点须为配对安全边界。源 = 设计档 `CONTEXT-COMPACTION.md` §6.14 / D-CC20。

- **【用户需求】** **模型主动整理上下文（`context` 工具 · 操作区分）**：
  - **F-CC1 感知**：模型可查当前上下文的**用量与构成**（总量 / 距压缩阈值 / 各段占比）——「该压了吗」要有数（现态 = 模型看不见自己的占用 ✓）。
  - **F-CC2 主动压缩（携要求）**：模型在**它判定的时点**（工作方向转换 / 自认上下文嘈杂）携 **focus 要求**发起压缩；机制**自动附上**当前任务 / 目标面（task · goal），使摘要在取舍上对齐将要做的工作；实现**走既有压缩机器**（安全点 / 摘要链 / 压缩面板 / 失败可见面全复用 ✗ 不另起）；**回执须露可回查锚**（全史所在（当前会话文件路径）与取回路径——使「压掉的可取回」**一步可行动**）。
  - **F-CC3 噪声清理**：模型可丢弃**陈旧的工具输出**——与压缩**语义正交**（删 vs 摘要）；记录面不死（见边界）。
  - **F-CC4 方向转换轻推**：任务 / 目标面变化后，在上下文落**一行提示**（「可考虑压缩 ✗ 当前目标 = X」）——**提示非命令** ✗ 压缩决策恒在模型。
  - **F-CC5 工具形态**：上述能力收为**单一 `context` 工具，以操作区分**（感知 / 清理 / 压缩三操作）——工具表 +1 项，双端（CLI / VSC）一致；工具说明 = 运行时可见面（教模型写「下一步要什么」）。
- **【用户需求】** **预算保真（估算不低估 · 校准活过重启 · 越窗可自愈）**（2026-10-27 报障：1M 窗口会话发 723K 被服务端判 1,116K 超限，界面却显示 491K）：

  - **F-CC6 估算基准**：token 估算的 ASCII 系数由 `4` 收到 `3` 字符/token（实测 723,272 ÷ 491K ≈ 1.47 ⇒ 实际约 2.7 字/token）；非 ASCII 仍按 1 字/token（保守方向不变）。系数常量化 + 估算器版本位，改系数即改版本。
    - 判定句：`estimateText("x".repeat(4000)) === 1334`；混排 `"x"×200 + "字"×200 ⇒ 267`；估算器版本随系数变更递增。
  - **F-CC7 校准样本跨进程持久化**：`_tokRatio` 的自校准样本随会话落槽、随会话恢复读回——**恢复大会话时不必等一次成功响应才校准**（现态：进程内变量，恢复后必回 1，而校准需成功响应 ⇒ 首请求必然失败的死锁）。
    - 判定句：槽带合法样本 ⇒ 恢复后 `_tokRatio = max(1, num/den)`（下界 1——比 < 1 会把整条估算缩小、重开「该压没压」，故合法样本也不低于 1）；样本的估算器版本或 `format:model` 键任一不符 ⇒ 回 `1`（不跨版本、不跨模型复用）。
  - **F-CC8 越窗自愈**：服务端回越窗 400 时，**压一次 + 重试一次**，成功即返回；二次仍越窗 ⇒ 报 typed 错误、不再压、不静默截断。
    - 判定句：构造首请求越窗 ⇒ 压缩恰 1 次 ∧ 重试恰 1 次 ∧ 成功则回合继续；构造二次越窗 ⇒ typed 错误（含三实数）∧ 零截断。
  - **边界（不做）**：不改 `limit = window − reserve` 的预算公式（它是对的，错的是进 `limit` 的那个数）；**不改阈值取值**（触发判据的可达性门见本段之后的门条目——它只加一条判据，不动任何数值）；不替用户改 `maxTokens` 取值；`compress` / `distill` / 续写三面对事前净判的豁免保持不变（判它 = 判掉止血动作本身）。

  - **判定句**：① 携两条**相斥 focus** 各压一次 ⇒ 两份摘要的取舍方向**可断言**（聚焦词命中计数差额）；② 压缩后 `read_history` / 人读线**全量不变**（记录面不死）；③ 清理后活上下文占用下降 ∧ 记录面不变；④ 方向转换后提示行**恰一次**（去重）∧ 零调用时零副作用；⑤ 双端工具表各 +1 项（`context`）× 三操作可达。
  - **边界（不做）**：阈值自动压缩**保留为兜底**（语义不动 ✗ 双轨并存）；**记录面不死**（机器线之外全量不变——承 §4.2 F3 口径）；**不做自动方向检测**（轻推 = 一线提示 ✗ 不得自动压）；**不新增用户侧命令**（`/compact` 类 ✗ 本期未要求）；**子代理面** = 设计轮裁定（**须带可回查性论证**：子代理现无 `read_history` 通道 ✗ 若给则同轮论证可达性，否则明确登记为边界）。

- **【已定决定】** 压缩触发面增**可达性门**（台账 `#1833`）：`压 ⟺ total > threshold ∧ post(plan) ≤ threshold`——压完仍到不了线下就不压。理由 = 压缩只能压 `history`，`system + tools` 是压不掉的固定开销；把固定开销算进触发判据，等于对着一面敲不动的墙反复付费，而每付一次都可能吃掉一个真实响应。设计单源 = `docs/core/design/CONTEXT-COMPACTION.md` §6.17。

- **【用户需求】压缩线目标 = 窗口 60%**（2026-10-27 定）。口径 = **「不越窗」优先于「线高」**——线压低，压缩来得早，但不会走到「预算算出来了却发不出去」那一步：
  - **阈值链**：显式 `config.agent.compactThreshold` 优先；auto = 可用窗口与 `⌊窗口 × 0.6⌋` 取小（`thincoder-core/config.mjs:53` `COMPACT_RATIO = 0.6`）。**可用窗口 = `usableWindow(窗口, 预留)`——窗口减预留；预留 ≥ 窗口时退到 `⌊窗口 / 2⌋`**（预留占满整窗时裸减会得 0，阈值与真限一起归零，那一档就永远发不出任何请求）。**预留 = 实发 `maxTokens`；未发时按规格 `maxOutput` 保守计，不封顶**（封顶会让预算面与发送面脱钩，产生「算预算用 25%、实发 39%」的死区）——`resolveCompactThreshold` 单源，**派生值不回写活配置**（auto 值落显式键 = 换模型后不跟随的陈旧值）。
  - **压缩线取值与预留量互斥（预留 &lt; 窗口 时）**：两者取小，故线高不会超过「窗口 − 预留」。今日实例 = `maxTokens 393,216`（占 39%）⇒ 可用窗口 606,784，`⌊窗口 × 0.6⌋ = 60.0%` 更小 ⇒ 压缩线落 **60.0%**（取小取了比例项）；同一档若预留降到 0，压缩线仍停在 60%，**不会回升**。**取舍判据 = 「不越窗」优先于「线高」**——线高由比例项封顶，**预留 ≥ 40% 窗口时**才进一步压低它；**预留 ≥ 窗口时半窗退化接管，线 = `⌊窗口 / 2⌋`（不再降）**。
  - **报面**：主口径 = **窗口占用**（`total / window`）；压缩线以**具名数值**露出（不再作百分比分母）；同名输出不得两个无名百分比并存；**请求预算行 = 五实数**（窗口 + 来源 ∥ 实发 max_tokens + 来源 ∥ **全量 prompt 占用**——含 system + tools，字面名取设计已定的 `prompt` ∥ 距压缩线 ∥ 距真限）。预留占比不单列：它由「窗口」与「max_tokens」两个在场数直接相除得出，再列一遍等于同一事实两处出现。
  - **判定句**：① 逐档推算全表（`model-specs.mjs` 全量）——预留 ≤ 40% 窗口的档 = **60.0%**（比例项更小）；预留 &gt; 40% 且 &lt; 窗口的档 = `窗口 − 预留`（可用窗口项更小；恰 40% 时两式同得 60%）；**预留 ≥ 窗口的档 = `⌊窗口 / 2⌋`（半窗退化）**；且该两类须在报面明示该档的预留占比；三式与 `min(usableWindow(窗口, 预留), ⌊窗口 × 0.6⌋)` 逐档互推一致；② stats 首行恰含一个具名百分比（分母 = 窗口）∧ 压缩线以具名数值在场 ∧ 请求预算行五实数在场；③ 溢出风险论证三件在场（真溢出后果 ∥ 兜底接法 ∥ 高风险档清单）。
  - 源 = 设计档 `CONTEXT-COMPACTION.md` §6.2 ∥ §6.16.4 ∥ D-CC29–D-CC30。

## 4. 需求条目

### 4.1 压缩体验——F1–F4

- **F1**：压缩**开始**时立即提示（用户马上知道「在压缩，不是卡死」）。
- **F2**：压缩执行中在 TUI 显示**进行中状态**，完成后显示结果（摘要长度 / 耗时 / 成功或失败）。
- **F3**：压缩失败不再静默——错误文本可见（UI 行 + console.error），诊断可追踪。
- **F4**：非 TUI 环境（headless / VS Code 桥）不崩不阻塞——回调缺省安全。

### 4.2 探索结果语义摘要——F1–F3 · N1–N3

> **需求（用户报告「主 agent 历史质量差」）**：机器线历史（`history`）在压缩阈值触发前就因内联探索逐步结果而膨胀；即便触发压缩，LLM 摘要也可能丢关键信号。在**每轮 runAgent 最终返回时**把本轮写入机器线的探索类结果蒸馏为语义摘要、并强化压缩保真，使机器线在任意时刻信号密集、可恢复。

- **F1**：当一轮内连续 / 成批的探索类工具结果写入机器线后，在轮末被 LLM 蒸馏为语义摘要（发现了什么、在哪、关键结论），而非裸堆结果或机械截断。
- **F2**：压缩摘要（SUMMARIZE_PROMPT）在压缩时，除「已完成 vs 进行中」外，显式新增保留：已改动文件清单、未决点 / 待办。
- **F3**：人读线 `_fullHistory`（落盘 `fullHistory`）保持全量不变；机器线 `history`（落盘 `contextHistory`）承载摘要后的信号密集形式。（**记录 / 落盘语义**——完整记录在盘、压缩不触；运行期内存表示为有界窗口，机制见 `docs/core/design/SESSION.md` §6.14。）
- **N1**：摘要质量优先，token 成本不作决策变量；摘要调用必须 `thinking:null` 且不接 onToken / onReasoning。
- **N2**：压缩机制落地单一权威面：压缩面**单源**（`thincoder-core/context.mjs`）；一致性由单源承接。
- **N3**：轮末摘要失败不得阻塞 / 影响 runAgent 返回（静默跳过，原始历史保留）。
