> 板块 = **方法论**——三观的实践延伸："三观回答'为什么'，方法论回答'怎么做'"。
> **上位需求 = `docs/core/requirements/PHILOSOPHY.md`**——只承接指针、不复制条文（D2 单一权威源；PHILOSOPHY 的 §6 方法论 3 条 = 上位思想，本档是其机制判据的需求层）。
> **设计侧关系（不重述）**：方法论机制的设计落地 = **提示词**（`thincoder-core/prompts/`——纪律层 `thincoder-core/prompts/discipline-engineering.md` / `thincoder-core/prompts/discipline-normal.md`）+ **机制档承载规则细则**（设计 / 需求档）+ **提示词内容测试**（`docs/core/design/TESTING.md` §6 散文锚禁令族——内容锚断言）。**方法论不设独立设计档**（设计落地 = 提示词 + 机制档承载细则 + 内容锚断言，不另立一档）。

## 1. 总体定位

方法论需求 = 给「怎么做才正确」画**执行判据**的一层需求：三观定「你是谁 / 为什么」，方法论定「怎么做」。
**两模式遵循同一套规则**——同一个判据集（三观 + 本档 + 公共层 + 工具面）；**差别只在流程强度**：工程模式 = 强流程（约束靠**结构**实现），普通模式 = 纪律驱动（无结构约束）——**不是两套标准，也不是「严 / 松」两档**。
各模式需求档（`docs/core/requirements/ENGINEERING-MODE-V2.md` / `NORMAL-MODE.md`）是这些判据的**实例化执行面**。本档只登记需求的「什么」与**可机器验证的判定句**——机制正文一律指针、不重述（D2）。

**设计侧关系（不重述）**：

1. **方法论的设计落地 = 提示词 + 机制档**——骨干住纪律层槽位：`thincoder-core/prompts/discipline-engineering.md`
   （基本流程四步）· `:39` 文档规范（三层模板 / 方案选型对比 / 多实现面纪律 / 板块归属四问）· `:169` 需求池攒批工作流 ·
   `:184` R24 挂钩；`thincoder-core/prompts/discipline-normal.md:53`（代码结构判据——理解成本分层）· `:112` 常用纪律。
2. **规则本体住机制档**（落档于 `docs/core/requirements/PROMPT-SYSTEM.md` §2.1 / §4.2：提示词 = 代码单源 =
`thincoder-core/prompts/`（唯一副本）——无同步脚本、不做 byte-identical 硬一致）。
3. **验证 = 提示词内容测试 / 内容锚断言**（`docs/core/design/TESTING.md` §6.3 禁令：新增断言只允许行为面与结构机检——`docs/core/design/TESTING.md:210`；C1-a 提示词句子不豁免——`docs/core/design/TESTING.md:191`；内容锚断言 = 结构机检保留面封闭枚举——`docs/core/design/TESTING.md:183`）。**挂指针不复制**（D2）。

故设计侧**不需要**独立 METHODOLOGY 设计档——设计落地物已在位。

## 2. 功能性需求

### 2.1 基本流程

| 编号 | 需求 | 判定句（可机器验证） | 范围边界 / 指针 |
|---|---|---|---|
| F2-1 | **四步硬流程**：任何开发任务走需求 → 设计 → 开发 → 测试，不跳步；三步要写文档（需求 / 设计 / 测试） | 工程模式批次档含 §1 需求收口 → §2 任务书 → 设计评审 → 实施 → 验收的完整链记录；不存在"跳过设计直接编码"的批次 | 四步不是最佳实践而是硬流程；细则 = `thincoder-core/prompts/discipline-engineering.md:8`；**受控旁路**：细节面 = 轻通道（直改先行 → 收尾全链闭合；旁路 ≠ 取消）——需求 = `docs/core/requirements/LIGHT-CHANNEL.md` |

| F2-5 | **测试步骤**：验证 + 测试文档——每条用户故事至少一个测试用例，覆盖正常 / 边界 / 异常；每条用例写清测什么、给什么输入、期望什么输出，不写实现细节 | 用例表三态齐全且每条功能性需求 ≥1 条映射 | 测试分层 / 寿命 / 门禁细则 = `docs/core/design/TESTING.md` |
| F2-6 | **设计前置 = 同类先例勘察**：设计任一功能前，先勘**同类 / 相似功能的现行做法**（实现坐标 ∥ 设计档对应节 ∥ 先例批）——**对齐优先**（沿既有形：组件 ∥ 布局 ∥ 判据 ∥ 用词）；有意偏离 ⇒ 设计里**显式理由**（为何既有形不适用）；默认「别出心裁」= 违规 | 设计档含「同类先例」一行（先例坐标 + 对齐 ∥ 偏离理由）；设计评审可核（评审维度随正——载体 `docs/core/design/ADVISOR-CONVERGENCE.md`） | 与 F7-2（方案与理由）互邻：先例 = 选型的输入面；细则落提示词（`thincoder-core/prompts/`；设计轮出逐字块） |
| F2-7 | **分支须有出处**：设计里每一条针对输入 / 状态的分支，必须能指到它的出处——真实观测（数据读数 ∥ 日志 ∥ 用户报告）或可复现的失败路径（给出复现命令）；两者都给不出 = 对不存在场景的防御 ⇒ 删 | 设计档每条分支带「依据」列（观测读数 ∥ 复现路径）；评审维度可核——无出处的分支判红；无依据分支在仓内出现 = 该批设计评审不合格 | **真需要的防御能过**：给出复现路径即可，杀的是「说不出场景」的分支，不是防御本身。**代价面**：一条分支自带告警 ∥ 文案 ∥ 三端一致性 ∥ 用例四份配套；没有真实场景时这四份都验证不了，改的时候也没人敢删。判据落地 = 提示词三处（`thincoder-core/prompts/advisor-design.md` 评审维度 · `thincoder-core/prompts/persona-eng-designer.md` 落笔格 · `thincoder-core/prompts/discipline-engineering.md` 代价句） |

|---|---|---|---|

| F3-3 | **协作原则 8–10**：注释与决策同行（写"为什么"——决策 / 坑，不写"是什么"）· 双端 parity（CLI / VS Code 镜像结构同步演进，不各自漂移）· 撞到错误结构就改，不挂账（**当场登记 + 就地开批走流程修**；禁止在错结构上叠最小补丁掩盖症状） | 码评 / 审计维度核查（撞上即登记且开批走流程 = 合规（**射程内入库 `trigger` = `归批`**）；**登记后不再过问〔挂账即了事〕= 违规**） | 撞错结构就改 = 「铁律②」（`thincoder-core/prompts/discipline-engineering.md`「铁律」节） |
| F3-4 | **动手自检**：拆前四问（这段能被读者独立理解吗 / 改动会波及其他模块吗 / 能独立测试吗 / 读者需要多少上下文）· 拆后两验（骨干可复述——不看细节能说出模块做什么；行为零变 + **断言数不减**） | 结构重构批过拆后两验（断言数不减——迁移 / 拆分类重构差额 = 清单数，存量清理轮走删除清单制） | 断言数不减红线 = `docs/core/design/TESTING.md:63` |

### 2.3 常用纪律

| 编号 | 需求 | 判定句（可机器验证） | 范围边界 / 指针 |
|---|---|---|---|

**为什么 = 提示词 `thincoder-core/prompts/discipline-engineering.md`（§🔴 铁律 · 第 3 条）——本档只挂指针、不重述（D2）**。

⇒ **判据**：**分级本身不违规**（必须 / 可要可不要 / 不做，都得由用户拍）——**违规的是「让用户以为还会做」**。任何「待以后 / 有条件 / 认账不排期」**必须落成台账条目**，且**不得在册面上写成还会做**；**不落册的「以后」= 丢弃且瞒报**。

### 2.3b 工程模式「铁律」组的出身 · ④「零裁量」现义

**出身（用户 2026-10-16 04:07 原话）**：「其实**所有这些铁律都不是我的习惯，是你的习惯，那些铁律都是你写的**」——⇒ **本组铁律 = 早期由 agent 自加**（非用户起草、非用户习惯）。⇒ **由此定一条纪律**：本组每条都是我**方自加物**，**须能答「靠哪个结构、值不值」**；**前提一变即重新过堂**——不得因为「它一直在那儿」就当用户口径。

**④「零裁量」现义（用户 2026-10-16 04:10 裁定；原话「我同意，乙可以」——「乙」= 按下引块改写为现义，不退役、不留旧句）**：

> **默认全流程；分流只走轻通道（每笔交底、用户可改判）；不得反复重开「是否走流程」的辩论。**

**成因（用户口径 · 04:07）**：模型有「**特别不喜欢走工程模式流程，老想着绕过去，绕不过去就纠结，一直想办法绕，消耗很多轮次**」的惯性 ⇒ 本条要治的是**纠结循环**（反复重开「要不要走流程」），**不是合理分流**。

**本条今日之义 = 门框**：框住轻通道——**默认全流程；出口只此一条，且须交底**。**理由**：独立人格与轻通道已落地，**合法出口已存在**——要治的只剩纠结循环。

## 3. 非功能性需求

| # | 维度 | 标准（含度量） |
|---|---|---|---|
| N-1 | **理解成本判据** | 理解成本是状态不是行数——关键在读者能否局部推理；分层省上下文（读哪层只加载哪层）、降幻觉（局部代码比全貌易推理）——模型是高频第二读者 + 写者 |
