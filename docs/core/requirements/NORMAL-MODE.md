## 1. 总体定位

Normal 模式 = 默认（非工程模式）会话的提示词基底。装配层把**人格 / 公共 / 纪律**三类槽位按场景组装为系统提示——
人格定义「我是谁」，公共层给跨模式协作基础，纪律层给该模式的干活规则；项目层（`AGENTS.md` / skills）作为尾部追加。
同一机制只在一处装配（表驱动、固定序），避免多路拼装漂移。

## 5. 普通模式产品行为需求（CLI 侧同名档并入面 · 2026-09-15）

> 来源 = `thincoder-cli/docs/requirements/NORMAL-MODE.md`（原地留参照）——该档与 §1–§4 **不同题**（装配层 ⇄ 产品行为面），故全量并入本节。
> 定性：普通模式 = 产品**默认工作模式**——你说要什么就直接干（改 bug / 加功能 / 写脚本 / 查问题），边做边交代；质量靠纪律和自查。
> 与工程模式**互斥**（同一时刻只能一个），提示词两套独立、可随时切换（两种工作模式对照 = `docs/core/requirements/PROJECT.md` 产品定性面）。

### 5.1 总体需求

把人从「写代码」里解放出来，同时让交付**可信**：改动要验证、结论要有据、取舍要交代。
与工程模式的差别只有一条——**它是强流程（约束靠结构实现），普通模式没有结构约束**：要求同样认真，靠纪律与工具（verify / advisor）保证落地。

### 5.2 功能性需求

| # | 需求 | 约束 |
|---|---|---|
| F1 | **全能力干活** | 直接文件写权限 + 全套工具；「整个项目的代码都是我的」 |
| F2 | **任务分档** | complex（3+ 步 / 新功能）：读文档→需求→设计→开发→测试，写设计档 + `task` + 台账条目（跨会话持久）；medium（2-3 步 / 重构）：读文档→计划→改→更新所属文档 + `task`；small（错字 / 一行修）：读文档→改→验证→更新所属文档 + `task`。分不清按 complex |
| F3 | **复杂任务先计划** | plan mode：只读探索 → 设计 → 呈现计划 → 批准后实施；complex 档时 plan mode 即设计步骤 |
| F4 | **文档先行** | 改代码前先读所属文档；**文档与代码冲突时以文档为准**；用户指示与文档冲突时先讲清→改文档→再写码；文档归属单一权威源（一处详述，其余引用） |
| F5 | **完成前验证门** | 每次 write/edit 后 `lint`；宣布完成前按项目 AGENTS.md 的方法跑验证并向 `verify` 声明结果——**verify 机械把关但不代跑**；无法验证就明说，绝不把未验证说成完成 |
| F6 | **交付透明** | 改了什么 / 为什么 / 简化了什么 / 没做什么——逐条交代（用户看不见代码，只听得见你说的话） |
| F7 | **自动代码评审** | 改完代码调 `advisor`（须给 paths 或 documents）；评审后按裁决表回应；🔴 不得埋；≤5 轮收敛；全清后跑 `verify` |
| F8 | **委派** | 子代理 explore / coder / plan（普通模式装配；工程模式禁用 coder 角色） |
| F9 | **跨会话记忆** | `memory` 工具（search / put / list / delete / clear）——存 bug、约定、偏好 |
| F10 | **任务跟踪** | 每档都用 `task`（同时只有一条 in_progress）；complex 档另建**台账条目**（跨会话持久、每条需求一条——`/ledger`） |

### 5.3 非功能性需求

| # | 维度 | 标准 |
|---|---|---|
| N1 | **无机械门禁** | 不像工程模式那样拦截写文件——质量由纪律 + verify + advisor 承担（两模式的根本差别） |
| N2 | 工具路由 | 专用工具优先；bash 只用于包管理器 / CLI 子进程、服务器、TTY 程序、无专用工具表达的一次性管道 |
| N3 | 可逆性分级 | 本地编辑——自主；破坏性（rm -rf、强推）——先确认；外发（commit / push / publish）——每次确认 |
| N4 | 长输出先落盘 | 长测试 / 长命令先重定向到日志再查；日志写在工作区之外并读后删除 |
| N5 | 无 TTY | 命令一律非交互执行（`git commit -m`、`--no-pager`、`-y/--yes`） |
| N6 | 并行纪律 | 独立读类调用合并一批并发；不并行：同文件写入、依赖步骤、审批类命令、同仓并发 git、有状态操作 |
| N7 | 编辑纪律 | old_string / 行号 / 哈希**只来自最新一次读取**；同一形态第二次失败必须重读文件，绝不第三次重试同一输入 |
| N8 | 上下文压缩后 | 信摘要结论，但**重读 AGENTS.md 与设计档**（权威内容可能被丢） |
| N9 | 枚举输入必用选择器 | 固定取值集合（enum / level / mode / flag）必须给选项，不得要用户手打 |
| N10 | 用户约定逐字执行 | 交互 / 行为约定以**用户原话**为准——不得用「等效实现」替换；已确认约定的简化必须提前上报，不得包装成「升级」交付 |

### 5.4 范围边界（不做）

- 不做机械拦截门禁（那属工程模式）——不得为「更安全」私自加硬拦；
- 不跳过验证声明（N1 的代价由 F5 兜底，二者不可拆）；
- 不静默改文档：实现偏差先修正代码到与文档一致；真文档漂移 / 超范围变更交用户；
- 不把未验证的工作说成已完成（也不把已完成的降级包装成「可接受」）。

### 5.5 开放项

- **本面与提示词的双向核对**：本面原自提示词实现面反推——需一次逐句核对（提示词里是否有本面未覆盖的要求、本面是否夹带实现细节）；
- 普通模式是否有**可机械化的**保障（现只有 verify 一个门）——与工程模式的边界是否要重新划。

## 6. 偏差审计与两段式委托（F-N1.1–F-N1.6）

> 来源 = CLI 侧同名档 §6（2026-09-11 自 CLI 旧设计档 §21 迁入——原初需求 = 2026-09-04 用户「普通模式也应该有文档……审计：① 口头指令落设计文档了吗？② 实现和文档和口头指令一致吗？」）。
> 机制叙述 = `docs/core/design/AGENT-LOOP.md` §6.17（普通模式轻量审计）；实现面 = 提示词 `persona-normal` / `common` / `discipline-normal`
> （运行期 `thincoder-core/prompts/` · 正本 `docs/core/design/prompts/`——零额外 LLM：审计复用既有交付核对动作）。

**总体需求**：普通模式的交付必须**可审计**——口头指令落档、实现与文档及指令三向一致、偏差显形并被处置（修正或上报）；审计不新增步骤、不新增 LLM 调用。

| # | 需求 | 判定句（验收语义） |
|---|---|---|
| F-N1.1 | 指令落文档审计 | 核验交付时对照用户指令与所属文档：指令未落档 → 就地补一段短变更记录（文档地图定位归属）；零豁免 |
| F-N1.2 | 三向一致审计 | 对照 ① 本轮用户指令 ② 所属设计文档 ③ 实现：偏差按四类（部分实现 / 静默简化 / 文档漂移 / 超范围）识别；实现类偏差就地修正或退回 coder 后才算完成，文档漂移 / 超范围上报用户（不擅改文档） |
| N-N1 | 零额外 LLM（成本约束） | 审计不新增步骤、不 spawn 独立审计器——核对与既有交付验证共用同一轮读；结果并入交付复核 |
| F-N1.3 | 开发前落档 | 任何档位改代码前先经文档地图定位所属文档并读它；完成后变更 / 决策回填所属文档（单行修复亦无豁免） |
| F-N1.4 | 完成前核对与修正闭环 | 宣布完成前对照所属设计文档核对产出：实现偏差（部分实现 / 静默简化）由主代理修正至与文档一致后才宣布完成；真实文档漂移 / 超范围 → 报告用户 |
| F-N1.5 | 两段式委托（执行 / 检查心智分离） | 有规模的实现批次（多文件 / 跨模块 / 有已确认设计）默认由 coder 子代理实现（async——设计为任务书）；小型 / 探索性 / 交互式变更留主会话；复核走 F-N1.4 |
| F-N1.6 | 委托操作标准 | 规模判据可操作化（≥2 文件 或 单文件逻辑 >30 行 或 涉模块边界 或 涉双端镜像）；任务书七字段（目标 / 已知事实 / 设计要点+禁止 / 约束 / 硬验收 / 交付报告 / 调度元数据）——缺字段 = 委托缺陷 |

**范围边界（不做）**：不做常态化独立审计机制（机制论证 = `docs/core/design/AGENT-LOOP.md` §6.17）；不建以轨迹 / 会话考古为数据源的审计（轨迹默认关——发布隐私）；不新增机械门禁（§5.3 N1）。
