## 1. 总体定位

结构债的病痛与治疗时机**错开**（平时无症状、撞上才暴露），因此必须靠**文档显式追踪**防「挂账不处理」。
本板块规定：结构债如何度量、何时必须处理、每批如何独立立项。

**「修」的定义（本机制判据的根 · 用户口径）**：「修」= **走流程修**——登记（台账条目 / 批次档）→ **就地开批** → 设计 → 评审 → 实现 → **验证**。**不存在「不经流程的改代码」这回事**；「当场就地」限定的是**时机**（撞上即登记、当即开批，不往后排），不是**手段**。
⇒ 要治的病是**挂账即了事**——登记完就没人管了。**登记本身不是违规；登记后不再过问才是**。

**射程**：射程内 = **被本次改动撞到的那些**结构问题（判据兜底 = 纪律层「铁律②」）——**射程内入库 `trigger` 只能是 `归批`**（撞到即须开批，不适用 `条件` / `认账不排期`）。

**射程外**（看见未撞到）照常按入账形态登记。
**无旁路**：撞到的结构问题一律就地开批走全链（设计 → 评审 → 实施 → 验证）——用户 2026-11-02 23:30 逐字「以后不再有小改动这种定义了，一切直走标准流程，一律走全链」⇒ 任何例外通道都不存在；适用条件以 `docs/core/requirements/ENGINEERING-MODE-V2.md`（变更面分流）为准，提示词只承载执行句；**本档不重述（D2）**。

## 2. 功能性需求

| # | 需求 | 说明 |
|---|---|---|
| **F-SD1** | 显式追踪 | 结构债评估与清理在文档面显式记录（设计侧总账 = `docs/core/design/STRUCTURE-DEBT.md`；具体清理随批落批次档 / 归属设计档） |
| **F-SD2** | 每批独立立项 | 每批独立走工程模式（设计 → 评审 → 实现），批档独立成文 |
| **F-SD3** | 触碰到即处理 | 撞上结构问题 ⇒ **当场登记入账 + 就地开批**，把修走完流程（设计 → 评审 → 实现 → **验证**；无旁路）——**挂账即了事（登记后不再过问）= 违规**；任何情形下禁止在错结构上叠最小补丁掩盖症状。**核验面**：射程内台账行 `trigger` = `归批` ∥ 挂靠批档的开批状态（评审 / 批准 / 收口在场） |
| **F-SD4** | 不建平行登记面 | 同一机制只在一处详述（单一权威源）——结构债不在多处各立清单 |

## 3. 非功能性需求（硬指标）

| # | 维度 | 标准 |
|---|---|---|
| **N-SD1** | 源码文件超硬限 = 必须拆 | 文件行数硬限 = 800（无豁免通道，>800 必须拆）；越 500 软线的文件在设计里必须带拆分计划 |
| **N-SD2** | 超软线 = 主动拆分评审 | 文件 >500 行 = 软线（advisory），触线即主动审视 |
| **N-SD3** | 函数档是第一判据 | 文件未超硬限但含超长单体函数仍不合规（函数随生长即分解，不先写整体再拆） |
| **N-SD4** | 文档同标准 | `docs/` 文档无 >300 字符单行（表格行豁免 + **历史区豁免**——区带内超宽行不计；区带名集 ∥ 判据 = `docs/core/design/DOC-DISCIPLINE.md` §3.15） |
| **N-SD5** | 合并仓单一标准 | 范围 = 合并仓全仓（核包 + 两产品树）——同一标准、一次检查 |

## 4. 范围边界（不做）

- 不做自动重构（判定与清理走批次立项，不设常驻自动改写）。
- 不建第二份债清单（唯一总账 = 设计侧 `docs/core/design/STRUCTURE-DEBT.md`）。
- 软件结构债不设「存量豁免 / 入基线」通道（存量不是合法态）。
