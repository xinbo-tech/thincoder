# 文档体系（DOC-SYSTEM）· 需求

> 板块 = **文档体系**——`docs/` 的**落点规划（core / CLI / VSC / desktop / render-core 五部分）** · 命名规则 · 归属判据 · 交叉引用形态 · 机检的引擎 / 路由表切分。
> 设计档 = `docs/core/design/DOC-SYSTEM.md`（方案选型 / 接口契约 / 受影响文件 / 关键决策 / 验收回指 / 用例表 / 边界）。
> **只做规划，不执行迁移**：不改两产品树里任一档的物理位置、不改机检脚本、不改提示词文件、不写产品树。
> **判据权威分层（D2 单一权威源）**：工作流机制（批次档六段 / 需求池状态机 / 台账条目形态 / 文档自持边界）= `ENGINEERING-MODE`；
> 锚判据全文 = `ENGINEERING-MODE` §2.32.3（CLI 锚）· `DOC-CODE-RECONCILE` §4（VSC 锚）——本板块只给**切分与修法**，不重述判据全文。
> **本档只收本仓事项**（各仓记各仓：本板块的规划对象 = 本仓 `docs/` 与两产品树的产品级文档）。

## 1. 总体需求

**为谁解决什么问题**：为 thinCoder 合并仓建立 **core / CLI / VSC / desktop / render-core 五部分**的文档落点秩序。
合并仓已含一核两壳（`thincoder-core/` · `thincoder-cli/` · `thincoder-vscode/`），而 `docs/` 下的需求 / 设计目录
仍是一条**不分部分的平铺清单**（根层 16 + 16 板块档，无部分轴）；两产品树里另压着大量未迁的旧档。
不先定落点，则「开始整文档」时必然出现四类失控：**同名不同物** · **归属争议** · **跨部分引用不可解析** · **机检域拍不准**。

**范围边界（明确不做）**：零搬迁（两产品树任一档的路径不变）；零代码（机检脚本不改）；零提示词改动；零 commit。

## 2. 功能性需求（FR1–FR8 · FR10）

| # | 需求（用户故事） | 验收（可机判 / 可逐条核） |
|---|---|---|
| **FR1** | 作为**文档维护者**，我想要 `docs/` 下 core / CLI / VSC / desktop / render-core 五部分各有明确的需求 / 设计落点（含跨部分共享面），以便新档一落就有位置、不必现场争论 | 完整目录树 + 现有 16 板块档与提示词（唯一副本 = `thincoder-core/prompts/`）的**去向** |
| **FR2** | 作为**文档维护者**，我想要一套**可机判的命名规则**，以便「同名不同物」不再出现（已实证发生） | 命名规则 + 方案对比（≥2 候选 · 含否决理由） |
| **FR3** | 作为**文档维护者**，我想要**可判定的归属判据句**，以便任一新档 / 旧档一眼归类 | 判据句 + 现有产品树文档的**初分类** |
| **FR4** | 作为**文档维护者**，我想要跨部分引用的**统一形态**且有**可判据句**可依，以便引用不靠人工记忆 | 引用形态规范 + 判据句（**人读核**——R2 层前缀 ∥ R3 全路径；不设机检） |
| **FR5** | 作为**项目负责人**，我想要本规划与既有四条裁定（基准层 / 参照历史 / 提示词落地面 / 逐档随批迁）逐条自洽，以便不产生两套矛盾口径 | 四条逐条自洽说明（有冲突即指出并给修法） |
| **FR6** | 作为**产品维护者**，我想要机检的「**普适引擎**（该进产品）」与「**本仓路由表**（该可声明）」切开，并给射程修法，以便换一个项目时这套检查开箱可用 | 逐族切分（含行数估算）+ 射程修法（外部参照面域声明） |
| **FR7** | 作为**文档维护者**，我想要两处**悬空文档锚**被收正（`docs/core/design/CORE-UNIFICATION.md` 两行），以便根域锚检查回到悬空 0 | 实修 + 源面核（两处锚的档路径 + 节号在盘实读存在） |
| **FR8** | 作为**主 agent**，我想要**台账两池判据**的落点与文本（需求池 / 技术待办），以便新条目不再靠临场判断 | 落点与文本（台账头部文本 + 提示词层落点）——**只出文本，不代写台账** |
| **FR10** | 作为**被开发项目的文档维护者**，我想要**文档纪律机检由产品内建、以工具形式提供给 agent**——判据参数由项目 `PROJECT-MANIFEST.json` 声明（不硬编码本仓路径），**项目自建检查器不作判据**（本仓现值 = `scripts/doc-check.mjs` 退场），以便换一个项目开箱可用、判据不随仓漂移 | ① 工具形 = agent 可调（与 `manifest` / `ledger` / `batch` 同级）；② 声明面读数：改项目 manifest 声明 ⇒ 行为随之变；③ **起步判据 = 两条**：锚（文档指针可解析）· 行宽（单行 &gt; 阈值字符；豁免 = 表格行 / fenced 块 / 可执行行 / 连续引文，加历史区等区带）；④ **非门禁**（不阻断、不作拒执行的理由——用户令 &gt; 机检）；⑤ 项目自建脚本不在判据链上；⑥ 无本仓路径的样例仓可跑 |

> **FR10 边界（用户 2026-10-16 17:51 裁定「宁可现在少以后加」）**：不做退役措辞残留（语义面 ⇒ 归收口核对 / 评审眼）· 不做在册标记交叉核（后加）· 不做行数读数与计数一致性（前者内容已废、后者判据不应存在）· 不新增纪律条文 · 起步范围只两条，**不加机制**。

## 3. 非功能性需求（N1–N4）

| # | 标准 | 度量方式 |
|---|---|---|
| **N1** | **可判**：命名规则 / 归属判据 = **判据句**（可写进机检谓词）；**引用形态 = 判据句（人读核、清单化——不设机检**，口径住 `design/DOC-SYSTEM.md` §7 R1–R3）——皆非「注意一下」类表述 | 逐条给出判据句 + 判据面（机检落点 ∥ **人读核面**） |
| **N2** | **零假阳优先**：任何新增判据不得制造「红一片」——判据不精确即等于没有（承 DOC-CODE-RECONCILE §4.7 判据） | 外部参照面等新判据须给出**零报样例** |
| **N3** | **格式合规**：本板块新增 / 改动的档须过仓根**锚 + 行宽**两项判据（`check-ledger` 已随台账 schema 作废；**读数器禁调**——用户 2026-10-15 令「不再跑、不再引其读数、不再以其红 / 绿作任何判据」） | 源面 / 静态面读数（`grep` ∥ 直读档 ∥ 逐档比对） |
| **N4** | **可回退**：落笔只含文档（设计 / 需求 / 地图指针 / 批次档），**零代码零迁移** ⇒ 全部改动为可 `git revert` 的纯文本 | `git status` 自证改动集 |
