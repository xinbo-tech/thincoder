# 工程模式 v2（需求）

> 状态：草案 · 方向讨论中
> 写权：父侧直接执行（讨论捕获）；正式需求由 eng-designer 精化
> 定位：本档 + §13 继承机制 = 现行权威。

> **总体需求（两模式对称锚）**：普通模式靠纪律提示词约束模型；工程模式是**强流程**——「设计先行、评审把关、验证收尾」由**结构**保证落地。**实现方式 = 结构设计，不是机械硬拦**（与
 §1「约束即结构」同源）：让**对的路径成为唯一顺手好走的路**（三账 = 流程必经载体 · 提交物自带形状 · 状态在结构里可见），而不是在出错点上装闸。

 **上结构约束的判据（三合取）**：该处失守会付**真实代价** ∧ 纪律与可见性**确实兜不住** ∧ **不增加正常路径的负担**。

 **默认倾向 = 纪律 + 可见性**（报告 / 登记 / 停下上报）。**反模式（明令禁止）**：为臆想中的失败逐点加限制
 · 用计数器 / 上限替代「有结论 + 停下上报」 · 把纪律句机械化成机检 · 以「拦截」代替「让正确的路更好走」。

 核心承诺三条：① 代码必须先有**被评审过的设计**；② 评审对象**由任务定义**、不靠遍历猜测；③ 评审循环在**实现者内部闭环**（不依赖父代理持有凭证）。
>
> **与普通模式的唯一差别 = 流程强度**（反向锚 = `NORMAL-MODE.md` §5.1）：工程模式 = **强流程**（约束靠结构实现）；普通模式 = **纪律驱动**（无结构约束）。工程模式的**结构化约束点**（流程里绕不过的关口）= **写权凭证**（designToken）· **设计先过评审再写码** · **批次档 /
 任务书必备**（四项核心 + 第五项按角色 + `round`（eng 角色）+ `batchDoc` 体检）· **`verify` 收尾门** · 需求 / 设计 / 测试三档逐条可机判。共享面 = 三观（`PHILOSOPHY.md`）· 公共层提示词 · 方法论判据（`docs/core/requirements/METHODOLOGY.md`）· 工具面——**差别只在流程强度，不在「要不要认真」**。
> 细节单源 = 本档 §13 继承机制与 `ENGINEERING-MODE-V2-SPEC-*` 系列（D2——本段只承「总体定义」一职，不重述机制）。

## 1. 定位与灵魂

工程模式 v2 是**工程模式机制本身的一次重构**——不是加几条规则，是把机制的哲学从「靠自觉」翻转到「靠结构」。

**灵魂：约束即结构（Constraints as Structure）——不靠自觉，靠结构。**

v1 把纪律写成「期望」：角色边界写在提示词里（模型可无视）、纪律写在文档里（漂移无人拦）、交接靠自觉（该拒的不拒）、委派靠心情（想派就派）。全指望对方记住，于是会漂移、会滥派、会瞎收。

v2 把纪律从「文字」变成「机器」——**能靠结构拦的，就不靠人记；让对的路成为唯一好走的路，让错的路被结构挡住。**

**判据句**：每一条纪律，必须能回答「靠哪个结构兜底？」——答不上来的，就不是 v2 的纪律，是 v1 的期望。

## 3. 机制全貌

一条流水线串起整个机制：

```
阶段（初始开发 | 上线运行——决定纪律重心）
   ↓
批次循环【开批 → 设计 → 评审 → 裁决 → 实施 → 收口 → 冻结】
   ↑_____________________________|
   （一个交付目标 = 一批，批界命中即另起新批）
```

- **运转核心**：三账（项目状态档 > 台账 > 批次档——见第 5 章，整机制围绕它们转）。
- **角色**：主 agent（对话面，贯穿全程）· eng-designer（设计段）· advisor（评审段）· eng-coder（实施段）。
- **文档**：需求档、设计档（写作约定见第 6 章）。
- **规则**：交接契约、委派治理、纪律兜底、提示词单向生成（第 8 章）。
- **情境**：阶段、轮次——两把「调轻重的旋钮」（第 9 章）。

## 4. 项目方法论（主 agent ↔ 用户沟通方法）

> 主 agent 是 thincoder 与用户交互的**唯一界面**，但「怎么跟用户一起做项目」不能靠零散规矩——要有一套融合传统软件开发项目管理经验的标准方法。**本章指导主 agent 的一切沟通行为。**

### 4.1 项目两分（需求主体不同）

项目从某个维度上可以分成**研发项目**和**委托开发项目**，两种项目里「需求的主体」是不一样的：

- **研发项目**：用户就是需求的主体，你跟他是甲方乙方的关系——他提需求，你落实。
- **委托开发项目**：你的直接用户并不是需求的主体，真正的主体是**委托方（甲方）**；你的用户跟你**一起跟甲方沟通**。

沟通方式不能一刀切：研发项目「听用户的话」就行；委托开发项目里，用户是战友，主 agent 要**帮着用户一起向甲方**澄清需求、出方案、扛责任。

**两套阶段观对应两种项目类型**：委托开发 = 纵向交付生命周期（调研设计 → 开发 → 测试 → 验收 → 上线运营）；研发 = 产品成熟度（初始开发 → 上线运行）。

**分层关系（关键）**：**研发项目** = 本档第 5-11 章描述的机制本体（需求 → 设计 → 评审 → 实施 → 收口，三账，角色分工）；**委托开发项目** = 本体之上**多套一层「项目方法论」**（本章 4.2-4.8），因为多了一个「甲方」这个外部实体，沟通与风控都不一样。研发项目用本体，委托开发用「本体 + 方法论增量」。

### 4.2 委托开发五支柱

委托开发项目有：**甲方、预算、项目周期、沟通体制、风险控制机制**（其中**预算不是技术人员管的事**——主 agent 不碰预算，归 PO/商务）。

### 4.3 找对人（甲方四类人）

沟通机制上最重要的是**找对人——正确的事情跟正确的人说**。甲方的人分四类：

| 角色 | 是谁 | 跟他沟通什么 |
|---|---|---|
| **甲方项目经理（PM）** | 负责跟乙方对接、协调项目活动 | 进度、协调、活动安排 |
| **Project Owner（PO）** | 为项目买单的人 | 目标、预算、重大取舍 |
| **Function Owner（FO）** | 决定某个模块要做什么、不做什么，通常是甲方某块业务的负责人/部门经理 | 该模块的需求、范围 |
| **User / KBU** | 你开发出来的功能的真正使用者，职位最低，但却是更高阶人员对你成果评价的信息来源；User 很多不可能都跟你对接，KBU 是用户的代表，通常是业务骨干 | 真实使用反馈 |

**深意（关键）**：User 虽然人轻，但他们的反馈往往能决定项目的生死。User 很多不可能都对接，KBU 是代表。所以**找对人 = 把正确信息送到正确层级，尤其不能轻视 User/KBU 这一层的反馈。**

**角色-模块映射表（项目启动第一产出）**：项目启动时，通常会立即整理一张表，**按业务和模块把对应的人都找到**：
- 一个功能**找不到 FO** → 你就不知道这个功能如何确定（做什么/不做什么没人拍板）；
- **找不到 KBU** → 意味着你对业务具体该怎么操作、怎么使用，没有沟通对象；
- 一个项目**说不清楚这些角色具体是谁** → 失败概率就是 **100%**。

缺人不是软提醒，是**硬阻塞**——角色映射表不全，说明项目没就绪，不能开干。

### 4.4 接手流程（先盘信息 → 内部消化 → 见甲方）

**① 盘基本信息**：接手一个项目，通常需要先了解这个项目的基本信息——**甲方是谁？项目的目标是什么？有没有之前给他们的提案？内容是什么？项目的周期是多久？甲方 PM 是谁？** 等等。有了这些信息以后，再消化理解。

**② 内部消化（先在公司内部）**：这时候还在公司内部，是先跟**销售之类的人**沟通。消化这些信息以后，准备出**下一步需要调研的问题清单**——能够内部澄清的，先内部澄清；澄清不了的，留待跟用户接触以后继续澄清。

**③ 见甲方 PM（带问题清单，先找 PM）**：下一步就是带着问题去见甲方了，通常是**先找到甲方 PM**。先跟甲方 PM 进一步了解对方的需求信息——**目标是什么？周期？里程碑？** 以及**涉及哪些业务部门、要实现什么功能**等等。有了这些以后，**Function Owner 基本上也就清楚是谁了**。

**④ 定时间计划**：FO 清楚以后，你要先定个计划，**把时间计划先确定下来**。有了这些，项目就可以准备启动了。

**⑤ 项目启动**：正式的话会开个**项目启动会**；轻松一点的话，就是 PM 带着你去认识 Function Owner。

### 4.5 生命周期与阶段成果物

项目通常会分成几个阶段：**需求调研和设计阶段 → 开发阶段 → 测试阶段 → 上线后持续运营**。

**需求调研和设计阶段**：先要搞清楚甲方——所处的行业、做什么业务、我们项目的目的是什么、**他们原来是怎么做的**、人员是如何分工的、原来有哪些业务数据、形式是什么样的、**有没有样例样本**——搜集下来。下一步的目标是**交付方案**。这个阶段最重要的成果物有三个：**方案**（给甲方的解决方案文档）、**计划**（实施时间计划）、**交付物清单**（验收时对着它逐项签收）。

**开发阶段**：主要是我们（乙方）内部做；有问题会**通过甲方 PM 去找 FO 和 KBU 讨论**（不绕过 PM）。最终交付的是**测试报告**，说明方案中约定的模块和功能点我们都已经实现了。

**测试阶段**：给用户，由 **KBU 来测**；成果物也是**集成测试报告**。

**验收**：对着**交付物清单**（甲方在调研设计阶段已签字确认过的交付标准），逐项让甲方签字确认收到——**全签收了，那就是验收过了**（清单勾销，不靠「甲方说好」）。

**部署与持续运营**：验收之后就是**生产环境部署**，进入**持续运营阶段**。

**关键闸门**：
- 调研设计 → 开发：**方案 + 计划 + 交付物清单**都必须甲方签字确认（确认后才进开发——**交付物清单不签字确认，就没有交付标准，验收时无从对账**）；
- 测试 → 验收：集成测试报告交付；
- 验收：对交付物清单逐项签收，全签收 = 验收过。

### 4.6 沟通机制

**问题驱动的沟通 = 找对人**（前文四类人已铺垫）：开发中碰到问题，**功能取向的问题找 FO，使用方式的问题找 KBU**；进度/协调找 PM，目标/预算找 PO。

**日报**：每天要出日报给甲方 PM。传统上通常有个内部晚会（甲方 PM 愿意参加也可以）；现在是 AI 开发、可能没有内部团队了，但**日报还是需要的**。

### 4.7 风险控制

**风控与日报关联**：风控主要看的方向是**进度偏差**——日报是进度偏差的「仪表盘」，风控靠日报发现偏差、早预警。

**风险分级标准（低 / 中 / 高，锚定「对进度的影响」）**：
- **低**：一个问题还看不出对进度造成影响；
- **中**：可能影响进度；
- **高**：已经影响进度。

分级锚定「对进度的影响」，不是「问题难不难」——难但没拖进度 = 低；简单但已拖进度 = 高。

**应对按级**：
- 低：记录、继续；
- 中：告知甲方 PM；
- 高：启动风控会议，跟甲方一起商量应对方案。

### 4.8 持续运营

落实到技术这一块，主要就是 **bug 报告和修复**。这一块不用过死过细——只要有机制能**报告 bug、记录 bug、做后续处理**就够了。

## 5. 运转核心：三账（项目状态档 PROJECT-MANIFEST > 台账 Ledger > 批次档 Batch Record）

> 工程模式的一切围绕**三本账**运转——它们是整套逻辑的状态容器，不是边角产物。角色是「谁写哪段账」，纪律是「三本账不漂移」，情境是「三本账在不同情况下的运转方式」。

### 5.1 项目状态档（PROJECT-MANIFEST）——「项目现在处在什么状态」的账

- **意义**：项目全局的**状态总览**——阶段、目录声明，一处记录。它是情境旋钮（阶段）的**记录落点**：没有它，阶段就没有「现在处于哪」的存档。
- **构成**（纯机器状态）：项目阶段（初始开发 / 上线运行）· 目录声明（doc-root，覆盖默认值）。
- **格式**：**JSON**（`PROJECT-MANIFEST.json`）——纯机器状态，机检机械校验（枚举合法、值形态合法、目录声明存在）。**关键决策不进 manifest**（那是文档层的事，住需求档约束依赖 + 设计档关键技术决策/方案否决理由；待裁事项住台账）。

**字段语义须达用点（2026-10-16 · 用户令 · 台账 `#1585`）**

- **问题（实测三条）**：① `manifest` 工具的描述只给**动作**（read / init / write）与**键名白名单**，**不给字段语义**——`phase` / `codePaths` / `docRoot.*` / `checkConfig.*` / `index.*` / `advisor.*` 各自「是什么、什么时候该动」在描述里读不到；② 提示词层全档 `manifest` 命中**只讲「怎么发现 / 怎么建档」**，**无一节讲「怎么管、有什么用」**；③ 语义单源在设计档 ⇒ **主 agent 在"用工具的那一刻"读不到**。
- **需求**：主 agent 仅凭**工具描述 + 提示词**，即可判断「某个键该不该改、改成什么、不改会怎样」——**不必翻设计档**。
- **边界**：不改键面语义 · 不改写门（fail-closed 零改）· 不改 manifest 结构 · 不新增字段。
- **验收**：给一个具体场景（例「本仓要排除归档目录不入索引」），只读工具描述 + 提示词即能答出「改哪个键、为什么、改错会怎样」。
- **前置性（入口门槛）**：工程模式下**必须先有它**——没有则先**初始化生成**：确定项目阶段 + 梳理现有文档和代码 + 盘清家底，再进正常循环。

### 5.2 台账（Ledger）——「还有哪些事的账」

- **意义**：需求池 + 技术待办 = 工程模式的**待办总账**，驱动「做什么、做没做、怎么排」。
- **存储**：**SQLite**（`node:sqlite`，零第三方依赖，memory 面已验）——并发写靠事务、计数自动（COUNT）、状态机靠字段枚举约束，替代 md 文件 + 手工纪律（今天的并发冲突、删条目漏改计数，根子就在 md + 手工）。**工作树外**（用户数据目录键控库——项目内不留文件，天然不进 git；用户裁定）。
- **可读面**：查询命令（`/ledger`）——agent 和用户都通过查询面看台账，**不导出 md 摘要、不直接读 DB**。
- **统一待办跟踪**：checklist 工具**废除**（用户裁定）——台账是**唯一待办跟踪面**。checklist 的 pending/in_progress/done 由台账六态承接，跨 session 由 DB 持久化承接，归档由归档表承接。
- **构成**：需求池（用户需求点）+ 技术待办（机制缺陷）+ 归档（已核销/已废弃——软删除或归档表）。
- **状态机**：六态（待讨论/待设计/在途/待核销/已核销/已废弃）——字段枚举约束，写错态即拒。
- **结构**：schema 约束替代手工纪律（一行一条 = 一行记录 · 计数 = COUNT · 指针（`task_book`）非空 = CHECK · 本仓自持 = 校验）。
- **模型使用面**：台账教学两分——**常识面**（全角色）需求住 `docs/core/requirements/PROMPT-SYSTEM.md` §2.3（第 13 节）· **用法面**（主 agent）住本档 §13.8（FR30）。

### 5.3 批次档（Batch Record）——「一件事怎么做的账」

- **意义**：一次实现轮的**账本**——「说做完 = 真做完」的可信载体。没有它，交付无从核、审、回滚。
- **构成**：六段一段一作者（§1 主 agent 目标+前情+条目+已定决定清单 · §2 designer 任务书 · §3 advisor 发现表 · §4 主 agent 核验裁决 · §5 coder 实施记录 · §6 父代理 收口+状态行）。
- **流转（状态机）**：开批 → 设计 → 评审 → 裁决 → 实施 → 收口（状态行「已收口」+ 核销 + 关链）→ 冻结（不再回改、不迁移不删）。**流程走到哪 = 批次档状态推进到哪**。
- **格式**：**md**（记录类文档——六段含大量叙述：评审理由、裁决、实施过程、收口判词；机检靠结构约定抽段头/状态行/计数，不靠 JSON 机器读）。
- **护栏**：单档 >1000 行另起 · §5 修正轮上限 5 · §3 评审无轮次上限 · 判定权 = 主 agent。
- **结构**：六段自写 + `batch` 越段即拒 + 状态机。

### 5.4 三账如何咬合（按重要性）

| | 项目状态档 | 台账 | 批次档 |
|---|---|---|---|
| 回答 | 「项目**现在处于什么状态**」 | 「还有哪些事**要做**」 | 「一件事**怎么做**」 |
| 驱动 | 情境旋钮（阶段） | 排期（触发条件） | 流程推进（状态机） |
| 收口时 | —（manifest 不参与收口——无批次指针） | 核销 → 归档 + 计数联改 | §6 收口 + 状态行冻结 |
| 兜底 | manifest 写门（M1——fail-closed） | SQLite 咬合 CHECK（非空 `task_book`） | `batch` append 段门禁 + 状态行冻结拒写 |

**一条需求的生命**：进台账（待讨论）→ 开批（批次档 §1）→ 设计（§2）→ 评审（§3）→ 实施（§5）→ 收口（§6）→ **台账核销归档**——批次档与台账在收口处闭合；项目状态档横切更新（阶段随进度变）。

### 6.1 需求文档（两层）

需求文档分两层，粒度不同、用途不同：

**上层 · 项目需求（Project Requirements）**——主 agent 写，全局视角，整个项目一份。七层：
1. 背景与问题（为什么做、现状、痛点/机会）
2. 总体目标（要达成什么——可验收的「状态」，不是「做好」）
3. 范围与边界（做什么 / **明确不做什么**）
4. 干系人与用户（为谁做、需求主体是谁）
5. 功能需求（逐条用户故事：`作为一个[角色]，我想要[功能]，以便[目的]`，只写 who/what/why）
6. 非功能需求（性能/安全/兼容/可用/可维护，**含度量**）
7. 约束依赖 + 验收标准（技术约束、外部依赖、假设；怎么算做完）

**下层 · 功能规格（Function Spec）**——按**架构设计定下的模块**拆，一个模块一份，**交给 designer 做设计的文档**（不是项目需求）。结构：
- 模块目标；
- 功能点（**含用户故事**——每个功能点用用户故事表达）；
- 边界（做什么/不做什么）；
- 验收标准；
- 依赖。

一个 Function Spec = 一个批次：designer 拿它出设计 → coder 实现 → 收口。

### 6.2 设计文档（两层）

与需求对称，设计也分两层：

**上层 · 架构设计（Architecture Design）**——总体视角，整个项目一份。内容：技术选型、**模块划分（Function Spec 的权威源——没经设计考虑的模块划分不成熟）**、模块间接口/依赖、关键技术决策、整体数据流。

**下层 · 模块设计（Module Design）**——对应一个 Function Spec，一个模块一份，交给 coder 实现。内容：① 问题陈述 ② 方案与理由（就方案本身说清为什么这么设计——**不强制列候选对比**） ③ 受影响文件全清单（源/测试标当前行数 + 预计增量） ④ 验收标准逐条回指 Function Spec（每条可机判）。

**对应关系（时序）**：项目需求 → **架构设计（定模块划分）** → 按模块拆 Function Spec → 模块设计 → coder 实现（一个批次）。

**新建 vs 更新**：写设计文档时——该模块**已有**设计文档 → **就地更新**；**无** → 新建。与 §6.3 就地更新规则同源（不另起炉灶）。

### 6.3 需求与设计文档就地更新规则

**总体需求 / 总体设计（项目需求、架构设计）允许多份历史演进**（不同时期逐步演进调整，如 v1/v2 并存）。**但模块级的需求与设计关系必须维护好、不能乱**：

- 一个模块的需求 = 一份 Function Spec，一个模块的设计 = 一份模块设计，**一一对应、关系不乱**；
- 涉及该模块的更新，就地更新对应的那份文档——不另起炉灶写另一份文档（另起炉灶会把文档体系搞散——用户裁定）；
- 需求变了 → 改该模块的 Function Spec 文档本身；设计变了 → 改该模块的模块设计文档本身；不新起「接线 / 迁移 / 补充 / 旁路」文档。

**检查点（约束即结构，不靠自觉）**：
- **designer 接单时**：先核查「该模块的需求文档（Function Spec）是否已存在」——不存在 / 发现另起炉灶 → **打回主 agent**，不自行补造方向；
- **文档评审时**：advisor 核查「需求与设计是否另起炉灶」——发现旁路文档 → 报发现。

### 7.2 角色 A · 主 agent（对话面 · 唯一）

> **提示词落点**：`thincoder-core/prompts/persona-engineering.md`——角色定义见 `docs/core/requirements/PROMPT-SYSTEM.md` §2.2 人格层（本角色 = 交叉引用回本节）。

**职责**：
- 需求讨论 + 登记
- 写需求文档（项目需求 + Function Spec，讨论捕获）
- PROJECT-MANIFEST 初始化 / 维护
- 批次收口（§1/§4/§6 + 核销 + 关链）
- 内容级核验设计稿（非重审）
- 评审发现裁决
- 按变更面派发
- 台账唯一作者

**红线**（判据句）：
- 不写设计档（designer 唯一；需求文档可落）
- 不写实现代码
- 不自发起评审
- 不挂「等」（只对真依赖）
- 不代提交他人档
- 不让 coder 自己勘察（派单钉死 file:line，禁「全量扫 X」）

**完成判据**：
- 收口四件齐（§6 非空 + 状态行 + 核销 + 关链）
- 裁决表 Dispatched→Fixed 带 file:line
- 派单三句齐
- 核销三联改

**派单尺寸（判据句）**：
- 一舱一单面：`files` 声明面 **≤15 档且不跨变更面**——跨面 ⇒ **按面拆舱**。
- 派单前**预检三闸**：档数 >15 ⇒ 拆 · 跨面 ⇒ 按面拆 · **未决口径落在实施面内 ⇒ 先裁**（不许留给实施者「视情况」）。
- **结构决定归设计 / 派单**：拆分边界 / 落点 / 形状在**设计期定死**，实施者只照表落码——**留给实施者的开放结构决定 = 读循环的入口**。
- **任务书 = 表，不是散文**：核心 = **逐行动作表**（动作 / 落点 file:line / 期望）——**「先读档清单」计入探索预算**，两者自相矛盾 = **派单缺陷**。

### 7.3 角色 B · eng-designer（设计文档唯一作者）

> **提示词落点**：`thincoder-core/prompts/persona-eng-designer.md`——角色定义见 `docs/core/requirements/PROMPT-SYSTEM.md` §2.2 人格层（本角色 = 交叉引用回本节）。

**职责**：
- 核对主 agent 写的 Function Spec 合规（五要素齐：模块目标 / 功能点 / 边界 / 验收 / 依赖，具体到可设计），不合规打回（§7.6 互锁）——**先验料，料不对打回，不白勘察**
- 勘察（一次，不跑多遍——A1 checklist）：
  - ① 定位所属设计文档 + 核查该模块 Function Spec 已存在（另起炉灶 → 打回主 agent，§6.3）
  - ② 读既有实现与先例
  - ③ 核测试
  - ④ 广度勘察委派 explore（≤6）
  - **目的**：验证设计可行 + 拿一手证据（`file:line`）+ 发现需求缺口，**不为「全面理解代码」**，够了就停
- 写设计文档（架构设计 + 模块设计；已有则就地更新，无则新建——§6.2/§6.3）
- 写批次档 §2
- 评审前预检（A3 四项，不过先修，不自发起评审）：
  - ① 需求具体到可设计（Function Spec 五要素齐、具体到可据此设计）？
  - ② 受影响文件全清单 + 行数标注（代码面标行数，文档面豁免）？
  - ③ 验收标准逐条回指需求（每条可机判）？
  - ④ UI/交互决策全落档（无「讨论过但没写」）？
- 设计修订（修正轮，单写者）

**红线**（判据句）：
- 不写需求档（需求档归主 agent，designer 只核对合规）
- 不写实现代码
- 不改提示词文件（`thincoder-core/prompts/**` = 产品代码 ⇒ eng-coder 笔；父侧改提示词 = 走 coder）
- 不发评审
- 只碰 §2 + 设计档
- 不代用户裁定（澄清必经主 agent）
- 修正轮不夹带新语义

**完成判据**：
- Function Spec 五要素齐、具体到可设计（核对合规通过）
- 受影响文件全清单 + 行数标注
- 验收逐条回指需求且可机判
- 预检四项过

### 7.4 角色 C · eng-coder（实现唯一执行者）

> **提示词落点**：`thincoder-core/prompts/persona-eng-coder.md`——角色定义见 `docs/core/requirements/PROMPT-SYSTEM.md` §2.2 人格层（本角色 = 交叉引用回本节）。

**身份**：被授权的实现者——父代理交任务书（批次档 §2）+ 设计 token，设计档是权威规格；你的角色是实现。

**授权**：设计评审 token 在 spawn 时机械验证——无需重跑设计评审；无有效 token，写工具全拒。

**边界**：
- 设计是权威规格——通读遵循、不得偏离；
- 发现设计缺口 → 停下报告父代理，不得静默偏离；
- **子代理**：任务已由父代理确认（授权已在上游行使）——**父代理就是子代理的用户**：决策级问题即发 `notify_parent`（即发即走）；**冲突类必发、不得拖终报**；不停轮等答复、不以「等待批准」结束回合、不发确认型请求；歧义在最终报告注明后返回；
- 独立工作，父代理只看最终报告。

**交付协议**：实现 → explore 偏差审计 → 自修（≤5 轮）→ advisor 代码评审 → 收敛交付；报告声明审计/评审轮次与终态（clean / stalled）。

**file 域声明**：超声明改动允许——逐条列出并说明理由；改了未报 = 静默越界。

**批次档纪律**：§5 自写（batch append）；执行者拒收——查不到任务书（§2 / `batchDoc` 不可读）→ 不执行、打回。

### 7.5 角色任务与交付物

| 角色 | 任务 | 交付物 |
|---|---|---|
| 主 agent | 需求讨论/写需求文档/manifest/收口/核验/裁决/派发/台账 | 项目需求 + Function Spec · PROJECT-MANIFEST · 批次档 §1/§4/§6 · 台账 · 裁决表 |
| eng-designer | 写设计档 + §2 + 勘察预检 + 设计修订 | 设计档 · 批次档 §2 |
| eng-coder | 按任务书实现 + 写 §5 + 内部审计自纠 | 实现代码（源码+测试）· 批次档 §5 · 交付报告 |
| advisor | 设计评审 / 代码评审 | 评审报告 · 批次档 §3 |

（explore = 只读辅助，非核心角色；plan 是否入工程模式——待定。）

### 7.6 互锁机制（交付物合规校验）

交付物不只各写各的——上下游互相校验，不合规打回：

| 环节 | 谁产出 | 谁校验 | 不合规 → |
|---|---|---|---|
| 功能规格 Function Spec | 主 agent | **eng-designer 核对合规**（五要素齐 / 具体到可设计） | 打回主 agent |
| 设计档 | eng-designer | 主 agent 内容核验（覆盖需求没、方案合理没）+ advisor 独立评审 | 打回 designer |
| 实现 | eng-coder | 主 agent 验收（测试/读数） | 打回 coder（修正轮） |
| 收口 | 主 agent | 台账核销 + 批次档 §6 收口（manifest 不参与——无批次指针） | 机检红 |

**核心**：「谁写」和「谁把关」分离——主 agent 写需求文档，但必须 designer 把关合规，否则主 agent 随心所欲乱写。

## 8. 运作规则

### 8.1 交接契约

**路由（任务类型 → 角色）**：排查/勘察 → explore · 设计/文档 → designer · 实现 → coder · 评审 → advisor。派单机械校验，不匹配即拒。**结构**：类型契约 + 拒收门。

**主 agent ↔ designer 交接界面**：

| 方向 | 交接内容 |
|---|---|
| 主 agent → designer（派单） | 批次档 §1（目标 + 条目 + 前情）· 本批 Function Spec 清单 · 架构设计（模块划分权威源）· 轮次（初始/修复）· 禁止范围 |
| designer → 主 agent（交回） | 设计文档（新建 or 就地更新）· 批次档 §2 任务书 · 报告（号→改动 file:line + 打回点） |
| designer → 主 agent（打回） | 缺 §1/清单不全 · 需求说不通（缺口/矛盾/不可实现）· 另起炉灶（模块需求文档不存在） |

**可拒绝情形**（接单方拒收）：查不到任务书依据（§1 / 清单）→ 拒收打回，不自行补造方向往下干。

### 8.2 委派治理

「该不该派 / 派什么 / 派出去怎么干」有门槛：小改父侧自做（判据句）· **工程角色（eng-coder / eng-designer）的任务书 = 批次档 §2**（零任务书文本参数——自由文本参数传入即拒并点名；§2 不够厚 ⇒ 打回，没有第二通道）· 非工程角色（explore / plan / coder）任务书 = 四项核心（`goal`/`knownFacts`/`acceptance`/`reportFormat`）+ `scope`（缺任一即拒）· `round` 仅 eng 两角色必带 · 禁「全量扫 X」。**结构**：门槛 + 单通道。

**工具面自解释**：结构化的约束要「用之前就能看到」，不能靠撞门来学。
- **任务书通道要可见**：工程角色 = 批次档 §2（零任务书文本参数，自由文本参数点名拒收）；非工程角色（explore/plan/coder）= 四项核心（`goal`/`knownFacts`/`acceptance`/`reportFormat`）+ `scope`；`round` = eng 两角色必带——这些必须在 `thincoder-core/tool-docs/subagent.md` 里写明，中文标签或英文等价形都行。机械门按参数面逐项判存在 / 类型 / 非空——不读内容。
- **档头要能填**：`batch` create 增加两个可选参数，`ledger`（台账编号）和 `board`（板块），建档时就把 `> 台账 = …` 这行填上；没给的话，回执里说清楚怎么补。
- **占位要能辨**：死占位扫描要分得清「占位没填」和「正文里引用了占位」。这条是自己踩出来的，讨论正文引到字面就被误杀。判据由设计定，不许放松成泛扫。
- 边界：只补可见性、可填性、可辨性这三样；门禁的标记集字面不动，判据修改只限「怎么区分没填和引用」；不加新工具。

### 8.3 纪律兑底

关键纪律靠**流程兑底**（收口核对清单）而不是堆机检（用户裁定：无限机检反感——M9 提示词机检已裁；锚检测待定）。**不新增纪律条文**（条文过多、执行不足）。**结构**：机检兕底（收口状态行、核销计数、交接路由——已落地者保留；提示词与机制档一致**不挂机检**——由收口核对兑底）。

### 8.4 提示词：代码单源

提示词 = **代码单源**（唯一副本 = `thincoder-core/prompts/`），规则的人读权威 = 中文机制文档：

- **规则本体**住中文机制文档（设计 / 需求档）——提示词只承载「怎么执行」
- **英文提示词 = 代码**（`thincoder-core/prompts/`）——机器执行物。

**流程**：提示词的任何修改**先改机制文档**（规则本体）；再由 **coder** 改 `thincoder-core/prompts/` 对应档（实现面）。

- **归属**：提示词 = **产品代码**（`thincoder-core/prompts/`）⇒ 唯一作者 = eng-coder（内容依据 = 机制文档）。

**无机检门**（用户裁定：无限机检反感；兑底 = 收口核对清单）。兑底核对清单四项 = `docs/core/requirements/ENGINEERING-MODE-V2-SPEC-PROMPT-PIPELINE.md` ②4（**D2 单一权威源——不重述**）。

### 8.5 评审与凭证（继承 v1 · 不取消）

设计文档出来 → 走 **advisor 设计评审**（用户发起）→ 通过后签发 **designToken** → eng-coder 持 token 实现。评审 + token 门是 v1 已验证可靠的机制，v2 **继承不取消、不重写**（只微调）。

### 8.6 测试纪律（简化 · 反过度工程）

v1 测试机制过度工程（三层分层 / 慢用例归册 / 多套脚本 / 退役台账），v2 大幅简化：

- **单元测试** = 开发期工具，改对代码即随批次档留存——**不处置、不删除**（与批次档同归档；**永不转集成**——`TESTING.md` F6 ∕ F8）；**不搞独立台账仪式**（料在档，零新增簿记）。
- **集成测试** = 项目资产——业务场景 + 生产问题补入，只断言业务可观察结果，常驻。
- **门禁** = 一条 `test` 全绿。

**砍掉**：慢测层归册（慢就慢，照跑）· run-fast / run-full / slow-gate 多脚本 · **独立**台账仪式（留存口径 = `TESTING.md` F6）。

**结构**：一条门禁命令，不建「管测试的官僚系统」。

### 8.7 机检引擎（简化 · 可迁移）

v1 三机检 = 必要内核 + 一大坨 thincoder 私有历史包袱（双引擎、三套源域、三套行宽判据、参照历史面豁免族、六档并入映射、V3 历史常量）。v2 砍包袱、留内核：

**留内核（普适判据）**：
- 锚检查：文档指针指到存在的档（引用可解析）——「文档不撒谎」的兜底；
- 行宽检查：单行 >300 字符（一条判据）；
- 台账一致性：由 SQLite schema 承接（check-ledger 作废）。

**砍包袱（thincoder 私有）**：双引擎（VSC/V5 两套）· 三套源域枚举 · V1/V2/V3 三套行宽判据 · 参照历史面豁免族 · 六档并入映射 · `V3_ERA_START` 历史常量。

**结构 = 一个引擎 + 声明面**：
- 引擎只留普适判据（引用可解析 / 行宽 / 台账 schema）；
- 项目特有的一切（扫哪些目录、豁免什么、阈值、参照面）→ 进 PROJECT-MANIFEST 的声明面（doc-root + 机检配置）；
- 换项目 = 改声明面，不改引擎脚本。

### 13.2 VSC 端镜像（FR23）

工程模式机制**两端同一套、各自实现**：batchDoc 门 / eng-designer 角色 / 行为纪律 / batch 工具 / V1–V3 机检 / 提示词（单一副本 `thincoder-core/prompts/`）——**语义同源于机制文档、原文自持**（不共用代码）；逐字一致的段在设计档定稿、实现面照抄不得自行解释；验收两层 = 机械面全绿 + **用户手动重载扩展后自验**（源码改动需重载才生效——「文件在了」≠「机制活了」）。

### 13.3 台账提醒与可见面（FR24）

把台账未决状态送到用户眼前——**有可动作项才出声，零噪音**：

- **状态行极简标记**：`台账 <需求池数>·<技术待办数>`，**按当前打开范围取值**——打开具体项目 ⇒ 只显该项目自己的数（不做兄弟合计）；打开容器根（其下含项目）⇒ 显示这些项目的合计（不可读项目跳过）；转警示色判据 = 老化 >0 ∨ 范围内有死执行者（全式单源 = `docs/core/design/LEDGER.md` §7.3.1）；两池分显不合计。
- **三处文本行**（落会话流可回看）：启动行（有可动作项才出）· 批次收口行（核销同步清单机械步骤）· 变化行（老化首次越线 / 需求池达阈值——事件驱动、一次性去重、**只在行真正落入会话流后才记账**）。
- **多项目判据**：当前项目 = 目录向上最近含台账者；项目集 = 当前 + 同级含台账者；明细行集 = 当前 ∪ 可动作项目。
- **数字单源**：解析/计数/老化/阈值一处实现，机检器与两端显示面共用口径。
- **零噪音与降级**：无可动作 → 零输出；台账不可读/坏档 → 降级不崩；headless 零新增输出；台账档只读。

设计见 `docs/core/design/LEDGER.md`（v2 SQLite 数据源——§7 可见面接口）。

### 13.4 文档体系各仓自持（FR25）

一个开发者同时维护多个产品时，任一产品的文档只承载自己的事项（事故溯源：跨仓登记外部产品线的债——内容层已清，机制层无闸；「能记一处就不写两处」= 同病两种形态）：

- **F1 台账射程**：台账（需求池 / 技术待办）只收本仓条目——禁登记本项目之外的事项；指针面收窄为**仓内可解析**。
- **F2 批次档同规**：批次档只登记本批范围（含本批的受影响文件与验收）。
- **F3 文档体系自持**：需求档 / 设计档 / 批次档 / 台账各自成套；**非复制**（语义同源、各端原文自持）。
- **F4 缺失层必须补齐**：缺的文档层就地补建——不得以「对端已有」「避免重复」为由省略；逐层成套。
- **F5 约束须落提示词层**：F1–F4 的行为面必须在提示词层落地——文档层是规格，提示词是代理运行期实际读到的纪律。
- **F6 机检闸**：台账条目的证据 / 指针路径须在**本仓内可解析**；违规一律 fail-closed（阈值 = 0）。
- **F7 核验职责**：同一机制跨多个实现面产出**一式多份设计**时，主 agent 有义务核验各份逻辑一致（核验四维 = 裁定同源 / 判据同一 / 边界同形 / 差异显式登记）；该职责须落提示词层。
- **F8 提示词通用化**：提示词中的多实现面条文不得绑死本产品两端；勘察 checklist 同步通用化。
- **F9 存量无豁免**：凡**触及对端**的存量批档一律处置（迁移 / 各仓持其份）；不得以「历史已收口 / 审计链 / 重复 / 量大 / 在飞」为由豁免。
- **F10 文档体系逐层成套**：各产品文档体系**逐层对位**；需求层**逐档三值齐备**（① 建本仓需求档 · ② 已有对位（允许异名）· ③ 本端无此面（写理由））；不得只建单层壳。
- **F11 需求层必须在本仓有档**：**需求层必须在本仓有档**——「对端有」「design 层有」不构成理由；**② 已有对位不得以 design 层充当**。
- **F12 结构档位硬限无豁免（适用范围 = 程序代码）**：>300 软线 / >500 硬限**仅约束程序代码（源 / 测试文件）**；**>300 软线 = 触发拆分评审**（方案登记 + 触发条件——非本批必拆）· **>500 硬线 = 超限档本批拆**；**文档（设计 / 需求 / 批次 / 台账）不受行数限制——无任何行数义务**（用户裁定）。
- **F13 对端引用形态零残留**：设计 / 需求 / 批次档正文引用对端产品文档一律**规范形态**（`名称（仓别）§N`）；存量不是合法态。
- **F14 先例不构成例外依据**：任何「以前也这样 / 已落形态 / 他批先例 / 存量在案」都不构成偏离规则的依据——**例外的唯一依据是判据句（可机判）**；找不到判据句 → 按规则办，或停下上报。**同条（残留即示范）**：合规形态必须显式；历史语义可保留、形态必须规范；「存量豁免 / 入基线」不得再设（阈值 = 0）。**同条（例外须带消解期）**：任何登记在案的例外必须写明消解路径与到期条件。

**非功能性**：N1 零假阳（机检新规则对本仓合法内容零命中）· N2 fail-closed · N3 可分步（存量迁移允许分期——每期有明确触发条件与逐档清单）· N4 否决在案（不得以「另有他档」为由放宽指针射程）。**两轴并列**：本节管**条目与归属**（轴一）；文档正文引用对端产品文档按既有 V1 边界规范（轴二）。

设计见 `docs/core/design/LEDGER-SELF-CONTAINED.md`（L4 判据 + 形态合规 V4）。

### 13.5 变更面分流（FR27）

任何改动动手前先判**变更面**：

- **三分面**：产品代码面（`thincoder-core/**` · 两产品 `{src,bin,webview,test}/**` · 产品文本面）= 走全流程；工程工具面（`scripts/**` · `.thincoder/**` · `.github/**` · `package-lock.json`）= 父侧可直改；文档面 = 按写权矩阵（D1）。
- **默认归类（fail-closed）**：未列入两枚举的路径一律按产品代码面处理——宁可走流程，不得默认直改。
- **直改三硬约束**：① 机械改 ⇒ 直改 + 改完实跑报读数 ② 改判据语义 ⇒ 仍走设计 ③ 凡直改 ⇒ 报告「父侧直接执行」+ 单笔可 revert。
- **授权判据 ≠ 绕过门禁**：门禁判定为准；与分流不一致 ⇒ 停下上报。

### 13.6 批次档生命周期（FR28）

六条判据（判定权 = 主 agent，子代理撞界 ⇒ 停下打回）：

- **界**：一批 = 一个交付目标 + 一组同批条目 + 一份批次档；交付目标变更 / 阶段跨越 / 条目集变更 ⇒ 另起新批新档。
- **护栏·长度**：单档 >1000 行 = 越界信号 ⇒ 另起新批。
- **护栏·轮次**：§5 修正轮上限 5 轮（触顶 ⇒ 本批自然边界）；§3 设计评审无轮次上限——触达停止判据（持续拒绝 >3 轮）⇒ 停下上报。
- **闭合/退役**：§6 收口 ⇒ 状态行「已收口 <日期>」+ 整档冻结（不回改；冻结档不迁移不删）；v2 机械兑底 = batch close/append 冻结拒写（`docs/core/design/BATCH-RECORD.md` §4.9/§4.13）。
- **收口前置·链完整性（用户 2026-10-18 18:47 裁定）**：`close` 与 `status → 已收口` 走**同一道**前置——§2 / §3 / §4 / §6 各段须有内容，或该段在 §1 以 `> 不适用：§N —— <理由>` 声明（仅 §2/§3/§4 可声明；**§6 不可声明**，收口段必须带验证内容；§5 段号豁免）。判空口径 = 段体内每行皆属「空行 / 标题行 / 状态行 / 模板占位 / 声明行」即判空（**「标题在、正文零行」须判空**）。不满足 ⇒ 拒并点名缺段。理由：无此前置时，链未跑完仍可标收口并永久冻结——缺口补不进、错标改不回。
- **重开路径（同上裁定）**：已收口档允许 `status → 进行中`，须携非空 `note` 作重开理由；工具在 §1 **段尾追加**一行 `**重开记录**：<日期> · 原收口 <旧日期> · 理由 = <note> · 操作者 = 主 agent`（只追加不改写正文，状态行单行改写；正文历史保留）。重开只恢复可写、**不冒充链已跑**——再次收口仍过链完整性门。
- **接续**：新批 §1 顶部前情指针 `前情 = docs/batches/<旧档> §N（已收口 <日期>）`。
- **护栏·暂缓复核**：暂缓（≠ 冻结）批必落**机读标记**（状态行 note 位携「暂缓 · 复核条件」句、值仍「进行中」；无标记不可枚举 ⇒ 违例）；复核 = 会话启动 ∕ 条件事件（报告 ∕ 交付入档、批收口、用户裁定）跑扫描、逐条对复核条件——满足 ⇒ 复启；对象消失 ⇒ 定去留（批档 §6 记「暂缓批复核」一行——无暂缓批记「无」；`docs/core/design/BATCH-RECORD.md` §5.1 L8 ∕ D-BR24）。

### 13.7 父侧轮次与提交纪律（FR29）

- **派发如实**：陈述「已派/在跑/已提交」⇒ 必须同轮发出调用；队列状态只能抄工具回执。
- **禁止零文本收尾**：每轮收尾必须给面向用户文本或显式进等待态。
- **写域声明**：`files` 只列内容产物（源/测试/设计档）；工程工具不入域。
- **提交纪律**：提交路径限定（`--only`）；不代提交用户/他人的档；归因先想「可能是用户在写」。
- **修正轮派单必写三句**：① Suggestion 列 = 评审员建议、处置执行人 = 你 ② 按发现号逐条改、报告「号 → 改动 file:line」 ③ 明写「本轮不做」清单。
- **父侧不代笔**：设计档落笔一律派修正轮给 eng-designer；需求档归主 agent 写，落笔前提 = 需求确认门。
- **Suggestion 列形态**：只写改法、不写执行人——禁「由主 agent 收正」式归属句。

### 13.8 台账用法面教学（FR30）

**射程**：本项只管**用法面**——工程模式（主 agent）「**何时动账**」。**常识面**（台账是什么 / 谁读写 / 六态 / 存哪）= 全角色系统常识 ⇒ 需求住 `docs/core/requirements/PROMPT-SYSTEM.md` §2.3（第 13 节「台账常识」），本档不复制（D2）。

台账要被用得对，光有机制不够——模型得知道**什么时候动它**。用法面 = 生命周期**事件 → 动作**绑定，五条：

- ① **批点火** ⇒ 状态推进（待讨论 → 待设计 → 在途）+ `task_book` 指针；
- ② **实施核验通过** ⇒ 在途 → 待核销 → 已核销，核销须**证据回写**（落点坐标 + 结账依据）；
- ③ **批收口** ⇒ 勾销核对（D7 收口行由「读数」升为「动作」）；
- ④ **发现新债**（停下上报产物 / 评审发现 / 文档漂移）⇒ **当日入账**，`trigger` 必填；
- ⑤ **上抛事项**（子代理 / 评审 / 停下上报递到父侧）⇒ **当场裁定**——能收正的**同轮收正**；不能收正的**当日入账**（`trigger` + 到期条件——落 `evidence`）；**禁止只留在报告散文或「待裁」清单里**（到期条件**非枚举文本**，落字段 = `evidence`）。

- **落点**：`thincoder-core/prompts/persona-engineering.md` 台账节——**不落 `thincoder-core/prompts/discipline-engineering.md`**（该档 eng-coder / eng-designer 也读，而台账写权仅主 agent，写入＝误导子代理）。
- **边界**：不为此加机械门（承 2026-09-18「为臆想的失败逐点加限制」= 反模式之裁）· 不重写攒批工作流本体（只补「时机」）· 普通模式暂不写「何时推进 / 核销」（**普通模式无结构强制链**——核销语义不同）· 子代理不教写账动作。
- **验收**：① 文档面可机检——`thincoder-core/prompts/persona-engineering.md` 含「事件 → 动作」**五行**判据 · 提示词面（`thincoder-core/prompts/`）语义一致（M9 单向机检已裁撤 ⇒ 收口核对兜底）· 新增行无超宽（≤300 字符）；② 行为面（**观察项，非机检**）——下一批的生命周期里，推进 / 核销 / 入账由模型**自主**完成，无需用户推动。

### 13.9 工程模式 plan 面排除（FR31）

**背景**：工程模式主 agent 的职能本身即「设计先行」（设计 → 评审 → 批准 → 实施）——plan 模式与其**语义重叠**，且其退出话术（`PLAN_EXIT_REMINDER`："Start implementing your plan … No need for … further confirmation"〔该文本 = 「呈计划 ⇒ 待批准 ⇒ 实施」〕）与工程链条**直接冲突**。
实测（用户观察）：glm-5.3-flash 等模型在工程模式下频繁进入 plan 模式 ⇒ 系统性误导源。

**需求（三条）**：

1. **排除形态 = 工具不注册**：工程模式下 `plan` 工具不进工具表（模型不可见——「看不见的选项不会被选」，优于「注册但报错」的干扰回合）。
2. **命令面同步禁**：TUI `/plan` 与 ACP plan 模式设置在工程模式下禁用，且给**明确提示**（非静默失败）。
3. **残留清零**：会话中途开启工程模式且 `planMode` 已为 true ⇒ 强制复位（防「工程纪律 × plan 只读限制」半状态叠加）。

- **边界（不做什么）**：普通模式零改（plan 模式照常全带宽）· **两条** reminder 文本本体不改（`PLAN_FULL_REMINDER`/`PLAN_SPARSE_REMINDER`——`thincoder-core/agent-tools/plan.mjs:11` · `:17`，普通模式仍用；`PLAN_EXIT_REMINDER`（`:21`）文本已收正）· 不为此新增机械门。
- **待设计实核**：工程子代理面是否随同排除——`plan` 工具现居固定段（`thincoder-core/agent/family-tools.mjs:173`，全模式全深度注入）；同类过滤先例 = 同档 `:44-49`（角色 enum 互斥）· `:66-67`（escalate 池装饰门：`action: (consultModels.length && !engineering)`——实读注释同句「装饰只对正常模式有意义」）。排除面矩阵由设计段实读后定。
- **验收**：① 工程模式装配面不含 `plan`（机检断言 · 双端同源核）；② `/plan` 与 ACP 面在工程模式下拒绝且提示可见；③ 开启工程模式时 `planMode` 强制 false（测试锁定）；④ 普通模式全带宽零回归。
- **落点**：装配面 = `thincoder-core/agent/family-tools.mjs`（裁剪形态由设计定）；命令面 = `thincoder-cli/src/tui/cmd-plan.mjs`（`/plan` 切换点）· `thincoder-cli/src/acp/handlers-session.mjs`（会话模式设置）；VSC 对位面 = 设计段实核。

### 13.10 批准即实施启动（FR32）

**背景**：用户报告（2026-10-19）：实例把用户对设计的「批准」读成「设计文档过关」，另等一句「开始」才派工，白耗一轮。规则原文只有两步——评审之后的明确签核解锁 eng-coder，**解锁即开工，没有第三步**；提示词面缺一句等价声明，同段几句叠读可被读成「批准后还要再等一次放行」。

**需求（四条）**：

1. **等价声明**：工程模式下，用户对设计的批准——或任何表达同一意图的等价表示（判据 = 意图，不是词表）——**即实施启动**：父侧当场 spawn eng-coder，不等第二句「开始」。
2. **唯一停相**：只有用户在批准时明确说「先别动 / 只批设计」（或等价表达）父侧才停；未说即默认派工。
3. **不豁免既有边界**：「设计评审只能由用户发起」照旧；设计讨论中对形态 / 选项的点头仍是需求确认、不是设计批准——该判据在评审通过后的批准门上生效，与此条不冲突。
4. **携 why**：提示词文本说明理由（批准 = 授权落地，解锁就是派工；再等一句只白耗一轮），不用禁令腔（用户 2026-10-17 裁定：要知其然知其所以然）。

- **边界（不做）**：不改批准门机制本体（token / 门禁 / 凭证生命周期）· 不新增机械门 · 不改普通模式 · 不动「评审 digest 是机器信号、不是放行」条（该条管评审 digest，与用户批准是两件事）。
- **验收**：① 工程主人格档有显式一句：批准（含等价表示）= 实施启动、无第三步、唯一停相；② 该句携 why；③ 与既有三句（评审发起权 / 点头 ≠ 设计批准 / digest 非放行）逐句对照无矛盾——对照结论记入批次档；④ 逐字稿与落盘提示词一次性比对全等。

### 13.21 推断不许当事实（FR43）

**背景**：用户 2026-10-22 11:39「当项目大的时候，agent 经常出拿推断当事实的问题」；11:44 否掉「本会话内」这个界（会话会被压缩、重启、被子代理绕开——划不出边）；11:45 定「只有当轮读有意义」；11:47 要求关键处少量关键约束，不要一整套措辞。

**三条约束**（现提示词已有「要么给 `file:line`、要么标 `unverified`」，缺的是可判的界，不是更多措辞）：

1. **依据 = 本轮读到的整行，抄得与现文一致**；抄不出就写 `unverified`。为什么：轮有硬边界——一条用户消息到一条回复，整行能被复核者对上；「上一轮读过」只剩记忆，与推断无从区分。
2. **摘要、子代理回报、长期记忆是线索，不是依据**；拿它做决定之前回原档重读，做不到就标 `unverified`。为什么：它们是派生物，原档一改就过时，而它们不会自己说「我过时了」。
3. **决定面必须带依据**——设计取舍、验收、收口、派单任务书、评审结论五处；非决定面可以不标，被引用进决定面时继承这条要求。为什么：复核只能复核有形的东西；决定面错了要重做，其余错了改一句话。

**落在三处**：`thincoder-core/prompts/common.md` 的 Evidence discipline 段把这三条写成能判的形（现有总则保留）；同档 `## Check the docs before you ask` 段的 checked-evidence 行补上「逐字一行」——提问那一刻适用的是同一条规则（查到写 `file:line` + 本轮读到的那一行逐字抄录；查无写「checked, nothing relevant」并点名查了哪个面，省得把「这个查询没命中」说成「没有」）；`advisor` 判据加一条——决定面无依据记 🟡。

**验收**：① 提示词面含上述三条 + checked-evidence 行的「逐字一行」（子串机判）；② 评审判据含「决定面无依据 ⇒ 🟡」。

### 13.22 机检是下限，不是目标（FR44）

**背景**：用户 2026-10-22 12:03 指出，文档行宽那条机检本来是为了保证人能读下去，结果实际效果是所有人都在想怎么过机检。

**这件事是怎么发生的**：机检只能数可以数的东西。行宽这条数的是「一行有多少字符」，它想代表的是「读者读起来累不累」。两者平时大体同向，一旦被当作考核，就会分开：读的人看到的是渲染后的段落，而段落在屏幕上会自动折行，所以把一段文字按三百字敲几个回车，源码行行达标，读者面对的仍然是同一团文字。

到这一步，机检就不再是下限，而是一门需要应付的考试。更麻烦的是它会自己长出规则来：本会话里，设计档为了解释「围栏八行」与「加六行」的出入，专门补了一条「落地形态」的规定，而那条规定存在的唯一理由，是让行数对得上。

**写的时候该怎么处理**：一段读不下去，先看它为什么读不下去。多数情况不是字多，是句子把好几件事串在一口气里——条件套着条件，主语隔了半句才出现。这时要重写，不是断开：把主句提到前面，把条件挪到后面，一句说一件事，长定语拆成两个短句。字数常常不减，读者却读得下去了。

把一段切成两段，如果句子本身没变，那只是换了个断开的位置。读者读到的还是同样绕的句子，中间多了一次换行而已。为过行宽而插换行更是如此：它改变的只是源码看起来的样子。

删字要分清两种。删掉重复、垫话、自我限定，读者读得轻松，知道的一样多；删掉一个条件、一个例外、一个坐标，读者确实轻松了，但少知道一件事。

**读数与判断要分开**：「最长段落多少字」这个读数，代理的是「这一段要不要拆」。读数与判断背离的时候——拆完之后仍然很长，或者字数达标但读不下去——改判断，不要改读数。把代理量当成目标之后，接下来所有讨论都会围着代理量转，而读者关心的那件事一次也不会被讨论到。

**一条只为机检存在的规则，应当删掉**：规则的读者是人。如果一条规则的实际效果只有让某个计数器通过，它就是在把成本转给后来读文档的人。这种规则还会自我繁殖：下一处同类矛盾出现时，大家照着先例再补一条，于是文档越来越像一份合规文件，越不像一份能读懂的东西。

**落点**：`thincoder-core/prompts/common.md` 的 `## Simple and clear` 段，写成一到两句英文，把上面那层因果带上：机检数得清的是行，数不清的是读者读不读得下去；两者背离时，按读者办。

**不做的**：不取消机检，它仍要拦住「一行两千字」那种极端情况；不改三百这个阈值，阈值是另一件事；不为本约束新增机检，「这句话是不是冲着计数器写的」机器判断不了。

**验收**：`thincoder-core/prompts/common.md` 的 `## Simple and clear` 段含上述意思的英文形；此后新写的设计段落，不再出现「为过行宽而折行」这种处理方式。

### 13.23 判据的单位是段，名字要说出真正的问题（FR45）

**背景**：用户 2026-10-22 12:09 指出，「行宽超标」这个说法本身把问题说错了。真正让人读不下去的，是一段文字太长，读者一口气读不完；而「行宽」说的是排版。名字错了，处理方式就跟着错：折行能把行宽治好，段落还是那一段。

**这件事在本次会话里的代价**：设计档为了凑行数，要求实施席把三段英文各写成「一整行」；三整行撞上行宽判据，整批被门拒写；随后又要为提示词面开一条路径豁免。一次命名错误，生出了三条补丁。

**判据**：

1. **单位是段，不是行。** 把相邻的非空正文行合并成一段（表格、标题、列表、引用、围栏不计），量这一段的字符数。为什么：读者看到的是一段文字，不是源码里的换行；合并之后，中间敲多少回车都不改变长度，能过判据的办法就只剩「把段落拆开」和「把话写短」。
2. **名字说出问题本身。** 常量 `paragraphMax`、模块 `paragraph.mjs`、报面「一段太长 N 段」，不再出现「行宽」。为什么：判据的名字是写作者唯一会记住的部分；名字指排版，人就去调排版。
3. **阈值 300 字符一段。** 用户 2026-10-22 12:12：「一段 300 字其实已经挺长的了，800 字够一篇作文了」。为什么不再放宽：阈值一放宽，清不动的存量就会换来豁免，而豁免一加，判据又变成可以绕的东西。
4. **存量与新增分域判。** 现行存量里超过 300 字符的段落有 1,992 段（2026-10-22 实测，333 份文档）；判据上线后，gate 只对「本批笔域」内的命中拒写，存量只点名、不计入拒因。为什么：不分域的话，任何一处改动都会被两千段历史债挡住，最后一件事也做不成。这一条与台账 `#1734` 是同一件事的两半。

**落点**：`thincoder-core/doc-check/width.mjs` → `paragraph.mjs`（算法换、名字换）；`thincoder-core/doc-check/index.mjs` 的常量与报面；`thincoder-core/doc-check-*.mjs` 与 `scripts/doc-check*.mjs` 的接线；`docs/core/requirements/DOC-CHECK.md` 的对应判据条；

  `docs/core/design/DOC-DISCIPLINE.md` 与 `docs/render-core/design/RENDER-CORE.md` 中引用「行宽」的口径句。

**不做的**：不改锚判（那是另一件事）；不在本批清存量（另批，按板块分批清）。**提示词面不设豁免**——用户 2026-10-22 12:23「提示词面更需要！」、12:24「提示词执行情况已经很差了，你再豁免下去，这个产品就死掉了」。

**为什么两面的「块」定义不同**：过渡豁免（行宽判定跳过 `thincoder-core/prompts/**`）已撤。**两面的「块」定义不同，理由在读者**：文档面由人读渲染结果，相邻非空行会并成一段，所以量段；提示词面由模型读原始文本，一行就是一个块，所以量行。同一份提示词实测 290 行超 300 字符，最长 1,486（`thincoder-core/prompts/persona-engineering.md:104`）——这是模型每次执行都要读的东西。

**验收**：① 引擎常量与报面里不再出现 `lineWidth` / 「行宽」；② 同一份文档，人为在段中插入换行后判定结果不变（折行失效的机判）；③ 一段 900 字符、分成三段的文字判为合规（拆段有效）；④ 存量命中数在同一份文档上比旧判据更少（单位变粗，假阳性下降）。

### 13.24 提示词面一条规则一行（FR46）

**背景**：模型读的是提示词的原始文本，一行就是一个块。实测 16 档里有 290 行超过 300 字符，最长一行 1,486 字符（`thincoder-core/prompts/persona-engineering.md:104`）。用户 2026-10-22 12:28：「你让一个 MoE 模型去看一端 3000 多字的提示词，它能看明白啥？」

**问题是怎么产生的**：一条规则常常和它的理由、例外、反例写在同一行里，靠分号串起来。写的人一次想说完，读的人却在一次前向里同时面对七八件事——哪句是规则、哪句是例外，没有边界可依。行长越界只是症状，真正的代价是模型按印象办事。

**改法（用户 2026-10-22 12:31 认可）**：重写，不是折行也不是切段。一条规则一行，行首一个短语点题；条件与例外放在规则之后，能独立成行的就独立成行；理由单独一行并以 Why 起头。

**三条手法（对没见过的行也适用）**：第一，每个处置给一个词，词后紧跟一句定义——词是检索单元，定义只解释这个词。第二，加粗只落在每行的题眼上；满行加粗等于没有重点。第三，需要回查的指代要改写或删除——读的人拿不到「那条规则就在附近」的保证。


**只写动作，不写组织**：提示词里只留「你不能动什么」这类动作约束；「谁拥有什么」的写权矩阵是产品侧的组织信息，住设计档与需求档，不进提示词。理由：组织信息会变（2026-10-19 取消中文设计面就是一例），变了以后提示词里那句短的旧话没人替它发现——它既不超长、也不含档名，两道门都看不见。承接者的提示词写「你能动什么」，派单者的提示词写「把某类档派给谁」——同一张矩阵，两种用法，各写各的那一半。

**同一理由延伸到数量与配置值**：并发上限、阈值、档数这类随配置变的数字，家在配置与设计档；提示词只写「按本会话配置读」和「怎么判」，不写具体值——写进去的是一份没人会去更新的副本。
**内容边界**：规则、条件、例外、理由四类必须保留，改写前后逐条对得上；指代、装饰性加粗、自我限定可以删。样板里删掉「the dual of the opening self-check」就是按这条办的——它是指代，不是内容。

**判据（取自改写前后的实例）**：`thincoder-core/prompts/persona-engineering.md:104` 原文 1,486 字符一行，改后 6 行。需求稿记的「最长 312」是初稿读数，设计稿把六行收到 130 / 213 / 200 / 252 / 183 / 288（最长 288 ≤ 300，父侧逐行复算过三行、与设计稿一致）——**样板现在过线了**；验收线 300 不变。

**两舱（16 档分两批，单舱 ≤15 档）**：甲舱 = 7 档 persona-* + 2 档 discipline-*（9 档）；乙舱 = `thincoder-core/prompts/common.md` + 4 档 advisor-* + `thincoder-core/prompts/consult-base.md` + `thincoder-core/prompts/subagent-base.md`（7 档）。甲舱先行，理由是 persona 与 discipline 每轮都读，读错的代价最高。

**实施顺序（硬前置，不许跳）**：

第一步，先由一个实施席**单独改完 `thincoder-core/prompts/persona-engineering.md`**（78 行，最长那档），交「改前 / 改后」对照与本档行长读数。父侧逐行核，用户过目。这一档从此成为往后每一档的比对样板。

为什么必须单做一档：重写是语义活，四个实施席会读出四种理解。样板没定就铺开，四份产物会长得不一样，而「不一样」在提示词里不是风格问题——它是模型每次执行读到的东西不同。

第二步，样板经用户确认后，其余档按舱并行，单批不超过引擎容量（本机 `agent.poolLimits.engCoder` = 12，实测值），每席一到两档。每份任务书必须带同一张尺子：行首短语点题 · 条件与例外在规则之后 · 理由独立成行且以 Why 起头 · 加粗只落在题眼；红线是四类内容（规则 / 条件 / 例外 / 理由）不得丢。

第三步，并行段结束后跑一次**横切检查**，逐档干净不等于整体一致：① 一次性脚本量 16 档逐行 ≤300；② 每档抽前 10 行比对形态是否同构（题眼加粗 + 冒号定义）；③ 每档交「原文行 → 新行」四列映射表，父侧抽查最长的那几行。

为什么要有第三步：并行产物各自合规，但可能 A 档写成三段式、B 档写成两段式。这种差异单看任何一档都看不出来，只有横着切才看得见。

**第四步：改完之后再查一轮（用户 2026-10-22 12:45 要求）**：

改写是语义活，边改边看只能看见自己那一行。所以全部改完（或每舱改完）后单独走一轮复查，不与被改的那一轮合并——写的人和查的人视角不同，同一轮里查，查出来的只会是「我写的时候想的那件事」。

这一轮查五类：

1. **改坏了没有**：逐档抽最长的十行，把「原文行 → 新行」摆在一起读，看规则、条件、例外、理由四类是否各自还在；有缺的，指到具体行。
2. **有没有长出原本不存在的东西**：新写的行里如果出现原文没有的约束，那就是实施席按自己的理解补的规则——提示词多一条约束，模型就多一条要守的东西，所以这条按缺陷算，不按润色算。
3. **形态是否同构**：每档抽前 10 行比对（题眼加粗 + 冒号定义 + 一行一件事）。各档自洽但互相不同构，等于给了模型两套写法。
4. **指代有没有留活口**：改写时删掉的指代（「见某某节」「与另一条规则对称」）如果还有残留，模型会去找一个它读不到的东西。
5. **口径不一致的地方**：本批牵动的相反口径（提示词面是否受行界约束 · 行数是否作断言 · 操作数是否算指针）按**判据句族**全仓扫一遍——不是按我记得的那两句扫。扫出来的每一处，要么改掉，要么在批次档里写明为什么留着。

复查由**没参与改写的人**做（评审席或独立 explore），产出按行给读数；父侧抽查其中最长的那几行。

**先例 ∥ 偏离**：先例 = 本档 §6.43 ∥ §6.44 的改写形制（一条一行、题眼加粗、理由独立成行）。偏离 = 提示词面自此受行界约束；此前相反的口径仍活在 `docs/core/design/PROMPT-SYSTEM.md:476`（「提示词档不在行宽机检域……新行 406 字符不折行」）、`:2818`（「行数不作断言」），本批的连带收正要把这两处改掉——两套口径并存，读者判不出哪份为准。

**勘察证据行**：`thincoder-core/prompts/` 16 档实读（行数/最长行，逐档见设计档表）；`docs/core/design/PROMPT-SYSTEM.md` §6.40–§6.44 的改写形制；`thincoder-core/doc-check/` 现为 `width.mjs`（无 `paragraph.mjs`）⇒ 本批的行长读数用一次性 `node` 脚本取，不依赖引擎改造。

**不做**：不改规则的语义与判据强度；不新增规则；不为过判据而删内容；不把理由挪走（理由仍要跟着规则，只是独立成行）。

**验收**：① 两舱各自每一行 ≤ 300 字符（一次性 `node` 脚本读数，改前改后各取一次）；② 语义对账：逐条给「原文行 → 新行」映射表，四列（规则 / 条件 / 例外 / 理由）**每列都要有判断**——该列没有内容时写「—（本条无）」，不许留空串，也不许为凑格编出一条（编出来的例外就是新增规则）；③ `prompt-refs-check` 命中 0；④ `docs/core/design/PROMPT-SYSTEM.md` 的相反口径已随本批收正（按**判据句族**扫全档，不是按两句原文串）。

### 13.25 动手前先查文档（独立规则 · FR47）

**问题**：现有的「先查文档」只在两种场合触发——**要提问时**（`thincoder-core/prompts/common.md:17` 那节）与**与文档冲突时**（指令优先级梯子第 4 条）。最常见的一种没有覆盖：用户给了一条指令，既不是问题、也不明显冲突，但它的正确做法写在文档里。模型照字面做完，没有违反任何一条现有规则，却做出一份与既定不一致的实现。

**用户裁定（2026-10-22 13:58）**：「要有条独立规则。」——不并进现有半句，因为它和「提问之前」是两个触发点，藏在半句里模型只会记住前者。

**规则（平实说法）**：动手之前，先看一眼这件事现在是怎么做的——接口、约定、以前定过的决定。用户的话说的是「要什么」，文档和代码说的是「它现在怎么运作」。

**为什么（四层，按落地顺序）**：

1. **你手里只有一部分**：一次会话完成的只是一个庞大任务中的一步，眼前的对话与打开过的几个文件，只是项目已知内容的一小部分。文档与代码是把其余部分带进来的路。
2. **把局部当整体**：只凭看得见的那一部分动手，就是把一片当成全部。每一处读法都可能对，整体仍然错（用户原话：「只知局部，不知整体，行动就是盲人摸象」）。
3. **为什么没有东西提醒你**：没有冲突、没有说不清的点，所以没有任何信号。等你发现，是评审时看到 diff 和一份自己没打开过的文档对不上。
4. **代价**：代码只记「是什么」，理由与后果住在文档里。一个决定可能撑着一条没有测试覆盖的要求——盲改之后，它护着的东西没了，而没有任何东西会报出来（Nygard，《Documenting Architecture Decisions》，2011-11-15）。

**文档沉默时怎么办**（这半句必须有，否则规则会退化成「查不到就不动」）：照做，并说清你看过什么——搜了什么、翻的哪份档、读的哪段代码。查过没查到，这个结果本身也值得说出来。

**边界**：不改指令优先级梯子（那管冲突，这条管动手前）；不要求每次动手都长篇查证——查的是「这件事的做法有没有已经写过」。

**落点**：`thincoder-core/prompts/common.md`——挂该档的七个场景（engineering / normal / eng-coder / eng-designer / explore / coder / plan）；advisor 与 consult 用自含基底，不在本规则射程内。

0. **灵魂**——「靠结构是对的」（「约束即结构」= 指导思想）。
1. **角色分工没定义**——「对每个角色定义和分工还没有定义清楚，该干什么、不该干什么、该怎么干、不该怎么干，没说清」。
2. **纪律没执行**——「工程纪律也没有良好的执行，比如你刚才盘查就发现了，提示词代码比文档要新」。
3. **交接接口没规范**——「各个角色之间，下的指令也没有个规矩，没有交接的规范，比如怎么会把排查任务下给 eng-coder？一个瞎下，一个瞎收，他也没拒绝」。
4. **没有阶段感**——「现实中的工程是有不同的阶段的……初始开发阶段的项目，和已经上线再持续运行中的项目，要求和做法肯定是不一样的」。
5. **没有入口差异**——「从头开始用工程模式开发的项目和半截开始用工程模式的项目也是不一样的，半截开始肯定要经过一个梳理阶段」。
6. **没有轮次差异**——「耗时巨大，排查面过宽，而且也没有区分初始轮和修复轮……修复轮一点点小事都会用一两个小时」。
7. **委派滥用 + 命令含糊**——「eng-designer 和 eng-coder 滥用的情况也比较突出，一点点小事就甩给子 agent，给的命令还含糊不清」。
8. **提示词修改无规矩**——「提示词修改现在很没规矩，直接就该代码了，我们要明确设计文档中的提示词模板是权威源，更新流程要明确下来」。
9. **文档结构**——「你不觉得现在这样的结构看着特别费劲吗」→「我是说整个文档的结构」。
10. **文档写作约定**——「需求和设计文档该怎么写，其实也是应该约定好的」。
11. **双账是核心**——「批次档和台账其实是核心，是整套逻辑的运转核心，被当作产物写，太不重视他们的作用了」。
12. **项目状态档**——「缺一个项目状态总览的核心档案」「工程模式下必须要先有这个项目状态档，如果没有，那就要初始化生成出来……盘清家底」。
13. **项目方法论**——「主 agent 是 thincoder 与用户交互的主要界面，但是应该如何跟用户沟通，其实还缺乏一套标准的方法」「立一个专门的章节写项目方法论」。
14. **项目两分**——「研发项目，你的用户就是需求的主体……委托开发项目不一样，你的直接用户并不是需求的主体，真正的主体是委托方，你的用户跟你是一起跟甲方沟通」。
15. **委托开发五支柱**——「委托开发项目是有甲方、有预算、有项目周期的，有沟通体制，有风险控制机制的」。
16. **找对人**——「沟通机制上最重要的是要找对人，正确的事情跟正确的人说」+ 甲方四类人定义。
17. **项目启动建角色表**——「项目启动的时候，我们通常会立即整理一张表，按照业务和模块把对应的人都找到……如果一个项目说不清楚这些角色具体是谁，那这个项目失败的概率就是 100%」。
18. **接手先盘信息**——「甲方是谁？项目的目标是什么？有没有之前给他们的提案？内容是什么？项目的周期是多久？甲方 pm 是谁？」。
19. **内部消化出问题清单**——「先跟销售之类的人沟通……准备出下一步需要调研的问题清单，能内部澄清的先澄清，澄清不了的留待跟用户接触后继续澄清」。
20. **见 PM 问目标/周期/里程碑**——「先跟甲方 pm 进一步了解对方的项目需求信息，目标是什么？周期？里程碑」。
21. **生命周期与成果物**——「需求调研和设计 → 开发 → 测试 → 上线后持续运营」+ 方案/计划/交付物清单 + 测试报告/集成测试报告。
22. **验收=对交付物清单签收**——「设计阶段我少说了一个文档：交付物清单。验收其实就是对着交付物清单，逐项让甲方签字确认收到，全签收了那就是验收过了」。
23. **交付物清单是交付标准**——「交付物清单甲方不签字不确认以后怎么做交付标准啊」。
24. **沟通机制**——问题驱动找对人（功能→FO，使用→KBU）+ 日报。
25. **风控**——进度偏差 + 低/中/高分级（锚定对进度的影响）+ 应对（低记录/中告知 PM/高风控会）。
26. **持续运营**——「bug 报告和修复……只要有机制报告和记录 bug 能做后续处理就行了」。
27. **预算边界**——「预算不是我们技术人员管的事情」。
28. **研发=现行机制本体**——「研发类型的项目就简单多了，基本上就是我们现行的这套工程模式机制」。
29. **文档体系两层**——项目需求（七层）+ Function Spec（「交给 designer 的应该是 function spec 这个级别的文档，而不是项目需求」）。
30. **设计也两层**——「设计档其实也应该是两层，总体文档 + 一个模块一份的设计」。
31. **模块划分权威源=架构设计**——「没有经过设计考虑的模块划分是不成熟的」。
32. **名称中英对照**——「现在这些名称中英文混杂，都需要中英文都有」。
33. **目录约定+默认值**——「这些文档放在哪个目录里要确定好」+「要有默认值」。
34. **每个 git 仓一份 manifest**——「project-manifest 应该放在项目根目录，cwd 根目录不对」+「每个仓库建一个 project-manifest」+「判断 git 目录很难吗」+「不要向上找」（判据 = .git 纯向下——锚自身仓 → 自身；否则向下找唯一带 manifest 的子仓）。
35. **manifest 用 JSON**——「决策我觉得不应该进，那应该是文档层面的事儿」→ JSON 纯机器状态。
36. **批次档用 md**——「批次档 md 可以」。
37. **台账进 SQLite**——「台账我一直有个想法，这个应该进数据库，否则并发写真的太多冲突了」+「查询命令是要的，md 可读面就算了」。
38. **checklist 废除**——「checklist 是不是就没必要了？台账应该能替代」。
39. **落地分期**——「不需要第一步就做委托项目，先把研发项目做实」。
40. **测试过度工程**——「现在的测试机制过于复杂，过度工程严重」。
41. **机检过度工程**——「这些机检有没有过度工程？」→ 砍私有包袱，留一个引擎+声明面。
42. **评审不取消**——「设计文档出来以后走文档评审还是要的，没说取消啊」。
43. **需求档七层**——「这三层你觉得够吗？反正觉得不够」→ 扩到七层。
