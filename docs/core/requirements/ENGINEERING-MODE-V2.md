## 1. 定位与灵魂

工程模式 v2 是**工程模式机制本身的一次重构**——不是加几条规则，是把机制的哲学从「靠自觉」翻转到「靠结构」。

**灵魂：约束即结构（Constraints as Structure）——不靠自觉，靠结构。**

v1 把纪律写成「期望」：角色边界写在提示词里（模型可无视）、纪律写在文档里（漂移无人拦）、交接靠自觉（该拒的不拒）、委派靠心情（想派就派）。全指望对方记住，于是会漂移、会滥派、会瞎收。

v2 把纪律从「文字」变成「机器」——**能靠结构拦的，就不靠人记；让对的路成为唯一好走的路，让错的路被结构挡住。**

**判据句**：每一条纪律，必须能回答「靠哪个结构兜底？」——答不上来的，就不是 v2 的纪律，是 v1 的期望。

## 2. 为什么重构（v1 八块痛点）

1. **角色分工没定义**——该干什么、怎么干、边界，没说清（需求/设计阶段最乱）。
2. **纪律没执行**——有规矩没人守、没兜底（提示词代码比文档新 = 活例）。
3. **交接接口没规范**——指令怎么下、该不该接、怎么拒，没契约（排查任务派给 eng-coder = 活例）。
4. **没有阶段感**——初始开发 vs 上线运行，要求做法一刀切。
5. **没有入口差异**——从零接入 vs 半截接入，半截该先「梳理」，现在没有这一步。
6. **没有轮次差异**——初始轮 vs 修复轮一刀切，修复轮小事也 1-2 小时。
7. **委派滥用 + 命令含糊**——小事甩子代理，命令还说不清（「全量扫 X」）。
8. **提示词无单一权威源**——直接改落地代码，绕过设计文档模板。

共同根：**纪律被写成期望，而非结构。**

## 3. 机制全貌

一条流水线串起整个机制：

```
阶段（初始开发 | 上线运行——决定纪律重心）
   ↓
批次循环【开批 → 设计 → 评审 → 裁决 → 实施 → 收口 → 冻结】
   ↑_____________________________|
   （一个交付目标 = 一批，批界命中即另起新批）
```

- **运转核心**：三账（项目状态档 > 台账 > 批次档——见第 5 章，整机制围绕它们转）。
- **角色**：主 agent（对话面，贯穿全程）· eng-designer（设计段）· advisor（评审段）· eng-coder（实施段）。
- **文档**：需求档、设计档（写作约定见第 6 章）。
- **规则**：交接契约、委派治理、纪律兜底、提示词单向生成（第 8 章）。
- **情境**：阶段、轮次——两把「调轻重的旋钮」（第 9 章）。

## 4. 项目方法论（主 agent ↔ 用户沟通方法）

> 主 agent 是 thincoder 与用户交互的**唯一界面**，但「怎么跟用户一起做项目」不能靠零散规矩——要有一套融合传统软件开发项目管理经验的标准方法。**本章指导主 agent 的一切沟通行为。**

### 4.1 项目两分（需求主体不同）

项目从某个维度上可以分成**研发项目**和**委托开发项目**，两种项目里「需求的主体」是不一样的：

- **研发项目**：用户就是需求的主体，你跟他是甲方乙方的关系——他提需求，你落实。
- **委托开发项目**：你的直接用户并不是需求的主体，真正的主体是**委托方（甲方）**；你的用户跟你**一起跟甲方沟通**。

沟通方式不能一刀切：研发项目「听用户的话」就行；委托开发项目里，用户是战友，主 agent 要**帮着用户一起向甲方**澄清需求、出方案、扛责任。

**两套阶段观对应两种项目类型**：委托开发 = 纵向交付生命周期（调研设计 → 开发 → 测试 → 验收 → 上线运营）；研发 = 产品成熟度（初始开发 → 上线运行）。

**分层关系（关键）**：**研发项目** = 本档第 5-11 章描述的机制本体（需求 → 设计 → 评审 → 实施 → 收口，三账，角色分工）；**委托开发项目** = 本体之上**多套一层「项目方法论」**（本章 4.2-4.8），因为多了一个「甲方」这个外部实体，沟通与风控都不一样。研发项目用本体，委托开发用「本体 + 方法论增量」。

### 4.2 委托开发五支柱

委托开发项目有：**甲方、预算、项目周期、沟通体制、风险控制机制**（其中**预算不是技术人员管的事**——主 agent 不碰预算，归 PO/商务）。

### 4.3 找对人（甲方四类人）

沟通机制上最重要的是**找对人——正确的事情跟正确的人说**。甲方的人分四类：

| 角色 | 是谁 | 跟他沟通什么 |
|---|---|---|
| **甲方项目经理（PM）** | 负责跟乙方对接、协调项目活动 | 进度、协调、活动安排 |
| **Project Owner（PO）** | 为项目买单的人 | 目标、预算、重大取舍 |
| **Function Owner（FO）** | 决定某个模块要做什么、不做什么，通常是甲方某块业务的负责人/部门经理 | 该模块的需求、范围 |
| **User / KBU** | 你开发出来的功能的真正使用者，职位最低，但却是更高阶人员对你成果评价的信息来源；User 很多不可能都跟你对接，KBU 是用户的代表，通常是业务骨干 | 真实使用反馈 |

**深意（关键）**：User 虽然人轻，但他们的反馈往往能决定项目的生死。User 很多不可能都对接，KBU 是代表。所以**找对人 = 把正确信息送到正确层级，尤其不能轻视 User/KBU 这一层的反馈。**

**角色-模块映射表（项目启动第一产出）**：项目启动时，通常会立即整理一张表，**按业务和模块把对应的人都找到**：
- 一个功能**找不到 FO** → 你就不知道这个功能如何确定（做什么/不做什么没人拍板）；
- **找不到 KBU** → 意味着你对业务具体该怎么操作、怎么使用，没有沟通对象；
- 一个项目**说不清楚这些角色具体是谁** → 失败概率就是 **100%**。

缺人不是软提醒，是**硬阻塞**——角色映射表不全，说明项目没就绪，不能开干。

### 4.4 接手流程（先盘信息 → 内部消化 → 见甲方）

**① 盘基本信息**：接手一个项目，通常需要先了解这个项目的基本信息——**甲方是谁？项目的目标是什么？有没有之前给他们的提案？内容是什么？项目的周期是多久？甲方 PM 是谁？** 等等。有了这些信息以后，再消化理解。

**② 内部消化（先在公司内部）**：这时候还在公司内部，是先跟**销售之类的人**沟通。消化这些信息以后，准备出**下一步需要调研的问题清单**——能够内部澄清的，先内部澄清；澄清不了的，留待跟用户接触以后继续澄清。

**③ 见甲方 PM（带问题清单，先找 PM）**：下一步就是带着问题去见甲方了，通常是**先找到甲方 PM**。先跟甲方 PM 进一步了解对方的需求信息——**目标是什么？周期？里程碑？** 以及**涉及哪些业务部门、要实现什么功能**等等。有了这些以后，**Function Owner 基本上也就清楚是谁了**。

**④ 定时间计划**：FO 清楚以后，你要先定个计划，**把时间计划先确定下来**。有了这些，项目就可以准备启动了。

**⑤ 项目启动**：正式的话会开个**项目启动会**；轻松一点的话，就是 PM 带着你去认识 Function Owner。

### 4.5 生命周期与阶段成果物

项目通常会分成几个阶段：**需求调研和设计阶段 → 开发阶段 → 测试阶段 → 上线后持续运营**。

**需求调研和设计阶段**：先要搞清楚甲方——所处的行业、做什么业务、我们项目的目的是什么、**他们原来是怎么做的**、人员是如何分工的、原来有哪些业务数据、形式是什么样的、**有没有样例样本**——搜集下来。下一步的目标是**交付方案**。这个阶段最重要的成果物有三个：**方案**（给甲方的解决方案文档）、**计划**（实施时间计划）、**交付物清单**（验收时对着它逐项签收）。

**开发阶段**：主要是我们（乙方）内部做；有问题会**通过甲方 PM 去找 FO 和 KBU 讨论**（不绕过 PM）。最终交付的是**测试报告**，说明方案中约定的模块和功能点我们都已经实现了。

**测试阶段**：给用户，由 **KBU 来测**；成果物也是**集成测试报告**。

**验收**：对着**交付物清单**（甲方在调研设计阶段已签字确认过的交付标准），逐项让甲方签字确认收到——**全签收了，那就是验收过了**（清单勾销，不靠「甲方说好」）。

**部署与持续运营**：验收之后就是**生产环境部署**，进入**持续运营阶段**。

**关键闸门**：
- 调研设计 → 开发：**方案 + 计划 + 交付物清单**都必须甲方签字确认（确认后才进开发——**交付物清单不签字确认，就没有交付标准，验收时无从对账**）；
- 测试 → 验收：集成测试报告交付；
- 验收：对交付物清单逐项签收，全签收 = 验收过。

### 4.6 沟通机制

**问题驱动的沟通 = 找对人**（前文四类人已铺垫）：开发中碰到问题，**功能取向的问题找 FO，使用方式的问题找 KBU**；进度/协调找 PM，目标/预算找 PO。

**日报**：每天要出日报给甲方 PM。传统上通常有个内部晚会（甲方 PM 愿意参加也可以）；现在是 AI 开发、可能没有内部团队了，但**日报还是需要的**。

### 4.7 风险控制

**风控与日报关联**：风控主要看的方向是**进度偏差**——日报是进度偏差的「仪表盘」，风控靠日报发现偏差、早预警。

**风险分级标准（低 / 中 / 高，锚定「对进度的影响」）**：
- **低**：一个问题还看不出对进度造成影响；
- **中**：可能影响进度；
- **高**：已经影响进度。

分级锚定「对进度的影响」，不是「问题难不难」——难但没拖进度 = 低；简单但已拖进度 = 高。

**应对按级**：
- 低：记录、继续；
- 中：告知甲方 PM；
- 高：启动风控会议，跟甲方一起商量应对方案。

### 4.8 持续运营

落实到技术这一块，主要就是 **bug 报告和修复**。这一块不用过死过细——只要有机制能**报告 bug、记录 bug、做后续处理**就够了。

## 5. 运转核心：三账（项目状态档 PROJECT-MANIFEST > 台账 Ledger > 批次档 Batch Record）

> 工程模式的一切围绕**三本账**运转——它们是整套逻辑的状态容器，不是边角产物。角色是「谁写哪段账」，纪律是「三本账不漂移」，情境是「三本账在不同情况下的运转方式」。

### 5.1 项目状态档（PROJECT-MANIFEST）——「项目现在处在什么状态」的账

- **意义**：项目全局的**状态总览**——阶段、目录声明，一处记录。它是情境旋钮（阶段）的**记录落点**：没有它，阶段就没有「现在处于哪」的存档。
- **构成**（纯机器状态）：项目阶段（初始开发 / 上线运行）· 目录声明（doc-root，覆盖默认值）。
- **格式**：**JSON**（`PROJECT-MANIFEST.json`）——纯机器状态，机检机械校验（枚举合法、值形态合法、目录声明存在）。**关键决策不进 manifest**（那是文档层的事，住需求档约束依赖 + 设计档关键技术决策/方案否决理由/变更记录；待裁事项住台账）。
- **前置性（入口门槛）**：工程模式下**必须先有它**——没有则先**初始化生成**：确定项目阶段 + 梳理现有文档和代码 + 盘清家底，再进正常循环。缺 manifest 时，机制**拒绝进入**正常循环。

### 5.2 台账（Ledger）——「还有哪些事的账」

- **意义**：需求池 + 技术待办 = 工程模式的**待办总账**，驱动「做什么、做没做、怎么排」。
- **存储**：**SQLite**（`node:sqlite`，零第三方依赖，memory 面已验）——并发写靠事务、计数自动（COUNT）、状态机靠字段枚举约束，替代 md 文件 + 手工纪律（今天的并发冲突、删条目漏改计数，根子就在 md + 手工）。**工作树外**（用户数据目录键控库——项目内不留文件，天然不进 git；2026-09-17 用户裁定）。
- **可读面**：查询命令（`/ledger`）——agent 和用户都通过查询面看台账，**不导出 md 摘要、不直接读 DB**。
- **统一待办跟踪**：checklist 工具**废除**（用户 2026-09-17 裁定）——台账是**唯一待办跟踪面**。checklist 的 pending/in_progress/done 由台账六态承接，跨 session 由 DB 持久化承接，归档由归档表承接。
- **构成**：需求池（用户需求点）+ 技术待办（机制缺陷）+ 归档（已核销/已废弃——软删除或归档表）。
- **状态机**：六态（待讨论/待设计/在途/待核销/已核销/已废弃）——字段枚举约束，写错态即拒。
- **结构**：schema 约束替代手工纪律（一行一条 = 一行记录 · 计数 = COUNT · 指针（`task_book`）非空 = CHECK · 本仓自持 = 校验）。
- **模型使用面**：台账教学两分——**常识面**（全角色）需求住 `docs/core/requirements/PROMPT-SYSTEM.md` §2.3（第 13 节）· **用法面**（主 agent）住本档 §13.8（FR30）。

### 5.3 批次档（Batch Record）——「一件事怎么做的账」

- **意义**：一次实现轮的**账本**——「说做完 = 真做完」的可信载体。没有它，交付无从核、审、回滚。
- **构成**：六段一段一作者（§1 主 agent 目标+前情+条目 · §2 designer 任务书 · §3 advisor 发现表 · §4 主 agent 核验裁决 · §5 coder 实施记录 · §6 父代理 收口+状态行）。
- **流转（状态机）**：开批 → 设计 → 评审 → 裁决 → 实施 → 收口（状态行「已收口」+ 核销 + 关链）→ 冻结（不再回改、不迁移不删）。**流程走到哪 = 批次档状态推进到哪**。
- **格式**：**md**（记录类文档——六段含大量叙述：评审理由、裁决、实施过程、收口判词；机检靠结构约定抽段头/状态行/计数，不靠 JSON 机器读）。
- **护栏**：单档 >1000 行另起 · §5 修正轮上限 5 · §3 评审无轮次上限 · 判定权 = 主 agent。
- **结构**：六段自写 + `batch_segment` 越段即拒 + 状态机。

### 5.4 三账如何咬合（按重要性）

| | 项目状态档 | 台账 | 批次档 |
|---|---|---|---|
| 回答 | 「项目**现在处于什么状态**」 | 「还有哪些事**要做**」 | 「一件事**怎么做**」 |
| 驱动 | 情境旋钮（阶段） | 排期（触发条件） | 流程推进（状态机） |
| 收口时 | —（manifest 不参与收口——无批次指针） | 核销 → 归档 + 计数联改 | §6 收口 + 状态行冻结 |
| 兜底 | manifest 写门（M1——fail-closed） | SQLite 咬合 CHECK（非空 `task_book`） | `batch_segment` 段门禁 + 状态行冻结拒写 |

**一条需求的生命**：进台账（待讨论）→ 开批（批次档 §1）→ 设计（§2）→ 评审（§3）→ 实施（§5）→ 收口（§6）→ **台账核销归档**——批次档与台账在收口处闭合；项目状态档横切更新（阶段随进度变）。

### 6.1 需求文档（两层）

需求文档分两层，粒度不同、用途不同：

**上层 · 项目需求（Project Requirements）**——主 agent 写，全局视角，整个项目一份。七层：
1. 背景与问题（为什么做、现状、痛点/机会）
2. 总体目标（要达成什么——可验收的「状态」，不是「做好」）
3. 范围与边界（做什么 / **明确不做什么**）
4. 干系人与用户（为谁做、需求主体是谁）
5. 功能需求（逐条用户故事：`作为一个[角色]，我想要[功能]，以便[目的]`，只写 who/what/why）
6. 非功能需求（性能/安全/兼容/可用/可维护，**含度量**）
7. 约束依赖 + 验收标准（技术约束、外部依赖、假设；怎么算做完）

**下层 · 功能规格（Function Spec）**——按**架构设计定下的模块**拆，一个模块一份，**交给 designer 做设计的文档**（不是项目需求）。结构：
- 模块目标；
- 功能点（**含用户故事**——每个功能点用用户故事表达）；
- 边界（做什么/不做什么）；
- 验收标准；
- 依赖。

一个 Function Spec = 一个批次：designer 拿它出设计 → coder 实现 → 收口。

### 6.2 设计文档（两层）

与需求对称，设计也分两层：

**上层 · 架构设计（Architecture Design）**——总体视角，整个项目一份。内容：技术选型、**模块划分（Function Spec 的权威源——没经设计考虑的模块划分不成熟）**、模块间接口/依赖、关键技术决策、整体数据流。

**下层 · 模块设计（Module Design）**——对应一个 Function Spec，一个模块一份，交给 coder 实现。内容：① 问题陈述 ② 方案与理由（就方案本身说清为什么这么设计——**不强制列候选对比**） ③ 受影响文件全清单（源/测试标当前行数 + 预计增量） ④ 验收标准逐条回指 Function Spec（每条可机判） ⑤ 变更记录（一行注记，不堆流水账）。

**对应关系（时序）**：项目需求 → **架构设计（定模块划分）** → 按模块拆 Function Spec → 模块设计 → coder 实现（一个批次）。

**新建 vs 更新**：写设计文档时——该模块**已有**设计文档 → **就地更新**；**无** → 新建。与 §6.3 就地更新规则同源（不另起炉灶）。

### 6.3 需求与设计文档就地更新规则

**总体需求 / 总体设计（项目需求、架构设计）允许多份历史演进**（不同时期逐步演进调整，如 v1/v2 并存）。**但模块级的需求与设计关系必须维护好、不能乱**：

- 一个模块的需求 = 一份 Function Spec，一个模块的设计 = 一份模块设计，**一一对应、关系不乱**；
- 涉及该模块的更新，就地更新对应的那份文档——不另起炉灶写另一份文档（另起炉灶会把文档体系搞散——用户 2026-09-17 裁定）；
- 需求变了 → 改该模块的 Function Spec 文档本身；设计变了 → 改该模块的模块设计文档本身；不新起「接线 / 迁移 / 补充 / 旁路」文档。

**检查点（约束即结构，不靠自觉）**：
- **designer 接单时**：先核查「该模块的需求文档（Function Spec）是否已存在」——不存在 / 发现另起炉灶 → **打回主 agent**，不自行补造方向；
- **文档评审时**：advisor 核查「需求与设计是否另起炉灶」——发现旁路文档 → 报发现。

### 7.2 角色 A · 主 agent（对话面 · 唯一）

> **提示词落点**：`persona-engineering.md`——角色定义见 `docs/core/requirements/PROMPT-SYSTEM.md` §2.2 人格层（本角色 = 交叉引用回本节）。

**职责**：
- 需求讨论 + 登记

- PROJECT-MANIFEST 初始化 / 维护

- 评审发现裁决
- 按变更面派发
- 台账唯一作者

**红线**（判据句）：
- 不写设计档（designer 唯一；需求文档可落）
- 不写实现代码
- 不自发起评审
- 不挂「等」（只对真依赖）
- 不代提交他人档
- 不让 coder 自己勘察（派单钉死 file:line，禁「全量扫 X」）

**完成判据**：
- 收口四件齐（§6 非空 + 状态行 + 核销 + 关链）
- 裁决表 Dispatched→Fixed 带 file:line
- 派单三句齐
- 核销三联改

### 7.3 角色 B · eng-designer（设计文档唯一作者）

> **提示词落点**：`persona-eng-designer.md`——角色定义见 `docs/core/requirements/PROMPT-SYSTEM.md` §2.2 人格层（本角色 = 交叉引用回本节）。

**职责**：
- 核对主 agent 写的 Function Spec 合规（五要素齐：模块目标 / 功能点 / 边界 / 验收 / 依赖，具体到可设计），不合规打回（§7.6 互锁）——**先验料，料不对打回，不白勘察**
- 勘察（一次，不跑多遍——A1 checklist）：
  - ① 定位所属设计文档 + 核查该模块 Function Spec 已存在（另起炉灶 → 打回主 agent，§6.3）
  - ② 读既有实现与先例
  - ③ 核测试面
  - ④ 广度勘察委派 explore（≤6）
  - **目的**：验证设计可行 + 拿一手证据（`file:line`）+ 发现需求缺口，**不为「全面理解代码」**，够了就停
- 写设计文档（架构设计 + 模块设计；已有则就地更新，无则新建——§6.2/§6.3）
- 写批次档 §2
- 评审前预检（A3 四项，不过先修，不自发起评审）：
  - ① 需求具体到可设计（Function Spec 五要素齐、具体到可据此设计）？
  - ② 受影响文件全清单 + 行数标注（代码面标行数，文档面豁免）？
  - ③ 验收标准逐条回指需求（每条可机判）？
  - ④ UI/交互决策全落档（无「讨论过但没写」）？
- 设计修订（修正轮，单写者）

**红线**（判据句）：
- 不写需求档（需求档归主 agent，designer 只核对合规）
- 不写实现代码
- 不改提示词文件（主 agent 内容权）
- 不发评审
- 只碰 §2 + 设计档
- 不代用户裁定（澄清必经主 agent）
- 修正轮不夹带新语义

**完成判据**：
- Function Spec 五要素齐、具体到可设计（核对合规通过）
- 受影响文件全清单 + 行数标注
- 验收逐条回指需求且可机判
- 预检四项过

### 7.4 角色 C · eng-coder（实现唯一执行者）

> **提示词落点**：`persona-eng-coder.md`——角色定义见 `docs/core/requirements/PROMPT-SYSTEM.md` §2.2 人格层（本角色 = 交叉引用回本节）。

**身份**：被授权的实现者——父代理交任务书（批次档 §2）+ 设计 token，设计档是权威规格；你的角色是实现。

**授权**：设计评审 token 在 spawn 时机械验证——无需重跑设计评审；无有效 token，写工具全拒。

**边界**：
- 设计是权威规格——通读遵循、不得偏离；
- 发现设计缺口 → 停下报告父代理，不得静默偏离；
- **子代理**：任务已由父代理确认，无用户可等——立即执行、绝不请求确认或以「等待批准」结束回合；歧义在最终报告注明后返回；
- 独立工作，父代理只看最终报告。

**交付协议**：实现 → explore 偏差审计 → 自修（≤5 轮）→ advisor 代码评审 → 收敛交付；报告声明审计/评审轮次与终态（clean / stalled）。

**file 域声明**：超声明改动允许——逐条列出并说明理由；改了未报 = 静默越界。

**批次档纪律**：§5 自写（batch_segment）；执行者拒收——查不到任务书（§2 / `batchDoc` 不可读）→ 不执行、打回。

### 7.5 角色任务与交付物

| 角色 | 任务 | 交付物 |
|---|---|---|
| 主 agent | 需求讨论/写需求文档/manifest/收口/核验/裁决/派发/台账 | 项目需求 + Function Spec · PROJECT-MANIFEST · 批次档 §1/§4/§6 · 台账 · 裁决表 |
| eng-designer | 写设计档 + §2 + 勘察预检 + 设计修订 | 设计档 · 批次档 §2 |
| eng-coder | 按任务书实现 + 写 §5 + 内部审计自纠 | 实现代码（源码+测试）· 批次档 §5 · 交付报告 |
| advisor | 设计评审 / 代码评审 | 评审报告 · 批次档 §3 |

（explore = 只读辅助，非核心角色；plan 是否入工程模式——待定。）

### 7.6 互锁机制（交付物合规校验）

交付物不只各写各的——上下游互相校验，不合规打回：

| 环节 | 谁产出 | 谁校验 | 不合规 → |
|---|---|---|---|
| 功能规格 Function Spec | 主 agent | **eng-designer 核对合规**（五要素齐 / 具体到可设计） | 打回主 agent |
| 设计档 | eng-designer | 主 agent 内容核验（覆盖需求没、方案合理没）+ advisor 独立评审 | 打回 designer |
| 实现 | eng-coder | 主 agent 验收（测试/读数） | 打回 coder（修正轮） |
| 收口 | 主 agent | 台账核销 + 批次档 §6 收口（manifest 不参与——无批次指针） | 机检红 |

**核心**：「谁写」和「谁把关」分离——主 agent 写需求文档，但必须 designer 把关合规，否则主 agent 随心所欲乱写。

## 8. 运作规则

### 8.1 交接契约

**路由（任务类型 → 角色）**：排查/勘察 → explore · 设计/文档 → designer · 实现 → coder · 评审 → advisor。派单机械校验，不匹配即拒。**结构**：类型契约 + 拒收门。

**主 agent ↔ designer 交接界面**：

| 方向 | 交接内容 |
|---|---|
| 主 agent → designer（派单） | 批次档 §1（目标 + 条目 + 前情）· 本批 Function Spec 清单 · 架构设计（模块划分权威源）· 轮次（初始/修复）· 禁止范围 |
| designer → 主 agent（交回） | 设计文档（新建 or 就地更新）· 批次档 §2 任务书 · 报告（号→改动 file:line + 打回点） |
| designer → 主 agent（打回） | 缺 §1/清单不全 · 需求说不通（缺口/矛盾/不可实现）· 另起炉灶（模块需求文档不存在） |

**可拒绝情形**（接单方拒收）：查不到任务书依据（§1 / 清单）→ 拒收打回，不自行补造方向往下干。

### 8.2 委派治理

「该不该派 / 派什么 / 派出去怎么干」有门槛：小改父侧自做（判据句）· 派单模板强制字段（目标/已知事实/禁止范围/验收/报告格式——缺字段即拒）· 禁「全量扫 X」。**结构**：门槛 + 强制字段。

### 8.3 纪律兑底

关键纪律靠**流程兑底**（收口核对清单）而不是堆机检（2026-09-17 用户裁定：无限机检反感——M9 提示词机检已裁；锚检测待定）。**不新增纪律条文**（条文过多、执行不足）。**结构**：机检兜底（收口状态行、核销计数、交接路由——已落地者保留；正本↔落地一致**不挂机检**——提示词双面翻译由收口核对兑底）。

### 8.4 提示词双面流程

提示词模板（`docs/core/design/prompts/`）= **中文审核面**（用户审核用）；落地档（`thincoder-core/prompts/`）= **英文运行面**（国外模型运行用）。更新流程 = 改模板（中文）→ 翻译生成落地（英文）；生成 = 翻译，不是 cp。**无机检门**（兑底 = 收口核对清单）。

### 8.5 评审与凭证（继承 v1 · 不取消）

设计文档出来 → 走 **advisor 设计评审**（用户发起）→ 通过后签发 **designToken** → eng-coder 持 token 实现。评审 + token 门是 v1 已验证可靠的机制，v2 **继承不取消、不重写**（只微调）。

### 8.6 测试纪律（简化 · 反过度工程）

v1 测试机制过度工程（三层分层 / 慢层归册 / 多套脚本 / 退役台账），v2 大幅简化：

- **单元测试** = 开发期工具，改对代码就退役——**不搞退役台账仪式**，写完即弃。
- **集成测试** = 项目资产——业务场景 + 生产问题补入，只断言业务可观察结果，常驻。
- **门禁** = 一条 `test` 全绿（不再 lint + test:full + test:integration 三层）。

**砍掉**：慢测层归册（慢就慢，全量跑）· run-fast / run-full / slow-gate 多脚本 · 测试退役台账。

**结构**：一条门禁命令，不建「管测试的官僚系统」。

### 8.7 机检引擎（简化 · 可迁移）

v1 三机检 = 必要内核 + 一大坨 thincoder 私有历史包袱（双引擎、三套源域、三套行宽判据、参照历史面豁免族、六档并入映射、V3 历史常量）。v2 砍包袱、留内核：

**留内核（普适判据）**：
- 锚检查：文档指针指到存在的档（引用可解析）——「文档不撒谎」的兜底；
- 行宽检查：单行 >300 字符（一条判据）；
- 台账一致性：由 SQLite schema 承接（check-ledger 作废）。

**砍包袱（thincoder 私有）**：双引擎（VSC/V5 两套）· 三套源域枚举 · V1/V2/V3 三套行宽判据 · 参照历史面豁免族 · 六档并入映射 · `V3_ERA_START` 历史常量。

**结构 = 一个引擎 + 声明面**：
- 引擎只留普适判据（引用可解析 / 行宽 / 台账 schema）；
- 项目特有的一切（扫哪些目录、豁免什么、阈值、参照面）→ 进 PROJECT-MANIFEST 的声明面（doc-root + 机检配置）；
- 换项目 = 改声明面，不改引擎脚本。

### 13.1 文档更新纪律 D1–D7（FR21）

七条纪律（v2 §6 文档写作约定的行为兑底）：

| # | 纪律 | 语义 |
|---|---|---|
| D1 | **写权矩阵** | 文档类唯一作者：批次档 = 主 agent · **需求档（项目需求 + 功能规格）= 主 agent** · **设计档（架构设计 + 模块设计）= eng-designer** · 提示词 = 主 agent 内容权 + eng-coder 落笔；父侧直笔三类例外（自有写域 / 纯机械形态收正 / 小修改）**皆须打标**（「父侧直接执行」+ 可 revert） |
| D2 | **单一权威源** | 一条机制只在一处详述，其余处只引用不重述 |
| D3 | **计数·枚举纪律** | 声明「N 项/N 处/N 条」必须与列表同时改；可机判（V2） |
| D4 | **指针纪律** | 指针形态 `文档:节`；行号只作 as-of 参考；禁相对指针 |
| D5 | **冻结窗口** | 评审在途不改被审文档（改了 = 评审对象已变 → stale，token 不签发） |
| D6 | **回读核对** | 任何写入后回读核实再报完成 |
| D7 | **变更留痕 + 核销同步** | 每批核销跑核销同步清单（批次档 §6）：角色表 / 状态行 / 计数 / 指针 / 变更记录 / 待办勾销（**含前批遗留核对**——条目已完成而挂靠批档未收口 ⇒ 兜底核销路径 = `design/BATCH-RECORD.md` §5.2）/ 台账可见面 |

机械校验最小集（V1–V5：段引用可解析 / 计数与列表一致 / 批次档 §3 轮次行 / 跨仓形态合规 / 文档锚一致性）——判据与引擎见 `design/DOC-DISCIPLINE.md`（v2 机检单引擎 = §7）；校验铁律 = 快层可跑 · 零假阳才常驻（阈值 = 0，违规一律阻断）· 不得靠自然语言理解。

### 13.2 VSC 端镜像（FR23）

工程模式机制**两端同一套、各自实现**：batchDoc 门 / eng-designer 角色 / 行为纪律 / batch_segment 工具 / V1–V3 机检 / 提示词双源——**语义同源·原文自持**（不共用代码）；逐字一致的段在设计档定稿、实现面照抄不得自行解释；验收两层 = 机械面全绿 + **用户手动重载扩展后自验**（源码改动需重载才生效——「文件在了」≠「机制活了」）。

### 13.3 台账提醒与可见面（FR24）

把台账未决状态送到用户眼前——**有可动作项才出声，零噪音**：

- **状态行极简标记**：`台账 <需求池数>·<技术待办数>`，只显当前项目，老化 >0 转警示色；两池分显不合计。
- **三处文本行**（落会话流可回看）：启动行（有可动作项才出）· 批次收口行（核销同步清单机械步骤）· 变化行（老化首次越线 / 需求池达阈值——事件驱动、一次性去重、**只在行真正落入会话流后才记账**）。
- **多项目判据**：当前项目 = 目录向上最近含台账者；项目集 = 当前 + 同级含台账者；明细行集 = 当前 ∪ 可动作项目。
- **数字单源**：解析/计数/老化/阈值一处实现，机检器与两端显示面共用口径。
- **零噪音与降级**：无可动作 → 零输出；台账不可读/坏档 → 降级不崩；headless 零新增输出；台账档只读。

设计见 `design/LEDGER.md`（v2 SQLite 数据源——§7 可见面接口）。

### 13.4 文档体系各仓自持（FR25）

一个开发者同时维护多个产品时，任一产品的文档只承载自己的事项（事故溯源：跨仓登记外部产品线的债——内容层已清，机制层无闸；「能记一处就不写两处」= 同病两种形态）：

- **F1 台账射程**：台账（需求池 / 技术待办）只收本仓条目——禁登记本项目之外的事项；指针面收窄为**仓内可解析**。
- **F2 批次档同规**：批次档只登记本批范围（含本批的受影响文件与验收）。
- **F3 文档体系自持**：需求档 / 设计档 / 批次档 / 台账各自成套；**非复制**（语义同源、各端原文自持）。
- **F4 缺失层必须补齐**：缺的文档层就地补建——不得以「对端已有」「避免重复」为由省略；逐层成套。
- **F5 约束须落提示词层**：F1–F4 的行为面必须在提示词层落地——文档层是规格，提示词是代理运行期实际读到的纪律。
- **F6 机检闸**：台账条目的证据 / 指针路径须在**本仓内可解析**；违规一律 fail-closed（「存量 / 入基线」已废——阈值 = 0）。
- **F7 核验职责**：同一机制跨多个实现面产出**一式多份设计**时，主 agent 有义务核验各份逻辑一致（核验四维 = 裁定同源 / 判据同一 / 边界同形 / 差异显式登记）；该职责须落提示词层。
- **F8 提示词通用化**：提示词中的多实现面条文不得绑死本产品两端；勘察 checklist 同步通用化。
- **F9 存量无豁免**：凡**触及对端**的存量批档一律处置（迁移 / 各仓持其份）；不得以「历史已收口 / 审计链 / 重复 / 量大 / 在飞」为由豁免。
- **F10 文档体系逐层成套**：各产品文档体系**逐层对位**；需求层**逐档三值齐备**（① 建本仓需求档 · ② 已有对位（允许异名）· ③ 本端无此面（写理由））；不得只建单层壳。
- **F11 需求层必须在本仓有档**：**需求层必须在本仓有档**——「对端有」「design 层有」不构成理由；**② 已有对位不得以 design 层充当**。
- **F12 结构档位硬限无豁免（适用范围 = 程序代码）**：>300 软线 / >500 硬限**仅约束程序代码（源 / 测试档）**；超限档本批拆；**文档（设计 / 需求 / 批次 / 台账）不受行数限制——无任何行数义务**（用户裁定 2026-09-16）。
- **F13 对端引用形态零残留**：设计 / 需求 / 批次档正文引用对端产品文档一律**规范形态**（`名称（仓别）§N`）；存量不是合法态。
- **F14 先例不构成例外依据**：任何「以前也这样 / 已落形态 / 他批先例 / 存量在案」都不构成偏离规则的依据——**例外的唯一依据是判据句（可机判）**；找不到判据句 → 按规则办，或停下上报。**同条（残留即示范）**：合规形态必须显式；历史语义可保留、形态必须规范；「存量豁免 / 入基线」不得再设（阈值 = 0）。**同条（例外须带消解期）**：任何登记在案的例外必须写明消解路径与到期条件。

**非功能性**：N1 零假阳（机检新规则对本仓合法内容零命中）· N2 fail-closed · N3 可分步（存量迁移允许分期——每期有明确触发条件与逐档清单）· N4 否决在案（不得以「另有他档」为由放宽指针射程）。**两轴并列**：本节管**条目与归属**（轴一）；文档正文引用对端产品文档按既有 V1 边界规范（轴二）。

设计见 `design/LEDGER-SELF-CONTAINED.md`（L4 判据 + 形态合规 V4）。

### 13.5 变更面分流（FR27）

任何改动动手前先判**变更面**：

- **三分面**：产品代码面（`thincoder-core/**` · 两产品 `{src,bin,webview,test}/**` · 产品文本面）= 走全流程；工程工具面（`scripts/**` · `.thincoder/**` · `.github/**` · `package-lock.json`）= 父侧可直改；文档面 = 按写权矩阵（D1）。
- **默认归类（fail-closed）**：未列入两枚举的路径一律按产品代码面处理——宁可走流程，不得默认直改。
- **直改三硬约束**：① 机械改 ⇒ 直改 + 改完实跑报读数 ② 改判据语义 ⇒ 仍走设计 ③ 凡直改 ⇒ 报告「父侧直接执行」+ 单笔可 revert。
- **授权判据 ≠ 绕过门禁**：门禁判定为准；与分流不一致 ⇒ 停下上报。

### 13.6 批次档生命周期（FR28）

五条判据（判定权 = 主 agent，子代理撞界 ⇒ 停下打回）：

- **界**：一批 = 一个交付目标 + 一组同批条目 + 一份批次档；交付目标变更 / 阶段跨越 / 条目集变更 ⇒ 另起新批新档。
- **护栏·长度**：单档 >1000 行 = 越界信号 ⇒ 另起新批。
- **护栏·轮次**：§5 修正轮上限 5 轮（触顶 ⇒ 本批自然边界）；§3 设计评审无轮次上限——触达停止判据（持续拒绝 >3 轮）⇒ 停下上报。
- **闭合/退役**：§6 收口 ⇒ 状态行「已收口 <日期>」+ 整档冻结（不回改；冻结档不迁移不删）；v2 机械兑底 = batch_segment 冻结拒写（`design/BATCH-RECORD.md` §4.9）。
- **接续**：新批 §1 顶部前情指针 `前情 = docs/batches/<旧档> §N（已收口 <日期>）`。

### 13.7 父侧轮次与提交纪律（FR29）

- **派发如实**：陈述「已派/在跑/已提交」⇒ 必须同轮发出调用；队列状态只能抄工具回执。
- **禁止零文本收尾**：每轮收尾必须给面向用户文本或显式进等待态。
- **写域声明**：`files` 只列内容产物（源/测试/设计档）；工程工具不入域。
- **提交纪律**：提交路径限定（`--only`）；不代提交用户/他人的档；归因先想「可能是用户在写」。
- **修正轮派单必写三句**：① Suggestion 列 = 评审员建议、处置执行人 = 你 ② 按发现号逐条改、报告「号 → 改动 file:line」 ③ 明写「本轮不做」清单。
- **父侧不代笔**：设计/需求档落笔一律派修正轮给 eng-designer；三类例外（自有写域 / 纯机械收正 / 小修改）皆须打标。
- **Suggestion 列形态**：只写改法、不写执行人——禁「由主 agent 收正」式归属句。

### 13.8 台账用法面教学（FR30 · 2026-09-19 用户口述 · 父侧直接执行 · 可 revert）

**射程**：本项只管**用法面**——工程模式（主 agent）「**何时动账**」。**常识面**（台账是什么 / 谁读写 / 六态 / 存哪）= 全角色系统常识 ⇒ 需求住 `docs/core/requirements/PROMPT-SYSTEM.md` §2.3（第 13 节「台账常识」），本档不复制（D2）。

台账要被用得对，光有机制不够——模型得知道**什么时候动它**。用法面 = 生命周期**事件 → 动作**绑定，五条：

- ① **批点火** ⇒ 状态推进（待讨论 → 待设计 → 在途）+ `task_book` 指针；
- ② **实施核验通过** ⇒ 在途 → 待核销 → 已核销，核销须**证据回写**（落点坐标 + 结账依据）；
- ③ **批收口** ⇒ 勾销核对（D7 收口行由「读数」升为「动作」）；
- ④ **发现新债**（停下上报产物 / 评审发现 / 文档漂移）⇒ **当日入账**，`trigger` 必填；
- ⑤ **上抛事项**（子代理 / 评审 / 停下上报递到父侧）⇒ **当场裁定**——能收正的**同轮收正**；不能收正的**当日入账**（`trigger` + 到期条件——落 `evidence`）；**禁止只留在报告散文或「待裁」清单里**（2026-09-19 22:37 用户裁定「A」补入；同 23:5x 收正——到期条件**非枚举文本**，落字段 = `evidence`）。

- **落点**：`prompts/persona-engineering.md` 台账节——**不落 `discipline-engineering.md`**（该档 eng-coder / eng-designer 也读，而台账写权仅主 agent，写入＝误导子代理）。
- **边界**：不为此加机械门（承 2026-09-18「为臆想的失败逐点加限制」= 反模式之裁）· 不重写攒批工作流本体（只补「时机」）· 普通模式暂不写「何时推进 / 核销」（无批次档体系，核销语义不同）· 子代理不教写账动作。
- **验收**：① 文档面可机检——`prompts/persona-engineering.md` 含「事件 → 动作」**五行**判据 · 模板面与运行期面同步（语义一致；M9 单向机检已裁撤 ⇒ 收口核对兜底）· 新增行无超宽（≤300 字符）；② 行为面（**观察项，非机检**）——下一批的生命周期里，推进 / 核销 / 入账由模型**自主**完成，无需用户推动。
