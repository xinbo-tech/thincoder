## 1. 总体需求

**为谁解决什么问题（一句话）**：为 ThinCoder 的两产品（CLI 与 VSC 扩展）消除「同一套机制两份实现」的长期税负——
把两产品共有的机制实现**与共享提示词内容**收敛为**单一权威源的可共享核**，两壳各自只保留**结构性不对称**的端特有部分（「一个核 + 两个薄壳」）；
归一后的行为**按逐条裁决结果**走（**不再要求**等于任一端的旧行为——见边界原则 4）。

**边界原则（A7 / A8 / A9——本板块的准入总则）**：

1. **提示词并入核**（A7）——`thincoder-core/prompts/` 16 档槽位提示词 + `thincoder-core/tool-docs/` 54 档工具描述，核内**唯一副本**；
2. **凡两产品功能基本对称的面都进核**（A8）——**含低相似度的真分叉面**（配置 · 会话管理 · 记忆 · 提示词，及一切对称机制）；
3. **差异不得作为排除理由**（A9）——差异是**本项目的工作内容**，不是排除依据；端特有桶只收**结构性不对称**（仅供单侧存在 / 依赖壳能力）；
4. **「行为不变」不作为判据**（A10）——验收 = **裁决是否落实**：**面内**（对称面）逐条归一，归一后的行为 = **裁决结果**（**不要求**等于任一端的旧行为）；
   **未涉面**（本次归一未触及的既有功能）**不得无故回归**（其既有测试仍须绿）；对外可见契约若随归一而变 ⇒ 须显式登记**并保留兼容**（旧配置可读 / 迁移说明 / CHANGELOG / 旧命令面保留 / 事件语义登记——A7 / **F13**）；**确无法兼容者单独上抛**（不得静默破）。
5. **逐条裁定关口**（A11）——凡归一将**改变可观察行为 / 对外契约**的条目，**逐条提交用户讨论裁定**（不得批量默认通过、不得代裁）；
   提交形式固定四要素（**左端行为 / 右端行为 / 建议归一形态 / 影响面**）；**裁定未完毕的条目不得进入实施段**。

**为什么现在做**：phase 1（目录合并）已把两产品收进单一 git 仓、原有跨仓机制全线退役；但**两份实现与两份文本仍在**。
phase 1 的实测（口径与复现命令 = `thincoder-cli/docs/requirements/TWO-REPO-MERGE.md` §1）与 phase 2 的逐档复核表明：
**内容层与实现层都存在真分叉**——不是个别档的漂移，是**成面**的：代码面多数档内容不同，提示词面同一子目录内也有整档不同（§1.2）。

**由此得到本板块的两条判据（也是设计的两条起点）**：

1. **「建核」不是搬运**——**内容层与实现层都有成面真分叉**（代码面多数档内容不同；提示词面同一子目录内也有整档不同——§1.2）
2. **凭空写中立核 = 造第三份实现**——正是 phase 1 否决「抽独立核心包」的理由（会让工作退化成重写）⇒ 核**必须从两套现有实现 / 两份现有文本提取**。

**做法（用户裁定的保守路线）**：**先建共同内核并验证可用，再把 CLI / VSC 迁移到新核**——不直接改两产品现有实现；
分段推进：S0 差异分析 + 逐模块裁决（零代码）→ S1 建核（两产品一行不改）→ S2 逐模块迁移 → S3 收尾。

### 1.1 度量口径（写给复核者；器具已退役）

**口径（逐字，勿改）**：成对判据 = 两产品 `thincoder-cli/src/**` 与 `thincoder-vscode/src/**` 下
**相对路径逐段相等**者成对（含全部档型，**不按扩展名过滤**）；相似度 = 两侧读成行、**去首尾空白 + 丢空行**后取**行集合**的
 **Jaccard**（|交集| / |并集|）；另报 sha256 **逐字节完全相同**对数。**度量器具已退役（用户裁定）、无承接件** —— 本板块的差异度量**今天复现不了**，**也不再用它做判据**（随「一核两壳」已完成，镜像配对已无对象）。


### 1.2 提示词面分叉（结论）

**结论**：提示词面（运行期槽位提示词 + 运行期工具描述）**同样成面分叉**，且**集中在角色 / 纪律 / 评审三族**（persona · discipline · advisor）——不是随机漂移。

**为什么单列这一条**：**子目录中位可以很高，而同一子目录内仍有整档内容不同** ⇒ **中位数不能代表一层**。判「内容层已同」不能靠中位，只能逐档看。

**结构面的另一半**：两端的 `src/tools/` 实现面**并非一一对应**——有同名不同内容的，也有**单侧独有**的档。**单侧独有属结构性不对称**（端特有桶收的就是这一类），与「内容分叉」是两件事，处置也不同（前者进端特有桶，后者进逐条裁决）。

**⇒ 对本板块的要求**：建核不得以「相似度高」为由跳过任何对称面；也不得把单侧独有的档当成内容分叉去归一。

### 1.3 一个分叉面的完整判例：记忆（A12）

| 面 | 事实 |
|---|---|
| CLI 记忆面 | 用 **`node:sqlite` 的 `DatabaseSync` + FTS5**（`thincoder-cli/src/memory/schema.mjs:9` / `:68`——零第三方依赖） |
| VSC 记忆面 | **零 sqlite 用法**（两套逻辑） |

**处置 —— 不做「取一侧」的合并，先做前提校验**：分叉源于**已失效的前提**（「VS Code 内置 Node 不支持 sqlite」）⇒ **用户裁定 A12：记忆面向 CLI 语义归一**（CLI 为准）。

**这条为什么写进判例**：两套实现分叉时，**先问「为何分叉？当年前提还成立吗？」**——若前提已失效，分叉的直接归一面就是消失。**先去问那个前提，比逐行比谁写得好更快，也更不容易把过时的折中就当成裁决结果。**

**连带面的处置已定**：VSC 引擎下限 = **`^1.104.0`**（不另做真机实测；资料推导链 + `activate()` 护栏兜底——设计档 §2.11 A8）。
下限值属对外契约变更 ⇒ **已过目**（F13 / F12 ②）。**旧数据迁移面**（VSC `personal` 层 md 档 / 遗留 `.json` / `modelPrefs`——无自动迁移路径）⇒ 逐条上抛（设计档 §2.12.3）。

## 4. 范围边界与既有需求的关系

**明确不做（9 条）**：

1. 不把「直接改两产品现有实现」作为第一步（用户裁定的保守路线：先建核、验证可用、再迁）；
2. 不做一次性重写（不做「核与产品同时换」的大步）；
3. 不凭空设计新 API / 新架构（核的语义面只来自两侧现有实现）；
4. 提示词**并入核、核内唯一副本**——端特有指令段以**注入**表达（不整档复制、不在核内按端分支）；
5. 不做「行为冻结」——对称面归一后行为按**裁决结果**走（A10）；但对外可见契约（命令面 / 配置格式 / 输出文案 / 事件语义）**要兼容**（A7 / **F13**）——旧配置可读 / 迁移说明 / CHANGELOG / 旧命令面保留 / 事件语义登记；**确无法兼容者单独上抛**（不得静默破 ✗）；**未涉面**不得无故回归；
6. 不改发布链对外命令接口（npm / vsce + ovsx）与双源流程、包名、版本号策略；不新增源码构建步骤（装载靠 npm / vsce 的**标准**依赖机制——设计档 §2.2.1）；不引入打包期垫片（链接 / 分阶段脚本）；核**单独发布在先**（发布顺序：核 → 产品）；
7. 不做文档全量重排、不改写历史留痕档；
8. 不做**对外可见语义**的「行为统一」（那另立需求）——本板块内两侧行为差异以**核内注入**承载（端特有段注入；**面内**归一后行为按裁决结果成立——A10），**不得**以「有差异」把对称面排除出核（A9），端特有只认**结构性不对称**（仅供单侧存在 / 依赖壳能力）；
9. 不新增第三方运行时依赖（核只用 `node:` 内建）。

**与既有需求的关系**：

- **phase 1「产品运行时行为零改动」在本板块不适用**（A10）：那是**搬迁批**的正确约束（纯位置变更不应改行为），**本板块是统一批**——
  分叉的实现与逻辑必然导致分叉的行为，那正是要解决的问题；替代判据 = **不得无故回归**。
- 与 phase 1 否决的 **X1「抽独立核心包」**：本板块承担的正是 X1 当时缺失的前置（实现层统一）；
  形态上核为**独立版本的真包并发布到 npm**（A5 放宽 / A6）——X1 的病根是**缺实现层统一**（凭空写第二份/第三份实现），本板块不重犯：核**从两套现有实现提取**（F3 / D-C2），见 `docs/core/design/CORE-UNIFICATION.md` §2.3.2。
- 与 phase 1 退役的「各仓自持 / 端差登记 / 禁跨仓 import」无冲突——单仓之内，核与壳的边界是**包边界**，不是仓边界。

**需求来源**：用户提案（「先把共同内核构建起来，试一下可用了再把 CLI 和 VSC 迁移到新核心上」）+
用户裁定「计划可以，干吧」；需求池 = 仓根 `docs/TODO.md`「phase 2：核心统一」。
