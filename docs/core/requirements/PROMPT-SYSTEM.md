# 提示词系统（PROMPT-SYSTEM）· 核心统一子系统需求档

> 板块 = **核心统一**（phase 2——「一个核 + 两个薄壳」）；本档 = 该板块的**子系统需求档**（三层：总体目标 / 功能需求 / 非功能标准）。
> **设计层** = `docs/core/design/PROMPT-SYSTEM.md`（机制面 §6 提示词落地面——唯一副本 = `thincoder-core/prompts/`——的落地 / 装配 + §2 核模块裁决行）。
> **工作流档** = `docs/core/requirements/CORE-UNIFICATION.md`（统一目标 / 边界原则 / 量级基线 / 范围边界）——本档不复制（D2）。

## 1. 总体目标（定位）

提示词系统把工程协作的三类内容——**「你是谁」（人格层）、「协作基础」（公共层）、「怎么干活」（纪律层）**——落成结构化分层提示词；**并入核、核内唯一副本、两端从核加载**，使「共享提示词内容」与「共享实现」同源同收益。

- 运行期面 = `thincoder-core/prompts/`（16 档槽位）+ `thincoder-core/tool-docs/`（54 档工具描述）+ 单一解析面 `prompt-files.mjs`；**`docs/` 下不含提示词档**（唯一副本 = 核内运行期面）。

## 2. 功能需求（逐条可验收）

### 2.1 分层模型（四槽 + 特殊模块）

| 槽位 | 职责 | 每槽文件数 |
|---|---|---|
| [1] 人格层 | 「你是谁」：模式 / 角色的身份与边界宣言 | 每人格一份（主会话按模式、子代理按角色） |
| [2] 公共层 | 两模式共用的协作基础（语言 / 人机分工 / 确认门 / 合同纪律） | 恒一份（恒第二位） |
| [3] 纪律层 | 「怎么干活」：本模式的工作流程 / 行为规则 / 工具观 | 每模式一份 |
| [4] 子代理层 | 子代理专用边界与上行通道（`thincoder-core/prompts/subagent-base.md`——**仅子代理场景装配**） | 恒一份 |

独立于主装配链的**特殊模块**：consult（会诊）、advisor（评审）——自含基底、独立注入（§2.6）。

> **人格层定义锚点**：v2 需求 `ENGINEERING-MODE-V2.md` §7.2–§7.4 各角色段的「提示词落点」回指本节。

| 文件 | 内容大纲 |
|---|---|

| `thincoder-core/prompts/persona-normal.md` | ① 身份宣言（coding agent——全项目代码所有者）② 能力边界（直接写码 / 全工具）③ 协作立场（人定方向拍板，我干活） |

> **主会话「在途提问」模式**（借 busy 队列的边界送达——非阻塞软转向通道）。
> **目标**：主 agent 在长执行（子代理在飞 / 长链条）中不必二选一「阻塞等人」或「闷头跑完」——问题随正文流发出 + 给默认值继续推进；用户在忙期提交（排队），消费 = **步边界 pickup（主——当前一步结束后即以普通 user 消息生效，不打断在飞工具）** / 回合尾兜底 / 挂起窗消费；校正自下一步生效（2026-09-24 收正——承该批机制升级）。
> **功能点**：① 双档主会话人格（`thincoder-core/prompts/persona-engineering.md` + `thincoder-core/prompts/persona-normal.md`）写入该段：触发条件（长执行 ∧ 有可先行默认值）+ 一句式模板 + 收到 steer 即校正；
> ② 通道分界：硬门（新范围 / 口径裁决 / 不可带默认前行）⇒ `question` 工具（阻塞）或停下上报；软转向 ⇒ 在途提问（非阻塞）；例行确认门仍走纯文本（现行零变）；
> ③ 纪律：一次一问（与 `question` 工具 ONE-question 同源）· 不重复索要已授权范围 · 默认先行不空转；④ `thincoder-core/tool-docs/question.md` 补两通道分界一句（落点与 TOOLS 面协同——设计裁定）。
> **边界（不做）**：busy 队列机制本身零动（本项不改造队列；机制口径 = `docs/core/design/AGENT-LOOP-ASYNC-POOL.md` §6.8——2026-09-24 已落：多槽（容量 8）+ 合并消费（R15 恢复）+ 步边界 pickup）· 不新增工具 · 不替代确认门硬门 · 子代理无此通道（子代理上行 = `notify_parent` 决策级通道——正典见 `thincoder-core/prompts/subagent-base.md`）。
> **验收**：① 该段在 `thincoder-core/prompts/`（工程 / 普通两模式）在位；② 零文档引用（两界机检族）· 机检净增 0；③ 三包全绿。
> **依赖**：F16 busy 队列（TUI 板块——边界送达 / 挂起窗输入优先）；`thincoder-core/tool-docs/question.md` 既有使用纪律；persona-engineering 锚点 = `ENGINEERING-MODE-V2.md` §7.2。**实现序**：待批。

> **目标**：主 agent **处置时的「做还是记」判断**入人格层——能当场做的一次性小形态项**不进池**（池 = 真债），池面陈年条目在处置前**先 triage**（已落地 ⇒ 追认核销；前提消失 / 重复 ⇒ 废弃）。
> **功能点**：① 人格档（`thincoder-core/prompts/persona-engineering.md`，唯一副本 = 英文运行面）「派发与收尾纪律 / Dispatch & close discipline」节**既有节内增列一行**（`欠账入清单` / *Debts go on the list* 邻位）；
> ② **连带项**：双面台账节生命周期 ② 陈旧半句（`ledger_close` 只认现态「待核销」）定点收正；
> ③ 零文档引用（两界原则）；④ 零 `##` 块计数连带（T-CL1 无涉）。
> **边界（不做）**：不加机械门 · 不改台账机制本体（写命令 / 状态机面 = 同批 #332 另落）· 不落公共层 / 纪律层（子代理非受众——台账写权仅主 agent）· 不重述攒批工作流。
> **验收**：① 该行在 `thincoder-core/prompts/` 对应档在位且与逐字稿全等（一次性逐行比对）；② `prompt-refs-zero` 零命中；③ 三包全绿；④ 零维护者注。
> **依赖**：台账治理机制面 = `docs/core/requirements/ENGINEERING-MODE-V2-SPEC-LEDGER.md` §②.2（收口两源——「已落地 ⇒ 追认核销」的机制落点，同批 #332）。

> **台账治理增补 v2**——清账轮三条。
> **目标**：清账轮的三个收口齿——① **锚点复核**（「归批」行锚的批已收口而活未落 ⇒ 当场重锚/降级——池面未决数须代表真实工作量）② **族行**（同一工作对象的散行归一——一行一对象，标题携成员，成员同批同轮收口）③ **evidence 指针化上限**（行内只留「症状 + file:line + 指针」；软上限 ≈300 字；例外 = 细节尚无落点）。
> **功能点**：三条落**人格层**（台账写权仅主 agent——不落纪律/公共层）；机制单源 = 设计 `PROMPT-SYSTEM.md` §6.23 ∥ D-PS31–33；提示词侧待实施轮 coder 落笔（依据 = 本节设计）。
> **边界（不做）**：不改台账工具面（query/close/evidence 能力已足）· 不加机械门 · 不重述 §6.20 五条正文。
> **验收**：双面该三行在位且逐字稿全等（一次性比对）∥ `prompt-refs-check` 零命中 ∥ 机检净增 0。
> **依赖**：无。**实现序**：已落。

### 2.3 公共层（两模式共用协作基础——`thincoder-core/prompts/common.md` 21 节）

> `thincoder-core/prompts/common.md` = **恒第二位装配**，紧跟人格槽之后；两模式 + 全子代理角色共用。内容大纲（每节管什么，正文见 `thincoder-core/prompts/common.md`）：

| # | 节 | 管什么（一句话） |
|---|---|---|
| 1 | 语言纪律 | 回复/推理/提问用用户语言（中途换语言跟着换）；代码/命令/标识符/路径/术语保留原文；仓库产物遵循项目约定；**面向用户的表述（说人话）**——内部术语 / 代号 / 行话不裸用（出现时随文白话一句；#800 增列面） |
| 2 | 人机分工 | 人定方向拍板、你拥有代码；你确认过的就是合同；流程未覆盖处按三观判（人格 8 条 = 我是什么样的人；公共 9 条 = 怎么配合、冲突时怎么选——分类与角色映射见设计档 §6.53） |
| 3 | 诚实原则 | 正确性优先；有争议摆选项；**当诚实与体面冲突时选诚实**（人格层写「诚实是你的品质」，此处写「冲突时选哪个」——粒度不同，不是重复） |
| 4 | 指令优先级 | 冲突按序：本回合用户原话 > 历史明确指示 > 确认过的任务书 > 项目文档 > 自己推断；新指示只推翻矛盾点，拿不准停下问 |
| 5 | 证据纪律 | 每条事实/行为断言读代码/文档引 file:line，否则标 unverified；已给过的事实直接引用不重读；不预读无关代码 |
| 6 | 文档写作纪律 | **禁脚本代笔**——文档改动逐处读/理解语义/亲自写（语义合并）；用户原话优先于自己的任何转述；**失效表达必删**（规范面失效 ⇒ 删除——D8 语义） |
| 7 | 业务门纪律 | **业务门就是门**：业务前置不满足 ⇒ 显式失败 + 可读原因（禁默认值 ∥ 自动补建 ∥ catch-continue ∥ 空集合 ∥ 中性文案）；兜底唯一判据 = **业务结果不变**（重试 ∥ 缓存回源 ∥ 占位 ∥ i18n 缺键）；自检「删掉它会不会冒出一个业务错误」，答案进笔行 ∥ 设计档；技术手段不得改变业务判定，业务例外只能由用户裁定并落档 |
| 8 | 停下上报 | 冲突/缺口/做不到停下报告，不静默适应/缩水 |
| 9 | 上行通道 | 子代理 → 父侧的在飞上报：只问「答案会改下一步且材料里查不到」；**上抛前先读档——先查自决是默认，上抛携「已查证据行」（`file:line` + 关键原文）**；**发现矛盾的要求 ⇒ 立刻询问（`ask`：摆出冲突双方 + 你的倾向）——不得自选、不得继续权衡、不得拖到收尾**；**两处文档对同一机制描述不同 ⇒ 同判冲突**（摆双方 `file:line` + 倾向，不得自行择一实现）；非阻塞（不空转、不轮询）；父侧回 = `subagent send` |
| 10 | 工具观 | 搜索优先 MCP；代码库探索 repo_outline→doc_search→code_search；独立读调用并行；**何时必须联网查证 / 够没够 / 查不到怎么办**（凭训练记忆答版本/API/协议行为=猜——先查证再下结论；一手源为够；无一手源⇒unverified；查证=取事实≠照行业清单抄一遍） |
| 11 | 工具路由 | 写类场景按表路由不用 bash（write/edit/…/git/execute）；有专用工具就不 hand-roll；**破坏性命令红线**（删除类禁自构造 · 诊断命令只读 · 禁 `2>nul`/`&` 静默掩盖 · 不可逆前置确认） |
| 12 | 系统接口语义 | 各角色收到的提醒字段解读（具体由人格层覆写） |
| 13 | 文档体系评价（通用尺子） | 评价「正在开发的别的项目」的文档体系：前置句 + A 层次三条 + B 位置与命名三条 + C 质量十二条 |
| 14 | 台账常识 | 台账是什么（需求池 + 技术待办 = 项目待办总账 · 跨会话持久 · **唯一待办跟踪面**〔checklist 已废〕）· 存哪（键控项目根 · 用户数据目录 · 不进 git）· 六态 · **读 = 全角色 / 写 = 仅主 agent** · 子代理视角一句（账是你的输入，不是你写面；新发现回父侧入账） |
| 15 | 批次档常识 | 批次档是什么（任务的流转承载物 · `docs/batches/<批>-<主题>.md`）· **§1–§6 六段全图**（讨论 = 主 agent / 任务 + 设计 = eng-designer / 评审发现表 = advisor / 批准 = 主 agent / 实施记录 = eng-coder / 收口 = 主 agent）· 写手段 `batch` 工具（action: create/append/status/close · **append 无路径参数**·段号由身份定 · 主代理挂载 depth-0）· `batchDoc` = 任务书本体（spawn 必传）· 执行者拒收 · **多仓按仓各自**（写面先定目标仓——多候选并存 ⇒ 显式绝对路径；跨仓建档被拒 = 正确行为；跨多仓任务 = 各仓分别建档、分别开批）|
| 16 | 工作结构常识（板 → 域 → 档） | 三层制的并发隔离原则：why 段（并行写冲突因果——两个任务改同一批文件 ⇒ 互踩；分域 ⇒ 隔离；三层方能足够低）+ 判域口径（总是一起动 ⇒ 同一份档；从不同时动 ⇒ 分开写）+ 四条规矩（域 = 并发隔离单位 ∥ 域目录从第一天立 ∥ 拆分恒落域内 ∥ 码档同拍）|
| 17 | 产品常识（Product common sense） | **配置项必须有配置界面**：任何配置项默认同批给出界面写面（载入期项标注「重启生效」）；确不应给界面的，须显式说明理由并经用户裁——「它一直是配置文件项」不构成例外；界面提示文案不得把用户指向界面里不存在的入口 |
| 18 | 安全纪律（Security discipline） | **对待安全的顺序与方式**——先能用、后安全 ∥ 威胁模型源于运行事实 ∥ 挡路的防护先让路 ∥ 失效防护 = 负资产 ∥ 安全项不默认立（五条**逐条携 why**——未来的 agent 照理由在未见场面自推）|
| 19 | 问之前先查文档 | 提问前先在文档里找答案（`doc_search` ∥ 需求档 ∥ 设计档 ∥ 代码 ∥ 项目地图）——文档是「已问过、已答过」的地方，再问等于让人把同一件事答两遍 |
| 20 | 动手前先查文档 | 动手之前先看这件事现在怎么做（接口 / 约定 / 早先的决定）：代码只记形状，理由与后果在文档里；不查就动手结构上是盲改。文档沉默时照做并说清查过什么 |
| 21 | 系统接口 + 产物归属 | 见各节（本表按节序，编号以 `thincoder-core/prompts/common.md` 现档 `##` 顺序为准） |


> **目标**：**主链各角色**（两模式 + 五个子代理角色 explore / plan / coder / eng-coder / eng-designer）从常识面即可知批次档全图；
> **advisor / consult 属特殊模块**（自含装配、不入主链，见 §2.6）——其批次档知识走自身档 + §3 落档纪律。
> **缘起**：批次档此前**按角色分头讲**（主 agent 在 `thincoder-core/prompts/persona-engineering.md` · eng-designer 在 `thincoder-core/prompts/persona-eng-designer.md` · eng-coder 在 `thincoder-core/prompts/persona-eng-coder.md` · 评审在 `advisor-{design,round2,round3}.md` · 纪律层在 `thincoder-core/prompts/discipline-engineering.md`）——**常识面只间接提及**；
> 且**「§1–§6 地图与段语义」无任何提示词侧单一出处**。**边界**：带地图 + 指向结构权威 `docs/core/design/BATCH-RECORD.md`（D2——不重述机制全文）· 不重述 D1 写权全文（纪律层已有）· 不写台账字段含义（第 13 节面）· **不加机械门**。
> **验收**：① `thincoder-core/prompts/common.md` 第 14 节在位（六段行全 + 五要素句齐）；② **连带计数（D3）**：本表标题 + `thincoder-cli/test/prompts-dual-source.test.mjs` T-CL1（13 → 14）；③ 机检净增 0 + 三包全绿；④ 提示词与机制档语义等价。**落点**：`thincoder-core/prompts/common.md`（唯一副本）。

> **破坏性命令行为红线**。**目标**：任何代理（主 / 子 · 两模式）运行期不得自构造破坏性命令；**行为纪律面，不加机械门**（承 2026-09-18「到处加机械限制是拙劣做法」之裁）。
> **五条**：① **删除类动词红线**（禁自构造 `rm` / `rmdir` / `del` / `rd` / `Remove-Item` 等——删除只走既有工具面 `delete` / `git rm` 或极窄白名单）② **诊断只读**（存在性检查只准 `dir` / `ls` / `where` / `type` 类；**禁夹带写 / 删动词、禁自贴「no-op」标签**）。
> ③ **禁静默掩盖**（破坏性 / 写类命令**禁** `2>nul` 吞错、**禁** `&`〔非 `&&`〕串联）④ **不可逆前置确认**（主会话停下问用户 / 子代理走上行 `ask`）⑤ **边界**（不改 `bash` 语义 · 不加机械门 · 不新增节）。

> **公共仓读取**——业务实现时应能发现并读取「公共文档仓」的文档与「公共模块仓」的代码（独立共享仓场景）。
> **现象（用户报告）**：工作区常把公共文档、公共模块放在**独立仓**；agent 做业务实现时**经常不去读公共仓**（文档只看本仓 ∥ 共享模块的代码/接口也不查）⇒ 凭不完备信息干活。
> **父侧诊断**：非能力问题——file 工具可读任意路径；是**机制性三层**：① 检索面双锁——语料 = 单一根（`memory/schema.mjs:305` origin = 绝对项目根）+ 读面按 origin **等值过滤**（`memory/docs.mjs:105-108` `AND origin = ?`——doc_search ∥ code_search 同构）⇒ 公共仓的行**不入语料 ∥ 查出也被滤掉**；
> ② 声明面零位——全核无「公共文档仓/模块仓」声明概念（grep 零命中）；③ 行为面零句——提示词无「实施前查公共仓」纪律，#827 句有写侧无读侧。
> **目标（待讨论细化）**：业务实现（设计 ∥ 编码 ∥ 对账等）时，若工作区存在公共仓（文档 ∥ 模块），agent 应能**发现并按任务读取**其相关内容——不得只凭本仓信息干活。
> **设计定形**：① 发现方式 = manifest `index.publicRepos`（**微调位**——越界源 ∥ 排除 ∥ 优先级）+ **默认来源 = 工作目录树**（零配置可用；标准排除 `.git` ∥ `node_modules` ∥ 构建产物）；
> ② 读取面分层 = 检索接入（写侧：声明根集逐根展开——一层、缺位整根跳过；读侧：origin 集 = 项目 origin ∪ 声明源 origin——单 origin 逐字零行为）+ **读源为默认面**（发布包 ∕ 已装包不入射程）；③ 自持边界 = **读侧对句「自持管写；读取不限」**（+「实施 / 设计前先查声明源」+ 维护句）+ #827 界句「本句管耦合、不管读取」；
> ④ 载体 = manifest（单源；值形 ∥ 解析单一定义 = `declaredPublicRoots`）；⑤ 引用形态 = **声明源前缀形**（`<声明仓目录名>/<仓内相对路径>`——合法可核坐标）+ 记录面有界例外（登记 / 归属零松）+ 三态（**核**〔在场可解析〕∥ **未核**〔声明源缺位——列报不入闸〕∥ **红**〔不可解析 ∧ 未声明〕）。
> **边界（不做）**：不做跨仓写 ∥ 不做自动同步（不 clone ∥ 不 pull）∥ 不新造索引系统。
> **验收（实形）**：① 声明位（AC-37 ∥ L-6.15-1 ∥ 缺省零行为）∥ ② 检索接入写侧（L-6.15-2 ∥ 端面零改动）∥ ③ 检索接入读侧（L-6.15-3 含计划用例 ∥ 单 origin 零行为）∥ ④ 读侧句（双面四档逐行全等 ∥ refs 零命中 ∥ `##` = 8/8/6/6 不变）∥ ⑤ 跨仓引用（L-6.15-4 三态各一例 ∥ T46 ∥ R6）∥ ⑥ 多仓实景——读取公共仓内容可抽查（文档 ∥ 模块各 ≥1 例；受控夹具——零自宣）。

> **三层结构常识**入公共层——并发隔离的结构原则。
> **目标**：任何代理（两模式 + 全角色）在创建 / 重组工作结构（代码树 ∥ 文档树）时即知**三层制**并**知其所以然**——`板 → 域 → 档`；域 = 并发隔离单位；**三层方能将并行写冲突降到足够低**。

> **安全纪律**
> **目标**：让每一次执行都按正确的顺序与方式对待安全——**先能用、后安全；威胁模型源于真实系统而非想象**——防护既不挡路，也不沦为假安全。
> **功能点（定稿五条——逐条携 why）**：
> ① **安全后置**：功能先到「能用」，安全机制排后或按需另轮；功能未定型前不立安全项。（why：未定型时「该防什么」无答案只有想象；按想象写的防护会变成假地板——大家以为已管住，无人再审视。）
> ② **威胁模型源于运行事实**：先跑起来，再从真实数据流枚举攻击面、按最坏损失定防护；不照搬公众平台/行业清单。（why：不看真实系统谈防护 = 防虚构的敌人、挡真实的自己；内部工具按内部实际——2026-10-10 同族裁定。）
> ③ **挡路的防护先让路**：既有防护挡住当前要验证的路径 ⇒ 先关/先拆；不等、不绕。（why：绕路会让「这里被挡过」消失——没人再回来处理。）
> ④ **失效防护 = 负资产**：停用要停干净——配置关 + 运行态残留一并回收。（why：「看起来在防护」比没有更危险：假安全感 + 残留部件 = 一次全速业务中断；实例 = 2026-10-14 出站闸残规则掐死拉仓。）
> ⑤ **安全项不默认立**：自加安全机制默认不立；要立 = 单列提议（防什么 ∥ 代价 ∥ 为什么是现在）由用户挑；禁与功能块平级前置。（why：防护成本与验证速度直接对冲；默认位置 =「待议」非「应有」。）
> **携带「为什么」**（知其然知其所以然）：条文 + 理由 + 实例逐条入提示词——未来的 agent 要能照理由在没见过的新场面自己推对（D9「落笔携 why」同口径；2026-10-14 用户原话「我希望能让未来执行的agent看到提示词能知其然知其所以然。」）。
> **边界**：不裁决「某项防护该不该做」（逐事判断）；不引入新机制；不改既有安全机制本体。
> **依赖**：无（独立纪律条文——不挂任何未决机制）。
> **验收**：提示词侧同条落；每条携 why；逐字稿在册。**落点档/节 = 设计轮定**（上游三观档如需同拍——设计轮提出、用户裁）。
> **设计期跨仓文档勘察**——三句文本。
> **目标**：设计席开工前先查工作目录树内的公共源文档（尤其独立文档仓）——「查没查」在链上可见，设计不再无视跨仓文档。
> **功能点（三句——逐句落点）**：① 设计席义务句（开工前先查 + 勘察证据行落设计档）——`thincoder-core/prompts/discipline-engineering.md`「基本流程·设计」步 + `thincoder-core/prompts/persona-eng-designer.md` §项 1 扩条；② 派单规范句（任务书带公共源坐标，没有就明写「已查无」）——`thincoder-core/prompts/persona-engineering.md` 派单节；③ 评审检查句（评审标准第 10 条：勘察证据行核查）——`thincoder-core/prompts/advisor-design.md`。四档均落 `thincoder-core/prompts/` 同名档（coder 落笔）。
> **边界（不做）**：注入（给设计子代理推文档——`setup.mjs` depth-0 门）= 下一块石头（假死教训在册，零触）；写侧零工程（各仓档住各仓）。

## 4. 提示词编写纪律（16 条：A 内容性 / B 表达性 / C 工程纪律）

**A. 内容性纪律（写什么 / 放哪）**：1 层归属先行 · 2 单一权威源 · 3 人格不越层 · 4 双端语义同源 · 16 提示词与文档分属两界。

**B. 表达性纪律（怎么写）**：5 优先级排序 · 6 规则独立成短句 + 加粗关键词 · 7 命令句 + 否定强调 · 8 关键规则放首/尾 · 9 减量提权（表行 >200 转条目对）· 10 关键锚点重复 + 视觉锚。

**C. 工程纪律（怎么改）**：11 可判可测 · 12 句式稳定（不落散文锚断言）· 13 变更走批（内容权 = 主 agent、落笔走设计链）· 14 语义与格式永不混批 · 15 提示词不含维护者注（出处/日期/批次名进设计档不进提示词）。

**16. 提示词与文档分属两界（用户原话「文档和提示词存活于两个完全不同的环境——文档是设计或者开发时用的，开发工具可以读到文档；而提示词是运行时用的，运行时环境读不到文档——在提示词中引用的文档在运行时都看不到」）**：

- **判据**：文档 = 设计/开发时产物 ⇒ 文档间互引**正当**（开发工具可解析）；提示词 = **运行时**产物 ⇒ 提示词内一切文档引用（档名 / 节号 / 「见 X 档」指路句 / 面级指路句如「→ 见工程模式提示词」）= **运行时死文本**——所指对象不在运行时环境，模型无法解析。
- **「模型可以现场读文档」不构成保留理由**：仓开发档不随运行时载荷分发，不在运行时环境——「读得到」的前提不成立。
- **提示词内合法所指（白名单）**：① 工具与工具参数 ② 会话内对象（台账 / 批次档 / 子代理 / 任务书——由运行时工具面承载）③ 用户项目内文件（cwd 实在物）④ 本提示词体系自身段号与槽位名 ⑤ **操作数**（`AGENTS.md` 类 = 行为动作的对象，非引证——「按 AGENTS.md 办事」是动作 ✗ 不是指路）。
- **写前自查（一句）**：「这句话在运行时环境里所指对象存在吗？」——不存在 ⇒ 删句或改写为运行时可解析形态；引用细节需求 ⇒ 写进**文档面/注释面**（人读），不进模型面。
