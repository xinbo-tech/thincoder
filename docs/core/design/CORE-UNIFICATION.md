### 2.2 目标形态与消费契约

目标形态 = 「一个核 + 两个薄壳」：核是**单一权威源**（一个真包，独立版本，**发布到 npm**），
核的内容 = **两产品共有的机制实现 + 共享提示词内容**（A7）；两壳各自只留**结构性不对称**的端特有部分（A9）；
核的引入**不冻结行为**（A10）——面内（已归一的对称面）行为按**裁决结果**走，未涉面不得无故回归。

```
<仓根>/                                ← 无 package.json（非 workspace——B12）
├── thincoder-core/                              ← 核包 @thincoder/core（唯一撰写处 · 独立版本 · 发布到 npm）
│   ├── package.json                   ← name / version / type / exports / files（含 prompts/ · tool-docs/）
│   ├── <模块>.mjs                     ← S1 逐模块提取（来源可追溯——§2.5 裁决表）
│   ├── prompts/                       ← 槽位提示词（唯一副本——A7；来源 = 两产品 src/prompts/）
│   ├── tool-docs/                     ← 54 档工具描述（唯一副本——A7；来源 = 两产品 src/tools/*.md）
│   ├── prompt-files.mjs               ← 提示词唯一加载面（本模块决定路径——D-C13）
│   └── test/                          ← 核自带测试（S1：两边测试合流）
├── docs/                              ← **基准层**（项目级唯一权威层：`core/requirements/` · `core/design/` · `batches/` · `TODO*.md`）

│   ├── src/prompts/ · src/tools/*.md  ← S2 逐端接线后**删空**（S3 零残留）
│   └── scripts/release-check.mjs      ← + 发布预检（核版本已发布 + 装入版本一致 + 提示词面完备——S2）
```

**运行期面 = 唯一面**：`thincoder-core/prompts/`（档数 = 实读）+ `thincoder-core/tool-docs/`（**54 档**——枚举工具 53 ∥ 目录档 54；读数口径出处 = `PROMPT-SYSTEM.md:310`，同档 `:18` / `:20` / `:153` 同为 54 档读数）；`docs/` 下不建提示词档。

**已撤面（不得再登记 / 不得产生）**：`core-link.mjs`（落 `scripts/`）· `package.mjs`（落 `thincoder-vscode/scripts/`）· 仓根 workspace `package.json` · 成员 lock 删除 · `.gitignore` 分阶段目录行——**整条垫片面不存在**（用户否垫片判定 + 实测证明不需要）。

**消费契约（10 条）**：

1. **核的边界 = 包边界（含提示词内容）**：核内容 = 两产品共有的机制实现 + 共享提示词内容（`thincoder-core/prompts/` ∥ `thincoder-core/tool-docs/` 两面全额——A7；档数 = 实读）；
   壳 = 各自**结构性不对称**部分（CLI 的 TUI / 命令面，VSC 的宿主 API / webview——A9 第 2 条）。
2. **核 → 壳禁止，壳 → 核允许**：核内 import 面**只含核内相对路径 + `node:` 内建**；核的依赖闭包必须落在核内（否则该模块不进核——§2.4 判定闸 G2）。
3. **壳按包名 import 核**：产品代码以裸名 `@thincoder/core`（含子路径导出）引用——**开发期**由本地链接解析、**生产期**由已发布核包解析。同一个 `dependencies` 声明两态通用（manifest 恒为真 semver 范围，无 `workspace:` / `file:` / `*`）。
4. **双态引用**：
   - **开发期 = 本地链接**：`npm link`（在 `thincoder-core/` 一次、在产品目录一次）⇒ `node_modules/@thincoder/core` 为指向 `thincoder-core/` 的链接；**不发布也能开发**，且**零 manifest / lock 污染**（§2.2.1 R8④——`npm link` **自身**零污染；链接态下**再跑 `npm install`** 会写 `"link": true` 条目 ⇒ 口径见 §2.6.1）。**S2 期间的本地 / CI 安装口径与机检见 §2.6.1**。
   - **生产期 = 已发布核包**：`npm publish`（核先发）→ 产品以真 semver 范围从 registry 解析；VSC 的 vsix 因 marketplace **无依赖解析**而**内嵌**核（反排除行，§2.2.1 R4/R5）。
5. **端差以注入表达**：两侧差异用显式参数 / 回调 / 配置项承载，核内**禁止 `if (vsc)` 式壳判断**与产品标识字符串。
6. **核测试独立**：核测试住核包内、只依赖 `node:` 与核内模块；产品侧测试中与核重叠的部分随 S2 改指或收敛（不重复两份断言）。
7. **CI 增设 `core` job**：核测试（B8 三 job 之外新增一个；两产品 job 内部命令不变——依赖由 `npm install` 自动解析）。
8. **提示词面 = 核内唯一副本 + 单一加载面**：核内 `prompts/`（槽位）与 `tool-docs/`（工具描述）为**唯一副本**（档数 = 实读）；
   两端**不得**自持提示词档（S2 接线 + 删档，S3 零残留）；解析面 = 核内 `prompt-files.mjs`（以 `import.meta.url` 为根——D-C13），
   产品侧只调用、不做路径运算。
9. **缺档语义按调用方保留（不统一）**：四个加载面各自的缺档行为是**现状可观测行为的一部分**（B4），
   核内加载面照搬：槽位 ⇒ 静默空串 + 装配期警告；advisor / 工具描述 / consult 消费点 ⇒ 抛错（§2.7 D-C13）。
10. **端特有段以注入进入共享档**：核内提示词档不得出现端名判断或产品标识分支；
    确属结构不对称的端特有指令段 ⇒ 端侧以**注入段**拼入（拼装点在产品装配层），核档内**保留锚点与注入位**（§2.4 提示词面适用性）。

#### 2.2.1 装载机制（机制点与结论）

> 本表只留**机制点与它得出的结论**；探针那一次跑出的取值（文件计数 / 版本号）不入表——机制行为不随场景变，取值会。

| # | 机制点 | 结论（机制行为） |
|---|---|---|
| **R1** | **workspace 依赖在 pack/publish 之后被写成什么** | **不重写**：tarball 内 manifest **原样**保留核依赖声明（写 `*` 或写真 semver 范围者同法）。**源码双证**（npm 内建源 `libnpmpublish` 的 `publish.js`——**非本仓档**，第 70–90 行）：`patchManifest` 只跑 `steps:['fixName']` + semver.clean，无依赖改写 · 同处（:104）`root.versions[v] = manifest` 原样入 packument ⇒ **发布到 registry 的依赖字段与 manifest 逐字相同** |
| **R2** | **`workspace:` 协议支持面** | `EUNSUPPORTEDPROTOCOL: Unsupported URL Type "workspace:"` ⇒ npm workspaces 只能写真范围或 `*`（**没有** pnpm/yarn 那种 publish 自动换版本机制） |
| **R3** | **消费者侧：`*` 声明的解析结果** | `*` 声明在消费者侧解析到 **registry latest**，**不是**打包时对照的那一版；bin 跑通但跑的是未对照版本 ⇒ **`*` 在生产期产生静默版本漂移** |
| **R4** | **消费者侧：真 semver 声明** | **精确命中声明范围对应的那一版**；bin 输出与之一致 ✓ ⇒ **「生产期引用已发布核包」成立** |
| **R5** | **核未发布时的两形态** | `*`/`^x.y.z` 声明者 ⇒ **E404 硬失败**（可见）；`bundledDependencies` 内嵌者 ⇒ exit 0 且自足运行 ⇒ 发布顺序是**真前置**（用户已接受），守卫 = 发布前预检（§2.7 D-C12） |
| **R6** | **vsce 于 workspace 成员目录内** | 默认 ⇒ `ERROR invalid relative path: extension/../package.json`（硬拒）；`--no-dependencies` ⇒ **exit 0 但产物无核**（静默）；再加 `--follow-symlinks` ⇒ **仍无核** ⇒ 成员目录内**绕不开**，必须分阶段 |
| **R7** | **vsce 于扩展目录内（非 workspace）** | **默认即含核**：产物条目内含 `extension/node_modules/@thincoder/core/{package.json,index.mjs,util.mjs}`；**零标志、零垫片** ✓ —— 形态选型的决定性一条 |
| **R8** | **`.vscodeignore` 正解 + 链接形态 + 开发期链接** | ① **devDependencies 一并进 vsix**（含人造 devDep 的探针证实）⇒ 删行**不可取**；② **含核且排除 devDep** ⇒ **正解**；③ junction 缺 `--follow-symlinks` ⇒ `Error: not a file`（yazl，exit 1——**响的失败**）；带标志 ⇒ 含核；④ 链接为 symlink、`package.json` 与 `package-lock.json` **哈希前后一致**（零污染），bin 跑通 ✓ |
| **R9** | **运行期解析（两产物）** | vsix 内 `activate()` 正常激活；内嵌核 version = 仓内核 version = 声明范围；CLI tarball 消费者侧 bin 输出正确 ✓ |
| **R10** | **断言机制可行性 + `file:` 形态反证** | `yauzl` 可列 vsix 条目（无需新增工具链）⇒ **含核断言可落在零构建脚本里**；`file:` 声明 **原样进 tarball**（消费者拿到的是打包机的本地路径）⇒ 该形态否决（§2.3.2 候选 d） |
| **R11** | **核内提示词随产物可达性（A7 · 待实测）** | **未实测**（R7 探针核内零 `.md` ⇒ 无直接读数；推断为「随反排除目录一并打包」，但**不得当保证**）。**处置**：S2 首模块接线前跑最小探针；不管探针结果如何，**断言 D 都是保证**（T-C7 扩判据 + T-C11 反证——缺档即红） |
| **R12** | **核包 `files` 白名单漏 `prompts/` 的失败形态（推演）** | **推演**（未实测）：tarball 无 `package/prompts/` ⇒ CLI 与 VSC 装到**无提示词档的核**；此时**槽位加载面静默空串**（B4）⇒ 系统提示词降级为不完整版且**不报错**——正是 A7 要消的病。⇒ **必须断言化**（核包自身 + 两产物均判档名集合，T-C7 / T-C11） |

**机制结论**：核作为**独立发布真包**时，「开发期不发布也能开发」与「生产期引用发布包」**各自落在标准机制上**——
开发期 = `npm link`（npm 标准开发命令，非打包垫片）；生产期 = `npm install` 依赖解析 + vsce 依赖收集面（两者都是工具默认行为）。

**代价** = 三项、全部登记在 §2.11 A3：① 发布顺序（核先发——用户明示接受）；② VSC 发布机须**真实安装态**（`npm ci`；dev 链接态打包实测硬错，但这不是保证）；③ `.vscodeignore` 反排除行是**唯一**的产品侧装载配置（漏掉 ⇒ 静默无核 ⇒ 含核断言必需）。

**提示词面的装载结论**：提示词档随**核包目录**走——与核模块**同一条通道**（CLI = npm 依赖解析；VSC = vsce 依赖收集面，反排除行同一覆盖范围）
⇒ **零新增装载机制、零新增垫片**（这是选 D-C13 而非另立提示词装载面的一条主要理由）；待实测项与断言兜底见 R11 / R12。

### 2.4 S0 的方法与产出形态

**边界原则（本段的总则——A8 / A9，不得反向使用）**：

1. **对称 ⇒ 进核**——凡两产品**功能基本对称**的面（含低相似度真分叉面）都是核的候选；**相似度低不是排除理由**。
2. **差异不得作为排除理由**（A9）——差异是**本项目的工作内容**；S0 对对称面的职责是产出「**以谁为准 / 融合 / 以何参数注入**」，**排除不是选项**。
3. **端特有桶只收结构性不对称**：① 该机制**只在一侧存在**（无对位）；② 或**依赖壳能力**（CLI TUI / 命令面；VSC 宿主 API / webview）。
   **给出「端特有」判定必须附结构性不对称的证据**（file:line 或「仅单侧存在」的枚举读数）——**不得**以「行为有差异 / 实现不同 / 合并费脑」为由（A9）。
4. **行为不冻结**（A10）——对称面归一后行为按裁决结果走；不要求等于任一端的旧行为；只有**未涉面**不得无故回归。
5. **逐条裁定关口**（A11）——凡归一将改变**可观察行为 / 对外契约**的条目 ⇒ 逐条提交用户裁定（三选一口径与四要素提交形式见 §2.5.1）；**裁定未完毕的条目不得进 S1**。

**范围**：107 对全量（67 `.mjs` + 40 `.md`）**逐条**分类
外加一遍**语义对位发现**（依据 B9——同路径对不是全部差异面；B16 实测：会话面同路径对 = **0**，必须靠对位遍配对）。
**范围口径**：语义对位遍与 107 同路径对**同等地位**（同为席位来源——B15 量级）。
**零代码**：S0 不改产品、也不改核（核尚不存在）。

**四分类（分类是本段唯一产出）**：

| 类 | 名称 | 判据 |
|---|---|---|
| ① | **近乎同（可直取）** | 相似度 ≥0.9 且逐行差异经判读属非语义（注释 / 空行 / 措辞）⇒ 取一侧入核 |
| ② | **语义同实现异（融合）** | 目的同一、实现不同（结构 / 命名 / 边界处理差异）⇒ 融合为一份，逐点记录取舍 |
| ③ | **语义真分叉（须判决）** | 两侧存在**行为可观察差异**（同名函数在边界 / 错误路径行为不同，或两侧测试期望相抵）⇒ 逐条裁决 |
| ④ | **端特有（不进核）** | **仅限结构性不对称**：只在一侧存在，或依赖壳能力（CLI TUI / 命令面；VSC 宿主 API / webview）⇒ 留在壳内 |

**提示词面的分类口径（与实现面不同形，但同规模）**：提示词档的「实现」就是它的**文本**；因此平行定义：

| 类 | 提示词面判据 |
|---|---|
| ① | 逐字节相同 ⇒ 直取（B14：槽位 8 档 / 工具描述 20 档） |
| ② | **指令等价**但文本 / 版式 / 注解 / 跨端文档指针不同 ⇒ 融合（取语义并集、形态归一、指针参数化） |
| ③ | 同一场景给出**相抵指示**（禁止 vs 允许同一行为）⇒ 逐条裁决 + 用户裁定 |
| ④ | 单端独有的**指令段**（对应结构不对称的端机制）⇒ 端特有段，以**注入**拼入共享档（契约 10；**不整档复制**） |

§ 注意：提示词面的 ④ **不是「整档端特有」**——档名集合两端相等（B14）⇒ 无整档端特有；只有**段**级端特有。

**前提校验遍（A12 派生方法；与分类同席、在其之前）**：每个**分叉面**（②/③/④ 候选）先回答两问——

1. **为何分叉？**——把分叉理由写成**可核的句子**（附两侧证据：`file:line` / 行为读数）；
2. **当年前提还成立吗？**——以**实测 / 权威源**核对（不凭记忆、不凭「以前以为」）。

处置：

- 前提**仍成立** ⇒ 按常规分类处置（② 融合 / ③ 裁决 / ④ 结构性不对称）；
- 前提**已失效 / 本就错误** ⇒ **直接归一**（理由消失 = 分叉消失）——**不得**当作 ③ 类行为裁决拉锯（禁止把「两侧实现不同」当成「需要选边的语义分歧」）；
- **范例（B20）**：记忆面分叉源于「VS Code 内置 Node 不支持 sqlite」——该前提不成立 ⇒ A12 判**记忆面向 CLI 语义归一**（以 CLI 为准）；
- ⚠ **归一的后果仍走 A11 裁定**：前提校验只消去「以谁为准」的争议，**不豁免**「改变可观察行为 / 对外契约」的逐条裁定（B20 的引擎下限即此类——§2.11 A8）。

**核内容的判定口径（5 条闸——按 A8 / A9）**：

1. **G1 两侧同职责（两义）**：
   - **G1-a（机制面）**：核只收两产品**都持有**该功能面的机制——**「持有 ≠ 实现一致」**：只要两侧都有这个面（功能对称）就过 G1；
     实现分叉（含相似度 <0.2）**不构成排除理由**，只决定该行进 ②（融合）还是 ③（须判决）。
   - **G1-b（提示词面）**：核收**两端同名提示词集合的并集**（两端集合**相等** ⇒ 无独有档）；
     单端特有的**段** ⇒ 端特有段（注入），**不构成整档排除**。
   - 单侧独有且**无对位** ⇒ ④（须附 B17 式枚举证据）。
2. **G2 依赖闭包在核内**：核内 import 只允许核内相对路径 + `node:` 内建；被依赖的模块若属壳 ⇒ 该模块不进核（依赖须一并下沉，或改注入）。
   **提示词面同理**：核内提示词读取**只从核包内目录**解析（不得指向产品侧 `src/prompts/` / `src/tools/`——N3）。
3. **G3 可独立验证**：无宿主 API（`vscode`）、无 TUI 依赖；测试可纯 Node 跑。
   提示词面：档存在 + 装配可跑（纯 Node）即满足。
4. **G4'「裁决落实 + 不得无故回归」（按 A9 / A10）**：
   - **现行读法** ✓：**先判对称性**（G1）——对称 ⇒ **进核**；该面的行为**由裁决决定**（以谁为准 / 融合 / 以何参数注入 ⇒ 归一后行为 = 裁决结果，**不要求**等于任一端的旧行为）。
   - **唯一的「不变」要求 = 未涉面不得无故回归**（N1 改写）：本次归一未触及的既有功能，其既有测试仍须绿。
5. **G5 差异以注入表达**：禁 `if (vsc)` 式壳判断与产品标识字符串（可读性约束，人工核 + 抽查）；提示词档内不得出现端名判断（契约 10）。

**对外契约（A7）**：S0a / S0b 的对外契约探测结果按 **§2.12** 逐类填兼容形态；**确无法兼容者**单列 §2.12.3 上抛清单——**不得静默破**（F13 / D-C18）。

#### 2.6.0「族」口径：按产品解耦（用户裁定）

**裁定**（追加裁定——实施顺序：CLI 先全完 ⇒ 才动 VSC）：
**S2 的迁移面先把 CLI 全部接完**（同路径对 + 提示词面 + 语义对位族），**VSC 侧一律押后** ✗。

**理由（登记 · 判据 = 用户裁定）**：**VSC = 当前工作台，不可自毁**——当前所有工作跑在旧的 VSC 扩展里，过早迁移 VSC 可能弄坏正在使用的工具；
**CLI = 工作台切换后的落点**——待 **CLI 完全可用**（真机验收通过）⇒ 改用 CLI 做后续工作 ⇒ **之后**才动 VSC（届时即使 VSC 出问题仍有 CLI 可做事）。

**术语收正**：本档此后称「**迁移单元**」（简称**单元**），不再以「族」指代执行单位；「族」保留其在 §2.5 的唯一旧义 = **语义对位族**（16 族 / 63 行——**分析面**，非执行面）。

#### 2.6.1 S2 期间安装口径（发布前 = `npm link`）与收口发布

**张力（本节机制为何必需）**：S2 逐模块接线后，产品 `package.json` 声明**真 semver 范围**（契约 3——产品代码以包名引用核）；
而**核的发布时点 = S2 收口**（§2.6 发布顺序硬约束）⇒ 核发布之前 registry 上无该版本 ⇒ 产品目录 `npm install` / `npm ci`
**E404 硬失败**（与 §2.2.1 R5 同族：核未发布 = 消费者 E404）⇒ S2 期间的依赖解析**必须**由本地链接承载；本节把该口径写死。

| 面 | 谁 · 何时跑 | 命令 | 说明 |
|---|---|---|---|
| **本地（开发者手动）** | **首次接线后** + **每次拉取 / 切分支 / `node_modules` 态变更后**；**核内容变更不需重跑**（链接指向真目录 ⇒ 即时生效） | ① `cd thincoder-core && npm link`（注册全局链接）② `cd thincoder-cli && npm link @thincoder/core`（在该产品目录建 `node_modules/@thincoder/core` 链接）；VSC 同法 ③ `node scripts/dev-link.mjs`（`thincoder` 仓根——dev 链接恢复 ∕ 判；详见表后注） | **零 manifest 污染**（实测：产品 `package.json` 逐字不变——不写 `file:` / `workspace:`） |
| **CI（workflow 加一步）** | workflow 步骤——**产品 job 的 `npm install` 之前**（job 结构与其余步骤零改；`core` job 按契约 7 新增） | 同左两条命令，**写成相对 job cwd 的形态**（两产品 job 均设 `defaults.run.working-directory`——`.github/workflows/test.yml:9` = `thincoder-cli` · `:22` = `thincoder-vscode`）：① `cd ../thincoder-core && npm link` ② `npm link @thincoder/core`（job cwd = 该产品目录）；CI 每次全新 clone ⇒ 必须显式链接（不加 ⇒ `npm install` E404） | 实测：链接就位后 `npm install` **exit 0 且不触 registry**，运行期 `import` 解析成功（全新 clone 同法成立） |
| **产物发布路径（不经过 link）** | 发布流程本身**零改**；执行时点 = **核发布之后**（S2 收口 / 产品发版），依赖由 **registry** 解析（真实安装态） | `npm publish`（核 → 产品）· `vsce package` / `publish-all.mjs`（VSC） | `npm link` 只是**开发 / CI 期解析面**，不进产物（`.vscodeignore` 反排除行取 `node_modules/@thincoder/core/**`；`npm pack` 取 `files` 白名单） |

⇒ 链的规范形恢复 ∕ 判定 = **`node scripts/dev-link.mjs`**（在 `thincoder/` 仓根跑；五链 = cli ∕ vsc ∕ desktop × core ∕ render-core）：

**锁面口径（同批实测发现——写死）**：`npm link` **自身**零 manifest / lock 污染（§2.2.1 R8④ 复核成立）；
但链接就位后**再跑 `npm install`**，产品 `package-lock.json` 会写入该依赖的**链接条目**（`"link": true` + `"resolved": "../thincoder-core"`）。
⇒ **S2 期间的产品 lock 变更不入提交**（开发期链接态 = 本机态）；产品 lock 的**权威形态**在 **S2 收口（核发布后 · 真实安装态）**生成并提交。

**验证（可机判）**：

| # | 机检判据 | 通过条件 |
|---|---|---|
| **L1** | 链接就位（本地 / CI） | 产品目录 `npm install` **exit 0 且不向 registry 取核**（反证：链接缺失 ⇒ E404）；`npm ls @thincoder/core --json` exit 0；版本探针（`import('@thincoder/core/package.json', { with: { type: 'json' } })`）输出**逐字等于**仓内 `thincoder-core/package.json` 的 `version` |
| **L2** | 锁面无链接条目（收口） | S2 收口时产品 `package-lock.json` 内 `"link": true` 命中数 = 0（真实安装态重生成） |
| **L3** | 收口 registry 解析 | 核发布后 `npm ls @thincoder/core --json` 由 registry 解析成立（断言 C）+ 真实安装态 `npm ci` exit 0 |

**收口动作（位置写死）**：**核发布 = S2 的收口动作**（核发布一次 → 产品发布在其后）；核发布**不是** S2 的**进入**条件（进入条件只需开发期链接就位——§2.6 段表）。
**open（登记 · S2 收口时定）**：核发布后 CI 该 `npm link` 步骤的去留（撤 = 按契约 7 由 registry 解析 / 留 = CI 恒测本地核）——两者均不改产物与发布链。

### 2.9 与既有纪律的冲突点核对

1. **F7（phase 1：产品运行行为零改动）**：**本板块不适用** ✗（A10）——它是**搬迁批**的约束（纯位置变更不应改行为），
   本板块是**统一批**；替代 = G4' / D-C15（**不得无故回归**）。
2. **D14**：与用户裁定 **A7** 相抵——本板块以 D-C5（提示词并入核）/ D-C13 / D-C14 承载现行口径（核内唯一副本 + 单一加载面）。
3. **「单一权威源」纪律**：核实现的唯一撰写处 = `thincoder-core/` 包本体；**提示词唯一副本 = 核内 `thincoder-core/prompts/`**（运行期加载面）；仓内零重复实现副本（**实现面 + 提示词面**）；
   dev 链接是解析指针、非撰写面——不构成第二权威源。（本条覆盖范围 = 实现面 + 提示词面。）
4. **「多实现面 · 语义同源、不做 byte-identical 硬一致」纪律**：本板块**跨端无多实现面**（核与壳是包边界；提示词运行期面亦为跨端单一份）；
   **保留的一致面（非端差） = 无**（单副本；无第二面可对）。
5. **CLI「零运行时依赖 / 无构建步骤」承诺**：**改述**——零依赖只约束**第三方**（B7 自述语境；自家核不在范畴）；「无构建步骤」= 两产品仍直接运行、无源码编译（装载靠 npm / vsce 的**标准**依赖机制，不引入打包步骤——D-C9）。N7（核内零裸包名）继续守住第三方零依赖。
6. **机器检查面**：核目录 `thincoder-core/` 不在 V5 的代码树枚举（`src` / `scripts` / `bin` / `test`）内 ⇒ 核**符号**不进宽形态索引（报告面，不入闸）；
   核路径锚的可解析性由「仓根相对路径」解析序保证。**S1 前须实跑一次确认零红**（N6）。
7. **发布链边界**：「不改发布链（npm publish / vsce + ovsx）」的边界解读 = **对外命令接口不变**；
   现行形态下发布链**连内部步骤都不新增**（无垫片、无分阶段），只在既有钩子上加**预检 / 断言**——F7 边界改述见需求档。
8. **零依赖 / 零构建与**核的发布**（新增）**：核发布到 npm 引入「核先发、产品后发」的顺序依赖——**不是**新增构建步骤，而是**发布编排**前置（D-C12 / §2.11 A3）；用户 A6 已明示接受该顺序。
9. **提示词面的「端特有段」**：端特有指令段（如 VSC 的池规则段）以**注入**保留在端侧；该端镜像档已退役，提示词唯一副本 = 核内；

- U2 落 CLI 侧**入口装配调用**：`configurePromptInjections(CLI 取值表)`——表 = §2.13.2「CLI 列」13 名（含显式空串）；调用时点 = CLI 进程入口、任何装配之前（调用期应用 ⇒ 无导入序要求）。
- VSC 表 = §2.13.2「VSC 列」——**只登记不实现**（VSC 押后；随其接线轮落地）。
- U2 验收②以本机制为前置；机制面由（五）守、端侧行为由 U2 用例守。
- **入口面（U2 补）**：「未配置 = 恒等」（（三））⇒ **入口漏配 = 静默回退到字面**（正是本机制要消灭的缺陷）⇒ 判据落**端侧入口用例**：起真实 CLI 入口径断言零字面 + 13 名取值在场；核内**不设** fail-closed（保「未配置 = 现行行为零变」）。

**（七）U0 排期形态（独立成笔与否）**

**结论：U0 = 独立「前置笔」——单笔提交 · 独立回退 · 排 U2 之前；不占单元号、不迁产品档。**

1. **核内面独立可验**：U0 只触核（原语 + 三装配面挂点 + 用例）；与产品侧零耦合 ⇒ 提交 / 回退粒度最细（`git revert` 单笔）。
2. **并入 U2 违提交纪律**：U2 = 40 档删除 + 3 根改指 + 3 单元测试档 + 供值；再并核机制 ⇒ 核机制与产品删档混一笔、验收混杂 ⇒ 违「单模块一步一提交」。
3. **前置性**：U2 验收②「装配后零字面」须机制在案（U2 只做接线 + 供值）。
4. 核回归基线随 U0 落轮收正（读数 = 落轮后实跑取数，本档不载值）。
