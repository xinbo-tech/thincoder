## 1. 分层纪律与测试门（v2）

### 1.1 分层纪律

一次代码改动的验证**按层收口**（浅改浅验 ∕ 深改深验 ∕ 链终收口时一次集成测试）——口径 = 需求档 `requirements/TESTING.md` §1 总纲 + §2 F1–F4；**本档只引用不重述**（D2 单一权威源）：

| 面 | 时机 | 内容 | 谁跑 |
|---|---|---|---|
| **改动内**（需求 F1） | 每次改动 ∕ 修正轮 | 只验本任务改动——跑改动面相关单元测试（单元测试档——§2；单档 ∕ 相关子集）；不得逐轮跑集成测试 | eng-coder |
| **链终收口**（需求 F3） | 链末 | **集成测试**（收口时恰一次/端——= 集成测试集）——不在 eng-coder 链内；入口 = 各包 `npm test`（§10 F1） | 父侧 |

- **报告义务句 = 需求 F2 原文逐字**（未跑集成测试时随报告带出）。
- verify 只收模型的 `verification.status` 声明，**不代跑任何测试**（需求 F4；verify 语义 = `design/VERIFY-REDESIGN.md`）。
- **脏树零回归判据**（跨板块通用实践沉淀）：工作树含他批 ∕ 并发在途改动时，「零回归」只能判**增量零**——先以**点名命令**跑一次取**实测基线**读数，变更后同命令复跑，判读数**逐字相等**（增量零）；**不得以绝对绿值（「集成测试全绿」）冒充零回归**。

### 1.2 slow 标注

`slow(name, fn)` = `export { test as slow }` **纯别名**（`thincoder-cli/test/slow.mjs`）——照跑、无 skip、无防漏拦截（§10 F3）。
判据 = AC-M10-3（`THINCODER_TEST_FULL` / `THINCODER_SLOW_GATE_MS` 代码面零匹配）。

**测试入口（v2——每包一条 `test`；分层与空集语义 = §10.3）**：

| 脚本 | 入口 | 用途 |
|---|---|---|
| `npm test` | `thincoder-cli/test/run.mjs` | **集成层**（收口时）· `test/integration/*.test.mjs` 单层收集 + 启动前反查 + 空集非零 |
| `npm test`（核） | `thincoder-core/test/run.mjs` | 无集成层 ⇒ exit 1 + `requirement N20` 说明（空集不读作绿） |
| `npm test`（VSC） | `thincoder-vscode/test/run.mjs` | 集成测试（收口时）· 显式清单 + 清单↔盘上两向自检（空集守卫未落——§10.3 面差） |
| 手工 | `node --test docs/batches/<档>.test.mjs` | 单元测试档直达（不经入口——需求 F5） |

**核树面**——第三实现面：`thincoder-core` scripts = `test`（`node test/run.mjs`）；**无集成测试层**（集成测试集射程 = cli ∕ vsc ∕ desktop——需求 §3 N20）⇒ 该入口不跑用例、exit 1 并说明（§10.3）；核的验证面 = 批内单测档 `node --test` + 语法门；CI 核作业（`.github/workflows/test.yml:36` ∥ `:48`）随本语义变红，处置 = CI 面另轮。

## 2. 测试库存治理（按需加 · 两层形态）

存量测试库存已清零，转入**两层形态**（口径 = 需求 `requirements/TESTING.md` §1 总纲 + §2 F6 ∕ §3 N1–N2；**本档只引用不重述**）：

- **单元 = 单元测试档**：零留存（用毕即删——批档 §5 留一行读数；一批带一至几个文件 · 名随批次档 · 住批次目录）——**永不进任何门**（集成测试 ∥ CI ∥ 发布钩子 ∥ 自建链——均含；零维护；**红不作门禁判据**）。
- **集成 = `test/integration/`**：业务设立 + 生产补入，常驻（窗口 50–100 ∕ 仓 · 只住三前端——需求 §3 N19 ∕ N20）；
- 测试不强制配给每次改动；补的测试若 >500ms 重 IO，仍标 `slow()`（纯别名——照跑，无 skip）；
- 红线：拆分 / 迁移类重构保证**断言数不减**（逐字迁移保真）；存量清理轮走**删除清单制**（逐条列明 + 父侧核销，差额 = 清单数，不再是“不减”）。

当前仓库的测试 = 批次本地单元测试档 + 集成测试集 + 真端点 smoke：`npm test`（单入口）= 集成测试（收口时）（§10）；冒烟测试不在入口内，手工跑（花真 API 钱）。

### 2.1 防膨胀机制映射（成本判据 · 口径 = 需求 §1.3 ∕ N21）

**根判据（本档成本取舍总纲）**：验证投入 ∝ 失败代价，与代码量脱钩——「留什么 ∕ 跑什么 ∕ 留多久」一律以此为尺。

两道闸的落地 = 本档已定形态（**机制零新增**）：

| 闸（需求 §1.3） | 本档机制面 | 落点 |
|---|---|---|
| **不累积**（单元） | **单元测试档**——零留存（用毕即删）、**永不进任何门**（无常驻集合 ⇒ 后续改动不为它缴税） | §3.1 ① ∕ §3.2 |
| **有上限**（集成） | 常驻集成测试集 + **规模窗口 50–100 ∕ 仓**——超窗裁减回窗内（域 = 三前端） | §2 ∕ §4 |

- 执行形：**纪律判据**——不配机械闸（承需求 §1.3）；守闸读数（现集成数 ∕ 窗口）随**收口测试行 ②半**（§3.3）逐批带出——零新增簿记。

### 2.2 单元测试档挂载面规范（双实例族防御 · #788）

单元测试档（批次目录 `*.test.mjs`）在「平 node 直测」下，凡取**产品码经 `@thincoder/*` junction 解析的件**（核件 ∕ render-core），取件路由必须与**消费面同源**
**禁直取仓根兄弟目录**（`thincoder-core/…` 直路）用于 `instanceof` ∕ 单例 ∕ 注入缝（seam）面。

- 机制（单源引用）：Windows junction 目标 = 规范形拼写（`scripts/dev-link.mjs` 单一产生口 ∥ `docs/core/design/CORE-UNIFICATION.md` §2.6.1）；直路拼写与 junction 目标不一致时（常见触发 = 小写 `d:` 拼写进程），同一文件生成两个 ESM URL 键 ⇒ 双实例（`instanceof` ∥ 单例比较 ∥ 缝注入失效；潜伏面）。
- 跨路恒等断言（「直路实例 === junction 实例」类）一律改形：**同路取件**（缝真效）+ **canonical realpath 同文件断言**（挂载面判据）。

### 2.3 现行态认账（「认账为骨架」）

> 本块 = 该现状的**唯一权威陈述面**（D2——包级文档引本块、不各自重述）；「认账」= 显式接受现状并使之可读、可见——**非**「测试已就绪」的宣称（自动绿不得被误读为未测面已被验证——承需求 `requirements/TESTING.md` §6.2 F26 同判据）。

## 3. 测试生命周期（三层来源）

> 术语辨异：**技法层**（单元 = 最小可测单元 ∕ 隔离依赖〔桩 ∕ 假件〕· 集成 = 组件组合与交互〔真实装配、可贯穿整条链〕——口径 = 需求 §1 总纲；**两技法永不互转**）· **来源层**（①②③——测试的出身与寿命）· **收口分工**（改动内单元测试 ∕ 链终收口时集成测试——一次改动何时跑什么；口径 = `requirements/TESTING.md` §2 F1–F4）——**三者正交**，勿混。

### 3.1 三层来源与寿命

| 层 | 落地物 | 来源 | 寿命 / 去处 |
|---|---|---|---|
| ① 单元（开发期） | **单元测试档**（批次目录——名随批次档） | 每批开发过程（批次档 §2 列着） | **零留存（用毕即删——批档 §5 留一行读数）**（不进任何门、零维护；无「再跑旧档」面）；**与②③ 永不互转**（§3.2） |
| ② 集成·业务 | `test/integration/` 常驻档 | 业务场景设立（开发期不产） | 常驻 + 发布门 |
| ③ 集成·生产 | `test/integration/` 常驻档 | 实际运行常出的问题补入 | 常驻（越用越准） |

- **零新增簿记**：① 档的来源票据 = 批次档 §2 文件表 / §5 交付表 + 对端登记差分——收口测试行直接引用，不建新台账。
- **零留存是常态**：单元测试档用毕即删、永不进任何门；**两层永不互转**（§3.2）——集成用例一律按业务需要单独设立。

### 3.2 两层界线（永不互转）

单元 ∕ 集成（技法层口径 = 需求 §1）**永不互转**（需求 F8）：单元测试档零留存（用毕即删）；集成用例一律按业务需要单独设立（业务设立 ∕ 生产补编——§3.4）。

### 3.3 批次档 §6 收口测试行契约（双半）与同步面

「测试」行（收口测试行）落在批次档 §6 核销同步清单（槽位枚举权威 = `design/DOC-DISCIPLINE.md` D7 行 + 工程纪律档两档 D7 枚举）。行内容两半：

| 半 | 内容 | 对账面 |
|---|---|---|
| ① 本批单元测试档清单 | 逐条：`<档名>——用毕即删`（批档 §5 留一行读数；两层永不互转） | 批次档 §2 / §5 清单（逐条可对） |
| ② 集成影响核 | `新增 <场景>` / `修订 <场景>` / `无` ＋ **窗口读数**（现集成数 ∕ 窗口；需求 §1.3） | 主 agent 评估结论（F10——不外包不自动） |

- **执行人** = 主 agent（§6 作者）；① 半零落手（用毕即删——零维护、零动作）。
- **同步面（落笔清单）**：`design/DOC-DISCIPLINE.md` D7 行（槽位枚举权威）+ 同前需求档 D7 行（eng-designer 修订）· 工程纪律档（EN）的 D7 枚举（主 agent 内容权 + eng-coder 落笔）· 对端两文件同款。
- **落笔时机** = **无冻结窗口冲突时**（父侧排程）。
- **收口走查纪律**：**收口看一张截图**——截图 ∕ 可见面工具只解决「**能不能看到**」，「**该看什么**」靠**程序级搁置清单回核**（逐条核设计档登记 ∕ 搁置项——口径 = `design/BATCH-RECORD.md` §5.3）；基建 = Electron `capturePage`（零依赖降级路）+ Playwright 直驱（可判引用件 = `thincoder-desktop/package.json` devDependencies 含 `playwright-core`）。

### 3.4 演进评估与 ③ 收编

- **触发**（主 agent 逐批核）：需求批次收口 / 行为变化（用户报“实际运行的常出问题”）/ 发布前。
- **评估动作**（不外包、不自动）：对触发来源逐条问——是否触及既有场景族语义？是否新增“常出问题”值得常驻？→ 需变则出条目（形态 = §6 收口测试行 ②半 或需求池指针），交 eng-designer 定形、eng-coder 落。
- **③ 收编**：真问题处理后——用户 → 主 agent 登记（落点 = 需求池条目或随 §6 行——不新增簿记）→ 转②（业务语气场景化——需求 F11）。

## 4. 集成测试集：承载、执行与发布门

**射程（需求 §3 N20）**：集成测试集**只住三个前端**（cli ∕ vsc ∕ desktop）——**核仓（`thincoder-core` ∕ `thincoder-render-core`）不设集成测试集**（测前端自然覆盖核）。「双端」（§4.3 ∕ §4.4）与 §5 用例表 = **CLI ∕ VSC 镜像对**（需求 F14）；桌面面的驱动 / 隔离面单源 = `docs/desktop/design/E2E-TESTING.md`。

### 4.1 承载选型

判据：① 扫①边界机械性（域界可判）② 既有入口约定与单文件调试 ③ 执行集零混入（「集成测试（收口时）」语义单义——§10 F1 单入口；无第二入口漂移）④ helpers / fixtures 复用成本 ⑤ 端内清单制适配 ⑥ 双端镜像成本。

| # | 候选 | 判据逐项评估 | 结论 |
|---|---|---|---|
| 1 | **[`test/integration/`] 子目录** | ①域界 = 目录界（扫①只碰顶层测试文件——机械可判）②同根（单文件直达）③单层 glob / 显式清单天然不含（零改）④同树复用⑤对端另立集成测试清单（登记制同性质）⑥双端同名同位 | **选定** |

**对照注**：隔离靠**域界**（机械可判），不靠**标记**（靠记得）。

### 4.2 runner 选型

集成测试集执行面 = **并入单入口的集成层**：`thincoder-cli/test/run.mjs` 收 **单层 glob `test/integration/*.test.mjs`**（收口时恰一次/端——§10 F1）；单元测试档不在任何入口的收集面（住 `docs/batches/`，`node --test <档>` 直达——§10.3）。

### 4.3 接口契约（双端）

| 项 | 本端（CLI） | 对端（同构） |
|---|---|---|
| 目录 | `test/integration/` | `test/integration/` |
| 文件命名 | `<场景名>.test.mjs` | 同 |
| 目标集合 | `test/integration/*.test.mjs`（单层 glob，零第二层） | 显式清单（沿对端“登记即跑”惯例） |
| 入口 | 集成层并入单入口 `npm test`（`thincoder-cli/test/run.mjs`；单元测试档不经入口） | 同款 |
| env 门 | 无（执行面 = 入口本身） | 同 |
| 发布门接线 | `thincoder-cli/scripts/release-check.mjs`（lint → `thincoder-cli/test/run.mjs` 集成测试（收口时）；失败详情自动提取——`:57-63`） | 对端 prepublish 同构 |
| 不变量 | 收集面反查（`test/` 下 `.test.mjs` 落在 `test/integration/` 之外 ⇒ fail-closed）+ 空集非零（§10.3）；单文件调试直达不经门 | 同（显式清单天然排除） |

- 裸 `node --test`（无参）非本仓入口（各入口均显式目标）——不设防线。
- 执行顺序：集成层随 `npm test`（§10 F1）；单元层无入口（`node --test <档>`——需求 F5）。

### 4.4 双端镜像策略

- 场景目录 = **共享语义源**；两仓**各自实例化**（语义同源、各端原文自持、不做字节一致）。
- **驱动手段允许各端不同**：本端 = 真子进程 / 模块直驱 + 脚本化 provider；对端 = 扩展模块 + 宿主 mock / DOM 环境——**判据语义对齐、宿主各自**。
- **不以任一端产物回改另一端（对齐经同源设计）**——实现形态纪律，✗ 不构成差异保留依据；**端差默认 = 消**（机制面差异 ⇒ 归核单源 / 两端口径统一）；保留仅限结构性不对称 + 证据 + 显式裁定（A9）；差异登记面 = 记录已裁的保留项，✗ 非未决差项兜底。

### 4.5 覆盖划分（不重复纪律）

- ① 可断言实现内部（开发自证自由度高）；②③ **只断言业务可观察结果**——允许读状态文件 / 产物验证结果，不锁私有结构形状。
- **判定探针（口径内）**：verify 关口的机械判定旗位属口径内判定探针——以其判定值断言“放行 / 打回”业务结果，不视为“锁私有结构形状”；机验不改挂输出串（文案随模型措辞漂移；探针 = 机械判定信号本身，更稳）。
- 禁止同断言双持；②③ 不做 ① 的机械改写（“同样的测试做两遍没有意义”）。
- 永不互转（§3.2）即该纪律在收口时的执行面。

## 6. 散文锚退役（PROSE-ANCHOR-RETIRE）

### 6.1 判据（执行版）与口径裁定

**判据三条**（同时成立即散文锚）：① 断言对象是**非测试文件文本**或其派生切片；② 断言其**文本内容**在场 / 缺席 / 出现次数 / 相对顺序；③ 断言对象**不是**结构机检保留面所判属性。

**口径裁定（分类的唯一执行口径）**：

| # | 裁定 | 说明 |
|---|---|---|
| C1 | 载体判据 | 按**被断言文本的载体**判，不按 needle 原产地判。断言对象 = **执行产物**（函数 / 工具返回值、子进程输出、渲染帧、测试自建临时域文件）或**结构 / 数值常量** → 不命中 ①（保留）；直接读非测试文件所得文本，或经 `import` 取到的源码静态文案字面量 → 命中 ① |
| C2 | 非测试文件边界 | **仓内一切非测试文件**：产品树 `src/**` · `docs/**` · `scripts/**` · `bin/**` · `webview/**` · `locales/**` · `package.json` · 仓根 `*.md` / `*.json` / `*.mjs` · `AGENTS.md` · `README*` |
| C3 | 保留面 = 封闭枚举 | 结构机检封闭枚举所判属性（段引用 / 计数 / 批次档轮次行 / 台账判据 / 行宽 / 归册 / **工具契约面**）。对非测试文件文本的**出现次数 / 相对顺序 / 位置**断言**不属**该枚举 → 按散文锚处置 |
| C4 | 存在性断言保留 | 文件存在性断言不属「文本在场 / 缺席」→ 判据 ② 不成立 → 保留 |
| C5 | 测试文件自身保留 | 断言读的是 `test/**`（含登记清单 / helpers / fixtures / 测试内常量）→ 判据 ① 不成立 → 保留 |

**判据补充（C1 的实质判法）**：

| # | 补充 | 说明 |
|---|---|---|
| C1-a | **提示词句子不豁免** | 载体判据按**实质**判——**不问文本从哪来**（读盘 / 装配器或渲染出口的返回值 / 写入 system prompt 的装配结果），只问**断言的是否是提示词句子**：断言提示词句子（含装配器传出的话语、注入块、降级句、槽文本，以及装配产物**与字面常量的全文相等 / 不等**）→ 命中 ①——**「不读文件」不是豁免理由** |
| C1-b | **工具契约面与工具返回文案保留** | **模型实际收到的工具契约对象**（工具 `description` / 参数说明）与**工具返回 / 拒绝文案** → 契约守卫 / 行为输出，非文档散文锁 → 保留。注：读源码档文本（含源码里的描述串）仍命中 ① |
| C1-c | **非句子对象保留** | 结构 / 数值 / 判定信号（槽文件表与集合成员、长度、警告清单与警告文案、旗位、退出码）→ 保留 |
| C1-d | **locales 资源文本保留** | `locales/**` 文本值 = **产品资源文案**（界面 / 本地化面——产品面）→ **不命中 ①**（保留、不进清单）；读非测试文件**源码 / 文档文本**仍命中 ① |

**归类三值**：`整删`（该用例全部断言均为散文锚——删后无内容残留）/ `段删`（夹锚断言——只删锚断言行，行为断言保留）/ `保留`（无锚断言；**不进清单**）。

### 6.2 方案选型与清单制

| # | 候选 | 判据逐项评估 | 结论 |
|---|---|---|---|
| 2 | **逐条删除清单制**（逐条列档 + 用例名 + 行号，父侧核销） | 零误删：✓；对账：✓（用例总数下降 == 整删条数，机判）；沿既有纪律：✓（存量清理轮走删除清单制）；键控：✓（档 + 用例名，行号 only as-of） | **选定** |

**清单制**：产出 = **逐条删除清单**（`档:行` + 用例名 + 归类依据），交父侧核销；**清单外断言零触碰**；**对账式**：`用例总数(批后) = 用例总数(批前) − 清单整删条数`（计数口径 = 单入口执行集内 `test(` / `slow(` / `it(` 起始行计数——§10 F1）。
**零误删**：结构机检 / 行为用例**零改动**（删除集与保留集互斥且穷尽）。
**点名项同批处置**：跨板块被点名的文本面断言随该批退役（形态 = 就地退役注记，保号）。

### 6.3 禁令（禁止新写）

新增断言**只允许**：**行为面**（业务可观察结果）与**结构机检**；**禁止新写散文锚**。
纪律落点 = 本仓提示词测试纪律节（EN）+ 需求档 + 本档；对端落点自持于对端档。
**相容口径（与端到端 harness 的关系）**：子进程输出 / 协议帧 / 工具返回文案等**执行产物**类断言**不命中**判据 ① ⇒ 非散文锚、属允许的行为面。

### 6.4 边界

- 检查器**语义与判据零改**（保留面不动）。
- 台账本体内容治理 · `slow` 标注纪律（纯别名——§1.2）· 行为测试的增删改——均不在本机制射程。
- **既有验收标准（AC）中的锚式判据**不随本机制清理（射程 = 已落地测试断言 + 点名项）；新批次的 AC 判据按禁令只写行为面 / 结构机检。

### 10.2 测试收集面**反向**自检（盘上 ⊆ 执行集）

**方案（本条目）**：

1. **域** = `test/` 树下全部 `*.test.mjs`（**递归**——嵌套档不许绕过）。
2. **判据** = 域内每一档都在**对应执行集**内；否则 fail。
3. **时序** = **先于 `node --test` 启动**（fail-closed——失败档不被执行、错误不被运行输出淹没）。
4. **白名单 = 无按档豁免名单**；豁免判据 = **命名约定**（域只含 `*.test.mjs`——helper / fixture / smoke 档（`smoke-settings.mjs` 等）命名不含该后缀、天然不入域；VSC 清单里的非域条目两向皆不受影响）。将来真出现「须在盘但不可执行」的档 ⇒ **改名**（`*.fixture.mjs`），不得加名单——名单即又一个静默漏跑的藏身处。
5. **文案（AC 断言对象）**——**三包同前缀** `✖ test manifest check failed: `；`<rel>` = **相对包根**的路径、正斜杠分隔（例 `test/foo.test.mjs`；基准 = `run.mjs` 自身的 `root`，同集成测试 ②）。下列三行 = **完整样例（逐字：前缀 + 故障类型 + 括注 + `<rel>`）**：

```text
✖ test manifest check failed: unregistered unit file (register it in test/files.mjs — an unregistered file is never executed): <rel>
✖ test manifest check failed: uncollected test file (move it into test/ or test/integration/ — an uncollected file is never executed): <rel>
✖ test manifest check failed: uncollected test file (move it up into test/ — this runner collects a single level; an uncollected file is never executed): <rel>
```

（行 1 / 2 / 3 = VSC 单元测试 / CLI 收集面 / 核收集面。）
6. **「零用例行」判据模式**（「自检先于测试运行」的机判面）：自检失败输出**不得含** `node --test` 的测试标记行（`ℹ tests <n>` / `ℹ pass <n>` / `ℹ fail <n>` 等 `ℹ ` 计数行——实测：跑过即打印 `✔ <用例名>` + `ℹ tests 1`）**且不得含** `✔ ` 用例行；`✖ test manifest check failed: ` 行自身 = 自检故障行（非用例行）。判据 = 命中该前缀行 **∧** 零 `ℹ ` 计数行。

### 10.3 执行层分离与空集处置（现行）

**分层**（口径 = 需求 F1 ∥ F3 ∥ F5）：

- `npm test`（每包单入口）= **集成层**：`thincoder-cli/test/run.mjs` 目标集合 = `test/integration/*.test.mjs`，单层 glob，零第二层。

- 因此 `npm test` 只证明一件事：集成层的发布门。改动内自查走单档直跑，不再与发布门共用一条命令。

**核仓口径**（需求 N20：核仓不设集成测试集）：

- `thincoder-core/test/run.mjs` **无目标集合**——不跑任何用例，只做收集面反查并说明「本包无集成测试集」。

## 11. UAT 验收总表（RTM）

> 定位：**交付物面**的验收报告——集成测试（= UAT · 用户验收测试）的文档面。用途 = 甲方签字后作收款凭证；故**甲方读得懂**、有**签署面**、**签后即证据**。
> 与内部面的分野 = **谁验收谁**：单元测试档 = 内部回路（不进任何门、零留存〔用毕即删——批档 §5 留一行读数〕）；RTM = 交付物面（常驻、与集成用例同寿命）。
> 依据 = 用户 2026-10-16 裁定（逐字见需求档条目区）；纲领层（标准）读数见 §11.7。

### 11.1 方案与理由

**目标状态一句话**：每个有集成用例的发布单元（端 = cli ∥ vsc ∥ desktop）在同测试目录下持有一份 Markdown 总表（`test/` 下的 RTM 总表——拟）——**按业务故事分节**，**一节一表、一行 = 一个集成用例**；行前段写「怎么做」（步骤），后段写「怎么算通过」（验收标准）；表尾 = 签署面。

**理由三条**：

1. **交付物须耐久，批档可整体清理**（机械事实）⇒ RTM 住包内 `test/`、随代码进 git（**不引用批档**与引用方向 = §11.6 行 1）。
2. **锚在集成用例上**，不另造证据面：行「证据」列指向 `test/integration/<场景名>.test.mjs`（沿用 §4.3 既有命名），可复跑、可重现。
3. **报告要素照公开标准收敛**，不自创字段（条款见 §11.7）。

**先例对齐**：先例设计节 = **§10**（增量设计：目标段 + 功能点 / 列定义表 + 验收表 + 边界）∥ 先例批次 = **无**（批档为一次性载体、可整体清理 ⇒ 长期面不指批次）；「证据」锚沿用 **§4.3** 的 `<场景名>.test.mjs` 命名——不另立命名。偏离：无。

**公共源勘察**：工作目录树内公共源文档已查（`docs/**` + 三前端 `test/**`）——相关 = 本档自身；标准发布方站点已查（ISO/IEC/IEEE 29119 系列官网 · 29119-1 免费正文 · GB/T 25000.51-2016 公开发布版）。第二独立文档仓：无。

### 11.2 落点 · 命名 · 份数

| 项 | 取值 |
|---|---|
| 落点 | `<包>/test/` 下的 RTM 总表（拟；包 = 端，如 `thincoder-cli/test/`） |
| 命名 | 文件名 = RTM 总表（拟）；文档标题 = 「UAT 验收总表（RTM）」 |
| 份数 | **已裁 = 每端一份**（cli ∥ vsc ∥ desktop）——RTM 是「该交付物验收的总表」，签署按交付物签 ∕ 行与用例同包 ∕ 零跨包引用；备选与取舍 = §11.12 O-1 |

- 落点 `test/` 不触收集面自检：自检域 = `test/` 下 `*.test.mjs`（§10.2 判据 4 命名约定），`.md` 天然不入域。
- RTM 是给人读的文档 ⇒ 遵守行宽纪律（无单行 > 300 字符）；是否入各包 doc-check 域 = 实施轮核实（§11.12 O-6）。

### 11.3 结构（故事节 + 一行一用例）

**一节 = 一个业务故事**（H3 标题 = 故事名 + 一句话目的）；**一节内一表**。无中间分组层。

**列定义（8 列）**：

| 列 | 取值 | 标准依据（§11.7） |
|---|---|---|
| 编号 | `<故事序号>-<用例序号>`（如 `1-3`；文档内唯一） | GB/T 25000.51-2016 §6.4.1.3 a) |
| 怎么做 | 操作步骤（业务语言：从用户可见入口起，一步一句） | GB/T 25000.51-2016 §6.3.1.1 d) |
| 怎么算通过 | 验收标准（可观察的通过条件） | GB/T 25000.51-2016 §6.3.1.1 e)–h) · ISO/IEC/IEEE 29119-1:2013 §4.15 / §4.26 |
| 结果 | `通过` ∥ `未通过` ∥ `未执行` | GB/T 25000.51-2016 §6.4.1.3 d) |
| 执行日期 | `YYYY-MM-DD` | GB/T 25000.51-2016 §6.4.1.3 b) |
| 执行人 | 姓名 + 职责 | GB/T 25000.51-2016 §6.4.1.3 c) |
| 异常 | `无` ∥ 异常编号（指向 §11.5「异常与更正」节） | GB/T 25000.51-2016 §6.4.1.3 e) / f) |

**示例行**（端 = CLI；故事 = 「普通模式的完整工具流」）：

|---|---|---|---|---|---|---|---|

**甲方可读列名映射**（同一列，业务语言读法）：

| 列名 | 甲方读法 |
|---|---|
| 编号 | 这条用例的编号 |
| 怎么做 | 我们是怎么验的（操作步骤） |
| 怎么算通过 | 满足什么条件算验收通过（验收标准） |

### 11.4 与 `test/integration/**` 的对应形（双向）

- **故事节 → 需求层用户故事**：节标题 = 该业务故事的用户故事名；节内注 = 本节所回指的需求条目（`requirements/TESTING.md` 功能需求层）。
- **行 → 用例**：行「证据」列写 `test/integration/<场景名>.test.mjs`（§4.3 的目录 ∕ 命名契约不变）。
- **用例 → 行**：集成用例档内的用例标题以 RTM 编号开头（如 `test('1-1 …')`）——用例标识符与报告标识符同字，标准 §6.4.1.3 a) 的「测试用例的标识符」由此机判。**次序：先定 RTM 编号 → 再落用例标题**（编号先行）；**实施轮随用例设立**（本设计不写 `test/**`）。
- **覆盖判据**：故事下每个用例一行；一个用例不出现在两张表（不重复登记）。
- **重建期现状**：集成用例现量 0（§2.3）⇒ RTM 起步为空表（故事节在位、用例行数 0，注「尚无集成用例」）；**不得以单元测试档凑行**（两层永不互转，§3.2）。

### 11.5 签署面

**表尾区块 = 签署面**（每端一份）：

| 项 | 内容 |
|---|---|
| 产品标识 | 端名 + 版本 + 变体 + 日期（GB/T 25000.51-2016 §4.1.12） |
| 结论声明 | 「上述业务故事及其全部用例均已验收通过。」（签的是什么 = **这一句**） |
| 验收方 | 单位 · 姓名 · 职务 · 签字 · 日期 |
| 供方 | 单位 · 姓名 · 职务 · 签字 · 日期 |
| 页脚 | 报告标识（端 + 日期）+ 页码 ∕ 总页数（GB/T 25000.51-2016 §7.5） |

**时序**：① 集成测试集全绿（各包 `npm test` 单入口，§10 F1）→ ② RTM 逐行填结果 ∕ 日期 ∕ 执行人 ∕ 异常 ∕ 证据 → ③ 正文定稿冻结 → ④ 导出签字版（打印 ∕ PDF）→ ⑤ 甲乙方签字 → ⑥ 扫描件归档 + 冻结（git 提交 ∕ tag = 签后基线）。

**签后约束**：正文**不可改**；唯一可写面 = **追加更正行**。

- 更正 = **新增一行**（编号延续 · 追加日期 · 原因 · 追加人），**不改既有行**。
- 承载节 = 「异常与更正」：异常编号 · 说明 · 严重程度 · 纠正日期 ∕ 纠正者 · 再测结果（依据 = 标准异常情况报告的纠正与再测验证字段，GB/T 25000.51-2016 §6.4.2.4 ∕ §6.4.2.6）。
- **无 changelog 节**：修改沿革由 git 承载 + 本节更正行承载（项目裁定 2026-10-15「需求 ∕ 设计档不设 changelog」优先于标准 §6.1.3.3 的「修改历史」项）。

### 11.6 三处相抵的正面解

| # | 相抵 | 正面解 |
|---|---|---|
| 1 | 批档可整体清理 ∥ 交付物须耐久 | RTM 住包内 `test/`、随代码进 git；**不引用批档**、行内不带批号（只带用例标识符 ∕ 结果 ∕ 日期）⇒ 批档清理不使 RTM 悬空；引用方向单向（批档 → RTM） |
| 2 | 「单元测试档零留存（用毕即删）」∥「测试报告是交付物」 | 二者**不是同一物的两种寿命，是两个对象**：单元测试 = 内部回路（不进任何门、零留存〔用毕即删——批档 §5 留一行读数〕）；RTM = 交付物面（常驻）。分野判据 = **谁验收谁**（自测 ⟷ 甲方验收）；标准同旨 = 29119-1:2013 附录 E.3 测试独立性 |
