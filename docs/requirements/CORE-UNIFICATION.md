## 1. 总体需求

**为谁解决什么问题（一句话）**：为 ThinCoder 的两产品（CLI 与 VSC 扩展）消除「同一套机制两份实现」的长期税负——
把两产品共有的机制实现收敛为**单一权威源的可共享核**，两壳各自只保留端特有部分（「一个核 + 两个薄壳」），且**不改变任一产品的可观察行为**。

**为什么现在做**：phase 1（目录合并）已把两产品收进单一 git 仓、原有跨仓机制全线退役；但**两份实现仍在**。
phase 1 的实测（口径与复现命令 = `thincoder/docs/requirements/TWO-REPO-MERGE.md` §1）表明：**内容层已同、实现层真分叉**——
提示词与工具文档（`.md`）同路径 40 对中位相似度 1.0000、逐字节同 28；而代码（`.mjs`）67 对中位仅 0.2829、逐字节同仅 1。

**phase 2 的第一手数据（按类型 / 按目录拆分 —— 2026-09-13 父侧复算；口径与复现见 §1.1）**：

| 切面 | 读数 |
|---|---|
| 同路径代码对（CLI `thincoder/src/**` ↔ VSC `thincoder-vscode/src/**`） | **107** 对 |
| 逐字节相同 / ≥0.9（全量口径） | **29** / **39** |
| **代码（`.mjs`）67 对** | 中位 **0.2829** · 逐字节同 **1** · ≥0.9 仅 **7** |
| `.mjs` 相似度分布 | ≥0.9 = 7 · 0.5–0.9 = 17 · 0.2–0.5 = 14 · **<0.2（真分叉）= 29** |
| 非代码（提示词 / 工具文档 `.md`）40 对 | 中位 **1.0000** · 逐字节同 **28** |
| 子目录中位（升序） | `agent` 0.0532 · `provider` 0.1124 · `traces` 0.1869 · **`agent-tools` 0.2060** · 顶层档 0.5247 · `advisor` 0.6465 · `tools` 0.9091 · **`prompts` 1.0000** |
| 最接近的代码档（核的先头部队） | `advisor/history.mjs` 1.000 · `prompt-overlays.mjs` 0.985 · `advisor/truncate.mjs` 0.960 · `advisor/convergence.mjs` 0.943 · `log.mjs` 0.929 · `tools/git-checkpoint.mjs` 0.909 |
| 最分叉的代码档 | `agent-tools.mjs` 0.0000 · `memory.mjs` 0.0093 · `mcp.mjs` 0.0130 · `agent-tools/subagent-run.mjs` 0.0135 · `agent-tools/subagent-async.mjs` 0.0204 · `tools/index.mjs` 0.0215 |

**由此得到本板块的两条判据（也是设计的两条起点）**：

1. **「建核」不是搬运**——内容层已同、实现层真分叉 ⇒ 核的构建必然包含**逐模块语义裁决**（以谁为准 / 融合 / 判端特有）。
2. **凭空写中立核 = 造第三份实现**——正是 phase 1 否决「抽独立核心包」的理由（会让工作退化成重写）⇒ 核**必须从两套现有实现提取**。

**做法（用户裁定的保守路线）**：**先建共同内核并验证可用，再把 CLI / VSC 迁移到新核**——不直接改两产品现有实现；
分段推进：S0 差异分析 + 逐模块裁决（零代码）→ S1 建核（两产品一行不改）→ S2 逐模块迁移 → S3 收尾。

### 1.1 度量口径与复现（写给复核者）

**口径（逐字，勿改——口径一变则历史数字不可比）**：成对判据 = 两产品 `thincoder/src/**` 与 `thincoder-vscode/src/**` 下
**相对路径逐段相等**者成对（含全部档型，**不按扩展名过滤**）；相似度 = 两侧读成行、**去首尾空白 + 丢空行**后取**行集合**的
**Jaccard**（|交集| / |并集|）；另报 sha256 **逐字节完全相同**对数。复现命令 = `node scripts/mirror-divergence.mjs`
（仓根执行；`--json` 给机器；口径逐字写于该脚本头注 `:5-12`）。

**缺口（S0 必须补）**：现脚本只出「同路径对数 · 逐字节对数 · ≥0.9 对数 · 全体中位 + 逐子目录中位」，
**不出**「按类型（代码 / 非代码）拆分」与「相似度分布分档」——上表该两行由父侧一次性脚本算出（口径同源）。
⇒ 需求 **F10** 要求把该拆分并入脚本，使**本板块引用的每一个数字都可复现**；
依据 = 台账既有教训「招牌数字必须可复现」（已核销条目，`docs/TODO.md` 与 `docs/TODO-archive.md`）。

## 2. 功能性需求（用户故事）

| 编号 | 用户故事 | 范围边界（明确不做） |
|---|---|---|
| **F1** | 作为项目维护者，我想要按 **S0 → S1 → S2 → S3** 四段推进（而非一次性重写），以便每一步都能独立验证、独立回退 | 不做一次性大迁移；不做「核与产品同时改」的混合步；不在本板块内改产品行为 |
| **F2** | 作为维护者，我想要在写任何核代码之前先拿到**逐模块裁决表**（每对一条：分类 + 依据 + 目标归属），以便核的边界由数据决定而非预设 | 不预设核的模块清单；裁决未完成不建核（S0 未分类不建核） |
| **F3** | 作为维护者，我想要核的每个模块都**从两套现有实现中提取**（取一侧 / 融合，来源可追溯），以便不产生第三份实现、行为可对照 | 不凭空写中立核；不做「另起一套新 API 的重写」；不在核内引入未在两侧出现过的语义 |
| **F4** | 作为用户，我想要核**自带测试并能独立跑绿**（不依赖任一产品），以便在动两产品之前先确认「核可用」 | 核测试不绿不进入 S2；不拿产品测试充当核测试；核测试不得依赖产品侧夹具 |
| **F5** | 作为维护者，我想要核建成后**逐模块**把 CLI / VSC 接到核上并删除旧实现，以便迁移单步可回退、单步可复跑 | 不做跨模块大包迁移；不改产品对外命令面 / 配置格式 / 包名 / 版本策略 |
| **F6** | 作为用户，我想要核的引入**不改变两产品的可观察行为**，以便收益是纯结构性的、不夹带功能变更 | 不为「统一」而统一行为——两侧行为确有差异的机制判**端特有**或以**注入**表达；行为统一另立需求 |
| **F7** | 作为用户，我想要**发布产物各自自足**（npm 包与 vsix 各自含核的运行期文件），以便「共享核」在真实安装场景成立、而非只在开发机成立 | 不改两产品发布链（npm publish / vsce + ovsx）；不引入构建步骤；不改 `files` 白名单语义 |
| **F8** | 作为维护者，我想要提示词布局**不因核而合流**（承 phase 1 D14），以便不触碰运行期硬加载 + 打包边界的机械约束 | 核目录内不含提示词档；不做提示词单副本；不改两产品提示词文件布局 |
| **F9** | 作为维护者，我想要 S3 把**残留删净**并把文档 / 机检收正，以便「统一」在机器可判的面上成立（无悬空锚、无残留双份、无死指针） | 不做文档全量重排；不批量改写历史留痕档（承 phase 1 D10 口径） |
| **F10** | 作为复核者，我想要本板块引用的差异数字**全部可复现**（脚本出按类型 / 按目录拆分，口径成文），以便裁决依据可被独立复核 | 不改既有度量口径；不手算数字入档（必须脚本可取） |

## 3. 非功能性需求

| 编号 | 标准 | 判据（度量方式） |
|---|---|---|
| **N1** | **零行为回归** | 两产品全量门禁（`npm run lint` / `test:full` / `test:integration`）与迁移前基线**逐数一致**；任何差异项须逐条登记且可解释 |
| **N2** | **可回退** | 每段有回滚点、S2 每个模块一步一提交；S1 期间两产品**零改动**（`git diff --stat` 对两产品目录为空）；回退演练后该产品全链复绿 |
| **N3** | **核独立可验证** | 核测试可独立执行（`node --test` 于核目录）且 exit 0；**核内 import 面零产品路径**（机检：核内不得出现指向产品侧的相对 import） |
| **N4** | **产物自足 · 发布链不断** | `npm pack` 与 `vsce package` 成功且产物内含核的运行期文件（与权威源逐字节一致）；两产品互不依赖对端包 |
| **N5** | **单一权威源 · 零漂移可判** | 核内容只在一处撰写；产品内副本与权威源**逐字节一致**，由机检 fail-closed 守（漂移即 exit 1，反证可复现） |
| **N6** | **机检零红** | 本板块两档 + 新增核路径纳入扫描域后，仓根三机检（`scripts/doc-anchors.mjs` / `scripts/check-doc-width.mjs` / `scripts/check-ledger.mjs`）exit 0 |
| **N7** | **零第三方运行时依赖** | 核内一律 `node:` 内建；核内零裸包名 import（保 CLI 零依赖承诺与 vsix 体积；不得抬升 Node / VS Code 版本要求） |
| **N8** | **结构尺度** | 核模块档 ≤300 行（软线）/ ≤500 行（硬限）；>300 行须在设计档给拆分计划；口径 = `wc -l`（承 phase 1） |

## 4. 范围边界与既有需求的关系

**明确不做（9 条）**：

1. 不把「直接改两产品现有实现」作为第一步（用户裁定的保守路线：先建核、验证可用、再迁）；
2. 不做一次性重写（不做「核与产品同时换」的大步）；
3. 不凭空设计新 API / 新架构（核的语义面只来自两侧现有实现）；
4. 不做提示词单副本合流（D14 仍有效：运行期硬加载 + 打包只收包根内文件 = 机械约束）；
5. 不改变两产品的可观察行为（含命令面 / 配置格式 / 输出文案 / 事件语义）；
6. 不改两产品发布链（npm / vsce + ovsx）、包名、版本号策略，不新增构建步骤；
7. 不做文档全量重排、不改写历史留痕档（承 phase 1 D10 的「新老划断」口径）；
8. 不做 S2 之后的「行为统一」——两侧行为有差异的机制归端特有或以注入表达，行为统一另立需求；
9. 不新增第三方运行时依赖（核只用 `node:` 内建）。

**与既有需求的关系**：

- 承 phase 1「**产品运行时行为零改动**」（`thincoder/docs/requirements/TWO-REPO-MERGE.md` §2 F7）——本板块把它提升为核的准入条件（F6 / N1）。
- 承 phase 1 **D14**（提示词不做单副本合流）——本板块不改其边界（F8）；核的副本机制**不外推到提示词**。
- 与 phase 1 否决的 **X1「抽独立核心包」**：本板块承担的正是 X1 当时缺失的前置（实现层统一），
  但**形态上不采用独立包**（理由见 `docs/design/CORE-UNIFICATION.md` §2.3.2）。
- 与 phase 1 退役的「各仓自持 / 端差登记 / 禁跨仓 import」无冲突——单仓之内，核与壳的边界是**包边界**，不是仓边界。

**需求来源**：用户 2026-09-13 提案（「先把共同内核构建起来，试一下可用了再把 CLI 和 VSC 迁移到新核心上」）+
主 agent 校验方案 + 用户裁定「计划可以，干吧」；需求池 = 仓根 `docs/TODO.md`「phase 2：核心统一」。
