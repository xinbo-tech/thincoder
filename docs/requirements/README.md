# 需求层（docs/requirements/）

> 本目录承载**需求层文档**——需求文档的权威存放处。总地图与文档规范见 `../README.md`。
> 建档：2026-09-10（文档目录结构重组批）。

## 1. 本目录是什么

**三层归属**（规范全文见 `../README.md` §2.1）：

| 层 | 内容 | 住哪 | 作者 |
|---|---|---|---|
| 需求层 | 总体需求 / 功能性需求（用户故事或规格句）/ 非功能性需求 | **本目录** `requirements/<板块>.md` | 主 agent（产品经理） |
| 设计层 | 方案选型与理由 / 架构·接口契约 / 受影响文件清单 / 关键决策记录 | `../design/<板块>.md` | eng-designer |
| 测试层 | 用例表 + 输入·预期输出 + 与需求条对应关系 | `../design/<板块>.md`（与设计同档） | eng-designer |

**板块镜像**：一个板块一对文件、同板块名——`requirements/<板块>.md` ↔ `design/<板块>.md`。

## 2. 迁移规则（新老划断）

本目录**当前为空**——存量需求内容仍在各设计档内（三层同档的历史形态）。迁移按**新老划断**执行：

- **新需求**：按新规范写入本目录（板块镜像命名）。
- **存量权威档**：**碰到哪个拆哪个**——当某板块的设计档因其他工作被修订时，顺带把其需求层拆入本目录；
  不为"拆档"本身发起批量内容手术（那是一次独立的内容工作，见 `docs/TODO.md` 后续项）。
- **批次档/变更史档**：不拆——它们已是冻结的历史记录（`../design/_archive/`）。

## 3. 与设计档的关系

需求与设计之间隔着**"设计 = 对需求的检验"**这道关卡（机制见同目录 `ENGINEERING-MODE.md` §1.2 FR9）：
设计者把需求翻译成可执行方案的过程就是需求的第一次严格检验——需求含糊/自相矛盾/不可实现，
在设计阶段必然暴露。因此需求文档**不过独立评审**（用户确认即可），而设计评审是必经节点。
