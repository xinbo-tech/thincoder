# 普通模式（Normal Mode）— 需求

> 板块：普通模式——产品的**默认工作模式**：直接干活、无机械门禁、质量靠纪律与验证工具。
> 本档为**架构级机制需求文档**：功能性需求以机制约束表述；非功能性需求完整。设计+测试见 `../design/`（待建）。
> 来源：2026-09-10 建档（用户裁定立档）——内容自 `PROJECT.md` §0.6 定性 + 提示词实现面（`src/prompts/persona-normal.md` /
> `discipline-normal.md`）反向抽取需求陈述。
> 状态：**现行**（机制已实现）。

---

## 0. 定性

你说要什么，我就直接干——改 bug、加功能、写脚本、查问题，边做边交代。质量靠纪律和自查。
与**工程模式**互斥（同一时刻只能一个），提示词两套独立，可随时切换。详见 `PROJECT.md` §0.6。

## 1. 总体需求

把人从"写代码"里解放出来，同时让交付**可信**：改动要验证、结论要有据、取舍要交代。
与工程模式的差别只有一条——**没有机械门禁**：拦不住的靠纪律与工具（verify/advisor）保证，而不是靠硬拦。

## 2. 功能性需求

| # | 需求 | 约束 |
|---|---|---|
| F1 | **全能力干活** | 直接文件写权限 + 全套工具；"整个项目的代码都是我的" |
| F2 | **任务分档** | complex（3+ 步/新功能）：读文档→需求→设计→开发→测试，写设计档 + `checklist` + `task`；medium（2-3 步/重构）：读文档→计划→改→更新所属文档 + `task`；small（错字/一行修）：读文档→改→验证→更新所属文档 + `task`。分不清按 complex |
| F3 | **复杂任务先计划** | plan mode：只读探索 → 设计 → 呈现计划 → 批准后实施；complex 档时 plan mode 即设计步骤 |
| F4 | **文档先行** | 改代码前先读所属文档；**文档与代码冲突时以文档为准**；用户指示与文档冲突时先讲清→改文档→再写码；文档归属单一权威源（一处详述，其余引用） |
| F5 | **完成前验证门** | 每次 write/edit 后 `lint`；宣布完成前按项目 AGENTS.md 的方法跑验证并向 `verify` 声明结果——**verify 机械把关但不代跑**；无法验证就明说，绝不把未验证说成完成 |
| F6 | **交付透明** | 改了什么/为什么/简化了什么/没做什么——逐条交代（用户看不见代码，只听得见你说的话） |
| F7 | **自动代码评审** | 改完代码调 `advisor`（须给 paths 或 documents）；评审后按三值裁决表回应（Fixed / Not an issue / Deferred）；🔴 不得埋；≤5 轮收敛；全清后跑 `verify` |
| F8 | **委派** | 子代理 explore / coder / plan（普通模式装配；工程模式禁用 coder 角色） |
| F9 | **跨会话记忆** | `memory` 工具（search/put/list/delete/clear）——存 bug、约定、偏好 |
| F10 | **任务跟踪** | 每档都用 `task`（同时只有一条 in_progress）；complex 档加 `checklist`（持久、每条需求一条） |

## 3. 非功能性需求

| # | 维度 | 标准 |
|---|---|---|
| N1 | **无机械门禁** | 不像工程模式那样拦截写文件——质量由纪律 + verify + advisor 承担（这是两模式的根本差别） |
| N2 | 工具路由 | 专用工具优先（git/read/grep/glob/ls/tree/process/时间）；bash 只用于包管理器/CLI 子进程、服务器、TTY 程序、无专用工具表达的一次性管道 |
| N3 | 可逆性分级 | 本地编辑——自主；破坏性（rm -rf、强推）——先确认；外发（commit/push/publish）——每次确认 |
| N4 | 长输出先落盘 | 长测试/长命令先重定向到日志再查（防截断、防失败详情丢失）；日志写在**工作区之外**并读后删除 |
| N5 | 无 TTY | 命令一律非交互执行（`git commit -m`、`--no-pager`、`-y/--yes`） |
| N6 | 并行纪律 | 独立读类调用合并一批并发；不并行：同文件写入、依赖步骤、审批类命令、同仓并发 git、有状态操作 |
| N7 | 编辑纪律 | old_string/行号/哈希**只来自最新一次读取**；工具报错即修法——同一形态第二次失败必须重读文件，绝不第三次重试同一输入 |
| N8 | 上下文压缩后 | 信摘要结论，但**重读 AGENTS.md 与设计档**（权威内容可能被丢） |
| N9 | 枚举输入必用选择器 | 固定取值集合（enum/level/mode/flag）必须给选项（选择器/菜单/按钮），不得要用户手打 |
| N10 | 用户约定逐字执行 | 交互/行为约定以**用户原话**为准——不得用"等效实现"替换；已确认约定的简化必须提前上报，不得包装成"升级"交付 |

## 4. 范围边界（不做）

- 不做机械拦截门禁（那属工程模式）——不得为"更安全"私自加硬拦
- 不跳过验证声明（N1 的代价由 F5 兜底，二者不可拆）
- 不静默改文档：实现偏差先修正代码到与文档一致；真文档漂移/超范围变更交用户
- 不把未验证的工作说成已完成（也不把已完成的降级包装成"可接受"）

## 5. 开放项（待搞明白后续）

- **本档与提示词的双向核对**：本档是自提示词实现面反推的需求——需一次逐句核对（提示词里是否有本档未覆盖的要求、本档是否夹带了实现细节）
- 普通模式是否有**可机械化的**保障（现只有 verify 一个门）——与工程模式的边界是否要重新划
