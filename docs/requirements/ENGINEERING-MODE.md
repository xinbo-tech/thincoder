# 工程模式（Engineering Mode）— 需求

> 板块：工程模式——thincoder 的严格方法论工作流：design-before-code、纪律层槽位提示词驱动、双门禁（设计评审 + 代码评审）。
> 本档为**架构级机制需求文档**：功能性需求含**用户故事**（§1.2——从用的人角度看价值）+ **FR 机制约束表**
> （§1.3——实现口径）；非功能性需求完整（§1.4）。设计+测试见 `../design/ENGINEERING-MODE.md`。
> 来源：2026-09-10 自 `../design/ENGINEERING-MODE.md` 抽取（需求层拆分批——§0 铁律 / §1 需求 / §1.5 裁定清单 / §4 边界）。
> 状态：**现行**（机制已实现）。**待设计需求**：FR9 角色三段链（§1.5 九条裁定）+ FR10-FR15 可移植性（§2）。
> 本档定位（FR10）：工程模式是**面向任意项目的产品功能**，不是本仓自用工作流。

## 0. 铁律（发起权与批准权归用户——2026-08-24 决策）

背景：agent 曾两次越权抢跑（自行提交设计评审 → 拿 token → 直接开发，其中一次全程零确认）。此后固化四条铁律：

1. **设计评审只能由用户发起**——agent 准备并提醒"设计就绪，可以评审"，不自行调 advisor。
2. **打回后逐条呈递**——评审打回后每轮呈递发现 + 修复建议，**用户逐条拍板**再改（agent 不自行修完重送）。
3. **交付 code review 保持流程节点自动**——eng-coder 返回后自动评审，不问用户（2026-09-02 起由 eng-coder 内部协议默认承担）。
4. **系统推回（guard）在工程模式一律关闭**——未来若启用也只作提示，评审仍由用户发起。

## 1. 需求（Requirements）

### 1.1 总体需求

普通模式靠纪律提示词约束模型；工程模式把"设计先行、评审把关、验证收尾"提升为**半机械流程**——可硬性拦截的环节一律拦截（写文件门禁、token 校验），无法硬拦的靠纪律层槽位提示词约束。核心承诺：**代码必须先有被评审过的设计；评审对象由任务定义而非遍历猜测；评审循环在实现者内部闭环（不依赖父代理持有凭证）。**

### 1.2 用户故事（从用的人角度看——为什么需要这些机制）

**发起权（对应 §0 铁律）**

- 作为开发者，我想**自己决定什么时候发起设计评审**——在我的需求讨论完了、我认为可以了的时候——
  而不是 agent 自己觉得想清楚了就开评。
- 作为开发者，我想让评审打回后**逐条听 agent 说发现和修复建议、由我决定改哪些**，
  而不是它自己改完直接送回——否则我看不到它替我做了什么决定。

**设计先行（FR1/FR2/FR3）**

- 作为开发者，我想让有规模的任务**先写出“打算怎么做”并经过独立评审、我点头，才允许改代码**，
  这样我不会一觉醒来看到一堆没经过我同意的改动。
- 作为开发者，我想**只有我批准的方案才能进入实施**（凭证落到实现者手里），
  这样没人能跳过评审直接改代码。

**独立评审（FR2/FR5）**

- 作为开发者，我想让**另一个独立的评审角色**（不是写方案的那个、不共享它的上下文）挑毛病，
  这样我不会被写方案的 agent 的自信误导。

**实现者的纪律（FR4/FR6）**

- 作为开发者，我想让实现者在交给我之前**先自查、再被独立评审一遍**，这样我不用当第一个 QA。
- 作为开发者，我想让实现者**撞到设计漏洞时停下来告诉我**，而不是自己编一个方案继续干。
- 作为开发者，我想让改动**超出原定范围时逐条告诉我**，而不是悄悄改。
- 作为开发者，我想在它**卡住、没收敛时被告知**，而不是等一个看起来正常的失败。

**并行与留痕（FR7/FR8）**

- 作为开发者，我想能**同时推进多个互不相干的任务**，而不必排队等。
- 作为研发负责人，我想让技术待办**集中在一处**，而不是散在设计文档里到处找。
- 作为团队的一员，我想让**每一步的决定都有据可查**（谁提的、什么时候批的、怎么验证的），
  这样半年后或换了人也能接手。

### 1.3 功能性需求（机制约束，架构级表述）

| # | 机制需求 | 约束 |
|---|---|---|
| FR1 | 设计先行 | 设计文档（三层）存在且通过设计评审前，任何代码文件（含 `src/prompts/*.md`）不可被修改 |
| FR2 | 设计评审独立 | design review 由独立上下文执行；评审对象 = 调用时显式传入的文档清单（documents + object 参数），不遍历 git diff |
| FR3 | 授权链 | 评审通过签发 token + 随机 designId，存于会话内多设计槽；spawn eng-coder 须携带匹配凭证；链终消费（详见下方 FR3 注） |
| FR4 | 代码评审归属 | eng-coder 交付前自查（对照验收标准/文件范围，非 LLM）→ **内部协议闭环**：实现 → explore 偏差审计 → 自修 → advisor(type=code) 复评 → 收敛后一次交付（完整协议权威 = 设计档 §2.2 step 6）；LLM 验证 3 次/链（③审计 → ⑤advisor 首审 → 终审复评），修正轮默认不重跑审计/复评；父侧复核保留可选（默认由内部协议承担——stalled/存疑才复核） |
| FR5 | 评审时机 | **设计评审仅由用户发起**（agent 呈递就绪并提醒，不自行调 advisor）；打回后每轮呈递发现 + 修复建议、用户逐条拍板；**交付 code review 流程节点自动**（eng-coder 内部协议默认承担——in-child advisor 复评自动运行、不问用户；父侧复核保留可选——stalled/存疑才复核）；advisor 失败停止重试 |
| FR6 | 范围约束 | **A 裁定**：去掉"文件清单外不可改"硬约束——清单外改动**允许**（交付必要），但**必须逐项报告中说明**（透明）；审计"out-of-list"判据 = "**改了且未报告 = 偏差**（静默越权）"；已报告 = 透明可接受；父代理不得修改设计文档外的范围；超范围停下提出设计更新 |
| FR7 | 待办管理 | 技术待办统一在 `docs/TODO.md`，不落入设计文档（避免触发重新 doc review） |
| FR8 | 多任务并行 | 相互独立的设计可**并行推进**，上限 ≤4 并发（提示词纪律——无机械门禁）。**调度器条款（现行口径）**：spawn 声明 `files`+`dependsOn`——冲突/顺序交调度器自动处理（重叠域 queued、依赖链自动顺序、同步冲突报错），不再手动串行——锚句 "overlapping domains are queued by the scheduler, never hand-serialized"（AGENT-LOOP §10）；未声明 files 不参与冲突检测。token 按 designId 隔离互不覆盖；发起权不变（FR5） |
| FR9 | **角色三段链**（2026-09-10 用户裁定；分工口径同日细化） | **主 agent = 产品经理（会话面）**：收集/登记/澄清/与已有需求文档对账 + **批次式记录**（`docs/batches/`）+ 编排/确认/核验 + 设计判断权；<br>**eng-designer = 设计与需求成文（写稿面）**：依批次登记需求、**维护需求文档体系的整体性**，需求成文后再写设计；自勘察；无 token；不发起评审；eng-coder = 实现。<br>定位：设计 = 对需求的检验；撞问题 → 停下报告交回主 agent。见 §1.6 与 §1.5。 |

> **FR3 注（授权链细则）**：designId 为**同 scope 实例恒定**（复审沿用同 id，旧 token 存活至 TTL 保留）；
> 不锚定文档路径/内容（"文档锚失效"路线已否决）。spawn 单设计时 designId 可省略。
> token 随会话 slot 持久化跨进程（**TTL 7 天 fail-closed**）。**链终核销由父侧 consume-design 消费**
> （设计见 `../design/ENGINEERING-MODE.md` §2.6）。


### 1.4 非功能性需求（技术标准）

| # | 维度 | 标准 |
|---|---|---|
| NFR1 | 性能 | token 校验在 spawn 时同步完成（<10ms，无网络依赖——**设计目标，非机械测试**）；design review 每轮一次 LLM 调用 |
| NFR2 | 收敛性 | code review 最多 5 轮（MAX_ADVISOR_ROUNDS），第 6 次调用被机械拒绝；design 评审不消耗该预算（cap 豁免） |
| NFR3 | 安全 | token 机械匹配（格式 + TTL fail-closed）+ designId 定位槽；token 为**无签名流程凭证**（格式 `uuid:expiresAt`——HMAC 防伪层已删，非现行机制）；复审失败不波及其他设计的槽（旧 token 存活至 TTL——已知取舍）；token 随 slot 持久化跨进程（TTL 7 天 fail-closed——重进 TTL 内恢复、过期重新评审）。存量旧 3 段格式 token 拒绝语义见节后注 |
| NFR4 | 兼容 | 两种模式互斥：工程模式禁用 `coder` 角色，普通模式禁用 `eng-coder`；行为不互相污染（提示词两套独立） |
| NFR5 | 可维护 | 判定逻辑单一来源：`isProductCode(p) = /^src[\\/]/.test(p) \|\| !isDocFile(p)`（相对路径语义）；对存绝对路径的 `_touchedFiles` 使用组件级匹配 `/(?:^|[\\/])src[\\/]/`——统一用于门禁/guard/doc-only 判定 |
| NFR6 | 可恢复 | eng-coder 失败/中断可重新 spawn（同 token——链中未消费）；advisor 工具失败不重试，向用户报告 |

> **NFR3 注（存量旧 3 段格式拒绝——活机制）**：旧 3 段格式 token（`uuid:expiresAt:HMAC` 形态——HMAC 指历史防伪层签名段，2026-09-06 已删，此处仅作拒绝判定的格式描述）即使 TTL 内也**格式即判错** → fail-closed 拒绝 → 需重新设计评审（迁移代价：已批准未实现的设计重评一次，已接受）。

### 1.5 角色重定义裁定清单（FR9 澄清产物——2026-09-10 用户逐条确认；需求层，待设计）

| # | 事项 | 裁定 |
|---|---|---|
| 1 | 主 agent 是否保留编排/核验/确认/发起权 | **全部保留**（产品经理 + 流程编排者） |
| 2 | 主 agent 对设计稿的核验深度 | **内容性核验**（判断设计方案对不对、是否覆盖需求）——非仅流程核验 |

### 1.6 工作流程（主 agent 的理解——2026-09-10，待用户确认）

**一句话**：人按批次提需求；主 agent 收、对、问；需求清爽且人点头后，才交给设计者；
设计者**先把需求文档整合干净，再写设计**。

**分步**

1. **人提需求——按批次**。想起什么说什么，交代给主 agent（不是一次把整个产品想清楚）。
2. **主 agent 负责会话**：收集、登记本批需求，把含糊处问清楚。它是人与后续角色之间唯一的对话口。
3. **与已有需求文档对账**：新需求要跟**现有需求文档**比对——跟已有条款冲突、重复、或语义打架的地方，
   **回头问人**，不自己挑一个解释。
4. **需求清晰 + 人同意 → 才进设计**：本批需求都问明白了，且用户同意开始，主 agent 才去调 **eng-designer**。
5. **设计者先整需求、再写设计**：eng-designer 接手后**第一件事不是写设计文档**，而是把本批需求
   **整合进整体需求文档**——保证全篇逻辑连贯、前后不矛盾、没有互相打架的条款。
6. **整不动就把问题打回**：整合中发现需求本身说不通（缺口、矛盾、不可实现）——**打回主 agent**，
   由它向用户澄清；澄清后再继续。
7. **需求文档干净了，才写设计文档**：需求整合完整是写设计的前置条件。

**这个流程里我读出的要点（用户 2026-09-10 补充确认）**

- **张力是客观存在的，不是缺陷**：需求文档要的是**整体性**，而人提需求是**批次式**的（跟着交互节奏走）——
  这个张力**正是 eng-designer 存在的理由**：由他把批次性的输入维护成整体性的文档体系。
- **分工（用户观点）**：
  - **主 agent：以批次式记录需求**——适应与用户的交互节奏。**但记在哪里需要定义**（开放项，见下）。
  - **eng-designer：根据批次去登记需求，维护需求文档体系的整体性**。
- 因此不是"主 agent 写需求、设计者只写设计"，也不是"设计者替主 agent 做需求"：
  **批次记录在会话面，整体成文在写稿面**。

**记录规范（2026-09-10 用户定——也是本批讨论的教训）**

- **记理解，不记原话**：需求文档记主 agent 的理解（结论），不搬用户口述原文；理解错了由用户纠正。
- **记录不加工**：主 agent 把口述整理成条目时**不得掺入自己的排序/推断**——那是解读不是记录。
- **需求层问题当回合改**：定性与流程属需求本身的问题，不等攒批。

**批次记录的载体（2026-09-10 用户定；粒度同日定）**

- **`docs/batches/<批>-<板块>.md`**——**批次记录档**（**一批一份，三段 append-only**）：§1 讨论（主 agent）·
  §2 批次任务（eng-designer 追加）· §3 验收结论（主 agent 追加）。
  生命周期：起草于讨论开始 → 需求谈清后由 eng-designer 抽入 `requirements/` → **本档冻结**（append-only，不回改）。
- **为何一批一份**（用户裁定）：滚动档要求 agent 反复"定位不漂/结构不错位/记录不加工/长档不腐"——
  恰是它最弱处且已实证（本仓滚动档全腐化、批次档零腐化）。**形态迁就 agent**：新建一份、写完冻结。
- **跨批检索**靠 `TODO.md` 需求池台账（每条需求 → 哪批谈的 + 状态）。规范见 `docs/README.md` §3.8。
  （本批记录档：`docs/batches/2026-09-10-ENGINEERING-MODE.md`）

**需求池（2026-09-10 用户定——与批次记录档互补）**

- 需求池 = **需求落地台账**（`docs/TODO.md` 需求池组）：跟踪**每一条需求做到哪了**
  （待讨论 → 待设计 → 在途 → 待核销 → 已核销）。
- 与批次记录档**职能不同**：批次档记“这批怎么谈的/派了什么/验收如何”；需求池记“每个点落地没落地”。
- 为何必须有：没有它，要知道哪条需求落地了只能**遍历全部文档**。定义见 `docs/README.md` §3.9。
- **职责分工（用户 2026-09-10 裁定）**：
  - **记录**（登记条目）= **主 agent**；**提交给 designer 时必须带上本批 todo 项**（todo 作为输入随任务传递）。
  - **维护**（状态推进）= **eng-designer**。理由（用户）：**子 agent 上下文干净、还有可能记住维护；
    主 agent 上下文脏，真保证不了**。
  - 机械面无冲突（2026-09-10 修正——我曾误报为冲突）：黑名单只管 **`files` 参数**（调度器的冲突检测面）；
    设计者改 `TODO.md` 是**提示词规定的动作**，与 `files` 无关——它只需**不在 `files` 里声明 todo.md**
    （免把并行排成串行）。现行语义：file 域 = **预期触碰面**（调度 + 披露基准），**非授权边界**。

**两道关（谁审谁——2026-09-10 用户定）**

主 agent 与 eng-designer 的互动**很类似一个 advisor 循环**（来回呈递/修正），区别只在分工：

| | 负责什么 | 不管什么 |
|---|---|---|
| **第一关：主 agent ↔ eng-designer**（同层边写边核） | 设计者：**需求不漏、跟踪不乱、据需求做好设计**；主 agent：核需求是否漏、跟踪是否乱（台账/文档体系），问题回给设计者改 | 不审设计好坏（无判断设计质量的职责） |
| **第二关：advisor 文档审核**（下一步、独立上下文） | **审核设计本身是否有问题** | 不管需求收集与跟踪 |

**顺序**：先过第一关（需求并入体系 + 设计成文）→ 再交 advisor 审设计（发起权在用户）。

### 1.7 主会话需求讨论循环（2026-09-10 用户确认——“步骤可以，以后需改再说”）

> 循环**由用户驱动**（想起什么说什么，一句话/一段吐槽/一次几个点都行）——agent 不主动起头。

| # | 主 agent 的动作 | 关键点 |
|---|---|---|
| 1 | **复述确认** | 用自己的话把你的表述复述一遍（“你是说 X，对吗”）——**只复述，不加工**（不排序、不补全、不揣测言外之意） |
| 2 | **落批次记录** | 写进 `batches/<批>-<板块>.md` §1——**按模板骨架填槽**（批次范围 / 谈成什么 / 对账结果 / 本批需求清单 / todo 项 / 过程留痕 / 状态；骨架见地图 §3.8），不自行组织结构 |
| 3 | **与已有需求文档对账** | 去 `requirements/` 逐条比：冲突 / 重复 / 语义打架 → 记下；相关不冲突 → 增量；全新 → 新板块 |
| 4 | **把对账结果回给你** | 有冲突/含糊/缺边界的**一次问一个**（不连珠炮）；**不自己挑一个解释** |
| 5 | **问缺** | 追边界（不做什么）、验收怎么算过、与既有条款怎么共存 |
| 6 | **收口回读** | 本批说完 → 回读“本批需求清单” → 你说“就这些” = 本批收口 |

**出口**：收口后**停住**（发起权在用户）——你说开始设计，主 agent 才去调 eng-designer。
交出去的东西：批次记录档（§1 讨论）+ 相关现有需求文档 + 本批清单。**需求层不过评审**（用户确认即定稿）。

**循环期间的纪律**：批次档不是规格（需求永远在 `requirements/` 成文）· 冲突一律回问（无“自己决定”的口子）·
随时可改口（追加/修正 → 回到第 1 步，批次档跟着改）· 猜攒批（零散点先落批次档，攒够了你决定何时正经谈）。

**已定配套**：需求池保留作落地台账（地图 §3.9）；**批次记录档一批一份、三段、整档冻结**（§1.6 / 地图 §3.8）。

### 1.8 eng-designer 工作流（主 agent 设想——2026-09-10，待用户确认）

**授权范围 = 需求文档体系整体**（非单板块）。理由（用户 2026-09-10 反问）：
只改自己能改的**保证不了全体系一致性**——跨板块矛盾会永远无人处理（本仓实例：旧地图自相矛盾、
PROMPT-SYSTEM 状态行与施工档打架、METHODOLOGY 已退役而产品仍拿它当门禁）。

**边界（我能改什么）**：

| 可自主修 | 必须打回澄清 |
|---|---|
| **一致性问题**：跳板块重复、措辞矛盾、结构错位、过时表述、指针失效 | **需求语义**：改含义、砍范围、改优先级——那是用户的决定 |
| 均需**逐条报告**（改了哪几处、为何）——不得静默改 | 打回主 agent → 用户澄清 |

**收到什么**：批次记录档 §1 讨论（`batches/<批>-<板块>.md`）+ **本批 todo 项**（主 agent 提交时必须包含）+ 需求文档体系（`requirements/`）+ 本批需求清单 + 归属板块。
**缺料（归属不明/清单不全）→ 打回**，不自己猜。

| # | 动作 | 产出 |
|---|---|---|
| 1 | **自己勘察现状**——读代码/文档/既有设计，拿 `file:line` 证据（可派 explore 并行）——只有设计者自己勘察才能发现需求缺口 | 现状事实 |
| 2 | **把本批需求并入 `requirements/`**（含 **todo 项状态推进**——维护职责在本角色，理由：子 agent 上下文干净、可能记住维护）——新条目落位（不新开档）；**并做全体系对账**：与任何板块的既有条款冲突/重复/矛盾 → 修正（一致性问题自主 / 语义问题打回） | 需求文档体系更新 |
| 3 | **每条需求配验收口径（判定句）**——执行面（进 eng-designer 提示词）+ 判据面（判定句落需求档，供核对） | 需求完备 |
| 4 | **需求成文后写设计** `design/<板块>.md`——方案 + （≥2 候选时）选型对比 + 受影响文件清单（带行数）+ 验收标准（逐条回指需求）+ 测试用例表 + 边界（不做什么） | 设计文档 |
| 5 | **自检 + 交回**——逐条核需求覆盖、需求档与设计档一致；报告 + **停** | 交付报告 |

**失败路径（一律打回，不自己编）**：需求说不通（缺口/矛盾/不可实现）· 勘察发现需求与现实冲突 · 归属不明。

**纪律**：不发起评审（发起权在主 agent/用户）· 不写实现代码 · **写稿面唯一作者**（需求文档 + 设计文档）；澄清必须经主 agent（它是唯一对话面）。

**产出要求（设计文档本身要达到的标准——缺一项即设计不完备）**：

| # | 内容 | 判据来源 |
|---|---|---|
| 1 | **批次任务**（用户 2026-09-10 定名）——**必须独立成件**：落 `docs/batches/<批>-<板块>.md` §2（**不写进设计档**——一次性内容混进长期档，下批会覆盖掉这批的任务）。<br>内容：本批覆盖的需求条目 + 明确不在本批的条目 + 受影响文件 + 验收标准（**eng-coder 任务书从它派生**）。<br>为何必要：需求并入体系后会**化掉批次边界**——不写它，"本次开发要做什么"就找不着了 | 本档新增 |
| 2 | **方案选型与理由**——候选 ≥2 时**必须有对比表**（候选 / 判据 / 取舍 / 否决理由）；单方案显式声明豁免 | 纪律层文档规范 |
| 3 | **架构 / 接口契约** | 同上 |
| 4 | **受影响文件清单**——源/测试文件**带当前行数 + 预计增量**；跨档位文件**带拆分计划**（文件档：>300 主动拆分评审，>500 必须拆；**函数档是第一判据**） | 评审八维 #8 + 结构硬指标 |
| 5 | **关键决策记录**（含被否决的备选） | 纪律层文档规范 |
| 6 | **验收标准**——**逐条回指需求**（与第 1 项的本批条目清单对齐），且**可验证**（含正常/边界/错误） | 评审八维 #5 |
| 7 | **测试用例表**（正常 / 边界 / 错误 + 输入/预期输出） | 三层结构·测试层 |
| 8 | **边界**（不做什么） | 纪律层文档规范 |
| 9 | **UI/交互决策全落档**——未定部分标 `open`，**绝不静默发明** | 主流程 step 1 |

**合格判据**（设计算不算过）= **advisor 设计评审八维**——权威源 `src/prompts/advisor-design.md`
（需求覆盖 / 可行性 / 方法论合规 / 清晰度 / 验收标准 / 范围 / 文档归属 / 受影响文件规模标注）；
此处不复制（单一权威源）。**其中"需求覆盖有漏点" = 🔴 必须处理**。

**设计的边界（不做）**：不发明需求（缺口→打回）· 不过度设计（不加没人要的能力）· 不写实现代码 ·
不碎片化（不为既有章节新建档）· 不静默改需求语义。

**两个原开放项（均已定）**：

- **spawn 粒度** → **已定（2026-09-10 用户裁定）：一批次一次**。依据：其职责就是**体系整体一致性**——
  一次能看全体系；按板块拆会让跳板块矛盾掉进缝里（正是要防的），且多写者并改 `requirements/` 会写冲突。
  例外口子：某板块设计明显独立且巨大时可拆（默认不拆）。
- **验收口径——已定（2026-09-10 用户裁定）**：
  - **规则进 eng-designer 提示词**（执行面）——“每条需求必须带验收口径（判定句），没有不算完”；
    用户裁定：**提示词比文档靠谱**（文档对 agent 无执行力——今日实证：档里写了“记录不加工”照样犯错）。
  - **判定句落需求档**（判据）——供第一关/第二关/用户核对时当标尺（没有它就只能“凭感觉”）。
  - 二者成对：只写文档没人拦得住；只写提示词没法判合格。

### 1.9 eng-coder 工作流（按现状落档——2026-09-10 用户定：“现有流程执行较好，照现状写”）

> 来源：现行实现（设计档 §2.2 step 5-8 + `persona-eng-coder.md`）。本节的职责是**记录现状**，不是重新设计。

**收到什么（任务书）**：designToken + designId（授权凭证，**经参数传、绝不进任务文本**）+ 涉及文档（设计文档路径）
+ 文件清单 + 验收标准（从设计逐字引用）。

**授权与边界**：

| 项 | 现状 |
|---|---|
| 机械门禁 | 无有效 token 时 write/edit/apply_patch/hashline_edit/insert_after/delete 全拒；spawn 时按 designId 定位槽比对 token，不符即 throw |
| 设计是权威规格 | 通读设计、遵循、不偏离；**撞设计缺口 → 停下报告**，不静默适应 |
| file 域声明 | = **预期触碰面**（调度排队 + 披露基准），**非授权边界**；超声明 ≠ 越权，**如实披露即可** |
| 永不编辑设计文档 | 真实文档漂移写报告，归父侧处理 |
| 子代理身份 | 任务已被父代理确认过——**不等用户、不请确认**，立即执行 |

**内部交付协议（子代理内闭环，权威 = 设计档 §2.2 step 6）**：

实现 → 自查透明表 → **explore 偏差审计**（审计任务书 = 父 spawn 任务书 ∪ 实际 `_touchedFiles` 机械并集；
查四类偏差：部分实现 / 静默简化 / 文档漂移 / 超清单改动未报告）→ dirty 自修（**修正轮 ≤5**）→ clean →
**advisor(code) 复评**（documents = 设计文档 + 交付文件清单）→ findings 自修 → **收敛交付**。

- 标准链 LLM 验证 = **3 次/链**（③审计 → ⑤advisor 首审 → 终审复评）；**修正轮默认不重跑审计/复评**。
- 审计节点 ≤6 次（第 7 次机械拒绝 = stalled 信号）；不收敛 → 报告 `stalled`，**绝不静默**。

**交付报告（最后一条消息 = 父侧看到的全部）**：改了什么/为什么 · 碰过的文件路径 · 怎么验证的（命令 + 结果）·
**交付透明表**（Done / Simplified / Not done，无 deferred 列）· 审计/评审轮次 + 终态（`clean` | `stalled`）。

**父侧接手（不改）**：交付 settle → 改动合并进父代理 → 父侧对照验收标准核、跑 **L2 全量恰一次** → verify →
链闭合后 `consume-design` 消费槽。**父侧不再自动 spawn 审计/评审**（防双重审计）。

### 1.11 交界面契约（每个环节传什么/怎么传/产出什么/怎么放）

**传递方式只有三类**（先立规矩，下表引用）：

| 类 | 用途 | 铁律 |
|---|---|---|
| **对话** | 人与主 agent——**唯一对话面** | 子代理无对话面；引擎室向用户澄清必经主 agent |
| **参数** | spawn 调用面（凭证/文件域/评审对象） | **token / designId 走参数，绝不进任务文本** |
| **文档路径** | 产物与输入都落盘，交界面只传路径 | 产物**不靠消息传**（消息只用于报告） |

| # | 交界面 | 传什么进去 | 怎么传 | 产出什么 | 怎么放 |
|---|---|---|---|---|---|
| B1 | 用户 → 主 agent | 需求表述（口述/吐槽/几点） | 对话 | 批次记录 §1 | `batches/<批>-<板块>.md`（新建） |
| B2 | 主 agent ↔ 需求体系 | 本批需求 + 现有 `requirements/` | 读（doc_search/read） | 冲突/含糊/缺边界清单 | 记入批次档 §1；冲突**回问用户** |
| B3 | 主 agent → eng-designer | 批次档 §1 + **本批 todo 项** + `requirements/` + 本批清单 + 归属板块 | spawn：task 文本（**传路径，不搬内容**）+ `files` 声明（**不声明 todo.md**） | — | — |
| B4 | eng-designer → 需求体系 | 本批需求 | 直接编辑（**写稿面**） | 需求条目（**带判定句**）+ 全体系对账修正 | `requirements/<板块>.md` |
| B5 | eng-designer → 需求池 | todo 项状态推进 | 直接编辑（**提示词规定的动作**；不在 `files` 声明） | 状态更新 | `docs/TODO.md` 需求池组 |
| B6 | eng-designer → 批次档 §2 | **批次任务** | **追加**（不重写 §1） | 本批覆盖条目 + 不在本批条目 + 受影响文件 + 验收标准 | `batches/<批>-<板块>.md` §2 |
| B7 | eng-designer → 设计 | 设计 | 直接编辑（写稿面） | 设计档（**产出要求 9 项**） | `design/<板块>.md` |
| B8 | eng-designer → 主 agent | —（交回） | **最后一条消息**（报告） | 改了哪几处 / 设计在哪 / 自检结果 / 打回点 | 报告不落档；主 agent 核（**第一关**） |
| B9 | 主 agent → advisor | documents 清单 + object 声明（type/target/status/reason/exclude） | advisor **参数**（**发起权在用户**） | 发现表 + VERDICT + token/designId | **凭证入会话槽，不落文档** |
| B10 | 用户 → 主 agent | 显式 sign-off / 逐条拍板 | 对话 | 批准（或打回） | — |
| B11 | 主 agent → eng-coder | 任务书（Docs involved / 文件清单 / 验收标准——从 §2 批次任务派生）+ designId + designToken | spawn **参数**（凭证走参数）；task 文本 + `files` 声明 | — | — |
| B12 | eng-coder → 交付 | 设计（权威规格）+ 任务书 | 读文件 | 代码改动 + 报告（透明表 + 轮次 + 终态） | 改动留**工作区未提交**；报告走最后一条消息 |
| B13 | 父侧验证 → 收口 | 验收标准 | 跑 L2 全量 + verify | 验收结论 | `batches/<批>-<板块>.md` §3 |
| B14 | 链闭合 → consume | designId | 参数 | 槽消费（同 designId 再 spawn 机械拒） | 会话态 |

**三条界面铁律**（从上表提取）：

1. **产物落盘，消息只报告**——交界面传路径不搬内容（防上下文膨胀 + 防双源）。
2. **凭证走参数**——token/designId 绝不进任务文本、绝不落文档。
3. **澄清必经主 agent**——任何子代理撞到需要用户决定的事，一律打回主 agent；无旁路。

## 2. 可移植性需求（2026-09-10 用户裁定——工程模式是产品功能）

**定位前提**：ThinCoder 是**面向任意项目的产品**（npm 发布 / marketplace 上架 / 全球 i18n）——
工程模式是其**产品功能**，必须在**任何项目**上可用，不得假定用户项目形如 ThinCoder 自研仓。

| # | 需求 | 约束 |
|---|---|---|
| FR10 | **不得假定项目约定** | 产品不得假定用户项目的文档布局/命名/语言/构建/测试方式；凡需知道项目约定处，必须由**项目自述**（AGENTS.md 等）或**配置**提供；**缺失时降级可见**（写进报告），不得静默失效 |
| FR11 | **开启前提不得依赖本产品自退役的物** | 开工程模式不得把某个硬编码文件名当门禁（现况：`src/tui/cmd-eng.mjs:31` 要求项目根 `METHODOLOGY.md`，而其模板文件已不存在——选项必炸；且该概念在本仓已退役）——前提应为**项目自述的可用性**或无前提 |
| FR12 | **代码/文档判据不得写死目录名** | “什么算产品代码”不得以 `^src/` 之类**字符串锚定**判定（现况：嵌套布局 `packages/foo/src/x.md` 被当文档，**静默绕过设计门禁**；非 `src/` 布局项目则所有文件都当产品代码）——判据须**单一权威 + 项目自述/配置可诉**，且任何布局不漏判 |
| FR13 | **纪律层不得把本产品形状强加给用户项目** | 纪律层提示词不得教 agent 在用户项目里建 ThinCoder 形状的目录/维护本产品的流程文件（`docs/TODO.md` 需求池、CHANGELOG 维护边界）；不得要求跑**本仓自带**的脚本（现况：`src/prompts/discipline-engineering.md:182` 教跑 `scripts/check-doc-width.mjs`——用户项目必有此脚本才不炸） |
| FR14 | **推进档位入需求** | auto（每步自动推进）/ manual（每步等用户放行，叫停即切）是**用户可感知的交互契约**，须在需求层有据（现况只活在提示词里） |
| FR15 | **非 git 项目行为有定义** | 工程模式在非 git 项目（无 `.git`）下的行为需明确定义——现况：评审范围采集/代码索引/检查点均依赖 git，缺失时**部分静默为空** |

> 上述六条均为**需求**（待设计）——具体实现方式（配置项 / 项目自述 / 探测策略）属设计层，本档不预设。
> 验证方向：用一个**非 Node、非 `src/` 布局、无 `docs/` 树、非 git** 的项目试跑工程模式全流程——
> 不得出现静默失效，不得被不存在的文件卡住。

## 3. 边界（信任模型）

- **eng-coder 拦截型机械约束**：token 校验、写文件门禁。质量靠 eng-coder 自查 + 交付前自评。
- **父代理拦截型机械约束**：design token 前写产品代码被拒。其余（等批准、不写实现、验收）靠纪律层提示词。
- **门禁豁免边界**：豁免仅覆盖设计产出物（`docs/**`、根级 README/AGENTS/LICENSE）；`src/` 下一切文件（含 prompts/*.md）为产品代码。判定 `isProductCode(p) = /^src[\\/]/.test(p) || !isDocFile(p)`（一致化已实现）。
