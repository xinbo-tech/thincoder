- 不改 provider 的 `max_tokens` 发送面（absent 语义不动）

### 五个问题的答复

**Q1 · absent 档的 limit 怎么算**

预留口径的取证在修正轮推翻了一半：`api-docs.deepseek.com/api/create-chat-completion` 一手源逐字写着「When not set, the default is 8K in non-thinking mode, 64K in thinking mode (128K with `reasoning_effort` set to `max`)」，同页写着上限「must be between 1 and 384K (393216)」。

所以默认值**有**公开来源；真正没有来源的是「该端服务端按哪个值预留」。失效现场的 400 报文「393216 in the completion」与上限逐位相同、与默认值不同 ⇒ 该端按上限预留。

结论不变、依据更新：absent 档预留取规格 `maxOutput`（deepseek 384,000 = 393,216 的十进制近似，再保守 9,216），`limit = 1,000,000 − 384,000 = 616,000`；实测 prompt 674,867 > 616,000 ⇒ **守卫本该开火**，只是被 absent 门整段跳过了。

退化档（规格 `maxOutput` ≥ 窗口，doubao 三行）今天 `limit` 为负 ⇒ 判据恒真 ⇒ 永久发不出去；给 `limit` 一个**地板**：absent 档 `limit = max(window − reserve, threshold)`（其余档仍是 `window − reserve`）。

证明只有退化行变化：若 `reserve < window` ⇒ `usable = window − reserve > 0` 且 `threshold = min(usable, 0.8w) ≤ usable` ⇒ `limit` 与今天逐位相同；若 `reserve ≥ window` ⇒ `usable = ⌊w/2⌋`（半窗退化，`config.mjs:72-76`）⇒ `limit = ⌊w/2⌋`。

落值：deepseek 616,000 · kimi-k3 868,928 · DEFAULT_SPEC 96,000 三行不变；只有 doubao 三行从负值抬到 128,000。

**Q2 · 估算偏小从哪来**

估算式 = `_estimateSingle`（`provider/rate.mjs:62-66`）：`Math.ceil((s.length - nonAscii) / 4) + nonAscii`，即 ASCII 4 字符/token、CJK 1 字符/token——没有分词器，是字符数除法。
偏差不是「算错了」，是分母对内容类型不成立：4 字符/token 是英文散文的 BPE 经验值，代码 / JSON / 路径 / 十六进制落 2.5–3。

口径混用更正是必要的：状态栏 `489k` 是 `historyPercent`（**仅 history** 估算），400 报文 `674,867` 是服务端 `prompt_tokens`（**含 system + tools**）。两者不同分母，相除的 1.38 只是上界。

该会话的固定开销未单独实测；按本档小窗口档的量级 30–50K 估（此为估计，非读数），history 侧真值 ≈ 625–645K ⇒ ratio ≈ 1.28–1.32 ⇒ 隐含 3.0–3.1 字符/token。两种读法都指向「估算低 25% 以上」，而**设计不依赖这个数**——校准吃服务端真值（见下），这个区间只用于诊断叙述。

修法 = 用服务端自己的 `usage.prompt_tokens` 做**池化比**：每次成功响应后累加 `num += prompt_tokens`、`den += estimateRequestTokens(body) − (body.max_tokens ?? 0)`（分子分母同取输入侧），`_tokRatio = num ÷ den`。`key = format + ":" + model` 变了就归零重采；`/new` 清空。
为什么不是 EWMA + 样本门槛：门槛要一个无现场的魔数；池化比按样本自身大小加权，小样本自带小权重、动不了比值，分支因此消失。

**Q3 · 重试路径与压缩入口**

重试路径**不在 provider 层**：`requestWithRetry`（`provider/core.mjs:385`）会重试，但 400 在 `isNonRetryableError`（`provider/errors.mjs:36`：400–499 且非 429 且不在 `RETRYABLE_STATUS`）被判终局，`core.mjs:449` 直接抛。⇒ 用户看到的三次尝试**不是** `requestWithRetry` 干的事，O2 未定位。

同文件另两条重发路径已读过并**排除**：`MAX_OVERLOAD_RETRIES` 同 `body` 重发（`core.mjs:266-273`，判据 = `finishReason === "insufficient_system_resource"`）、续写链再走一次 `chat(...)`（`core.mjs:289-303`，判据 = `finishReason === "length"`）——两者都在成功响应之后，与三次 400 不符。剩余未定位面 = 任务外的多轮新开发送。

结构结论：发送面**是**唯一漏斗，但 `chat()` 今天不做预算判断，任何调用方漏了安全点都能把越窗请求发出去。修法三件：

- (a) **发送面净判，落四个装配面**（不是 `chat()`）：`chat()` 入参只有 `messages` / `tools` / `logCtx`（`core.mjs:84`），没有 body，取不到输出预算字段；body 在四面各自组装。判点 = 四面既有估算点 `core.mjs:252` · `anthropic.mjs:208-211` · `google.mjs:121` · `responses.mjs:231`，就地用已有 `estimated`，零新算式；`google` / `responses` 两面既有估算只含 messages，补 `tools` 项。
- (b) **内部阶段豁免**：`logCtx.stage ∈ {"compress","distill"}` ∥ `isContinuation === true` ⇒ 跳过净判。压缩请求自带≈整段历史且不传 `max_tokens`（`context.mjs:203-215`），判它 = 判掉止血动作本身。残余风险 = 该次压缩仍可能被服务端判越窗 ⇒ 走既有失败链（三次后 `compressFallback` 确定性截断、零网络），回合请求随后才发。
- (c) **HTTP 400 越窗分类**：`core.mjs` 错误出口按报文特征（`maximum context length` / `context_length_exceeded` / `prompt is too long`）标 `kind = "context_overflow"` · `retryable = false`；词表复用 `errors.mjs:122-123`（同 kind / 同 retryable / 同 `/compact` 提示），不新增词。
- **不做**「自动压缩后自动重发」：压缩入口在 agent 层、provider 无历史；§6.17 禁同安全点连压第二次。目标由 (a) 达成——重发在本地被拒绝。

**Q4 · 相互依赖，先修哪个能单独止血**

**① 单独即可止血**：`limit = 616,000`，实测 674,867 > 616,000 ⇒ 强制压缩一次 ⇒ 请求体落到约 15% 窗口 ⇒ 发得出去。
② 单独**不够**：估算准了会提前压缩，但守卫仍不覆盖 absent 档；压缩失败仍会发出越窗请求。
③ 单独**只防重复付费**：本地净判拒绝，被拒的回合仍过不去。

**修正上一版的一处错误结论**：三者**不是**无共享状态——① 与 ③ 落在同一条发送面上（① 依赖的那次压缩请求也走 `chat()` 与四面），先前的净判会把它一并拒掉。现在的分离手段 = (b) 的阶段豁免，不是「互不相干」。
依赖方向：① 只动 `requestBudget.limit` + 守卫条件；② 只动 `contextUsage` + 采样点；③ 只动四面估算点 + `errors.mjs`。**可分别落、分别验**，但 ③ 必须先有 (b) 才能与 ① 共存。

**Q5 · 怎么可复现地造「absent 档 + 超限」**

不需要真 provider，桩路四条（用例正文与夹具 = design §6.17 RB17–RB23）：

① absent + 越窗：`provider = { format:"openai", model:"deepseek-flash" }`（无 `maxTokens` ⇒ `maxTokensSource === "absent"`、`limit === 616000`），history 造到估算 620,000；`fetch` 桩按 `logCtx.stage` 分别计数。

② 压后仍超（确定夹具）：摘要桩返回 700,000-token 内容（`"y".repeat(2_800_000)`）⇒ 压后估算仍越线 ⇒ 抛 `context_overflow`、回合请求 fetch 0。

③ 校准：桩 body 逐字 + `usage.prompt_tokens := 2 × (estimateRequestTokens(body) − body.max_tokens)`。

④ 退化档不误伤：`{model:"doubao-seed-2-1-pro-260915"}` absent ⇒ `limit === 128000` ∧ 估算 100,000 时零压缩零抛。

真机复现留父侧收口：同一会话跑到状态栏 > 45% 后继续追加大报告，观察 400 之前是否出现一次压缩。

## 本批记下的两条教训

**一、数值类的批量影响，不能靠枚举错误，要靠校验不变量。**

`COMPACT_RATIO` 0.8 → 0.6 这一个改动，波及设计档二十多处由它算出的 `threshold`。前四轮都用「枚举已知错误值」的方式扫，每轮漏几个；第五轮改成**正向扫**（抓所有数字、逐个复算）才一次扫净——67 个值，0 不符。
