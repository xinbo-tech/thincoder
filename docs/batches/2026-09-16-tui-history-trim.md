### 2.1 问题陈述（根因终稿）

**缺陷**：`syncLineBudget`（`thincoder-cli/src/tui/display-budget.mjs:166-180`）字符超额裁剪无有效保底——循环守卫只保 1 行
（`lines.length > 1`），步进 `take = min(1000, lines.length - 1)`（:167）在行数 ≤1001 且超额时**一轮裁到只剩 1 行**；
收据计数 = 裁后 `lines.length`（:173），即用户实测的「1 lines remaining」。
本设计轮直驱实测（2026-09-16）：1001 行 × 2000 码元 → 裁后 2 行、收据「1 lines remaining」；200 行 × 60000 码元 → 同样 2 行。

**触发面现实（非极端）**：2M 码元 ÷ 典型 1–2K 码元/行 ≈ 1000–2000 行即触发；裁到近空后（字符近零）再长回 2M 时行数恰 ≈1002
⇒ 实测每约 999 次 push 复现一次「裁到 1」——长会话**周期性近空**，非一次性事故。会话启动恢复（`restoreLines` 一次 materialize ≤200 条消息——
`thincoder-cli/src/tui/startup.mjs:125-149`）在字符存量 > 2M 的会话里同型触发（用户 00:52 实测点）。

**§1 未解项核清（三点——明确结论 / 反证）**：

① **阈值与保底**：保守下限**不存在**（实保底 = 1 行——上式实核）；与行环路径（`thincoder-cli/src/tui/index.mjs:288-290`：>5000 行裁 1000 行 →
保底 ≥4001 行、收据计数不可能出 1）**口径不一致**。**裁定 = 固定行保底 `LINES_TRIM_FLOOR = 200`（导出常量）+ 最小步进裁剪**
（只裁至额度内所需最少行数；触底即停、接受超额）。本设计轮以修复算法直驱验证：1001×2000 → 保 1000 行；2501 行（超额 5000 码元）→ 只裁 7 行；
200×60000 → 零动作（保底）；常规内容稳态窗口 ≈1000 行。

② **恢复路径记账**：**不绕过（假设被否——反证）**。`restoreLines` = 直算重对账 + 重跑 `syncLineBudget`（`startup.mjs:147-148`）；
`loadOlder` = 逐行 `accountLine` + 占位行入账 + 重跑（`startup.mjs:185-194`）；`/session` 切槽 = 账归零 + `restoreLines` 重入账
（`thincoder-cli/src/tui/cmd-session.mjs:97-99`）；`/new` / `/clear` = 行集清空同步归零（`cmd-new.mjs:21-22` / `cmd-clear.mjs:11-19`）。
「裁了又回来」真正成因 = **materialize→对账裁剪 循环**：每次恢复 / 切槽 / 翻页从存储重建窗口，重建即过 `syncLineBudget`；
存量 > 2M 时每次重建都被裁、旧颗粒下每次裁到近空 ⇒ 用户看到「历史又回来（重建）→ 又没了（裁）」。
**修复点 = 裁剪策略（本批），记账面零改动。**

③ **双层 scrollback**：**外层不承载会话（假设被否）**。TUI 全程 alt screen（`\x1b[?1049h`——`thincoder-cli/src/tui/ansi.mjs:10`；
启动序列 `tui-lifecycle.mjs:15`）：alt 屏不累积终端自身 scrollback、退出即弃；滚轮经 TUI 鼠标上报拦截走内层（`index.mjs:225-243`），
PgUp 同内层（`key-handler.mjs:266-277`）。用户可见历史 = 内层 `state.lines` **单层**；「视口错位」机理全在内层
（裁后近空 + 自底偏移 clamp——`render-loop.mjs:71-87`）。**裁定：不加外层锚定动作 / 提示**；内层既有语义（自底偏移 / 增长补偿 / clamp）
与收据行语义均不改。

### 2.2 方案选型对比

判据（来自 §1 期望与结构纪律）：① 保底（不清到一屏以下，可机判）② 裁剪最小化（不多丢）③ 内存上界（N10 有界性保持）
④ 确定性与可测性（无 dims 耦合）⑤ 既有机制一致性（收据 / 锚点 / 行数环）⑥ 改动面（单点闭环）。

| # | 候选方案 | ①保底 | ②最小化 | ③上界 | ④确定性 | ⑤一致性 | ⑥改动面 | 结论 |
|---|---|---|---|---|---|---|---|---|
| 1 | **保底 200 行 + 最小步进裁剪** | ✓ | ✓ | △（保底态接受超额——上界 = 200 × 单行上限 ≈ 2.8e5 ≈ 5.6e7 码元，仍远低于事故面） | ✓ | ✓ | ✓（display-budget 单点） | **选定** |
| 2 | 保底 200 行 + 保留 1000 行步进 | ✓ | ✗（超额 1 码元也裁 1000 行——实测 2501 行场景丢 1000） | △ | ✓ | ✓ | ✓ | 否决：②不满足——颗粒根因未除（半修） |
| 3 | 动态保底「一屏」（按 `state.dims` 行数现算） | ✓ | ✓ | △ | ✗（leaf 模块引入 dims 耦合；同一状态不同终端裁剪结果不同——机判不稳） | ~ | ~ | 否决：逻辑行 ≠ 显示行（折行不可折算）；非确定性伤机判 |
| 4 | 字符下限保底（保 ≥ K 码元） | ✗（胖行下 K 码元 = 2–3 行——仍近空） | ✓ | ✓ | ✓ | ~ | ✓ | 否决：不满足「不清到一屏以下」的行数判据 |
| 5 | 抬高 `LINES_CHAR_BUDGET`（不动裁剪逻辑） | △（只推迟触发） | ✗ | ✗（内存上界抬升——TUI-OOM 批动机面回退） | ✓ | ~ | ✓ | 否决：不治本（触发点后移、近空仍会发生） |

**记账对齐三形态评估**（§1 未解项②候选面）：① 恢复路径纳入 `accountLine`——现状**已满足**（反证见 2.1②）→ 无需改；
② 重载后重跑 `syncLineBudget`——现状**已满足**（同上）→ 无需改；③ 双层记账——第二账无消费者、与既有直算对照测试
（`accountAll === _linesChars`）叠床架屋、引入漂移源 → **否决**。

**定稿形态（实现契约）**：`while (_linesChars > LINES_CHAR_BUDGET && lines.length > LINES_TRIM_FLOOR)` 内按「至额度内所需最少行数
（need = 超额 + 收据上界预留 ≈96 码元）」逐行累加取数（上限 = `lines.length − FLOOR`）、裁头 + 收据 + `onTrim(state, i)`；
触底（i = 上限）即停（接受超额）；收据文本 / 计数口径逐字不变；`pushLineLike` / `onTrim` 两注入参数语义不变。
