### 1.4 我要的规则（**父侧的判定，不是用户原话**）

**核心一句：一本批档 = 一条台账行。**

**理由**：台账行是**执行单位的账**，批档是执行单位的载体。**两套账并存，必然出现「批里已结、账上还开着」或反过来。** 条目的可追溯性由批档 §1 逐条登记原条目号补回，不靠台账上多条行。

**点火时先数这本覆盖几条旧账，三条分支：**

| 这本覆盖 | 怎么做 |
|---|---|
| **0 条**（新开的活） | `create` 不带 `ledger` ⇒ 自动开一行 |
| **1 条**（这本就是那条债） | `create` 带 `ledger: <id>` ⇒ **接管**它（`task_book` 改指本批档、状态推进） |
| **N 条**（清账批，覆盖多条旧债） | **接管最相关的一条**（或新开一行），**其余同轮并入**：撤回该行 + `evidence` 写「并入 `#<新行>`；内容在本批档 §N」。**并入 ≠ 丢弃** —— 内容在哪一节要写清，查得到 |

**收口时**：`batch close` 只重锚 `task_book` = 本批档的行 —— **所以指针必须指对，指错了收口就漏行。**

**这条的硬含义（父侧推出来的，需要用户认）**：

**认领 = 承诺本批做完。** 所以点火时要先判「这条债能不能在这批做完」，**判不能 ⇒ 不认领**。

**两条调和路径（父侧倾向 A）**：

| | 处置 | 后果 |
|---|---|---|
| **A（倾向）** | 认领即承诺；**确实做不完 ⇒ 收口时标「计划失误」+ 解绑（`task_book` 清空、退回 `待讨论`）**，由后续批**重新认领** | 账上是一次「退回」，不是「接力」；一条债在任何时刻只有一个持有者 |

**规则定形**：

| 时点 | 要求 |

### 机制设计（一句话）

台账行 = 要求点的账；批档 = 执行载体。**本档的账 = `task_book` 指回本档的行集**（单源 `resolveBatchRows`），点火时把这个集合填满：覆盖 0 条新开一条、1 条接管、N 条把 N 条全绑回本档。
做没做完按行算（`docs/core/design/BATCH-LEDGER-REVIEW-UNIFY.md` §2.7 分流），所以不撤回并入——只有重复登记才撤回。

### 与 §1.4 的差异（请父侧裁）

§1.4 的 N 条分支 = 接管一条 + 其余「撤回 + `evidence` 记并入」。本设计改为 **N 条全绑**，撤回只留给重复登记。
