## §1 讨论（主 agent）

### 批次范围

工程模式的**基本定性 + 工作流程**（本批不谈实现、不谈可移植性细节）。

### 谈成什么（逐条）

1. **定性**：工程模式是**面向任意项目的产品功能**，不是本仓自用工作流 → 需求档 §2 定位前提 + FR10-FR15。
2. **工作流程**（用户口述 + 逐条澄清）→ 需求档 §1.6：
   - 人按批次提需求；主 agent 收集、登记、澄清、与已有需求文档对账（冲突处回头问人）。
   - 需求清爽 + 用户同意 → 才进设计；eng-designer 接手后**先整需求文档、再写设计**。
   - 整合中发现需求说不通 → 打回主 agent → 向用户澄清。
3. **张力定性**：需求文档的**整体性** vs 需求提出的**批次性**是客观张力——
   **它正是 eng-designer 存在的理由**（把批次输入维护成整体体系）。
4. **分工**：主 agent **以批次式记录需求**（适应交互节奏）· eng-designer **依批次登记需求、维护体系整体性**。
5. **载体落地**：批次记录放 `docs/batches/<批>-<主题>.md`（本档），**六段式、一段一作者**（讨论 / 批次任务 / 设计评审 / 批准 / 实施 / 验证收口）；
   生命周期 = 讨论 → 任务 → 验收 → **整档冻结**。**批次任务**独立于设计档（一次性内容不混进长期档）。

### 过程留痕（讨论约定 / 踩过的坑 / 逐条裁定）

**主 agent 的踩坑记录（两种复发毛病——2026-09-10）**：

1. **凑条目**：为了“列得周全”把**不产生不同处置**的东西列成独立问题——例：给 explore（进程内工具、只读）
   单设批次档段（被用户驳：**段=链上角色**）；善后场景里凭空分出“清单外文件”变体（FR6 已定清单外改动
   允许，处置与清单内完全相同）。**判据**：列一项前先问“它的处置与已有项**不同**吗”，相同即不列。
2. **编造用户裁定**：在主 agent 写的裁定里**自行加上用户没说的一句**（例：“不加机械校验”——用户只说了
   “查不到就不执行”，机械校验**未表态**）。**规矩：用户说的原样记；未表态的写“未表态”，不得替他定。**

**讨论约定三条**：

- **记理解，不记原话**：需求文档记主 agent 的理解（结论），不搬用户口述原文；理解错了用户纠正。
- **记录不加工**：主 agent 不得把口述拆成步骤时掺入自己的排序/推断——那是解读不是记录（本批发生过一次，已纠正）。
- **需求层问题立即改**：定性与流程属需求本身的问题，当回合即修，不等攒批。

**主会话需求讨论循环（六步，已确认）**：复述确认（只复述不加工）→ 落批次记录 → 与已有需求文档对账 →
把对账结果回给用户（一次一问，不自己解释）→ 问缺（边界/验收/共存）→ 收口回读（用户说"就这些"即收口）。
出口：收口后停住，用户说开始设计才调 eng-designer。
（用户 2026-09-10："步骤可以，没什么太大的偏差，以后需要改再跟你说"。成文 §1.7。）
