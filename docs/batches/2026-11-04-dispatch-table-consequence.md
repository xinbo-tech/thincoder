## 缺口实读

- **规则在、落点不在**：`thincoder-core/prompts/persona-engineering.md:328` 逐字「**The `why` in a task book must carry the reasoning, not just the order**: state what happens ∥ why that is bad (the cost chain — not "because the user said so") ∥ what to do when the rule and the case seem to diverge.」
- **模板不给位**：同档 `:340` 逐字「**A task book is a table, not prose**: the core of a dispatch is a **row-by-row action table** (action / landing point — the file path plus the exact words, or the symbol / expected result);」——表只有 动作 ∥ 落点，没有「后果」。
- **设计档同形**：`docs/core/design/PROMPT-SYSTEM.md:428` ④ 逐字「**任务书 = 表，不是散文**——核心 = 逐行动作表（动作 / 落点 file:line / 期望），散文只留目标与边界」。

**上一条已定决定更正（用户当场纠）**：第三列是**原因**，不是后果。

- **已定决定（更正）**：派单动作表 = 「动作 ∥ 落点 ∥ **原因**」——第三格写**为什么这么做**（依据 / 理由），不是「不这么做会怎样」 · 用户原话：「不是后果，是原因」 · 时间：2026-11-04 04:41
- **为什么这一步错不得**：后果是**推测**（「不改会怎样」是还没发生的事，写它等于让派单者替执行席预演失败）；原因是**可核对的事实**（依据哪条设计、哪个判据、哪次实测），执行席能拿它去对盘，也能在它不成立时反过来质疑指令。表里放推测，等于把「可验证的依据」换成了「说服性叙事」。
- 据此，`:328` 那句「state what happens ∥ why that is bad」是**在讲怎么把理由写透**（一句话里带上事实与代价），不是要求表里另起一列写后果——本批只动模板列名，那句原文零改。
