## 批次范围

工程模式的**基本定性 + 工作流程**（本批不谈实现、不谈可移植性细节）。

## 本批谈成什么

1. **定性**：工程模式是**面向任意项目的产品功能**，不是本仓自用工作流 → 已入需求档 §2 定位前提 + FR10-FR15。
2. **工作流程**（用户口述 + 逐条澄清）→ 已成文需求档 §1.6：
   - 人按批次提需求；主 agent 收集、登记、澄清、与已有需求文档对账（冲突处回头问人）。
   - 需求清爽 + 用户同意 → 才进设计；eng-designer 接手后**先整需求文档、再写设计**。
   - 整合中发现需求说不通 → 打回主 agent → 向用户澄清。
3. **张力定性**：需求文档的**整体性** vs 需求提出的**批次性**是客观存在的张力——
   **它正是 eng-designer 存在的理由**（把批次输入维护成整体体系）。
4. **分工**：主 agent **以批次式记录需求**（适应交互节奏）· eng-designer **依批次登记需求、维护体系整体性**。
5. **载体落地**：批次记录放 `docs/discussion/<板块>.md`（本目录），生命周期 = 讨论 → 抽入需求文档 → 留痕。

## 本批的讨论约定（过程性，值得留痕）

- **记理解，不记原话**：需求文档记主 agent 的理解（结论），不搬用户口述原文；理解错了用户纠正。
- **记录不加工**：主 agent 不得把口述拆成步骤时掺入自己的排序/推断——那是解读不是记录（本批发生过一次，已纠正）。
- **需求层问题立即改**：定性与流程属需求本身的问题，当回合即修，不等攒批。

## 主 agent 的讨论循环（2026-09-10 用户确认）

六步：**复述确认**（只复述不加工）→ **落批次记录**（\`discussion/<批>-<板块>.md\`）→ **与已有需求文档对账**（冲突/重复/语义打架）→ **把对账结果回给用户**（一次一问，不自己解释）→ **问缺**（边界/验收/共存）→ **收口回读**（用户说"就这些"即收口）。
出口：收口后停住，用户说开始设计才调 eng-designer。

> 状态：**已确认**（用户 2026-09-10："步骤可以，没什么太大的偏差，以后需要改再跟你说"）——
> 另就地修正两处配套：需求池保留作台账、讨论档改一批一份谈完冻结。成文见 \`requirements/ENGINEERING-MODE.md\` §1.7。

## eng-designer 工作流（本批讨论）

- **授权范围疑点**（用户反问）：`只改自己能改的` 能否保证全体系一致性？——**不能**（跨板块矛盾永无人管）。
- **结论**：eng-designer 授权 = **需求文档体系整体**：一致性问题自主修（跳板块重复/措辞矛盾/结构错位/过时表述/指针失效），
  **需求语义问题打回澄清**（改含义/砍范围/改优先级是用户的决定）；一切修改**逐条报告**，不得静默改。
- 五步：勘察现状（自拿 file:line 证据）→ 并入需求文档体系 + 全体系对账 → 配验收口径 → 写设计（需求成文后）→ 自检交回停。
- 未定：spawn 粒度（一批一次 / 按板块）；验收口径位置（写需求时 / 设计阶段）。成文见 `requirements/ENGINEERING-MODE.md` §1.8（待确认）。

## 两道关模型（2026-09-10 用户定）

主 agent 与 eng-designer 的互动**类似一个 advisor 循环**（来回呈递/修正），区别在分工：

- **第一关：主 agent ↔ eng-designer**（同层边写边核）——设计者负责 **需求不漏、跟踪不乱、据需求做好设计**；
  主 agent 核需求是否漏、跟踪是否乱（台账/文档体系），问题回给设计者改。**不审设计好坏**。
- **第二关：advisor 文档审核**（下一步、独立上下文）——**审核设计本身是否有问题**；不管需求收集与跟踪。

顺序：先过第一关 → 再交 advisor 审设计（发起权在用户）。成文见 §1.6。
