### 结论（进入设计的判据）

1. **「建核」不是搬运**：内容层已同（提示词 28/40 逐字节相同），**实现层才是真分叉**（`.mjs` 中位 0.28、29 档 <0.2）⇒ 核的构建必然含**逐模块语义裁决**（以谁为准 / 融合 / 判为端特有）。
2. **凭空写中立核 = 造第三份实现**——正是 phase 1 否决 X1「抽独立核心包」的理由（会让工作退化成重写）⇒ 核**必须从两套现有实现提取**。
3. 因此采纳用户保守路线，并细化为四段（下）。

### 路线（四段 · 每段独立可验、可回退）

| 段 | 内容 | 铁律 |
|---|---|---|
| **S0 差异分析 + 逐模块裁决**（零代码） | 67 对逐条分类：① 近乎同（可直取）② 语义同实现异（融合）③ 语义真分叉（**须判决**）④ 端特有（不进核）；产出 = **核模块清单 + 每条的裁决依据** | 未分类不建核 |
| **S1 建核**（两产品**一行不改**） | 新目录逐模块**从两边提取** + 每模块自带测试（两边测试合流）+ 独立跑绿 | 核可独立验证 = 用户要的「试一下可用」 |
| **S2 逐模块迁移** | 一次一个模块接过去 + 删旧实现 + 复跑该产品全链 | 单步可回退；先接一产品再另一产品 |

### 边界与约束（设计须遵守）

- **另建板块文档**（`docs/README.md` 地图登记）——不在 `TWO-REPO-MERGE.md` 内扩张（§2.13 明文边界）。
- **产品运行时行为不变**（承 phase 1 F7 口径）；核的引入不得改变 CLI/VSC 的可观察行为。
- **提示词不做单副本合流**（D14 仍有效：运行期硬加载 + 打包只收包根内文件 ⇒ 机械约束）——核**不得**试图统一提示词文件布局。
- **每段可回退**：S1 不动两产品；S2 单模块一步一提交。
- 关联技术待办「CLI 无『子 agent 被丢弃』提醒（与 VSC 不对称）」= 本病的现成实例（可为 S0 的样例）。
