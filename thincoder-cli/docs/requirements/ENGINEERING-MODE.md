## 0. 铁律（发起权与批准权归用户——2026-08-24 决策）

背景：agent 曾两次越权抢跑（自行提交设计评审 → 拿 token → 直接开发，其中一次全程零确认）。此后固化四条铁律：

1. **设计评审只能由用户发起**——agent 准备并提醒"设计就绪，可以评审"，不自行调 advisor。
2. **打回后逐条呈递**——评审打回后每轮呈递发现 + 修复建议，**用户逐条拍板**再改（agent 不自行修完重送）。
3. **交付 code review 保持流程节点自动**——eng-coder 返回后自动评审，不问用户（2026-09-02 起由 eng-coder 内部协议默认承担）。
4. **系统推回（guard）在工程模式一律关闭**——未来若启用也只作提示，评审仍由用户发起。

## 1. 需求（Requirements）

### 1.1 总体需求

普通模式靠纪律提示词约束模型；工程模式把"设计先行、评审把关、验证收尾"提升为**半机械流程**——可硬性拦截的环节一律拦截（写文件门禁、token 校验），无法硬拦的靠纪律层槽位提示词约束。核心承诺：**代码必须先有被评审过的设计；评审对象由任务定义而非遍历猜测；评审循环在实现者内部闭环（不依赖父代理持有凭证）。**

### 1.2 用户故事（从用的人角度看——为什么需要这些机制）

**发起权（对应 §0 铁律）**

- 作为开发者，我想**自己决定什么时候发起设计评审**——在我的需求讨论完了、我认为可以了的时候——
  而不是 agent 自己觉得想清楚了就开评。
- 作为开发者，我想让评审打回后**逐条听 agent 说发现和修复建议、由我决定改哪些**，
  而不是它自己改完直接送回——否则我看不到它替我做了什么决定。

**设计先行（FR1/FR2/FR3）**

- 作为开发者，我想让有规模的任务**先写出“打算怎么做”并经过独立评审、我点头，才允许改代码**，
  这样我不会一觉醒来看到一堆没经过我同意的改动。
- 作为开发者，我想**只有我批准的方案才能进入实施**（凭证落到实现者手里），
  这样没人能跳过评审直接改代码。

**独立评审（FR2/FR5）**

- 作为开发者，我想让**另一个独立的评审角色**（不是写方案的那个、不共享它的上下文）挑毛病，
  这样我不会被写方案的 agent 的自信误导。

**实现者的纪律（FR4/FR6）**

- 作为开发者，我想让实现者在交给我之前**先自查、再被独立评审一遍**，这样我不用当第一个 QA。
- 作为开发者，我想让实现者**撞到设计漏洞时停下来告诉我**，而不是自己编一个方案继续干。
- 作为开发者，我想让改动**超出原定范围时逐条告诉我**，而不是悄悄改。
- 作为开发者，我想在它**卡住、没收敛时被告知**，而不是等一个看起来正常的失败。

**并行与留痕（FR7/FR8）**

- 作为开发者，我想能**同时推进多个互不相干的任务**，而不必排队等。
- 作为研发负责人，我想让技术待办**集中在一处**，而不是散在设计文档里到处找。
- 作为团队的一员，我想让**每一步的决定都有据可查**（谁提的、什么时候批的、怎么验证的），
  这样半年后或换了人也能接手。

### 1.6 工作流程（主 agent 的理解——2026-09-10 **用户已确认**）

**一句话**：人按批次提需求；主 agent 收、对、问；需求清爽且人点头后，才交给设计者；
设计者**先把需求文档整合干净，再写设计**。

**适用范围（2026-09-10 用户定——A6，用户同日纠正措辞）**：**纯文档维护同样是需求**——它**入口走需求侧**
（登记进需求池 → 澄清/收口），**但不需要走代码侧的后续流程**：

| | 代码变更 | **纯文档维护** |
|---|---|---|
| 需求侧（登记/澄清/收口） | 走 | **走** |
| 设计评审 → 用户批准 → eng-coder 实施 → 验收链 | 走 | **不走**（没有开发，哪来后面那些） |
| 实施者 | eng-coder | **写稿面唯一作者（= eng-designer）**——**它做了就完**（落地注记已核销：eng-designer 第 2 批落地 CLI、第 5 批镜像 VSC——本格现由其实际承担）。 |

**理由**：代码侧那些环节（评审/批准/凭证/验收）保护的是"**改代码**"这件事；文档改动由写稿面唯一作者实施，
**做完即完**。**"不拦"≠"免登记"**——免的是代码流程，不是需求登记（否则无设计无评审地连续改动会把体系改乱，
**本批即实证**：主 agent 一天内改了几十处文档（含新增 8 节），自审出四处自身造成的混乱：
①需求档头部状态行过期 ②FR16 注复制 §1.12（双源）③批次档 §1 大段复述需求档（双源漂移风险）
④§1.2 用户故事未跟上新 FR——已登记入需求池待处理）。

**分步**

1. **人提需求——按批次**。想起什么说什么，交代给主 agent（不是一次把整个产品想清楚）。
2. **主 agent 负责会话**：收集、登记本批需求，把含糊处问清楚。它是人与后续角色之间唯一的对话口。
3. **与已有需求文档对账**：新需求要跟**现有需求文档**比对——跟已有条款冲突、重复、或语义打架的地方，
   **回头问人**，不自己挑一个解释。
4. **需求清晰 + 人同意 → 才进设计**：本批需求都问明白了，且用户同意开始，主 agent 才去调 **eng-designer**。
5. **设计者先整需求、再写设计**：eng-designer 接手后**第一件事不是写设计文档**，而是把本批需求
   **整合进整体需求文档**——保证全篇逻辑连贯、前后不矛盾、没有互相打架的条款。
6. **整不动就把问题打回**：整合中发现需求本身说不通（缺口、矛盾、不可实现）——**打回主 agent**，
   由它向用户澄清；澄清后再继续。
7. **需求文档干净了，才写设计文档**：需求整合完整是写设计的前置条件。

**这个流程里我读出的要点（用户 2026-09-10 补充确认）**

- **张力是客观存在的，不是缺陷**：需求文档要的是**整体性**，而人提需求是**批次式**的（跟着交互节奏走）——
  这个张力**正是 eng-designer 存在的理由**：由他把批次性的输入维护成整体性的文档体系。
- **分工（用户观点）**：
  - **主 agent：以批次式记录需求**——适应与用户的交互节奏。**但记在哪里需要定义**（开放项，见下）。
  - **eng-designer：根据批次去登记需求，维护需求文档体系的整体性**。
- 因此不是"主 agent 写需求、设计者只写设计"，也不是"设计者替主 agent 做需求"：
  **批次记录在会话面，整体成文在写稿面**。

**记录规范（2026-09-10 用户定——也是本批讨论的教训）**

- **记理解，不记原话**：需求文档记主 agent 的理解（结论），不搬用户口述原文；理解错了由用户纠正。
- **记录不加工**：主 agent 把口述整理成条目时**不得掺入自己的排序/推断**——那是解读不是记录。
- **需求层问题当回合改**：定性与流程属需求本身的问题，不等攒批。

**批次记录的载体（2026-09-10 用户定；粒度同日定）**

- **`docs/batches/<批>-<主题>.md`**——**批次记录档**（**一批一份，六段 append-only**）——完整机制与模板见 **§1.12**。
  生命周期：起草于讨论开始 → 需求谈清后由 eng-designer 抽入 `requirements/` → **本档冻结**（append-only，不回改）。
- **为何一批一份**（用户裁定）：滚动档要求 agent 反复"定位不漂/结构不错位/记录不加工/长档不腐"——
  恰是它最弱处且已实证（本仓滚动档全腐化、批次档零腐化）。**形态迁就 agent**：新建一份、写完冻结。
- **跨批检索**靠 `TODO.md` 需求池台账（每条需求 → 哪批谈的 + 状态）。机制与模板见 **§1.12**（地图 §3.8 只记本仓路径）。
  （本批记录档：`docs/batches/2026-09-10-ENGINEERING-MODE.md`）

**需求池**——机制与条目形态见 **§1.13**（本档）；与批次记录档互补：批次档记"这批怎么谈的/派了什么/验收如何"，需求池记"每个点落地没落地"。

**两道关（谁审谁——2026-09-10 用户定）**

主 agent 与 eng-designer 的互动**很类似一个 advisor 循环**（来回呈递/修正），区别只在分工：

| | 负责什么 | 不管什么 |
|---|---|---|
| **第一关：主 agent ↔ eng-designer**（同层边写边核） | 设计者：**需求不漏、跟踪不乱、据需求做好设计**；主 agent：核需求是否漏、跟踪是否乱（台账/文档体系），问题回给设计者改 | 不审设计好坏（无判断设计质量的职责） |
| **第二关：advisor 文档审核**（下一步、独立上下文） | **审核设计本身是否有问题** | 不管需求收集与跟踪 |

**顺序**：先过第一关（需求并入体系 + 设计成文）→ 再交 advisor 审设计（发起权在用户）。

### 1.7 主会话需求讨论循环（2026-09-10 用户确认——“步骤可以，以后需改再说”）

> 循环**由用户驱动**（想起什么说什么，一句话/一段吐槽/一次几个点都行）——agent 不主动起头。

| # | 主 agent 的动作 | 关键点 |
|---|---|---|
| 1 | **复述确认** | 用自己的话把你的表述复述一遍（“你是说 X，对吗”）——**只复述，不加工**（不排序、不补全、不揣测言外之意） |
| 2 | **落批次记录** | 写进 `batches/<批>-<主题>.md` §1——**按模板骨架填槽**（批次范围 / 谈成什么 / 对账结果 / 本批需求清单 / todo 项 / 过程留痕 / 状态；骨架见 §1.12），不自行组织结构 |
| 3 | **与已有需求文档对账** | 去 `requirements/` 逐条比：冲突 / 重复 / 语义打架 → 记下；相关不冲突 → 增量；全新 → 新板块 |
| 4 | **把对账结果回给你** | 有冲突/含糊/缺边界的**一次问一个**（不连珠炮）；**不自己挑一个解释** |
| 5 | **问缺** | 追边界（不做什么）、验收怎么算过、与既有条款怎么共存 |
| 6 | **收口回读** | 本批说完 → 回读“本批需求清单” → 你说“就这些” = 本批收口 |

**出口**：收口后**停住**（发起权在用户）——你说开始设计，主 agent 才去调 eng-designer。
交出去的东西：批次记录档（§1 讨论）+ 相关现有需求文档 + 本批清单。**需求层不过评审**（用户确认即定稿）。

**循环期间的纪律**：批次档不是规格（需求永远在 `requirements/` 成文）· 冲突一律回问（无“自己决定”的口子）·
随时可改口（追加/修正 → 回到第 1 步，批次档跟着改）· 猜攒批（零散点先落批次档，攒够了你决定何时正经谈）。

**已定配套**：需求池保留作落地台账（地图 §3.9）；**批次记录档一批一份、六段、整档冻结**（§1.6 / §1.12）。

### 1.8 eng-designer 工作流（主 agent 设想——2026-09-10 **用户已确认**）

**授权范围 = 需求文档体系整体**（非单板块）。理由（用户 2026-09-10 反问）：
只改自己能改的**保证不了全体系一致性**——跨板块矛盾会永远无人处理（本仓实例：旧地图自相矛盾、
PROMPT-SYSTEM 状态行与施工档打架、METHODOLOGY 已退役而产品仍拿它当门禁）。

**边界（我能改什么）**：

| 可自主修 | 必须打回澄清 |
|---|---|
| **一致性问题**：跨板块重复、措辞矛盾、结构错位、过时表述、指针失效 | **需求语义**：改含义、砍范围、改优先级——那是用户的决定 |
| 均需**逐条报告**（改了哪几处、为何）——不得静默改 | 打回主 agent → 用户澄清 |

**收到什么**：批次记录档 §1 讨论（`batches/<批>-<主题>.md`）+ **本批 todo 项**（主 agent 提交时必须包含）+ 需求文档体系（`requirements/`）+ 本批需求清单 + 归属板块。
**缺料（归属不明/清单不全）→ 打回**，不自己猜。

| # | 动作 | 产出 |
|---|---|---|
| 1 | **自己勘察现状**——读代码/文档/既有设计，拿 `file:line` 证据（可派 explore 并行）——只有设计者自己勘察才能发现需求缺口 | 现状事实 |
| 2 | **把本批需求并入 `requirements/`**（**todo 侧 = 需求档条文修订**——状态推进 / 物理落笔归主 agent，2026-09-11 归属修订）——新条目落位（不新开档）；**并做全体系对账**：与任何板块的既有条款冲突/重复/矛盾 → 修正（一致性问题自主 / 语义问题打回） | 需求文档体系更新 |
| 3 | **每条需求配验收口径（判定句）**——执行面（进 eng-designer 提示词）+ 判据面（判定句落需求档，供核对） | 需求完备 |
| 4 | **需求成文后写设计** `design/<板块>.md`——方案 + （≥2 候选时）选型对比 + 受影响文件清单（带行数）+ 验收标准（逐条回指需求）+ 测试用例表 + 边界（不做什么） | 设计文档 |
| 5 | **自检 + 交回**——逐条核需求覆盖、需求档与设计档一致；报告 + **停** | 交付报告 |

**失败路径（一律打回，不自己编）**：需求说不通（缺口/矛盾/不可实现）· 勘察发现需求与现实冲突 · 归属不明。

**纪律**：不发起评审（发起权在主 agent/用户）· 不写实现代码 · **写稿面唯一作者**（需求文档 + 设计文档）；澄清必须经主 agent（它是唯一对话面）。

**产出物（两件——不要混为一谈）**：

| 产出 | 内容 | 落点 |
|---|---|---|
| **A. 批次任务**（独立产物） | 本批覆盖的需求条目 + 明确不在本批的条目 + 受影响文件 + 验收标准 | `batches/<批>-<主题>.md` §2（**不写进设计档**——一次性内容混进长期档，下批会覆盖掉这批的任务） |
| **B. 设计档** | 下表 8 项 | `design/<板块>.md` |

**为何批次任务必须独立成件**：需求并入体系后会**化掉批次边界**——不写它，“本次开发要做什么”就找不着了。
**下游**：**它就是 eng-coder 的任务书**（用户 2026-09-10 裁定——不另派生副本；spawn 只传本节路径 + 凭证参数）；
**advisor 设计评审也要读它**（八维 #1 需求覆盖 / #6 范围 靠它判）。

**设计档必须包含（8 项——缺一项即不完备）**：

| # | 内容 | 判据来源 |
|---|---|---|
| 1 | **方案选型与理由**——候选 ≥2 时**必须有对比表**（候选 / 判据 / 取舍 / 否决理由）；单方案显式声明豁免 | 纪律层文档规范 |
| 2 | **架构 / 接口契约** | 同上 |
| 3 | **受影响文件清单**——源/测试文件**带当前行数 + 预计增量**；跨档位文件**带拆分计划**（文件档：>300 主动拆分评审，>500 必须拆；**函数档是第一判据**） | 评审八维 #8 + 结构硬指标 |
| 4 | **关键决策记录**（含被否决的备选） | 纪律层文档规范 |
| 5 | **验收标准**——**逐条回指批次任务里的需求条目**，且**可验证**（含正常/边界/错误） | 评审八维 #5 |
| 6 | **测试用例表**（正常 / 边界 / 错误 + 输入/预期输出） | 三层结构·测试层 |
| 7 | **边界**（不做什么） | 纪律层文档规范 |
| 8 | **UI/交互决策全落档**——未定部分标 `open`，**绝不静默发明** | 主流程 step 1 |

**合格判据**（设计算不算过）= **advisor 设计评审八维**——权威源 `src/prompts/advisor-design.md`
（需求覆盖 / 可行性 / 方法论合规 / 清晰度 / 验收标准 / 范围 / 文档归属 / 受影响文件规模标注）；
此处不复制（单一权威源）。**其中"需求覆盖有漏点" = 🔴 必须处理**。

**设计的边界（不做）**：不发明需求（缺口→打回）· 不过度设计（不加没人要的能力）· 不写实现代码 ·
不碎片化（不为既有章节新建档）· 不静默改需求语义。

**两个原开放项（均已定）**：

- **spawn 粒度** → **已定（2026-09-10 用户裁定）：一批次一次**。依据：其职责就是**体系整体一致性**——
  一次能看全体系；按板块拆会让跨板块矛盾掉进缝里（正是要防的），且多写者并改 `requirements/` 会写冲突。
  例外口子：某板块设计明显独立且巨大时可拆（默认不拆）。
- **验收口径——已定（2026-09-10 用户裁定）**：
  - **规则进 eng-designer 提示词**（执行面）——“每条需求必须带验收口径（判定句），没有不算完”；
    用户裁定：**提示词比文档靠谱**（文档对 agent 无执行力——今日实证：档里写了“记录不加工”照样犯错）。
  - **判定句落需求档**（判据）——供第一关/第二关/用户核对时当标尺（没有它就只能“凭感觉”）。
  - 二者成对：只写文档没人拦得住；只写提示词没法判合格。

### 1.9 eng-coder 工作流（按现状落档——2026-09-10 用户定：“现有流程执行较好，照现状写”）

> 来源：现行实现（设计档 §2.2 step 5-8 + `persona-eng-coder.md`）。本节的职责是**记录现状**，不是重新设计。

**收到什么**：**任务书 = 批次档 §2（路径，不是消息副本）**——designToken + designId（授权凭证，**经参数传、绝不进任务文本**）+ 涉及文档（设计文档路径）
+ 文件清单 + 验收标准（从设计逐字引用）。

**授权与边界**：

| 项 | 现状 |
|---|---|
| 机械门禁 | 无有效 token 时 write/edit/apply_patch/hashline_edit/insert_after/delete 全拒；spawn 时按 designId 定位槽比对 token，不符即 throw |
| 设计是权威规格 | 通读设计、遵循、不偏离；**撞设计缺口 → 停下报告**，不静默适应 |
| file 域声明 | = **预期触碰面**（调度排队 + 披露基准），**非授权边界**；超声明 ≠ 越权，**如实披露即可** |
| 永不编辑设计文档 | 真实文档漂移写报告，归父侧处理 |
| 子代理身份 | 任务已被父代理确认过——**不等用户、不请确认**，立即执行 |

**内部交付协议（子代理内闭环，权威 = 设计档 §2.2 step 6）**：

实现 → 自查透明表 → **explore 偏差审计**（审计任务书 = 父 spawn 任务书 ∪ 实际 `_touchedFiles` 机械并集；
查四类偏差：部分实现 / 静默简化 / 文档漂移 / 超清单改动未报告）→ dirty 自修（**修正轮 ≤5**）→ clean →
**advisor(code) 复评**（documents = 设计文档 + 交付文件清单）→ findings 自修 → **收敛交付**。

- 标准链 LLM 验证 = **3 次/链**（③审计 → ⑤advisor 首审 → 终审复评）；**修正轮默认不重跑审计/复评**。
- 审计节点 ≤6 次（第 7 次机械拒绝 = stalled 信号）；不收敛 → 报告 `stalled`，**绝不静默**。

**交付报告（最后一条消息 = 父侧看到的全部）**：改了什么/为什么 · 碰过的文件路径 · 怎么验证的（命令 + 结果）·
**交付透明表**（Done / Simplified / Not done，无 deferred 列）· 审计/评审轮次 + 终态（`clean` | `stalled`）。

**父侧接手（不改）**：交付 settle → 改动合并进父代理 → 父侧对照验收标准核、跑 **L2 全量恰一次** → verify →
链闭合后 `consume-design` 消费槽。**父侧不再自动 spawn 审计/评审**（防双重审计）。

### 1.11 交界面契约（每个环节传什么/怎么传/产出什么/怎么放）

**传递方式只有三类**（先立规矩，下表引用）：

| 类 | 用途 | 铁律 |
|---|---|---|
| **对话** | 人与主 agent——**唯一对话面** | 子代理无对话面；引擎室向用户澄清必经主 agent |
| **参数** | spawn 调用面（凭证/文件域/评审对象） | **token / designId 走参数，绝不进任务文本** |
| **文档路径** | 产物与输入都落盘，交界面只传路径 | 产物**不靠消息传**（消息只用于报告） |

| # | 交界面 | 传什么进去 | 怎么传 | 产出什么 | 怎么放 |
|---|---|---|---|---|---|
| B1 | 用户 → 主 agent | 需求表述（口述/吐槽/几点） | 对话 | 批次记录 §1 | `batches/<批>-<主题>.md`（新建） |
| B2 | 主 agent ↔ 需求体系 | 本批需求 + 现有 `requirements/` | 读（doc_search/read） | 冲突/含糊/缺边界清单 | 记入批次档 §1；冲突**回问用户** |
| B3 | 主 agent → eng-designer | 批次档 §1 + **本批 todo 项** + `requirements/` + 本批清单 + 归属板块 | spawn：task 文本（**传路径，不搬内容**）+ `files` 声明（**不声明 todo.md**） | — | — |
| B4 | eng-designer → 需求体系 | 本批需求 | 直接编辑（**写稿面**） | 需求条目（**带判定句**）+ 全体系对账修正 | `requirements/<板块>.md` |
| B5 | **主 agent** → 需求池 | todo 项状态推进（**2026-09-11 归属修订**） | 主 agent 直接编辑（**台账管理权归主 agent**；子代理一律不在 `files` 声明台账档） | 状态更新 | `docs/TODO.md` 需求池组 |
| B6 | eng-designer → 批次档 §2 | **批次任务** | **追加**（不重写 §1） | 本批覆盖条目 + 不在本批条目 + 受影响文件 + 验收标准 | `batches/<批>-<主题>.md` §2 |
| B7 | eng-designer → 设计 | 设计 | 直接编辑（写稿面） | 设计档（**产出要求 8 项**——口径与 FR19:78 一致） | `design/<板块>.md` |
| B8 | eng-designer → 主 agent | —（交回） | **最后一条消息**（报告） | 改了哪几处 / 设计在哪 / 自检结果 / 打回点 | 报告不落档；主 agent 核（**第一关**） |
| B9 | 主 agent → advisor | documents 清单（**设计档 + 需求档 + 批次档§2 批次任务**——**§3 段不在评审对象清单内**）+ object 声明（type/target/status/reason/exclude） | advisor **参数**（**发起权在用户**；设计评审带 `batchDoc` 路径——有批次档在飞时必传；工具侧口径 = **若传则须可读**，不传即不挂载、评审照常跑） | 发现表 + VERDICT + token/designId | **凭证入会话槽，不落文档** |
| B10 | 用户 → 主 agent | 显式 sign-off / 逐条拍板 | 对话 | 批准（或打回） | — |
| B11 | 主 agent → eng-coder | **批次档 §2 路径**（= 任务书本体——不另写副本）+ designId + designToken | spawn：task 文本 = **极简指针**（按 `<路径>` §2 执行）+ `files` 声明；凭证走**参数** | — | — |
| B12 | eng-coder → 交付 | 设计（权威规格）+ 任务书（批次档 §2）+ **批次档路径** | 读文件 | 代码改动 + **自写批次档 §5**（交付摘要/透明表/审计与代码评审/终态） | 改动留**工作区未提交**；§5 落档；消息只报指针 |
| B13 | 父侧验证 → 收口 | 验收标准 | 跑 L2 全量 + verify | 验收结论 | `batches/<批>-<主题>.md` §6 |
| B14 | 链闭合 → consume | designId | 参数 | 槽消费（同 designId 再 spawn 机械拒） | 会话态 |

**五条界面铁律**（从上表提取）：

1. **产物落盘，消息只报告**——交界面传路径不搬内容（防上下文膨胀 + 防双源）。
2. **凭证走参数**——token/designId 绝不进任务文本、绝不落文档。
3. **澄清必经主 agent**——任何子代理撞到需要用户决定的事，一律打回主 agent；无旁路。
4. **三方条目一致**——批次档 §2 本批条目 = 设计档验收标准回指的条目 = 需求档条目。
   advisor 八维的 #1 需求覆盖 / #6 范围**靠这份清单判**，所以 B9 的 documents 清单必须含批次档 §2。
5. **批次档随件传递、各写己段**——每个环节的子代理都收到批次档路径，**只写自己那一段**（append-only，
   段不重叠 → 无写冲突）；**子代理自写，不经父侧转述**（转述 = 二次加工 = 失真源）。
    **例外：§6 验收归父代理**——验收子代理成果是父代理的职责，不是转述（子代理不能自己验收自己）。

### 1.12 批次记录档（产品机制）

> 归属说明（2026-09-10 用户指出）：本机制属**产品需求**（要能装到任意项目），不归本仓地图——
> 地图 §3.8 只记本仓路径并指向本节。

**定位：任务流转的核心依据**（2026-09-10 用户观察）——**全链路唯一贯穿的档**：

| 环节 | 靠它做什么 |
|---|---|
| B1 讨论落档 | §1 讨论 |
| B3 → eng-designer | §1 是本批输入源 |
| B6 designer 追加 | §2 批次任务 |
| B9 → advisor | §2 是八维 #1 需求覆盖 / #6 范围的判据基准 |
| B11 → eng-coder | **§2 即任务书**（路径传递，无副本） |
| B13 父侧验收 | §2 验收标准为对照基准 → 结论入 §6 |
| 需求池核销 | §6 是证据 |

**为何只有它全链**：需求档管“现状是什么”（**无批次概念**——条目并入即化掉批次）· 设计档管“怎么做”
（跨批次演进，下批覆盖上批范围）· **任务书即 §2（不再是消息、不再落空）**。**只有批次档有“起 → 派 → 验”完整链条。**

**由此两条硬要求**：

1. **它不能缺、不能写歪**——它是外部记忆（agent 上下文会丢），缺件 = 全链路失准。
2. **“不是规格”的边界不得模糊**——它是**流程依据**，不是**现状依据**（现状只看 `requirements/` + `design/`）。

**依据缺失的处置**（#9——用户 2026-09-10 裁）：**查不到任务书就不执行、打回去**——
执行者（子代理）spawn 时若**任务书／依据不存在或不可用**（coder 找不到批次档 §2、
designer 找不到 §1 讨论），**拒收并打回**（同“撞需求缺口一律打回”一族——§1.8 失败路径）。
**归属 = 执行者纪律**（提示词层）。

**机械校验（父侧门禁——2026-09-10 用户裁）**：**一律规定必须传 `batchDoc` 参数**（批次档路径），
**designer spawn 与 coder spawn 都要求**；**没传即拒绝（打回）**。

- **判据只到“参数在 + 路径可读”**——**不校验内容/措辞**（不做正则匹配“已收口”之类——脆且把措辞写死）；
  **内容够不够由“执行者拒收”兜底**（上条）。
- 实现面（设计阶段）：spawn 参数 schema 加 `batchDoc`、两处角色门禁校验、纪律层任务书写法、测试（缺参数 / 路径不存在）。

**粒度**：**一批一份**——`batches/<批>-<主题>.md`（批 = 日期）。
**主题**（2026-09-10 用户裁——勿理解成“板块”）：**批次的概括词**——通常就是主板块名，但**允许跨板块**；
跨板块批用能概括的主题词，**仍是一份档**（档内分区：本批需求清单/覆盖条目按板块分组列）。
历史实践即如此（`CODE-HARDENING-BATCH` / `DOC-CLEANUP-BATCH` / `SYSTEM-SPLIT-BATCH` 均为跨板块主题批）。
**六段 append-only，一段一作者**
（**核心纪律**：一个段只有一个写手——两写手共段 = append-only 破功 + 归属含糊）：

**为什么不是“一板块一份滚动档”**（用户 2026-09-10 裁定）：滚动档要求 agent 反复做四件事——定位不漂、
结构不错位、记录不加工、长档不腐——**它们恰好是 agent 最弱的地方，且已被实证**（滚动档全部腐化：
`TODO.md` 条目过期、`FEATURES.md` 漂移、旧地图积累出自相矛盾；而批次档从未腐化）。
**形态迁就 agent**：agent 只做它做得住的——**新建一份、写完冻结、永不回改旧档**。

**生命周期**：§1 讨论起草于批次开始 → 需求谈清由 eng-designer 抽入 `requirements/` → §2 批次任务 → §3 设计评审
→ §4 用户批准 → §5 实施记录 → §6 验证与收口 → **整档冻结**（append-only 指不重写已有段；冻结指**整批做完**不再改）。

**模板（固定骨架——agent 只填不定位）**：

```markdown
# <板块> · 批次记录（<批>）

> 六段 append-only，**一段一作者**：§1 讨论（主 agent）· §2 批次任务（eng-designer）·
> §3 设计评审（评审子代理）· §4 用户批准（主 agent）· §5 实施记录（eng-coder）· §6 验证与收口（父代理）。
> 不是规格：需求在 requirements/ 成文；整批做完整档冻结。

## §1 讨论（主 agent）
### 批次范围
### 谈成什么（逐条）
### 对账结果（与现有需求文档的冲突/含糊 + 用户澄清）
### 本批需求清单（回读给用户 → 用户确认）
### todo 项（提交 designer 时必须带上）
### 过程留痕（可选：讨论约定/踩过的坑）
### 状态：未收口 | 已收口 <日期> | 已撤回 <日期> | 已废弃 <日期>

## §2 批次任务（eng-designer 自写）
### 本批覆盖的需求条目
### 明确不在本批的条目
### 受影响文件（带当前行数 + 预计增量）
### 验收标准（逐条回指需求）
### 任务书就绪（本节即任务书——spawn 传路径，不另写副本）

## §3 设计评审（评审子代理自写）
### 轮次与发现（发现摘要 / 🔴 处置——**凭证值不落档**）

## §4 用户批准（主 agent 记）
### 批准（日期 + 批准范围）

## §5 实施记录（eng-coder 自写）
### 交付摘要（改了什么 / 碰过的文件 / 如何验证）
### 交付透明表（Done / Simplified / Not done）
### 审计与代码评审（轮次 / 终态 clean|stalled）
### fix round（如有：发现 → 修复）

## §6 验证与收口（父代理自写）
### 父侧验证（L2 全量结果 + verify）
### 逐条验收结论（通过 / 未过 / 未做 + 理由）——**验收勾销住本节，不进设计档（用户 2026-09-10 裁定）**
### 需求池核销
### 核销同步清单（逐项打勾——逐项核：角色表 / 状态行 / 计数 / 指针 / 变更记录 / 待办勾销 / 台账可见面（收口行））
### 遗留项
```

**段与环节的对应**（保证不落阶）：§1 = B1-B2（讨论）· §2 = B3-B7（designer 产出）· **§3 = B9（评审）** ·
**§4 = B10（批准）** · **§5 = B11-B12（实施交付）** · **§6 = B13-B14（验证/核销/收口）**。
**凭证铁律**：§3 只记“评审通过（轮次 N）”，**token/designId 值绝不落档**（凭证是运行时态）。

**各段作者 + 随件传递**（2026-09-10 用户定）——**批次档随任务传给环节上的每个子代理，各写自己那一段**：

> 编号约定：本节及全档提到 **§N 一律指批次档的段**（本档自身的节写作“§1.x”或“§2/§3”带章节标题）——
> 批次档六段与需求档章节不同层，勿混。

| 段 | 作者（一段一作者） | 写入手段（2026-09-11 第 22 批同步） | 为何是他 |
|---|---|---|---|
| §1 讨论 | 主 agent | 普通文档写（工具链无 `batch_segment`——不变量 3） | 它是唯一对话面 |
| §2 批次任务 | **eng-designer** | `batch_segment`（段 = §2——**无路径参数**，spawn 绑定批次档） | 任务出自它的设计——一手 |
| §3 设计评审 | **评审子代理（advisor）** | `batch_segment`（**仅设计评审、工具已挂载时**——轮次标题由工具生成；代码评审只读、无此工具） | 它自己的发现——一手（同 §2/§5 之理）；仍不碰代码/设计档 |
| §4 用户批准 | 主 agent 记 | 普通文档写（同 §1） | 批准发生在会话面——只有主 agent 看得到 |
| §5 实施记录 | **eng-coder** | `batch_segment`（段 = §5——**无路径参数**，spawn 绑定批次档） | 它自己的交付/透明表/轮次——**父侧转述 = 二次加工（失真源）** |
| §6 验证与收口 | **父代理** | 普通文档写（父代理不走本工具——不变量 3） | **它是验收者**——对子代理成果逐条验收是它的职责，不是转述 |

**段的划分标准**（2026-09-10 用户纠正——主 agent 曾提议给 explore 单设一段，被驳）：

**段 = 链上的角色，不是“环节里的每个动作”**。入场者 = 有独立写手身份的链上角色
（主 agent / eng-designer / 评审子代理 / eng-coder / 父代理）。**进程内工具不设段**——
只读子代理（explore 偏差审计）与子代理内部调用的 advisor 评审都是 **eng-coder 的内部工具**，
不是链上角色：它们的结论由调用者（eng-coder）写进 §5。

**可信度靠机制而非段位**（现行设计已有旧）：①审计任务书 = 父 spawn 任务书 ∪ 实际 `_touchedFiles` **机械并集**（非自述）
②内层 advisor = **独立上下文** ③父侧保留可选复核（stalled/存疑）。

**实现差量（登记——已落地；2026-09-11 第 22 批注）**：advisor 自写 §3 的写权限 = **仅设计评审挂载的 `batch_segment`**
（写权限仅自己那段，不碰代码/设计档；代码评审保持纯只读）——原「待实现」条件已消解（设计 `../design/ENGINEERING-MODE.md` §2.20）。

**机制要点**：①**每个子代理都收到批次档路径**（作为任务输入）②子代理**只写自己那一段**
（append-only，**段不重叠 → 无写冲突**）③子代理最后一条消息只报指针（“§N 已更新”），内容住档里。

**为何要模板**（用户 2026-09-10 提出）：固定骨架把 agent 的“定位/结构/合并”负担换成“填空”——
它只做自己做得住的事（照槽写、不重写已有段）。

**执行面**：本骨架要进**主 agent 与 eng-designer 的提示词**——理由同“规则进提示词、内容落文档”
（§1.8：文档对 agent 无执行力，提示词才有）。

### 1.13 需求池（产品机制）

> 归属（同 §1.12）：产品机制不归本仓地图——地图 §3.9 只记本仓路径并指向本节。

**职能**：跟踪**每一条需求的落地情况**——一行一条，条目级台账。
没有它，要知道“哪条需求落地了没有”就只能遍历全部文档。

**条目形态（一行一条——2026-09-10 用户定：TODO 里直接挂任务书）**：

```
- [ ] <需求句> → 需求 `<板块档>` §X · 任务书 `batches/<批>-<主题>.md` §2 · status=<状态>
```

**铁律：不展开任务细节**——TODO 是**指针台账**，不是第二份任务书。细节住在需求档与批次档 §2；
**在 TODO 里重述 = 漂移源**（两处不一致时信谁），也把台账变成长条垃圾场。

**为何挂任务书**：一条需求“做到哪了”→ 点开指针直接看任务书/验收结论，无需到处找。

**状态机**：

| 状态 | 含义 | 任务书指针 |
|---|---|---|
| 待讨论 | 已登记，还没谈清 | `—` |
| 待设计 | 需求收口，等设计 | 可挂批次档（讨论段） |
| 在途 | 设计已批准，实现中 | **必填**（批次档 §2） |
| 待核销 | 已实现，等验收/签入 | **必填** |
| 已核销 | 完成——勾销（锚行改 `- [x]`）后**移入 `docs/TODO-archive.md`**（活文件只留未决——2026-09-11 追加裁定） | 保留指针（已冻结）——随条目入归档档 |
| **已废弃** | **终止**（需求撤回 / 批次废弃 / 中途叫停——§1.14 #5/#6）——**同移入归档档** | 保留指针（含批次档状态标注）——随条目入归档档 |

**两池不混**（用户 2026-09-10）：需求池收**用户需求点**；**技术待办**（设计遗留/评审发现/债）
另组分列——两者同一格式、同一铁律（指针化），但**不混放**。**重分组口径**（2026-09-11 用户批）：
全档按两池**重分组**——需求点一律入需求池组，技术项一律入技术组（组内可按板块分子组）；
分组不是排版偏好而是**归属判定**（错组 = 后续状态推进认错对象）。
**组计数**（每组「N 条」）与组内实条目数**必须同改**（D3）——计数口径 = **未决数**（活文件只留未决；归档条目不计入——2026-09-11 追加裁定）。

**状态取值面**（2026-09-11 第 8 批补 + 范围扩展修订）：台账 `status=` **只能取上表六态**——机判面 = 设计档
`ENGINEERING-MODE.md` §2.24.6 L3④（技术组无 `status` 场者豁免；机外取值**不再入基线**——违规照报（阈值 = 0；F14 同条））。
**活文件内取值实为未决四态**（待讨论 / 待设计 / 在途 / 待核销）；**已核销 / 已废弃 = 归档态**——勾销（锚行改 `- [x]`）后
**整体移入同仓 `docs/TODO-archive.md`**（2026-09-11 追加裁定——替代原「就地 `[x]` 保留、计入组计数」；与 `checklist-done.md` 同口径）。

**技术待办的指针形态**（2026-09-11 用户批——FR7 与 FR18 的口径衔接；FR7 只规定"技术待办不进设计文档"，
未规定它在台账里长什么样，此处补定）：

- **(b) = 指针（可指则指）+ 最小证据行**（`file:line` + 症状短语）。
  - **可指则指**：技术项凡有归属档/设计节（如"评审注入路径硬编码"→ `ADVISOR-CONVERGENCE.md` §5.1），
    **必须挂指针**；无归属档时指针写 `—`。
  - **证据行是不可省的那一半**：技术项没有"需求档 §X + 任务书 §2"这两根天然锚，`file:line` + 症状
    是它唯一可核验的锚——**没有证据行 = 无从验证这是真问题还是印象**。
  - **正文细节仍归设计档 / 批次档**：台账里只留"哪条、在哪、什么症状"，方案与推演不进台账（铁律同需求池）。
- 需求池与技术组**同一铁律**（不展开任务细节），但**锚的形态不同**（前者挂需求档节 + 任务书，后者挂
  归属档节 + 证据行）——这是"两池不混"在**格式层**的必然结果，不是两套规则。

**触发字段与老化报告**（2026-09-11 追加裁定——技术待办专属）：

- **触发字段**：每条技术待办**带一种触发**（随条目尾，与 `status=` 并列）：`触发=归批（<批名/批号>）` /
  `触发=条件（<条件句>）` / `触发=认账不排期`——三者为**合法选项**（`认账不排期` 区别于遗忘）。
- **无任何触发的条目 → 审计批默认进「待处置」**；审计模式输出「**待处置清单**」（全部无触发技术条目；
  **行龄超 N 天**者标「老化」——N 默认 30 天、行龄 = 条目行最近变更时间）。
- **报告不自动删 / 不改文件**——处置要人判（主 agent 与用户）；机检契约 = 设计档 `ENGINEERING-MODE.md` §2.24.9。

**职责分工（用户 2026-09-10 裁定 + 2026-09-11 归属修订）**：

- **记录 + 状态推进 + 物理落笔（`TODO.md` / `TODO-archive.md` 编辑）= 主 agent**（台账管理权归主 agent；
  2026-09-11 修订（原口径作废——追加裁定见批次档 `../batches/2026-09-11-POOL-LEDGER.md` §1）。
- **提交给 designer 时必须带上本批 todo 项**（todo 作为输入随任务传递——不变）；
  **eng-designer 的台账侧职责 = 需求档条文修订 + 收拢应用清单**（判定交付——不落笔台账本体）。
- 机械面无冲突：黑名单只管 **`files` 参数**（调度器的冲突检测面）；**台账档不入任何子代理 `files` 声明**
  （父侧维护档——提示词动作，与 `files` 无关）。
  file 域 = **预期触碰面**（调度 + 披露基准），**非授权边界**。

**可见面**（提醒 / 状态行 / 明细行）= **§1.18**（FR24）——本节的口径（未决数 / 行龄 / 阈值）由彼处消费，本节不重述。

### 1.15 文档更新纪律（FR21——2026-09-10 用户裁定；设计见 `../design/ENGINEERING-MODE.md` §2.19）

**动机（用户原话）**：“你根本没想过更新文档的复杂度，随便写要不了几下就把文档体系搞乱了了。”
写稿权唯一（§1.5 #10）只是**必要条件**；两轮设计评审反复栽的是**更新纪律缺位**：

| # | 纪律 | 一句话 |
|---|---|---|
| D1 | **写权矩阵** | 文档类 → 唯一作者（§1.5 #10）：批次档=主 agent · 需求/设计档=eng-designer · 提示词=主 agent 内容权 + eng-coder 落笔 |
| D2 | **单一权威源** | 一条机制**只在一处详述**，其余处**只引用不重述**（模板同理——批次档模板只在 §1.12） |
| D3 | **计数·枚举纪律** | 声明“N 项/N 处/N 条”必须与列表**同时改**；可机判（V2） |
| D4 | **指针纪律** | 指针形态 = `文档:节`；行号只作 **as-of** 参考；**禁**“见上/见该节”式相对指针 |
| D5 | **冻结窗口** | **评审在途不改被审文档**（改了 = 评审对象已变 → stale，token 不签发） |
| D6 | **回读核对** | 任何写入后**回读核实**再报完成（本会话三次事故已入批次档踩坑记录——本批升为纪律） |
| D7 | **变更留痕 + 核销同步** | 每批核销跑**核销同步清单**（批次档 §6 模板新槽位）：角色表 / 状态行 / 计数 / 指针 / 变更记录 / 待办勾销 / 台账可见面（收口行）——跑 `scripts/check-ledger.mjs --summary`，输出即明细行（实现后同步（2026-09-12）：行锚逐字化——原「（收口行——跑 …」变体不含逐字子串 `台账可见面（收口行）`，AC86 的 §1.15 面锚不达；本次改为逐字形态、语义零变） |

**机械校验最小集**（可机判的才上机械——语义一致性仍归评审）：

| 校验 | 内容 |
|---|---|
| V1 **段引用可解析** | `docs/**/*.md` 内 `§N` / `文档:节` 引用，目标节号在目标文档或本档内存在 |

## 2. 可移植性需求（2026-09-10 用户裁定——工程模式是产品功能）

**定位前提**：ThinCoder 是**面向任意项目的产品**（npm 发布 / marketplace 上架 / 全球 i18n）——
工程模式是其**产品功能**，必须在**任何项目**上可用，不得假定用户项目形如 ThinCoder 自研仓。

| # | 需求 | 约束 |
|---|---|---|
| FR10 | **不得假定项目约定** | 产品不得假定用户项目的文档布局/命名/语言/构建/测试方式；凡需知道项目约定处，必须由**项目自述**（AGENTS.md 等）或**配置**提供；**缺失时降级可见**（写进报告），不得静默失效 |
| FR11 | **开启前提不得依赖本产品自退役的物** | 开工程模式不得把某个硬编码文件名当门禁（现况：`src/tui/cmd-eng.mjs:31` 要求项目根 `METHODOLOGY.md`，而其模板文件已不存在——选项必炸；且该概念在本仓已退役）——前提应为**项目自述的可用性**或无前提 |
| FR12 | **代码/文档判据不得写死目录名** | “什么算产品代码”不得以 `^src/` 之类**字符串锚定**判定（现况：嵌套布局 `packages/foo/src/x.md` 被当文档，**静默绕过设计门禁**；非 `src/` 布局项目则所有文件都当产品代码）——判据须**单一权威 + 项目自述/配置可诉**，且任何布局不漏判 |
| FR13 | **纪律层不得把本产品形状强加给用户项目** | 纪律层提示词不得教 agent 在用户项目里建 ThinCoder 形状的目录/维护本产品的流程文件（`docs/TODO.md` 需求池、CHANGELOG 维护边界）；不得要求跑**本仓自带**的脚本（现况：`src/prompts/discipline-engineering.md:182` 教跑 `scripts/check-doc-width.mjs`——用户项目必有此脚本才不炸） |
| FR14 | **推进档位入需求** | auto（每步自动推进）/ manual（每步等用户放行，叫停即切）是**用户可感知的交互契约**，须在需求层有据（现况只活在提示词里） |
| FR15 | **非 git 项目行为有定义** | 工程模式在非 git 项目（无 `.git`）下的行为需明确定义——现况：评审范围采集/代码索引/检查点均依赖 git，缺失时**部分静默为空** |

> 上述六条均为**需求**（待设计）——具体实现方式（配置项 / 项目自述 / 探测策略）属设计层，本档不预设。
> 验证方向：用一个**非 Node、非 `src/` 布局、无 `docs/` 树、非 git** 的项目试跑工程模式全流程——
> 不得出现静默失效，不得被不存在的文件卡住。

### 1.16 批次档段写入工具（FR22——2026-09-10 用户裁定；需求澄清已收口）

#### 总体目标

六段机制要求「**一段一作者**」，但子代理**没有写批次档的手段**——现实是**父侧代写**（第 1、2 批实际如此），而代写 = 二次加工 = 失真源（§1.11 铁律「产物落盘消息只报告」的同族问题）。本项给子代理一条**受控写入通道**：各写各段、写到准确位置、不留后门。

#### 功能性需求

- **F1 单一工具 + 无路径参数**：工具不接收目标路径；**目标批次档路径由 spawn 时注入**（照 §1.12/第 1 批 `batchDoc` 门样式：参数在 + 路径可读，否则拒）——**语法上就写不到别处**。
  **评审侧口径（实施同步——2026-09-11 第 22 批）**：设计评审的 `batchDoc` = **若传则须可读**（非必传）——不传即工具不挂载、评审照常跑（不改无批次档场景的评审行为）；主 agent 侧纪律 = 有批次档在飞时必传（§1.11 B9）。
- **F2 角色 × 段白名单**：`eng-designer → §2` · `设计评审子代理 → §3` · `eng-coder → §5`；**跨段/越段写入被拒**（"一段一作者"从纪律升为**机械事实**）。父代理**不走本工具**（它走普通文档写；本工具只管子代理各写己段——用户 2026-09-10 裁定）。
- **F3 append-only**：只追加，不覆写、不删除已有段；多轮评审 → 追加 `### 轮次 N（评审子代理）` 小节。
- **F4 §3 内容 = 评审结论全文**（2026-09-10 用户定：**「完整发现表」必须落档**）：该轮的 **🔴/🟡/🔵 发现表（逐字）+ VERDICT 行 + 计数**；多轮各自成节。理由：评审报告只活在 session，**批次档是唯一持久档案**——无表的 §3 是空壳。
  **来源戳口径（N4 实施前澄清）**：小节标题 `### 轮次 N（评审子代理）` **由工具生成**——N 只数**工具写入过的**轮次行（固定骨架行 `### 轮次与发现（…）` **不计**）。
- **F5 逐字，不经转述**：表由评审者自己的人话原样写入（父侧不得代为润色/缩减）。
- **F6 凭证剥除（工具做，非纪律）**：写入前过滤 token / designId 形态行（§2.7：凭证绝不落档）——**模型可能忘，机械不能忘**。
  **形态口径**（实施前澄清）：本平台真实形态 = `[DESIGN-TOKEN:uuid:epoch]` 与 `designId: uuid`（**冒号态**）——
  工具用**自有正则**，**不得复用 §2.7 的巡检正则**（它要求参数名后接空白，匹配不到这两种形态）。
- **F7 失败语义**：写入失败（路径不可读/越段/工具被拒）→ **明示报告「§× 未写入」**；回退父侧代写**必须打标**（不得静默退回、不得假装写过）。

#### 非功能性需求

- **N1 安全面不扩**：**代码评审保持纯只读**（零 git、只读工具集不变）——写权只对**设计评审**（评审文档面）开；不给 advisor 通用 `write`。
- **N2 与 D5 不冲突**：§3 写在**批次档**——**§3 段不在评审对象清单内**（B9 只含批次档 **§2**）——追加 §3 **不改变被审内容**，故冻结窗口（§1.15 D5）不受影响，设计需写明这一点以免下轮评审当矛盾。
- **N3 可机械校验（V3）**：**「某批 §3 非空且含工具写入的轮次行」**（否则“评审跑完但没写档”无人察觉）——与 V1/V2 同族，快层可跑。
  触发条件 **只取机器判据「§4 或 §6 非空」**——**不引用 §1 讨论状态词「已收口」**（同名不同义：在飞批次的 §1 就是“已收口”而 §4/§6 为空）。
- **N4 不可伪造来源**：工具写入的段落**由工具加盖来源戳**（`### 轮次 N（评审子代理）`，N 由工具计）——代写与自写一眼可辨。
- **N5 零回归**：既有 spawn / 评审 / 门禁行为不变；本项是**新增通道**，不是在既有路径上扩权。

#### 归属与待设计项（设计阶段定）

- 归属：`docs/requirements/ENGINEERING-MODE.md`（本档）· 设计落 `docs/design/ENGINEERING-MODE.md` §2.2x。
- **待设计（选型对比）**：①批次档路径怎么到评审者手里——**advisor 工具加 `batchDoc` 参数 + 门禁**（倾向） vs 活动批次自动推导；②是否加 V3 机械校验（倾向要）；③工具名与参数形态；④与 §1.12 段作者表的指针关系（段表是否加「写入手段」列）。

### 1.18 台账提醒与可见面（FR24——2026-09-12 用户裁定）

> 来源：用户 2026-09-12 发现「从未见过任何提醒」（实查：两仓 40 条技术待办 · 触发字段 0/40 ·
> 老化报告仅 `--audit` 慢层 · 零推送面）——逐条裁定「开」。批次档 `../batches/2026-09-12-LEDGER-SURFACE.md` §1。
> 归属：机制 = 本节；设计 + 测试 = `../design/ENGINEERING-MODE.md` §2.30（行文本逐字契约在彼处）。

**总体目标**：把台账（§1.13）的未决状态送到用户眼前——**有可动作项才出声，其余时间零噪音**；
状态行给常驻的两个数，会话流给三处可回看的文本行；两端（CLI / VSC）**语义同源、各自实现**。

#### 功能性需求

- **F1 两池分显（不合计）**：每个项目的两个数（需求池未决数 / 技术待办未决数）分列显示——**不混一个数、不合计**。
- **F2 状态行极简标记**：`台账 <需求池数>·<技术待办数>`（如 `台账 4·32`）——**只显当前项目**；
  **老化 > 0 转警示色**；不铺开、不多行、不可点击（点击展开面板在否决列）。
- **F3 三处文本行（明细面）**：各自落入所在会话流（可回看）——
  ① **启动行**：会话开始时出现，**有可动作项才出**（**判据 = 有可动作项才输出**——`recentCrashHint` 的同形态实现见 `src/crash-reports.mjs:132`）；
  ② **批次收口行**：核销同步清单（§1.12 §6 模板）内的机械步骤——**单源命令的输出即收口行**；
  ③ **变化行**：**老化首次越线 / 需求池达阈值**——事件驱动、一次性去重（F5）。
- **F4 多项目判据**：**当前项目 = 上下文目录向上（含自身）最近的含台账目录**（CLI = cwd；VSC = 当前项目目录）；
  **项目集 = 当前项目 + 其同级兄弟仓中含台账者**（台账 = `docs/TODO.md`）；
  **明细行集 = 当前项目 ∪ 可动作项目**（每项目一行）；**无台账的根不显**。
- **F5 变化行一次性去重**：同一事件（同一条条目老化 / 同一次阈值达成）**只报一次**；
  去重载体**跨会话、跨端**（`~/.thincoder/ledger-notify.json`——键 = 台账绝对路径）；
  **只在行真正落入会话流后才记账**（未送达不计——否则用户永远看不到）。
- **F6 收口行 = 机械步骤**：核销同步清单新增「台账可见面（收口行）」项——跑单源命令（`scripts/check-ledger.mjs --summary`），
  输出即明细行；**保留在会话流**（不落档、不改台账、退出码 0）。
- **F7 数字单源**：台账解析 / 计数 / 老化 / 阈值**一处实现**（`thincoder-core/ledger.mjs`；VSC 端自有等价实现，语义同源）——
  机检器（`scripts/check-ledger.mjs`）与两端显示面**共用该口径**。
- **F8 VSC 增量**：状态栏 item（文本 = F2 标记；**原生 tooltip = 同款明细行**；老化>0 = 警示底色）+ chat 流文本行（同 F3）——**纯增量、非新机制**。

#### 口径（判定句的基础——详情见设计 §2.30.3）

- **计数**：`##` 组标题含「需求池」→ 池组；含「技术」→ 技术组；计数 = 组内 `- [ ]` 未决条目数（与 §1.13 组计数同口径）。
- **老化**：技术组中**无 `触发=`** 的条目，**行龄 > 30 天**（git blame 行级时间；取不到 = 不计——零假阳）。
- **阈值（可开批）**：`池 ≥ 3` 或 `任一板块 ≥ 2`——板块 = 池条目指针所指需求档的文档名（攒批口径，与提示词锚#2 同源）。
- **可动作项**：`老化数 > 0` 或 `阈值达成`（即 F3① 的出现条件）。

#### 非功能性需求

- **N1 零噪音与降级**：无可动作项 → 零输出；台账不可读 / 非 git / 去重档损坏 → 降级不崩（静默跳过该维度）；
  headless（`thincoder chat` / ACP）零新增输出；台账档**只读**（本机制唯一写面 = 去重档）。
- **N2 成本有界**：刷新 = 周期（常量 120s）+ 事件触发（VSC 项目切换）；无候选条目时不跑 git 子进程；单次刷新 ≤ 500ms（两仓夹具）。

#### 判定句（逐条回指设计验收）

F1–F8 与 N1/N2 的判定句见设计 `../design/ENGINEERING-MODE.md` §3.1 **AC80–AC90**；用例见 §3.2 **T97–T110**（T105 已退场——整删，删除记录 = `TESTING.md` §11.3）。

### 1.19 文档体系各仓自持（FR25——2026-09-12 用户裁定；设计见 `../design/LEDGER-SELF-CONTAINED.md`）

> **两仓合并批 3（S6）收窄注**：本节体例收窄为仓内口径——「各仓自持」隔离条款（F3 · F11 等）失去对象、随之退役；射程与引用纪律（F1 / F13 / 两轴）收窄为产品侧形态；逐条注记见下（依据 = `../design/TWO-REPO-MERGE.md` §2.4 R12；验收 = 其 §3 T-M24）。

**动机（事故溯源）**：2026-09-12 凌晨的泄露事故 = **跨仓登记**——他方把外部产品线的债（含一条安全项）登记进本仓台账，随主线合入并推到两个公开远端。
内容层已清（历史移除 + 远端改写 + 本地清对象），**机制上没有闸**：同形态条目今天可以照样再登记进来。

**同病的第二种形态**：本产品的两个仓（CLI ↔ VSC）之间互相承载对方的事项——CLI 仓承载本该住 VSC 仓的台账条目、批次档与需求；VSC 仓活台账 2/2 条指针指向 CLI 仓。
病因同一：**「能记一处就不写两处」**。

#### 总体目标

一个开发者在一个工作区里同时维护多个产品时，任一产品的文档只承载自己的事项——对端产品的事项不写进来；缺的文档层就地补齐，不因「对端已有」而省略。

#### 功能性需求

- **F1 台账射程**：台账（需求池 / 技术待办）只收本仓条目——禁登记本项目之外的事项（他项目 / 他产品线）；指针面收窄为**仓内可解析**（原对端指针禁令已随两仓合并退役——批 3）。
- **F2 批次档同规**：批次档只登记本批范围（含本批的受影响文件与验收）。
- **F3 文档体系自持**：需求档 / 设计档 / 批次档 / 台账各自成套；**非复制**（语义同源、各端原文自持——在案多实现面纪律）——**已随两仓合并退役（批 3：仓隔离语义失去对象——`../design/TWO-REPO-MERGE.md` §2.4 R12）。**
- **F4 缺失层必须补齐**：缺失的文档层就地补建——**不得以「对端已有」「避免重复」为由省略**；**逐层成套**（缺层逐层补齐 + 需求层逐档三值——不得只建单层壳）。
- **F5 约束须落提示词层**：F1–F4 的行为面必须在提示词层落地（不只文档层）——文档层是规格（人读 + 评审对象），提示词是代理运行期实际读到的纪律。
- **F6 机检闸**：台账条目的证据 / 指针路径须在**本仓内可解析**；违规一律 fail-closed（**「存量 / 入基线」已废**——阈值 = 0；F14 同条）；L4② 判序（含外仓前缀排除——不回退 basename）见设计 `../design/LEDGER-SELF-CONTAINED.md` §7.1。
- **F7 核验职责**：同一机制跨多个实现面产出**一式多份设计**时，主 agent 有义务核验各份逻辑是否一致（核验四维 = 裁定同源 / 判据同一 / 边界同形 / 差异显式登记）；该职责须落提示词层。
- **F8 提示词通用化**：提示词中的多实现面条文不得绑死本产品两端（不得以本产品术语作示例、不得夹维护者注）；A1 勘察 checklist ④ 同步通用化。
- **F9 存量无豁免（宽口径 + 溯及既往——2026-09-12 05:08 用户改判）**：凡**触及对端**的存量批档一律处置——① 实施面全在对端 → 迁移；② 两端均有实施面 → 各仓持其份（逐档拆分清单）；**不得以「历史已收口 / 审计链 / 重复 / 量大 / 在飞」为由豁免任何一档**（在飞档处置照给，执行时点随其收口）。
- **F10 文档体系逐层成套（2026-09-12 05:17 用户标准）**：各产品文档体系**逐层对位**（仓根档 / 文档地图 / 台账 / 需求 / 设计 / 提示词双源 / 批次档 / 归档 / 指南），每层对位形态逐行登记；需求层**逐档三值齐备**（① 建本仓需求档 · ② 已有对位（允许异名——注明本仓实际档名；**异层者一律建档——不得以 design 层充当**）· ③ 本端无此面（写理由））；**不得只建单层壳**。
- **F11 需求层必须在本仓有档（2026-09-12 10:57 用户裁定「全部啊！」）**：**需求层必须在本仓有档**——「对端有」「design 层有」**不构成**需求层缺失的理由；**② 已有对位不得以 design 层充当**（需求住 `docs/requirements/`、设计住 `docs/design/`——两层各持其档）。范围边界：不动设计档的层位判定（设计档不迁层）。
  **已随两仓合并退役（批 3——单仓内失去对象；`../design/TWO-REPO-MERGE.md` §2.4 R12）。**
- **F12 结构档位硬限无豁免（测试档同规——2026-09-12 10:58 用户裁定）**：>500 行硬限**无豁免通道**——「存量 / 不增内容 / 有先例 / 历史已收口」均不构成豁免理由；超限档**本批拆**（拆分方案随同批设计落档；**拆分判据 = 设计档 D18 四条**：① 组内同面 · ② 迁出组夹具 ⊆ 新档自持集 · ③ 切点零交叉 · ④ 两档 ≤500 且余量充足）。范围边界：不改测试语义——迁出例逐字搬移（断言零改 / 零增 / 零删），**用例数守恒**（余档 + 新档 = 原档实测数）；新档自持夹具（零跨档 import）。
- **F13 对端引用形态零残留（2026-09-12 10:58 / 11:06 用户裁定）**：设计 / 需求 / 批次档正文引用对端产品文档一律**规范形态**（`名称（仓别）§N`——去 `.md` 后缀、去路径前缀）；**历史登记表 / 变更记录同受约束**（语义保留、形态规范化）；**存量不是合法态**——残留 = 破例先例源，禁以「存量 / 历史快照」为由留驻。
  范围边界：**实施面文件路径**（受影响文件表 / `files` 声明 / grep 面 / 证据行——含 `src/prompts/*.md` 类提示词档）按「**路径去仓前缀 + `（仓别）`**」标注，不按节号形态
  （路径无节号可指——**判据 = 设计档 D19 机判式**：坐标 = `路径（仓别）`——去仓前缀、保路径与 `.md`，仅限实施面语境）；迁移档名引用（批档互引）同按规范形态（无 `.md` 后缀、无 `batches/` 前缀）。

- **F14 先例不构成例外依据（2026-09-12 11:40 用户裁定）**：任何「以前也这样 / 已落形态 / 他批先例 / 存量在案」**都不构成偏离规则的依据**——**例外的唯一依据是判据句（可机判）**；找不到判据句 → **按规则办，或停下上报**；不得以先例为由放行。
  **同条（看得见的每一行都是先例）**：设计档 / 需求档 / 批次档 / 台账 / 变更记录中的**残留即示范**——合规形态必须显式（**机检命中即红**）；历史语义可保留、**形态必须规范**；**「存量豁免 / 入基线」不得再设（阈值 = 0）**。
  **同条（例外须带消解期）**：任何登记在案的例外必须写明**消解路径与到期条件**——否则 = 永久先例 = 变相废规。
  范围边界：判据射程 = **形态面**（A 类叙述性提及收紧为**封闭枚举**——枚举外即红）；散文语义本身不属机检射程（留评审——与 F1 边界同源）；不新设「枚举外白名单 / 逐项豁免」通道。

### 1.20 文档↔实装对账（FR26——2026-09-12 用户裁定；设计见 `../design/ENGINEERING-MODE.md` §2.32）

**动机（用户原话）**：「可以啊，我希望**完整的全面清理**解决。」背景：同批当晚串行排查中「撞见即清」**250+ 处**
（散文锚受益面 131 · 段删件断言级 52 · 旧指认/旧称/旧口径/已废机制 ≈70），但**没有全量清单**——清的是撞见的，不是存在的。

**病根四条**（批次档 §1 已结构化）：① 批次「受影响文件表」不列描述被改面的设计档 → 无归属 ② 一段一作者下 coder 不碰设计/需求档 → 描述句无人认领 ③ 子代理自查只核「我的改动是否自洽」→ 抓不到「全档与现态不符」④ 机检 V1–V4 管**形态**（引用形态 / 计数 / §3 轮次 / 跨仓形态）→ **不管「句子说的还是不是真的」**。

#### 总体目标

一个开发者在工程模式下长期演进一个仓时，**现行档（`docs/design` + `docs/requirements`）里的事实锚**（用例号 / 文件路径 / 符号）
能**机械地对上实装**——悬空的锚当场报红（阈值 0）；机器判不了的语义句**有归属、有周期**（巡检面）。

#### 功能性需求

**层 1 · 机检器（V5「文档锚一致性」）**

- **F1 三锚机检**：现行档内抽取锚三类（用例号 / 文件路径 / 符号）判其存在性——存在性域与逐条判据（正则、存在性域、排除式）落设计 §2.32.3；
  落点 = 独立档 `scripts/doc-anchors.mjs`（**不入产品提示词**——本仓自用工具，同 `scripts/check-doc-width.mjs` 口径）。
- **F2 零假阳（硬）**：已识别的假阳类（设计档内部编号 / 库·浏览器 API / 提交哈希 / 命令字面与 fenced 块 / 夹具占位路径 / 运行期面 / 组合简写）**逐条显式排除或转另类判定**——
  **判据不精确 = 红一片 = 无人看 = 等于没有**（与 V1–V4 被要求的「零假阳才能常驻」同一标准）。
- **F3 注记即通过**：锚带**退场/已废注记**（封闭标记集 + 来源指针——逐字枚举见设计 §2.32.3）⇒ **通过**；本轮已落处置形态（「已退场（段删——<批名>；删除记录 = <指针>）」「已废/收窄——源 = <file:line>」）被识别。
- **F4 报告态 → 阻断态（阈值 0）**：首落**报告态**（不阻断）——该层同时交付**全量清单**（量化）；清账完成后**转 fail-closed**（命中即红、阈值 0）。
  切换条件与两态语义（显式参数驱动、逐态可判）见设计 §2.32.3.5。
- **F5 全量清单**：检查器可输出**逐条清单**（档:行 + 锚 + 锚类）+ 汇总（各类候选数 / 悬空数 / 报告态标记）——作为层 2 清账的输入（可重定向落盘）。

**层 2 · 按锚类型清账**

- **F6 清账与处置形态**：每处命中逐条处置二选一——① **现态改写**（句子改为与现态相符）② **退场/已废注记 + 来源指针**；
  顺序 = 用例号 → 符号 → 路径；**不改代码 / 测试语义**（锚缺失若暴露真实代码问题 → **停下上报**，不自行改码）；清账后收紧容器（F4）。

**层 3 · 防回潮 + 流程入规**

- **F7 反查脚本**：输入 = 变更符号（+ 变更文件）；输出 = **必须跟着改的设计/需求档清单**（供批次「受影响文件表」收录）——落 `scripts/doc-impact.mjs`（轮 3 已落；**非门禁**：退出码 0，查询工具）。
